ADR-0012 — 上限の検出は専用 record (rate_limit_event) の構造化 field で行い、 本文への字面照合を畳む

本 ADR は IETF RFC 2119 および RFC 8174 / BCP 14 に定義される MUST / SHALL / SHOULD / MAY のキーワード解釈規約に従う。 ADR は決定時点の記録であり、 改訂は新しい ADR による supersede で行う。

§1. Context

器は実装役の claude を起こし、 その出力を 1 行ずつ読んでいます。 口座の使用上限に当たった周は便を止めたいので、 これまでは出力の文中に「上限」を意味する言葉が出てこないかを探していました。 ところが実際に器を動かして出力を保存してみると、 上限は専用の報告行として、 状態や使用率が項目に分かれた形で届いていました。 言葉を探す方法は、 本物の合図を見ておらず、 関係のない文に同じ言葉が混じったときだけ反応していた、 ということです。

器が起こす claude は --output-format stream-json で 1 行 1 record を吐き、 runner はそれを逐次読みして「口座の上限に当たった」周を rc 75 で止める (呼出側は Failed detail=rate-limit と記帳する)。 初版の判定は、 record 1 行の字面に上限の語彙 (rate_limit / rate limit / usage limit / 429 / 529 / overloaded) を contains で当てる形だった。

この形は 2 度、 実運用で誤爆した。 (1) 401 authentication_failed の record に含まれる session_id の 16 進へ 429 が現れただけで rc 75 になった。 判定は語彙の走査を本文 field (result / error / message / text / status) の値の中に限る形へ狭められた。 (2) claude は tool の失敗を type=user record の中の tool_result block ("is_error":true を持つ) として流すため、 cargo や grep の出力に 429 が混じるだけで便が「上限」で死んだ。 判定は種別の絞り (claude 自身が終端 / error として出す record だけ) を足す形へ狭められた。

それでも誤爆は残った。 {"type":"system","subtype":"error","message":"hook failed: 429 Too Many Requests"} の形は、 既存の歯が「真の上限」として持つ fixture と構造が同一で本文の字面だけが違うため、 形では弁別できない。 加えて、 本文 field の値を切り出す走査は病的な 1 行 (未閉じの入れ子を大量に持つ 180KB の record) で二次の計算量になることが実測された。

上限の真の形は、 実 run の raw stream を保存して初めて分かった。 器が初めて cargo を実行させた周 (2026-09-11) の stream に、 次の record が流れていた (uuid / session_id は伏字・他は逐語)。

{"type": "rate_limit_event",
 "rate_limit_info": {"status": "allowed_warning", "resetsAt": …,
   "rateLimitType": "seven_day", "utilization": 0.97,
   "isUsingOverage": false, "surpassedThreshold": 0.75,
   "unifiedWindows": {"five_hour": {…}, "seven_day": {…}}}}

この現物から 3 つが確定した。 (a) 上限は専用の record 種別 rate_limit_event と構造化された rate_limit_info (status / rateLimitType / utilization / isUsingOverage / surpassedThreshold / resetsAt) で来る。 (b) この record は error record ではない (is_error も subtype:"error" も持たない)。 (c) rate_limit_event は器が上限として扱う種別の集合に入っていない。 すなわち器は真の合図を一度も見ておらず、 2 度にわたって狭めてきたのは上限とは無関係な text に上限語が混じる誤爆だけだった。

§2. Decision

§2.1 判定の入力は専用 record の status で、 止める側を実測で持つ

上限かどうかは、 専用の報告行に書かれた「状態」を見て決めます。 器は「これが出たら止める」状態の一覧を持ち、 実際に見た値だけをそこへ入れます。 見たことのない状態では止めません——止める判断は claude を途中で打ち切るので、 まだ働けるはずの回を殺す方が、 名札を付け損なうより高くつくからです。 見た状態は毎回記録し、 一覧は実測で育てます。

器 SHALL 上限の判定を rate_limit_event 種別の record に限り、 その rate_limit_info.status の値を判定の入力とする。 器 SHALL 上限を表す status の閉じた集合を持ち、 status がその集合に属する周だけを上限として扱う (rc 75)。 集合に無い status では止めない (MUST NOT) — 未知の値も含む。

集合には実測で採れた値だけを入れる (MUST)。 記録時点で採れている status は allowed_warning の 1 つだけで、 これは「許可されつつ警告」の周＝止める側ではない。 したがって記録時点の集合は空であり、 器は当面 rc 75 を立てない。 上限に当たって止まる周の status を採取した時点で、 その値を集合へ入れる。 推測で値を足さない (MUST NOT)。

「許可側を列挙して未知を上限へ倒す」形 (§4 案 (A')) を採らない理由は失敗の重さの非対称である。 rc 75 は判定の名札ではなく実行の中断である — runner は上限と読んだ時点で claude を待たずに kill する。 取りこぼした周に起きるのは「rc 75 という分類が付かない」ことだけで便は claude 自身の rc で止まるが、 誤って上限と読んだ周では健全な便が殺される。 現に採れている status は 1 件だけで、 未採取の許可値 (例 allowed) が実在すれば全便が止まる。 ゆえに未知は「上限ではない」へ倒す。

この極性は器の他の箇所と同じ向きである — 「分からない周は上限と名乗らない」。 種別を読めない record も、 集合に無い status も、 いずれも claude の rc を写す側へ落ちる。 加えて器 SHALL 観測した rate_limit_event の status を run の記録へ残す。 集合を実測で育てるための口であり、 これが無いと「実測で採れた値だけを入れる」が運用で回らない。

§2.2 本文への字面照合を走査ごと撤去する

出力の文中から言葉を探す仕組みは、 まるごと取り除きます。 本物の合図が別にあると分かった以上、 言葉探しは誤解の元にしかならないからです。 取り除くと、 これまで別々に追いかけていた不具合が 2 つとも消えます。

器 SHALL 上限の語彙表と本文 field の走査 (値を文字列 / 入れ子 / 裸の scalar の 3 形で切り出す実装と、 record 種別を深さ 1 の key から読む実装を含む) を撤去する。 上限の判定は §2.1 の経路だけを通る (MUST)。

撤去により、 未着手だった 2 件の不具合が不要になる。 (a) system 種別で本文の字面だけが違う誤爆 (形では弁別できないと判定済み)。 (b) 本文 field の値を切り出す走査の二次計算量。 どちらも走査そのものが無くなるため、 別便で追う対象ではなくなる。

§2.3 使用率の閾値で早期に止めない

使用率が高くても、 まだ許されている間は走り続けます。 口座は使い切るのが決まりなので、 手前で自主的に止めることはしません。

器 SHALL NOT utilization の閾値で便を止める。 status が許可側の集合に属する周は、 utilization の値に関わらず走り続ける (実測された現物は 0.97 で allowed_warning だった)。

根拠は憲法 C9.2 である。 器は口座を allowance の終わりまで使い切ると定められており、 手前の閾値で自主的に止める設計はその条に反する。 加えて、 閾値を持つ設計は規則値を manifest の行として置くことを要し、 その値には user 裁定 (裁定 id) が要る (C1 / C5) が、 現時点で値の根拠が無い。

§2.4 射程外

この決定は「止めるかどうか」だけを決めます。 使用率や次に使えるようになる時刻は、 止めた記録に残すだけで、 判断には使いません。 口座を選び直す仕組みは、 この版では作りません。

本 ADR は上限の検出のみを決める。 rate_limit_info の他の field (utilization / rateLimitType / resetsAt / isUsingOverage) は判定に用いない (MUST NOT) が、 止めた周の記録には残してよい (MAY)。 これらは口座の選定 (本版の射程外) の材料である。

上限に当たって止まる周の status 値は記録時点で未採取である。 本決定はその値を知らなくても実装できる (許可側だけを列挙するため)。 採取できた時点で許可側の集合を見直すが、 それは本 ADR の supersede を要さない (集合の中身は実測に従う運用であり、 決定の形は変わらない)。

§3. Consequences

良い面は、 誤って止まる経路が消えることです。 判断の材料が「文に何が書いてあるか」から「相手が何と言ったか」へ移るので、 実行結果や引用や識別子の中身に振り回されなくなります。 悪い面は 2 つあります。 ひとつは、 相手が別の言い方でしか上限を伝えない周を見落とすこと。 もうひとつは、 止める状態の一覧がいまは空なので、 本当に上限へ当たっても「上限で止まった」と記録できないことです。 どちらの場合も便自体は止まります — 止まった理由に名札が付かないだけです。

Positive: 誤爆の面が消える。 判定の入力が構造化された field になり、 tool の出力・本文の引用・識別子の中身に左右されない。 走査の実装が消えるぶん core の行数が減る (C4 の上限に対する余裕)。 未着手の 2 件 (§2.2) が不要になり、 追う対象が減る。

Negative (受け入れるリスク): claude が rate_limit_event 以外の経路でしか上限を伝えない周があれば取りこぼす。 その周に起きるのは「rc 75 という分類が付かない」ことだけで、 便は止まる — claude 自身が非 0 で終わり、 器は rc をそのまま写すためである (C11.2 の極性: 包みが独自の判定を足さない)。 台帳に「上限で止まった」と残らないぶん、 後から原因を読むときに 1 手増える。

Negative (記録時点の限界): 止める status の集合が空であるため、 器は当面 rc 75 を一度も立てない。 真に上限へ当たった周も Failed detail=rate-limit ではなく claude の rc による失敗として残る。 これは「上限を検出できる」と称して誤って止めるよりよい、 という判断の帰結であり、 status を 1 件採取すれば解消する。 §2.1 の記録の口がその採取を運ぶ。

未確定: 止まる周の status 値 (§2.4)。 現物は allowed_warning の 1 件のみで、 これは「許可されつつ警告」の周である。 rate_limit_event が警告帯の外でも流れるか、 そのとき status が何になるかは未測定であり、 現物 1 件からは推論できない。

§4. Alternatives Considered

3 つの案を退けました。 言葉探しを小さく残す案は、 保険の役には立つものの、 その保険が要るという証拠がありません。 使用率で止める案は決まりに反します。 何もしない案は、 誤って止まる経路を抱え続けることになります。

(A') 許可側の status を列挙し、 未知を上限へ倒す (fail-closed 側へ倒す形)。 却下: rc 75 は実行の中断であり (runner は claude を待たずに kill する)、 誤って上限と読むと健全な便が殺される。 採れている status は 1 件のみで、 未採取の許可値が実在すれば全便が止まる。 取りこぼし側の費用 (分類が付かないだけ) と釣り合わない。 なお本案は「上限専用 record なら未知も上限でよい」という読みに基づくが、 rate_limit_event が警告帯の外でも流れるかは未測定であり、 その読み自体が現物 1 件からの推論である。

(B) 字面照合を狭めて残す (専用 record を一次にし、 最終 result record だけ字面の fallback を残す)。 却下: 取りこぼしへの保険にはなるが、 その保険に証拠が無い — result record に上限が載る現物は未採取である。 保険のために誤爆 1 件と二次計算量を抱え続ける費用が、 取りこぼしの費用 (§3 の Negative — 分類が付かないだけで便は止まる) を上回る。 現物が採れた時点で本 ADR を supersede して戻せる。

(C) utilization の閾値で止める (例: 0.95 で Failed)。 却下: 憲法 C9.2 に反する (§2.3)。 加えて閾値は manifest の行と裁定 id を要し、 値の根拠が無い。

(D) 現状維持 (rate_limit_event を種別の集合に足すだけで、 字面照合も残す)。 却下: 誤爆の面が残り、 未着手の 2 件を別便で追い続けることになる。 真の合図が構造で来ると分かった以上、 字面を併用する理由が無い。

§5. Trace

出所は、 審査役の指摘と、 器を実際に動かして出力を保存した記録です。 保存は「何が流れたか」を後から読めるようにするためのもので、 このときの記録から本物の合図の形が分かりました。

  • 誤爆 (1) の実測 (2026-09-10): 401 authentication_failed の record で rc 75 になった周を実 run の記録から特定。 session_id の 16 進に 429 が現れていた。 走査を本文 field へ限る便で塞いだ。
  • 誤爆 (2) の実測 (2026-09-11): tool_result block に上限語を置いた record を実 binary へ流して rc 75 を再現。 対照として session_id 形が rc 1 になることも確認 (前便の修正が効いている裏取り)。 種別の絞りを足す便で塞いだ。
  • 残る誤爆の実測 (2026-09-11): {"type":"system","subtype":"error","message":"hook failed: 429 …"} を実 binary へ流して rc 75 を再現。 同時に、 既存の歯が「真の上限」として持つ fixture が同じ構造であることを現物で確認し、 形では弁別できないと判定した。
  • 二次計算量の実測 (2026-09-11・lens): 未閉じの入れ子を 20000 個持つ 180KB の 1 行で、 本文 field の切り出しが 11.99 秒 (対照 0.00 秒)。
  • 本物の合図の採取 (2026-09-11・claude 2.1.267): 器が初めて cargo を実行させた周で、 runner の raw stream (全 30 行) を file へ保存。 その中に rate_limit_event の record が 1 件流れていた (§1 に逐語・uuid / session_id は伏字)。 保存は tracked file に入れない運用の証跡として行った。
  • 同じ stream で、 assistant record の uuid に含まれる 429 が rc 75 を起こさなかったことも確認した (先行 2 便の修正が実 stream で効いている裏取り)。
