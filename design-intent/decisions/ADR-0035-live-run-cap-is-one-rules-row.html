設計判断記録 (ADR) scribe2 — 同時走行の最大値

host で同時に走る便の本数は rules 行 1 本の最大値を持つ (値は user 裁定・受付が live の便数を数えて typed に断る・ADR-0034 の「数値上限を持たない」句を部分 supersede)

並列の上限は write-set の交差と直列依存だけ、 という決定に host の最大値を 1 つだけ足す。 値は manifest の rules 行 pipe.max_live が持ち (裁定 id 付き)、 受付が live な便の本数を数えて上限以上の周は typed に断る。 走行中の便は止めず、 上限は起動にだけ効く。 launcher の変数や host.toml や散文には置かない。

この判断が約束すること (1 文サマリ)

host で同時に走らせる便の本数に、最大値を 1 つだけ持ちます。値は器の規則の表（rules 行 pipe.max_live）にだけ置き、user の裁定で決めます。便を起こす前の受付が「まだ終わっていない便」の本数を数え、最大値以上なら理由を付けて断り、その契約は列に残って次の機会に再判定されます。走っている便は止めません。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを、当日の実測から説明します。並列度を上げた周に memory は余っていたのに CPU と温度が上がり、user が最大値を持つと決めました。器には上限が無く、暫定の上限は器の外の script と環境変数に在り、要件書と前の決定記録は「数の上限を持たない」と書いています。

CTX1

並列度を上げた周に host が温度と load で悲鳴を上げた

2026-09-16 05:5xZ (ThinkPad・16 core) の実測は load average 18〜26・CPU 81 ℃・rustc 27 本・cargo 16 本・変異検査系 49 process・nextest の test binary 43 本で、 memory は 10 / 62 GB と余裕があった。 受付契約を便にする前の検査の段 (ADR-0021 §2.3・gate-cost.md §3.2) は host の memory の枠だけで本数を絞るので、 CPU と温度の逼迫は受付に映らない。 user は同じ周に、 走っている便は止めず次に走らせる分から同時本数を絞るよう直命し (逐語は台帳・CON2)、 admin は器の外の launcher の変数で暫定の上限を持った。

CTX2

user の裁定 — 最大値を 1 つ持つ・値は 16

06:39Z に user は、 当面の上限を保ったまま変異検査の総量を減らす便を先に land させ、 その後に同時本数の最大値を器の設定として持つ (これだけ並列できるようになった以上、 何らかの最大値は要る) と述べた (逐語は台帳 s2-07l notes・CON2)。 これは 01:0xZ の恒久直命 (並列の上限は write-set の交差と直列依存だけ) に host の最大値 1 つを足す user 本人の改訂である。 11:14Z の裁定で値は 16 と決まった (裁定 id = user 2026-09-16T11:14Z・逐語は台帳)。

CTX3

器には上限が無く、 暫定の上限は器の外の散文に在る

便を起こす口 (pipe run / intake → spawn) の受付 (契約を便にする前の検査の段) に live な便まだ終わっていない便の本数の上限は無い。 並列の枠 (pipe/admission.rs・受付とは別の実体) は変異検査の並列度を memory で数えるだけである。 暫定の上限は admin の launcher (LAUNCH_CAP と live-count.sh) が持ち、 live の弁別 (Landed / Stopped / Failed / Gated FAIL / Reviewed 非 PASS / retired を終端と読む) を script が器の写しから読み直している = 器に無い規則が散文と env に在る形 (憲法 C2.2 / N2) で、 ADR-0034 §1 が事故として挙げた「器に無い上限を席の散文で持つ」型そのものである。

CTX4

SRS FR68 と ADR-0034 は「数値の上限を持たない」と定めている

SRS FR68 の response は「同時本数の数値上限は持たず、 本数の絞りは受付の host の memory の枠が行う」と書き、 ADR-0034 の決定文は「器 SHALL NOT 便の同時本数の数値上限を持つ」を持つ。 本 ADR はその 1 句を部分 supersede する。 SRS への反映 (FR68 の同句の改訂) は ADR-0034 の FR30 / FR49 と同じ前例で user の /folio-architect の周に行い、 本 ADR は要件の文面を持たない。

03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 5 つ並べます。規則の表に最大値を持つ案、いまの launcher の変数を正式にする案、数の上限を持たず memory の枠だけで絞る案、host の宣言 file に手書きする案、そして dispatcher の hold の印で本数を絞る案です。

OPT1rules 行 pipe.max_live — 受付が live の便数を数えて上限以上なら typed に断り、 dispatcher は列に残す採用

manifest に Int の rules 行 pipe.max_live を 1 本足す (値は user 裁定・C5)。 便を作る前の受付が state dir の live な便 (intake の交差と同じ判定 = 終端でない run) を数え、 値以上の周は契約を断る理由の閉じた一覧に variant を 1 つ足して断る (live の本数と上限を運ぶ・run も event も作らない)。 dispatcher の列はその契約を留めて理由を持ち、 次の契機で再判定する。 走行中の便には効かない。 一時的に下げるのは rules 行の値の改訂 (裁定 id 付きの PR) でだけ行う。

器の規則の表に「同時に走らせる便の最大本数」を 1 行足します。便を起こす前に、器が「まだ終わっていない便」を数え、最大本数に達していれば理由を付けて断ります。断られた契約は列に残り、便が終わったら次の機会に起こされます。走っている便は止めません。一時的に減らしたいときも、この 1 行の値を裁定付きで変えます。

+ 利点

  • 値の出所が 1 つ (manifest) で、 変更は裁定 id 付きの PR = 憲法 C1 / C5 の形
  • 断りの理由が typed (閉じた一覧の variant と stderr の 1 行) に出て、 席が「なぜ出ないか」を読み直さない (dispatcher の列に同じ理由を載せるのは列の実装の後)
  • live の弁別を器の 1 関数に揃え、 launcher の script の読み直し (散文の規則) が消える

− 欠点

  • SRS FR68 と ADR-0034 の 1 句と食い違う期間が SRS 反映まで残る (user の /folio-architect の周)
  • 並列の上限が 1 つ増える = memory に余裕があっても上限で待つ便が出る (user 本人の改訂)
  • rules 行の連鎖 (閉じた型の variant・manifest・歯・生成物) が契約の write-set に載る
OPT2launcher の変数 (LAUNCH_CAP) と live-count.sh を暫定のまま正式にする不採用

器は変えず、 admin の launcher が env の値で本数を絞り続ける。

いま admin が使っている起動 script の環境変数を、そのまま正式な上限にする案です。器を変えずに済む一方、器の外に規則が残り、script が「終わっていない便」を数え直す 2 本目の判定になります。dispatcher が起動を持てば script 自体が無くなります。

+ 利点

  • 器の変更が無い

− 欠点

  • 器の外の env と散文に規則が在る (憲法 C2.2 / N2)。 dispatcher (ADR-0034) が起動を持つと launcher 自体が無くなる
  • live の弁別を script が器の写しから読み直す = 器の判定の 2 本目 (C2)
OPT3数値の上限を持たず受付の memory の枠だけで絞る (ADR-0034 の現行)不採用

上限を足さず、 本数は受付の host の memory の枠 (ADR-0021 §2.3) に任せる。

数の上限を持たず、memory の空きだけで本数を絞る今の形です。当日の実測では memory は余っていたのに CPU と温度が上がっており、user は最大値を持つと決めました。

+ 利点

  • SRS FR68 と ADR-0034 を変えない

− 欠点

  • CPU と温度の逼迫は memory の枠に映らない (CTX1 の実測 = memory 10 / 62 GB で CPU 81 ℃)
  • user が「最大値を 1 つ持つ」と裁定した (CTX2) = この案は裁定に反する
OPT4host.toml (host の宣言 file) に手書きの上限を置く不採用

値を host ごとの宣言 file に書き、 器はそれを読む。

host ごとの宣言 file に上限を手書きする案です。host ごとに違う値を持てる一方、値の出所が裁定でなくなり、host 固有の値で器の動きが分かれる形に寄ります。

+ 利点

  • host ごとに違う値を持てる

− 欠点

  • 値の出所が裁定でなくなる (rules 行の裁定 id を持たない・C1 / C5)。 host ごとの値は manifest の host 行の形で持つのが憲法 C10.2 の向き
  • host 固有の値で code が分岐する形に寄る (N3)
OPT5dispatcher の介入 hold で本数を絞る (契約ごとの印)不採用

上限を持たず、 減らしたい周は planner が契約に hold の印を付けて起こさない。

契約に「止める」印（hold）を付けて本数を減らす案です。新しい規則の行も型も要らない一方、印は契約 1 本ずつに付けるもので、host 全体の本数を表せません。本数を散文で数えて印を付けることになり、上限が散文に戻ります。

+ 利点

  • 新しい rules 行も variant も要らない

− 欠点

  • hold は契約単位の印で、 host の本数を表せない = 「N 本以下」を散文で数えて hold を付けることになり上限の散文化に戻る
  • user の直命は host の最大値 (本数) であって契約の名指しではない
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、それが要件書のどの要件を支えるかを示します。最大値は規則の表の 1 行が持ち、受付が「終わっていない便」を数えて上限以上なら型で断り、dispatcher はその契約を列に残して次の機会に再判定します。走っている便は止めません。

採用 — OPT1

器 SHALL 便の同時走行の最大値同時に走らせる便の最大本数を rules 行 pipe.max_live (Int・本) として manifest に 1 本だけ持ち (値は user 裁定 id 付き・C5・本 ADR は値を写さない)、 便を作る前の受付 SHALL state dir の live な便 (終端でない run・intake の交差と同じ 1 関数の判定・ADR-0019 §2.1) の本数を数え、 値以上の周は契約を断る理由の閉じた一覧に足した variant 1 つ (live の本数と上限を運ぶ) で typed に断り、 run も event も作らない。 dispatcher SHALL 断られた契約を列に留めてまだ出ていない理由の閉じた型で持ち、 次の契機 (管理 tick / Landed) で再判定する。 上限 SHALL 起動にだけ効き、 走行中の便を止めない。 器 SHALL NOT 上限を env・launcher の変数・host.toml・散文から読まない。 上限の一時的な引き下げ SHALL rules 行の値の改訂 (裁定 id 付き) でだけ行う。 本 ADR は ADR-0034 の決定文の 1 句「器 SHALL NOT 便の同時本数の数値上限を持つ」を置き換え、 他の句は変えない。

同時に走らせる便の最大本数を、器の規則の表の 1 行として持ちます。値は user の裁定で決まります。便を起こす前の受付が「まだ終わっていない便」を数え、最大本数に達していれば理由を付けて断り、その契約は列に残って次の機会に再判定されます。走っている便は止めず、上限は起動にだけ効きます。環境変数や script や宣言 file から上限を読むことはしません。 並列度が上がった周に host が悲鳴を上げたのは CPU と温度で、memory の枠には映りませんでした。user は「最大値を 1 つ持つ」と決めました。上限を持つなら、その値は憲法どおり規則の表の 1 行にだけ置き、裁定 id を伴わせ、断りは型で表します。「終わっていない便」の判定は intake の交差が既に持っているので、同じ 1 関数を使えば script の読み直しが消えます。走っている便を止めないのは user の直命であり、上限は起動にだけ効かせます。
