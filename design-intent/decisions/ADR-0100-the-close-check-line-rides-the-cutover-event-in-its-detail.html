設計判断記録 (ADR) scribe2 — close-check の線の記帳の形

close-check の線は切り替えの線と同じ event LifecycleCutover の 1 件に、 既存の任意の key detail の閉じた 1 語 close-check を持たせて記帳し、 新しい key も kind も足さない — 2 つの線は種類ごとに最初の行で読む (ADR-0088 の LifecycleCutover の key の組を部分 supersede)

局面の出力は、 閉じに由来する当てはまらない判定 (misfit) を close-check の線より後の閉じにだけ掛ける (SRS FR90)。 線は state dir ごとに 1 度だけ記帳すると要件は決めたが、 どの形で記帳するかは要件も記録も決めていない。 本 ADR は、 線を切り替えの線と同じ event の種類 LifecycleCutover の 1 件で記帳し、 旧い版の器がすでに受ける任意の key detail に閉じた 1 語 close-check を持たせることと、 2 つの線を種類ごとに最初の行で読むことを決める。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「局面の出力」は器が案件の今の状態を部品ごとに書き出す file の組、 「event log」は器が出来事を 1 行ずつ足していく記録です。 局面の出力は、 bead の閉じ方の誤り (misfit) を、 閉じの門を宣言した repo で「閉じを数え始める時」(close-check の線) より後の閉じにだけ数えます。 この時は state dir ごとに 1 度だけ記録すると要件で決まっていますが、 どんな形で記録するかは決まっていませんでした。 この記録は、 それを「この版の始まり」(切り替えの線) と同じ種類の出来事 1 件で記録し、 古い版の器もすでに読める欄 detail に close-check という決まった 1 語を置くこと、 2 つの線はそれぞれ最初の行で読むことを決めます。 まだ実装を待つ提案の段です。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 4 つから説明します。 線は要件にあるのに記録の形がどこにも決まっていない経緯・器の記録の読み手は知らない欄や種類を持つ行を断り、 1 行でも読めなければ記録の全部を読まない現物・出来事の種類を足すと閉じた型の手入れが 6 か所に広がる現物・決める範囲です。

CTX1

経緯 — 線は要件にあるが、 記帳の形はどこにも決まっていない

局面の出力案件の今の一覧 (SRS FR90・ADR-0088) は、 閉じに由来する misfit を 2 つの線より後の閉じにだけ掛ける。 切り替えの線この版の始まりは、 この版の器がその state dir で最初に全部を書き直した時刻で、 ADR-0088 が event の種類 LifecycleCutover (key version = 線を引いた器の版・key main = その書き直しが読んだ main の印) の 1 件で記帳すると決めた。 close-check の線閉じを数え始める時は、 全部の書き直しが main の先端の vessel 宣言で close-check (ADR-0097) を初めて true と読んだ時刻で、 要件は state dir ごとに 1 度だけ記帳し、 後の書き直しは動かさず、 切り替えの線より前にはならないと決めた。 しかし、 どの event の形で記帳するかは要件にも ADR-0088 にも ADR-0097 にも無い。 書き手はまだ無く (LifecycleCutover の書き手は src に 0 件)、 設計 doc case-lifecycle の行 c と行 c1 がこれから作る。

CTX2

現物 — event の読み手は、 知らない key と kind を持つ行を断り、 1 行でも読めなければ log の全部を読まない

event の 1 行の読み (fleet/event.rs の from_line) は、 行の key が既知の key の表 (KNOWN_KEYS) の外なら「未知の key」として、 kind が表の外なら「未知である」として、 その行を読めない行にする。 event log出来事の追記 file の読み (fleet/store.rs の read_events) は、 読めない行が 1 行でも在れば log の全部を Err で返す。 これは不正な入力を黙って落とさず、 読めない store を loud に断る決め (SRS NFR4) の実装である。 そのため、 新しい key か kind を持つ行を書いた後に、 その key か kind を知らない版の器 (同じ host で binary を戻した器など) がその log を読むと、 行 1 本のせいで log の全部を読めなくなる (verified)。 一方、 案件の一生の kind (LifecycleCutover を含む) の本体の読みは任意の key detail を受け、 LifecycleCutover の本体は version と main だけを読み、 detail を見ない (verified)。

CTX3

現物 — kind を足すと閉じた型の閉包が広がる

event の種類 (EventKind) の網羅の match は 6 か所 (fleet/mod.rs の as_str・default_actor・shape、 fleet/event.rs の読み、 fleet/replay.rs の 2 つ) に在り、 種類を 1 つ足すとそのどれにも手が要る。 設計 doc の契約表では、 dispatcher の行 a が EventKind を touches に持ち、 種類を名指す新しい file はその行の write-set に先に宣言する手が要る。 LifecycleCutover の本体の型 (Case::Cutover) は version と main の 2 欄を持つ。

CTX4

射程 — 決めるのは記帳の形と読みの規則だけ

決めるのは、 (1) close-check の線を記帳する event の形、 (2) 2 つの線を event log から読む規則、 (3) 記帳の条件と時の 3 つである。 変えないのは、 閉じの misfit の数え (SRS FR90・FR91・設計 doc)、 close-check の key の意味と起票の門の close の段 (ADR-0097)、 切り替えの線の意味と key version と main (ADR-0088)、 events.jsonl の形・path・schema 版、 局面の出力の欄 (出力は線を持たない・ADR-0088) である。 実装は設計 doc case-lifecycle の行 c (書き手が切り替えの線を足す) と行 c1 (close-check の線を足す)。 ADR を書く条件のうち 3 (跨版の形) と 4 (却下案を残す価値) に当たる。

03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 4 つ並べます。 古い版がすでに受ける欄 detail に決まった 1 語を置く案 (選んだ案) と、 選ばなかった 3 つです。 選ばなかった案は、 新しい欄 line を足す案 (設計の下書きが推していた案)・新しい出来事の種類を足す案・線を出力か別の file に持つ案です。

OPT1LifecycleCutover の既存の任意の key detail に閉じた 1 語 close-check を持たせる採用

close-check の線を、 切り替えの線と同じ kind LifecycleCutover の 1 件で記帳し、 旧い版の読み手がすでに受ける任意の key detail に閉じた 1 語 close-check を置く。 version と main は切り替えの線と同じ形。 切り替えの線は detail を持たない最初の行、 close-check の線は detail が close-check の最初の行と読み、 detail が他の値の行はどちらの線にも数えない。 決め手は現物 (既知の key と kind の表を広げずに済み、 旧い版の読みが変わらない)。

close-check の線を、 切り替えの線と同じ種類の出来事 1 件で記録し、 古い版の読み手がすでに受ける欄 detail に close-check の 1 語を置く案です。 古い版の器は行を今どおり読めるので記録の全部が読めなくなる事故が起きず、 型と表も増えず、 2 つの線はそれぞれ最初の行で 1 通りに決まります。 代わりに、 detail の意味がこの種類だけ決まった 1 語になり、 古い版の器は行を読めても線としては扱いません。

+ 利点

  • 旧い版の器は行を今どおり読め、 log の全部を読めなくなる事故が起きない (DR1)
  • 既知の key の表・kind の表・閉じた型の match は増えない (DR2)
  • 2 つの線が種類ごとの最初の行で 1 通りに決まり、 知らない値は線に数えない (DR3)
  • 線は event log にだけ在り、 出力は線を持たない (DR4)

− 欠点

  • detail は kind ごとに意味の違う自由な字の欄で、 この kind だけ閉じた 1 語の意味を持つ (読み手の約束が kind ごとに増える)
  • 旧い版の器は close-check の線を線として読まない (読めるが意味を知らない)
OPT2新しい任意の key line を足す不採用

LifecycleCutover に任意の key line (値は閉じた 1 語 close-check) を足し、 key の無い行を切り替えの線と読む。 設計 doc の草稿が推した形。 決め手は現物 (既知の key の表の外の key は、 旧い版の読み手が行ごと断る)。

LifecycleCutover に新しい欄 line を足し、 値を close-check にする案で、 設計の下書きが推していました。 欄の名が意味を直に言い、 種類も足さない点で勝ります。 けれども、 器の読み手は知らない欄を持つ行を断り、 1 行でも読めなければ記録の全部を読まないので、 同じ host で器を古い版へ戻すと、 この 1 行のせいで器の全部の口が止まります。 下書きが挙げた「古い版は知らない欄を読み捨てる」は、 現物では成り立ちません。

+ 利点

  • key の名が意味を直に言い、 detail の意味を kind ごとに覚えなくてよい
  • kind を足さないので、 閉じた型の match は増えない

− 欠点

  • 旧い版の読み手は表の外の key の行を読めない行にし、 行 1 本のせいで event log の全部を読めなくなる (同じ host で binary を戻すと器の全部の口が止まる) (DR1)
  • 既知の key の表と、 案件の一生の kind だけが持てる key の表を広げる (DR2)
OPT3新しい kind を足す不採用

close-check の線だけを持つ新しい kind を足す。 決め手は現物 (旧い版が行ごと断るうえ、 閉じた型の閉包が 6 か所に広がる)。

close-check の線だけを持つ新しい出来事の種類を足す案です。 線の種類が種類の名で見分けられ、 LifecycleCutover の形を変えない点で勝ります。 けれども、 古い版の読み手は知らない種類の行も断るので記録の全部が読めなくなり、 種類の網羅の分岐 6 か所と、 種類を扱う契約表の行の手入れも要ります。

+ 利点

  • 線の種類が kind の名で見分けられ、 読み手は kind だけを見ればよい
  • LifecycleCutover の形と意味を 1 字も変えない

− 欠点

  • 旧い版の読み手は表の外の kind の行を読めない行にし、 event log の全部を読めなくなる (DR1)
  • 種類の網羅の match 6 か所と、 種類を touches に持つ契約表の行の write-set に手が要る (DR2)
OPT4線を局面の出力か別の file に持つ不採用

線を lifecycle.json の欄か、 state dir の新しい file に置く。 決め手は既存の決定 (ADR-0088 は出力を導き出した物とし線を持たせず、 file を lifecycle.json と lifecycle.stale の組に限った)。

線を局面の出力の欄か、 新しい file に置く案です。 記録の形に触れず、 出力 1 つを読めば線も分かる点で勝ります。 けれども、 出力は消えても書き直しで戻る導き出した物なので、 真実の線を置くと消えた周に線が動きます。 出力の 2 つの file の外に file を増やすのは、 前の記録が新しい記録を要るとした形です。

+ 利点

  • event log の形に触れない
  • 読み手が出力 1 つを読めば線も分かる

− 欠点

  • 出力は消えても全部の書き直しで戻る導出物で、 真実の線を置くと消えた周に線が動く (DR4)
  • 組の 2 file の外の file は ADR-0088 が新しい ADR を要るとした形で、 置き場が増える (DR2)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 close-check の線は、 切り替えの線と同じ種類 LifecycleCutover の出来事 1 件で記録し、 欄 detail に close-check の 1 語を置きます。 切り替えの線は detail を持たない最初の行、 close-check の線は detail が close-check の最初の行と読み、 detail がほかの値の行はどちらの線にも数えません。 記録するのは全部の書き直しで、 宣言が true になった最初の周に 1 度だけです。

採用 — OPT1

器 SHALL close-check の線 (SRS FR90) を、 切り替えの線と同じ event の kind LifecycleCutover の 1 件で記帳し、 その行の既存の任意の key detail に閉じた 1 語 close-check を持たせる。 key version は線を引いた器の版、 key main はその全部の書き直しが読んだ main の印で、 切り替えの線と同じ形である。 新しい key も kind も足さず、 event の読み手の既知の key と kind の表は変えない。 読みは種類ごとに最初の行で決める: 切り替えの線は detail を持たない最初の LifecycleCutover の行、 close-check の線は detail が close-check の最初の LifecycleCutover の行で、 detail が他の値の行はどちらの線にも数えない。 記帳するのは局面の出力の全部の書き直しで、 読んだ main の先端の vessel 宣言が close-check を true で持ち、 event log に close-check の線が無い周に、 event の lock の内側で線が無いときだけ足す形で 1 件足す。 同じ周に切り替えの線も足すなら、 切り替えの線を先に足す。 後の書き直しと宣言の変化 (true から false へ) は線を動かさず、 宣言が在って読めない周は記帳しない。 1 つの state dir が 2 つ以上の repo を持っても線は state dir ごとに 1 本である。 events.jsonl の形・path・schema 版と、 局面の出力の欄は変えない。 実装は設計 doc case-lifecycle の行 c (切り替えの線の記帳と、 detail を持たない最初の行の読み) と行 c1 (close-check の線の記帳と読み)。

器は close-check の線を、 切り替えの線と同じ種類 LifecycleCutover の出来事 1 件で記録し、 その行の欄 detail に close-check の 1 語を置きます。 欄 version には線を引いた器の版を、 欄 main にはその書き直しが読んだ main の印を、 切り替えの線と同じ形で置きます。 新しい欄も種類も足さず、 読み手の知っている欄と種類の表は変えません。 読み方は、 切り替えの線が detail を持たない最初の行、 close-check の線が detail が close-check の最初の行で、 detail がほかの値の行はどちらの線にも数えません。 記録するのは局面の出力の全部の書き直しで、 main の先端の宣言が close-check を true で持ち、 まだ線が無い周に、 記録の鍵の内側で線が無いときだけ 1 件足します。 同じ周に切り替えの線も足すなら、 切り替えの線を先に足します。 後の書き直しや、 宣言を true から false へ戻すことでは線は動かず、 宣言が読めない周は記録しません。 1 つの state dir に repo が 2 つ以上あっても、 線は state dir ごとに 1 本です。 既存の欄 detail を選んだのは、 器の読み手が知らない欄や種類を持つ行を断り、 1 行でも読めなければ記録の全部を読まないからです。 新しい欄か種類で線を記録すると、 同じ host で器を古い版へ戻したとき、 線の 1 行のせいで器の全部の口が止まります。 detail は案件の一生の種類の行がすでに受ける任意の欄で、 LifecycleCutover の古い読み手は detail を見ないので、 古い版も行を今どおり読めます。 新しい種類を足さないのは、 読めなくなるうえに、 種類の網羅の分岐 6 か所と契約表の手入れが要るからです。 線を出力に置かないのは、 出力が消えても戻る導き出した物で、 真実を置くと線が動くからです。 2 つの線をそれぞれ最初の行で読むのは、 線は 1 度だけ記録して動かさないと要件が決めているからで、 detail がほかの値の行を線に数えないのは、 知らない値を既知の線に読み替えないためです。

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなること 3 つと、 代わりに引き受けること 4 つです。 良くなるのは、 古い版の器が記録を今どおり読めること、 型と表と手入れの場所が増えないこと、 2 つの線が 1 通りに読めることです。 引き受けるのは、 detail の意味が種類ごとに違うこと、 古い版は線を線として扱わないこと、 線を消す口が無いこと、 repo ごとの線は持たないことです。
