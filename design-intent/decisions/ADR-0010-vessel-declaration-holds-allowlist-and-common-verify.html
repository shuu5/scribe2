§1. Context

前の記録 (ADR-0009) は、 実装役が実行してよい command の一覧と、 どの便にも共通の検証を、 器 (scribe2) 自身の規則 file に置きました。 ところがその値は「相手の repo が何であるか」で決まるものです。 Rust でない repo を器に載せる日に、 器の規則 file を直さないと動かない形になっていました。

ADR-0009 §2.1 は allowlist の正本を manifest の rules 行 runner.allowed_commands (初期値 ["cargo", "git"]) と定め、 §2.4 は共通 verify の正本を rules 行 gate.common_verify (初期値 = flip check + done の定義 4 本) と定めた。 両行は 2026-09-10 に manifest へ land した (kind RunnerAllowedCommands / GateCommonVerify・値の形は List)。

この 2 つの値は器の規則ではなく対象 repo の性質である。 共通 verify の行は Rust repo の道具 (cargo xtask flip-check・cargo nextest・cargo clippy・cargo deny) を名指し、 allowlist も同じ道具から成る。 設計 doc pipeline §7 は「pipeline が Rust 固有の検査を内蔵する形は採らない (toy repo は Rust でないことがある)」と定め、 ADR-0009 §4 案 (v) も同じ理由で Rust 固有の検査の内蔵を退けた。 しかし値を器の manifest に置く形は、 manifest 経由で同じ内蔵を作っていた——器で別の言語の repo を開発するには、 器の manifest を C5 の手続きで書き換えるか、 その repo 向けの行を器に足し続けるしかない。 前者は対象 repo の都合で器の規則が揺れ、 後者は器が対象 repo の一覧を抱える。

憲法の面から見ると、 C1 は「規則の値は repo 内の manifest 1 file」と定め、 C10 は「宣言値・出所つき実測値・導出値・有効値を型で区別し、 宣言値は実測を経てだけ有効値になる」と定め、 C14 は「manifest は執行される規則の正本」と定める。 「相手の repo が何を実行するか」は器の規則というより相手についての宣言値であり、 既に所属の目印 .vessel (marker) が name と version をその形で持っている (SRS FR19 / FR24・ADR-0004 §2.2 面 1)。 ∴ 置き場を決め直す必要があり、 本 repo の作法「schema・on-disk 形式を決める便は ADR を先に書く」と「憲法条の解釈が要る便は ADR を書く」の両方に当たる。 選択肢は 2 つ (器の manifest のまま / 対象 repo の宣言へ) で、 選択が「器と repo のどちらが値を所有するか」という価値観に依存するため user 裁定を仰いだ (2026-09-10・推奨案を採用)。

§2. Decision

決めることは 6 つです。 宣言は目印の隣の file に置く、 器の規則 file は「宣言が名乗ってよい上限」だけを持つ、 便を受け付けるときに宣言を読んで上限と突き合わせ便ごとに凍結する、 実装役と審査は凍結した写しを読む、 器自身と練習用 repo にも宣言を置く、 そして今回決めない範囲、 です。

本 ADR は C1 / C10 / C14 の適用を記録する。 憲法本文は書き換えない。 C1 の読みは次のとおり: 器の規則は「宣言が名乗れる command の上限」と「宣言が無い repo では便を起こさない」であり、 いずれも manifest と型に在る。 対象 repo が何を実行し何を共通に検証するかはその repo についての宣言値 (C10 の Declared) であって器の規則値ではない——marker の name / version と同じ類である。 宣言値は intake の突合 (実測) を経てだけ有効値 (Effective) になる (C10)。 manifest は執行される規則の正本のまま (C14)。 rules manifest からは行を 1 本消す (C5・裁定 id = 本 ADR)。

§2.1 宣言 file — marker の隣に置く

目印 .vessel そのものには手を付けません。 前の版と共有する固定の形だからです。 その隣に .vessel.toml という file を置き、 「実装役が使ってよい command」と「どの便にも共通の検証」をその repo が自分で名乗ります。

vessel 宣言は対象 repo の root の tracked file .vessel.toml である (MUST)。 marker .vessel は変えない (MUST NOT change): marker は跨版 面 1 (ADR-0004 §2.2・要件カタログ R-O3) として版番号に依らず固定され、 読み手は 2 行厳格 (行数違いは Absent = hook が黙る側へ倒れる) で実装されている。 marker に行を足すと、 前の版と現在の版の両方の hook が「誰も名乗っていない」と読み、 write-set guard が黙って外れる——安全側と逆へ倒れる。 ∴ 宣言は別 file に置く。

宣言の形は契約 file と同じ TOML subset (ADR-0004 §2.3・section を持たない flat な key・値は文字列と 1 行の文字列配列・reader は契約 file と同じ 1 組で第 2 の parser を作らない) とする (MUST)。 key は 3 つですべて必須: schema (整数・初期値 1)、 allowed-commands (command 名の配列・実装役が実行してよいもの)、 common-verify (command 行の配列・どの便にも共通の検証・{base} は便の base に置換される唯一の穴)。 配列は空を受けず、 要素の空文字も受けない (manifest の List と同じ理由: 「規則が無い」を空で表せると書き間違いが空の allowlist を効かせる)。 未知 key は拒む。 不備は全件集めて行番号付きで返す (契約 file と同じ・FR1)。

§2.2 manifest は上限を持ち、 共通 verify の行は廃止する

器の規則 file にある「実装役が使ってよい command」の行は残しますが、 意味を「どの repo の宣言も、 この範囲の中でしか名乗れない」という上限に変えます。 上限を広げるには人の裁定が要ります。 「共通の検証」の行は器の規則 file から消します。 repo ごとに違う値を器が持つ理由が無いからです。

rules 行 runner.allowed_commands (kind RunnerAllowedCommands) は残し、 意味を上限 (ceiling) に変える (MUST): どの vessel 宣言の allowed-commands も、 この行の要素の部分集合でなければならない。 値は変えない (記録時点 ["cargo", "git"])。 上限を広げる (例: 別の言語の repo を載せるために uv や pytest を足す) には C5 の手続き (裁定 id 付きの diff) を要する——これは意図した摩擦である: 実装役が実行しうる command の宇宙を広げるのは「使う」に近い判断であり、 器の manifest でだけ広がる形にする。 包み (sh / bash / python -c 等) を上限に載せない規律は ADR-0009 §3 のまま不変。

rules 行 gate.common_verify と kind GateCommonVerify は廃止する (MUST remove・C5・裁定 id = 本 ADR)。 器が「Rust repo 向けの共通 verify」を持ち続けると、 宣言の無い repo でそれが黙って効く fallback の口になる (§4 案 (vi))。 RuleKind は閉じた enum なので variant の除去は型・manifest 行・裁定 id の 3 点が 1 PR に揃う形で行う (ADR-0009 §3 と同じ)。 廃止の実装は本 ADR の後の便に置く (本 ADR は docs のみ)。

§2.3 intake が宣言を読み、 上限と突合し、 便ごとに凍結する

便を受け付けるとき、 器は repo の宣言を読んで「上限の中に収まっているか」「検証の各行の先頭が宣言した command か」「repo の外を指していないか」を確かめ、 通ったものをその便の置き場に写して凍結します。 宣言が無い・空・上限の外なら、 その場で断って便を起こしません。 便が自分の実装の中で宣言を書き換えても、 自分の権限は広がりません。

intake は --repo の root の .vessel.toml を読む (MUST)。 読めない・不在・不備ありは rc 1 で拒み、 event を書かない (ADR-0009 §2.2 と同じ極性)。 読んだ値は C10 の Declared として型で持ち、 次の突合 (実測) を経て Effective へ昇格する: (1) allowed-commands の各要素が manifest の上限 runner.allowed_commands に含まれる。 (2) common-verify の各行について、 先頭 command (空白区切りの第 1 語) が宣言の allowed-commands に含まれ、 行が repo の外の path (絶対 path・home の短縮記号) を含む語を持たず、 穴は {base} だけである。 (3) 契約の verify 各行にも (2) と同じ検査を、 判定の基準を宣言の allowed-commands (上限ではない) として掛ける (ADR-0009 §2.2 の「runner.allowed_commands の外」は本 ADR で「宣言の allowlist の外」に読み替える)。 1 件でも外れれば rc 1 で拒む (MUST・全件を集めて報告)。

突合を通った Effective の値は <state_dir>/pipe/<run>/vessel.toml へ写す (MUST・契約 file を contract.toml へ写すのと同じ形)。 以後の段 (spawn・runner・gate・land・resume) はこの写しだけを読み、 対象 repo や worktree の .vessel.toml を読み直さない (MUST NOT)。 これにより、 便の実装が worktree の宣言を書き換えてもその便の権限と共通 verify は変わらない (自己拡張の閉塞)。 宣言を変える PR は通常の便として lens と CI の review を受け、 land した後に intake した便から効く。 event log の record 形は変えない (跨版の契約・ADR-0004 §2.5)——凍結は写し file で行い、 event に新しい field を足さない。

§2.4 runner・gate・land は凍結した写しを読む

実装役を起こすときは、 器が凍結した写しから「使ってよい command」を組んで渡します。 審査 (gate) と取り込み (land) は、 同じ写しの「共通の検証」を、 契約の検証の前に撃ちます。 写しを渡さずに実装役を起こすことはできません。

runner は --vessel <file> を必須 flag として受け (MUST・lens の --contract と同じ fail-closed 極性・無ければ claude を起動せず rc 1)、 その写しの allowed-commands の各要素を Bash(<cmd>:*) の形で --allowedTools に渡す。 --setting-sources project と PermissionRequest hook の一律 deny は ADR-0009 §2.1 のまま不変。 runner は manifest を読まない (MUST NOT)——上限との突合は intake で済んでおり、 runner が読む値は Effective だけである。 spawn の --runner seam は placeholder {vessel} を写しの path へ置換する (既存の 6 つの穴に 1 つ足す・置換の規律は不変)。

gate と land の機械検証は、 順序を変えず (① write-set の照合 → ② 共通 verify → ③ 契約 verify・ADR-0009 §2.4)、 ② の行を manifest でなく写しの common-verify から取る (MUST)。 {base} の置換・verify.jsonl の record 形・verify.stderr.log の診断は不変。 lens は Bash を撃たないので宣言を読まない (不変)。

§2.5 自己ホストと toy repo

器自身の repo にも同じ宣言を置きます。 中身は、 これまで器の規則 file にあった値 (cargo と git・flip check と done の定義 4 本) をそのまま移したものです。 練習用の小さな repo (toy repo) を作る歯も、 目印と一緒に宣言を commit します。

本 repo の root に .vessel.toml を置き (MUST)、 allowed-commands は廃止前の runner.allowed_commands の値、 common-verify は廃止する gate.common_verify の値をそのまま写す (値は変えない・変異検出線の cargo xtask mutants-diff --base {base} は ADR-0009 §2.3 のとおり実装の便で末尾に足す)。 toy repo を作る歯は marker と同じ理由で宣言も tracked にする (便の worktree は base の checkout なので、 untracked の宣言は写らない)。 toy repo の宣言は Rust を含まない (例: allowed-commands = ["git"]・common-verify は git だけで書ける 1 行) ——これが「pipe は言語を知らない」ことの歯になる。

§2.6 射程外

宣言の中身が妥当か (たとえば test を撃たない共通の検証を名乗っていないか) を機械が判定することや、 契約 file や起動 command の置き場、 上限の値そのものの変更は、 ここでは決めません。

次は本 ADR の決定ではない (MUST NOT be read as such): 宣言の意味的な妥当性の機械判定 (例: 自己ホストの宣言が done の定義 4 本を含むかを xtask check の検出線で測る案・別便の候補)、 上限 runner.allowed_commands の値の変更 (C5 の裁定)、 運用物 (契約 file・runner の起動行) の repo tracked な置き場 (ADR-0009 §2.6 のまま・A1 に掛かる)、 宣言を vessel init が生成すること (宣言は repo が書く tracked file であり、 器が値を推測して書くと宣言でなくなる)、 marker .vessel の形式改訂 (跨版 面 1・R-O3)、 憲法条文の改訂 (A2)。

§3. Consequences

良い点は、 Rust でない repo を器に載せられること、 便が自分の権限を広げられないこと、 値の変更がその repo の PR として審査されること、 器の規則 file が「何を許しうるか」の裁定だけに純化することです。 弱い点は、 新しい言語の repo を載せるたびに上限の裁定が 1 回要ること、 宣言の中身が妥当かを機械が見ないこと、 直前の便で足した行を 1 本消す手戻りがあることです。

Positive: 対象 repo が自分の道具を宣言できるので、 器の manifest を触らずに別の言語の repo を載せられる (設計 §7「pipe は言語を知らない」が manifest 経由の内蔵からも解放される)。 Effective の値が便ごとに凍結されるので、 便の実装が宣言を書き換えても自分の allowlist と共通 verify は変わらない (自己拡張の閉塞)。 宣言の変更が対象 repo の PR として lens と CI の review を通る (器の manifest を直す C5 の手続きより、 変更が「どの repo の何を変えたか」として残る)。 manifest は「宣言が名乗れる上限」という裁定の面に純化し、 repo ごとの値を抱えない。 C10 の Declared → Effective の昇格が、 型と intake の突合という実体を持つ最初の面になる。

Negative: 新しい言語の repo を載せる最初の 1 回は上限の裁定 (C5) を要する——意図した摩擦だが、 摩擦である。 宣言の中身 (共通 verify が test を撃つか・空虚でないか) は機械が判定しない (§2.6・lens と人の review の領分)。 直前の便で足した rules 行 1 本と RuleKind の variant 1 つを廃止する手戻りが生じる (型・manifest・裁定 id の 3 点を揃える 1 PR)。 宣言を変える PR 自身の gate には変更後の値が効かない (次の便から)——「PR で共通 verify を足したのに、 その PR は旧い共通 verify で審査される」を受け入れる。 対象 repo の tracked file が 1 つ増える (repo 側の責務)。 toy repo を作る歯は宣言の commit が 1 手増える。

§4. Alternatives Considered

6 つの案を退けました。 器の規則 file に置き続ける案、 目印 .vessel に行を足す案、 契約ごとに書く案、 便の作業 dir の宣言をそのまま読む案、 上限を置かず宣言だけにする案、 宣言が無いときは器の規則 file の値で動かす案です。

案 (i) 器の manifest のまま (ADR-0009 の形を維持): 却下。 利点は実在する——値の置き場が 1 か所で、 C1 を最も字義どおりに満たし、 実装は既に land している。 しかし値は対象 repo の性質であり、 別の言語の repo を載せる日に器の manifest を C5 の手続きで書き換えるか repo ごとの行を器に足すしかない (§1)。 設計 §7 と ADR-0009 §4 案 (v) が退けた「Rust 固有の検査の内蔵」を manifest 経由で作っている。 ∴ 置き場を repo 側へ移す。

案 (ii) marker .vessel に行を足す: 却下。 利点は file が増えないこと。 しかし marker は跨版 面 1 として版番号に依らず固定され (ADR-0004 §2.2・R-O3)、 読み手は 2 行厳格 parse で、 行数違いを「誰も名乗っていない」(Absent) と読む。 前の版と現在の版の hook が同時に黙り、 write-set guard が安全側と逆へ外れる。 marker の parser を緩める改訂は跨版契約の改訂であり、 本 ADR の費用に見合わない。 ∴ 隣の file に置く (§2.1)。

案 (iii) 契約 file に allowlist と共通 verify を書く: 却下。 便ごとに同じ値が手書きされ (C2 に反する・ADR-0009 §4 案 (vi) と同型)、 かつ契約を書く側が自分の便の allowlist を広げられる (自己拡張)。 ∴ repo 単位の宣言にし、 契約は便固有の行だけを持つ形を保つ。

案 (iv) 便の worktree の .vessel.toml を runner / gate が直接読む: 却下。 利点は写しが要らないこと。 しかし worktree は便の実装が書き換える面であり、 実装が宣言に sh を足せば (上限の内なら) 自分の gate をその値で通せる。 intake で凍結した写しを読む形 (§2.3) なら、 便の中で宣言を変えてもその便には効かない。 ∴ 写しを読む。

案 (v) manifest に上限を置かず、 宣言だけで決める: 却下。 利点は器の manifest から allowlist の行が消えて最も薄くなること。 しかし宣言に bash や python -c を書けば器はそれを許すことになり、 「実装役が実行しうる command の宇宙」を広げる判断が repo 側の PR だけで通る。 それは「使う」に近い判断であり、 器の manifest で裁定 id 付きにだけ広がる形 (C5) にする。 C1 の「規則は manifest」もこの上限が担う。 ∴ 上限を残す (§2.2)。

案 (vi) 宣言が無い repo では manifest の値で動かす (fallback): 却下。 利点は既存の toy repo の歯が宣言無しで動き続けること。 しかし fallback は「宣言し忘れ」を「Rust の共通 verify が黙って効く」に化けさせ、 別の言語の repo で cargo を撃って赤くなる (原因が manifest の側にあることが便の外から見えない)。 ADR-0009 §2.2 が採った「動かしてから黙って詰まるより最初に大きく落ちる」極性に反する。 ∴ 宣言が無い repo では intake が rc 1 で断り、 gate.common_verify 行は廃止して fallback の口を構造から消す (§2.2)。

§5. Trace
