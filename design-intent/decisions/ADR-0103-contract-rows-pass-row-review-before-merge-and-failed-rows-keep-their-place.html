設計判断記録 (ADR) scribe2 — 行の審査と落ちた行の順番

契約表の行は設計の PR を main に入れる前に行の審査を通し、 審査か gate で落ちた行は行の予約で順番を守り、 同じ設計の兄弟の行を直しが入るまで待たせる — 先撃ちは退役する

契約の審査は、 契約が起動の列に並んで便が起きた後に在る。 設計の穴はそこで初めて見つかり、 落ちた行は列から外れ、 同じ file を触る後ろの行が先に起きる。 事前に撃つ先撃ちは審査の層になっておらず、 判定の使い回しは 1 度も起きていない。 本 ADR は、 審査を設計の PR の段 (列に並ぶ前) へ移して merge の門で止め、 それでも落ちた行は触る file を取り置いて順番を守り、 同じ設計から出た兄弟の行を待たせ、 先撃ちを退役させると決める。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「契約表の行」は設計の文書に書いた 1 件の仕事の約束、 「便」はその約束を実装して main に入れる 1 回の流れです。 これまで、 約束の中身の審査は、 約束が起動の列 (起こす順番の並び) に入って便が起きた後に行っていました。 そのため設計の穴は並んだ後に見つかり、 落ちた行は列から外れて、 同じ file を触る後ろの行が先に起きていました。 事前に撃っていた先撃ちは、 判定を 1 度も使い回せていません。 この記録は、 審査を設計の変更を main に入れる前 (merge の前) へ移して通らない変更の merge を止め、 それでも落ちた行は触る file を取り置いて順番を守り、 同じ設計から出た兄弟の行を直しが入るまで待たせ、 先撃ちをやめると決めます。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 4 つから説明します。 便の失敗の大半が設計の側にあり、 審査が列に並んだ後に在るという経緯・落ちた行の file が誰のものでもなくなり、 兄弟の行を止める口が無いという現物・先撃ちが審査の層になっておらず使い回しが当たらないという実測・決める範囲です。

CTX1

経緯 — 便の失敗の 96 % は設計の側で、 審査は列に並んだ後に在る

2026-09-28〜09-30 に起きた便 165 本のうち、 FAIL か判断不能 (INCONCLUSIVE) は 76 件 (契約の審査 46・gate 30) で、 73 件の根は設計の側だった (code の事実の誤り 32・done の項目に落ちる歯が無い 24・設計の中の食い違い 9・書き足りない 8)。 runner の誤りが主因は 2 件、 環境 1 件、 審査役の誤りは 0 件。 契約の審査 (SRS FR49) は、 設計の PR を merge して行が起動の列に入り、 便が起きた後の Reviewed の段に在る。 そのため設計の欠陥は便の中で初めて見つかり、 審査は 1 周に穴を 1〜3 個しか名指さないので、 同じ行が 2〜4 周する (1 行で 4 周・55 分)。 持ち主は 2026-09-30 に、 審査で落ちた行が後ろに回り他の行が前に回るのは依存と優先度の順を崩すと指摘した。

CTX2

現物 — 落ちた行の file は誰のものでもなくなり、 同じ欠陥の兄弟を止める口が無い

起動の列は、 直前の便が終端に着き契約の中身が変わらない行を列外 (Settled) にする。 列外の行の write-set は交差の相手に数えず、 交差を測る相手は live な便と同じ周に起こした便だけである。 そのため落ちた行が直るまでの間と、 直って列に戻った行が待つ間に、 同じ file を触る後ろの行が起きる。 2026-09-30 に、 2 回落ちた P2 の行の直しの間に同じ P2 の別の行が起き、 直った行はその行の終わりを待った。 同じ設計の PR で書いた兄弟の行は、 先の行が同じ指示で落ちた 4 秒後に起こされ、 同じ理由で落ちた (直しは 53 分後)。 merge の門 (SRS FR92) は本文の trailer だけを読み、 行の中身を見ない。 gh の pr merge は head の sha を固定する flag (--match-head-commit) を持つ。 vessel 宣言の任意 key の読み手は、 どれも git で commit の宣言を読み、 作業ツリーの宣言を読まない。

CTX3

先撃ち — 審査の層になっておらず、 使い回しは構造上当たらない

先撃ち (依存を待つ行に事前に撃つ契約の審査・設計 dispatcher.md §27) は、 契約の審査で落ちた 46 件のうち 9 件にしか撃たれておらず、 そのうち 6 件は FAIL か判断不能を出したまま起動した (判定が起動を止めない)。 依存の無い行と再受付の便の 34 件には原理的に届かない。 判定の使い回しは全期間で 0 件で、 使い回しの口が在った窓の契約の審査 61 回でも 0 回だった。 理由は、 先撃ちの材料に予想の印の行が必ず入ること (114 本中 114 本)、 宣言だけの祖先は着地で変える既存の file を予想に写さず新しい file を空で置くので祖先の着地で材料が変わること、 lens の cmd に binary の置き場の path が入り 56 時間で 18 回変わったこと。 印を外しても材料が全部同じだったのは 20 回中 1 回で、 使い回すと先撃ちの見逃し (同じ版の PASS 11 回中 2 回を本番が FAIL にした) が素通りする。 費用は 09-28 以後 114 本で約 54.5 ドル (契約の審査の 41 %) で、 便の消費の記録に載らない。 lens の上限の値を 0 にしても、 先撃ちの一時の木と材料の組み直しは毎周撃たれる。

CTX4

射程 — 審査の時点・merge の門・列の順・先撃ちの扱いを決め、 審査役の道具は別の決定に任せる

決めるのは、 (1) 契約表の行を足す・変える設計の PR の head で、 変わった行ごとに機械の検査と契約の審査を撃つ口と、 その記録の形、 (2) merge の門がその記録を見て止める形と、 門に加わる repo の名乗り、 (3) 契約の審査の段が記録を使い回す条件、 (4) 先撃ちの退役の段、 (5) 落ちた行の行の予約落ちた行の取り置きと兄弟の行の待ち。 審査役に読みだけの道具を渡し作業場所を HEAD の写しにする形は、 同じ program の別の決定に任せ、 行の審査merge 前の審査の実装はその決定の実装の後に起こす。 SRS の FR49・FR68・FR92 の字は追加の round で直し、 実装の行はその後に起こす。 ADR を書く条件のうち 1 (C10・C17.2・N1 の解釈)・3 (記録の形・跨版)・4 (却下案を残す価値) に当たる。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 7 本のものさしです。 設計の穴を列に並ぶ前に止めること。 落ちた行が在っても列の順を崩さず、 待ち合いの輪を作らないこと。 同じ欠陥の兄弟の行を続けて落とさないこと。 同じ審査を 2 度撃たず、 見逃しを素通りさせないこと。 仕組みを足す前に消す仕組みを名指すこと。 消費側の repo を黙って変えず、 公開の repo の CI に口座を置かず、 席の入力欄への差し込みを増やさないこと。 判定できないことを、 そのまま通ることに倒さないことです。

DR1設計の穴を列に並ぶ前に止める — 便の中の審査と gate の FAIL の周回を減らす CTX1
DR2列の順 (依存・優先度) を、 落ちた行が在っても崩さず、 待ちの輪を作らない CTX1・CTX2
DR3同じ欠陥を持つ兄弟の行を連鎖させない CTX2
DR4同じ審査を 2 度撃たない — 撃ち直さない鍵は判定に効く入力の全部で取り、 見逃しを素通りさせない CTX3
DR5足す物の前に消す物を名指す (C17.2) — 口 1・on-disk の形 2・任意 key 1・門の断りの語 6・待ちの理由 2・rules 行 1・lens の flag 1 を足し、 先撃ちの module の残り・lens の --stage prelens・先撃ちの置き場の形 1・rules 行 2・使い回しの読み口 1 を消す。 event の種類は足さない (C17) CTX2・CTX3・CTX4
DR6消費側の repo を黙って変えず、 PUBLIC の repo の CI に口座を置かず、 席の入力欄への差し込みを増やさない CTX4
DR7測れないを通すに倒さない (C10) — 予想の審査と partial の判断不能を merge で通すのは、 その記録が契約の審査の段で写されず、 祖先の着地の後の契約の審査が実物で測り直して今どおり止めるからで、 測れないまま効く判定にはしない。 宣言や記録を読めない周は門を断る側に倒す CTX2・CTX4
03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 5 つ並べます。 merge の前に審査して門で止め、 落ちた行の順番を守り、 先撃ちをやめる案 (選んだ案) と、 選ばなかった 4 つです。 選ばなかった案は、 先撃ちの審査役を強い model に戻すだけの案・先撃ちの判定で起動を止める案・CI で審査を撃つ案・merge の後に審査する案です。

OPT1設計の PR の段の行の審査と merge の門・落ちた行の行の予約と兄弟の待ち・先撃ちの退役採用

設計の PR の head で、 変わった行ごとに受付と同じ機械の検査と契約の審査の lens を撃ち、 判定の鍵審査を写す鍵ごとに記録する。 merge の門は vessel 宣言で名乗った repo で、 head を固定しない merge と、 変わった行の審査が通っていない merge と、 審査の後に main で契約表が動いた merge を断る。 契約の審査の段は、 判定の鍵が同じ実物の PASS の記録だけを使い回す。 審査か gate で落ちた行は write-set を取り置き、 同じ設計の兄弟の行を待たせる。 先撃ちは rules 行の値 0 と code の退役の 2 段で畳む。 決め手は分析 (CTX1〜CTX3)。

設計の変更を main に入れる前に、 変わった行ごとに機械の検査と審査役の審査を撃って記録し、 名乗った repo の merge の門で止める案です。 落ちた行は触る file を取り置いて順番を守り、 同じ設計から出た兄弟の行を直しが入るまで待たせ、 先撃ちはやめます。 席が merge する行は並ぶ前に審査され、 先撃ちの届かなかった行にも審査が届き、 足す仕組みは消す仕組みと対にします。 代わりに、 設計の変更ごとに審査の費用と待ちが要り、 まだ無い祖先に頼る行と仕事の札の無い行の判断不能は merge を通ります。

+ 利点

  • 席が merge する設計の PR の行は、 列に並ぶ前に審査を通る (DR1)
  • 依存の無い行と再受付の行にも審査が届く (先撃ちの届かない 34 件) (DR1)
  • 落ちた行の file は取り置かれ、 直った行は元の順位のまま後ろの行より先に起きる。 落ちた行の依存の祖先は待たないので輪ができない (DR2)
  • 同じ設計の PR の兄弟の行は直しが入るまで起きない (DR3)
  • 撃ち直さない鍵と使い回しの鍵は判定に効く入力の全部と lens の子が出す版で取り、 予想の審査は写さない (DR4)
  • 足す物と消す物を対で名指し、 event の種類を足さず、 受付・事前審査・契約の審査・merge の門の既存の関数と口を借りる (DR5)
  • 門に加わるのは宣言で名乗った repo だけで、 審査は host の器が撃ち、 口は前面で最後まで走って席へ差し込まない (DR6)

− 欠点

  • 設計の PR ごとに読みの道具を持つ lens を行の数だけ撃つ費用が要る (未実測)
  • 記録は host の state dir に在り、 別の host から merge すると撃ち直しが要る
  • 祖先が未着地の行と bead の無い行の判断不能は merge を通り、 その行の穴は列に入った後の審査で止まる
  • 新しい doc を 1 本の PR で起こすと、 その doc の全部の行が兄弟になる
OPT2先撃ちを Opus に戻すだけ不採用

先撃ちの model を契約の審査と同じ model に戻し、 使い回しの条件を満たさせる。 決め手は実測 (CTX3)。

先撃ちの審査役を、 本番の審査と同じ強い model に戻すだけの案です。 仕組みを足さず、 規則の表の値 1 つで済む点で勝ります。 けれども、 判定を使い回す鍵は材料の違いで外れ、 model が同じだった期間でも 1 度も当たりませんでした。 当たっても先撃ちの見逃しがそのまま本番を素通りし、 届くのも依存を待つ行だけです。

+ 利点

  • 足す仕組みが無く、 rules 行の値 1 つで済む
  • 先撃ちの判定の質が契約の審査と揃う

− 欠点

  • 使い回しは材料の鍵審査材料の指紋で外れ、 model を揃えた窓でも 0 回だった (DR4)
  • 当たっても先撃ちの見逃しがそのまま素通りする (DR4)
  • 依存を待つ行にしか届かず、 審査が列に並んだ後に在る形は変わらない (DR1・DR2)
OPT3先撃ちの判定で起動を止める不採用

先撃ちが FAIL か判断不能を出した行を、 依存が閉じても起こさない。 決め手は分析 (CTX3)。

先撃ちが落とした行を、 依存が閉じても起こさない案です。 先撃ちの判定のまま起きてしまった 6 件は止まり、 待ちの理由を 1 つ足すだけで済む点で勝ります。 けれども、 届くのは依存を待つ行だけで、 審査で落ちた 46 件のうち 34 件には届きません。 落ちた行が列から外れて順番が崩れる形も残ります。

+ 利点

  • 先撃ちの判定のまま起動した 6 件は止まる
  • 待ちの理由を 1 つ足すだけで済む

− 欠点

  • 届くのは依存を待つ行だけで、 46 件中 34 件には届かない (DR1)
  • 落ちた行が列から外れて順番が崩れる形は残る (DR2)
  • 予想の空の file に由来する判断不能で、 着地で消える理由の待ちが生まれる (DR4・DR7)
OPT4CI で契約の審査の lens を撃つ不採用

設計の PR の CI の job で lens を撃ち、 合格を merge の条件にする。 決め手は分析と PUBLIC の制約 (DR6)。

設計の変更の CI (自動の検査の場) で審査役の審査を撃ち、 合格を merge の条件にする案です。 forge の必須の検査に載せられ、 どこから merge しても同じ記録を見る点で勝ります。 けれども、 公開の repo の CI に審査役の口座と model を持たせることになり、 口座の選び方や箱の上限や台帳は host の器の側に在るので CI からは届きません。 push のたびに撃つと費用も増えます。

+ 利点

  • merge の条件を forge の必須の検査に載せられる
  • どの host から merge しても同じ記録を見る

− 欠点

  • PUBLIC の repo の CI に lens の口座と model を持たせることになる (DR6)
  • 口座の選定・封じ込め・rules 行は host の器が持ち、 CI は台帳に届かない (DR5)
  • PR の push ごとに撃つと費用が push の数に比例する (DR4)
OPT5行の審査を merge の後 (列に入った直後) に撃つ不採用

契約表の行が main に入った直後に審査し、 判定を中身ごとに記録する (ADR-0045 の前の、 契約が出来た直後の審査の形)。 決め手は分析 (DR1・DR2)。

契約表の行が main に入った直後に審査する案で、 以前の形の復活です。 merge の門を変えずに済む点で勝ります。 けれども、 行は既に main に在るので、 落ちた行の直しにもう 1 本の変更が要り、 行の字が変わる merge の時点で止めないと、 落ちた行が起動の列の入力に残ります。

+ 利点

  • merge の門を変えずに済む
  • 審査は列に入る前に済む

− 欠点

  • 行は既に main に在り、 落ちた行の直しにもう 1 本の PR が要る (DR1)
  • 行の字が変わるのは merge の時点だけで、 そこで止めないと落ちた行が列の入力に残る (DR2)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 設計の変更を main に入れる前に、 変わった行ごとに機械の検査と審査役の審査を撃ち、 判定に効く入力の全部を鍵にして記録します。 名乗った repo の merge の門は、 先端を固定しない merge・審査が通っていない merge・審査の後に main で行が動いた merge を止めます。 便の中の審査は、 鍵が同じ実物の合格の記録だけを使い回します。 落ちた行は触る file を取り置き、 兄弟の行を待たせ、 先撃ちは 2 段でやめます。

採用 — OPT1

器は、 契約表の行を足す・変える設計の変更の先端で、 行の審査を撃つ口を持ちます。 口は、 main との分かれ目から中身の指紋 (行の digest) が変わった行のうち、 まだ着地していない行ごとに、 受付と同じ機械の検査と、 本番と同じ審査役の審査を読みだけの形で 1 回撃ちます。 判定は、 行の中身・材料・code の木・祖先の状態・審査役が自分で名乗る版を並べた鍵ごとに記録し、 同じ鍵の行は撃ち直さず、 先端ごとの結果を 1 語で残します。 口は最後まで前で走り、 席の入力欄へは知らせません。 祖先がまだ無い行は、 空の file を置かず、 祖先の行と節を材料に足して予想の審査にします。 名乗った repo の merge の門は、 main か変更の側のどちらかが名乗っていれば、 先端を固定しない merge・結果が通っていない merge・審査の後に main で契約表が動いた merge を断ります。 予想の審査と仕事の札の無い行の判断不能は通し、 FAIL は止めます。 便の中の審査は、 鍵が同じ実物の合格の記録の時だけ撃たずに写します。 先撃ちは、 規則の表の値を 0 にして材料の組み直しも止める段と、 code をやめる段の 2 段で畳みます。 起動の列は、 着地でない終わり方をした行の触る file を、 その行が次の便を起こすまで取り置き、 順番で後ろの行を待たせます (その行が待っている祖先は待たせません)。 審査か gate で落ちた行の兄弟 (同じ節の行と、 同じ設計の変更で審査された行) は、 直しが入るまで待ちます。 取り置きと兄弟の待ちが解ける契機は設計の文書が閉じた列で持ち、 既存の記録から毎回導き、 出来事の種類は増やしません。 merge の前に審査するのは、 行の字が変わるのは merge の時点だけで、 そこで止めれば席が merge する行は並ぶ前に審査済みになり、 落ちた行が列から外れて順番が崩れる形が生まれにくいからです。 先撃ちを強めない・判定で止めるだけにしないのは、 使い回しが材料の違いで外れて 1 度も当たらず、 依存を待つ行にしか届かないと実測で分かったからです。 CI で撃たないのは、 公開の repo に口座を置かず、 口座と箱と台帳を持つ host の器が撃つためです。 口が知らせを送らないのは、 席の入力欄への差し込みは閉じた列で持っていて、 新しい口は前に消した口の復活になるからです。 撃ち直さない鍵に材料と code の木と祖先の状態を入れるのは、 祖先の直しや code の着地で判定が変わりうるのに古い判定を写さないためで、 審査役の起動の字の代わりに審査役が自分で名乗る版を比べるのは、 字に本体の置き場が入り入れ替えのたびに外れるからです。 門が main と変更の両方の宣言を読むのは、 変更が自分で名乗りを外して門を素通りする形と、 名乗りを足す変更が自分の門を持たない形を両方塞ぐためです。 予想の審査の判断不能を通すのは、 祖先の本文は祖先が着地するまで存在せず、 止めると設計の変更が 1 本ずつになるからで、 その記録は便の中の審査で写さないので、 その行は列に入った後に実物で改めて測られます。 落ちた行の file を取り置くのは、 直した行を元の順位で先に起こすためで、 その行が待っている祖先を待たせないのは、 前提の行を足して直す形で待ち合いの輪を作らないためです。 兄弟を同じ節と同じ設計の変更に絞るのは、 同じ時に同じ前提で書いた行だけが同じ欠陥を持ちやすく、 指示が同じかは機械で判じられないからです。
