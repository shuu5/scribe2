設計判断記録 (ADR) scribe2 — code の索引と逆引きの表

code の事実は外の道具が作った索引を器が読んで数える — SCIP と構文の役の一致を器の読み手で平らな表にし、 行ごとの逆引きの表を審査の材料に足し、 受付が索引の閉包と事実の欄で断る

設計が code の事実を誤る・知らない型が、 便の失敗の最大の根である。 名の全 site とその役 (組み立て・呼び出し・match・可視性・歯) を数える道具は器に無く、 字面の閉包は別名も Self の構築も見ない下界である。 本 ADR は、 言語に依らない索引の形式 (SCIP) と構文の役の一致を外の道具に作らせ、 器は自前の読み手で平らな表にして、 行ごとの逆引きの表を件数と母集団つきで審査の材料に足し、 受付と起動の列が足りない file と古びた事実を機械で止めると決める。 外の道具を採ることは持ち主の裁定を待つ (proposed)。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「契約表の行」は設計の文書に書いた 1 件の仕事の約束、 「便」はその約束を実装して main に入れる 1 回の流れです。 便が落ちる理由でいちばん多いのは、 設計を書く人が code の事実 (ある型がどこで組み立てられ、 ある関数を誰が呼んでいるか) を知らずに書くことでした。 器には、 名の使われ方を数える道具がありません。 この記録は、 名の使われ方の表 (code の索引) を外の道具に作らせて器が自分で読み、 行ごとに「触る物の使われ方」を件数つきで設計者と審査役に見せ、 足りない file と古くなった事実を機械で止めると決めます。 外の道具を入れることは持ち主の裁定を待ちます。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 4 つから説明します。 設計が code の事実を誤るのが便の失敗の最大の根だったという経緯・器の閉包が字の一致だけで数える下界だという現物・外の道具を 8 つ試して採点した結果・何を決めて何を持ち主に聞くかという範囲です。

CTX1

経緯 — 設計が code の事実を誤る型が便の失敗の最大の根で、 事実は機械で先に取れた

2026-09-28〜09-30 の便の FAIL か判断不能 76 件のうち、 設計が code の事実を誤った・知らなかった型は 32 件で最も多い。 分類で「機械で先に取れた」と印を付けたのは 33 件で、 索引で取れる 27 件と compiler の試し撃ちで取れる 6 件だった。 渡っていなかった事実の型は、 型を名指す file の集合 (ほかの行の touches の閉包)・struct の literal の全 site・関数の呼び手・既存の歯が pin する物・item と親 module の可視性・path 形の名指しの site で、 どれも名の全 site とその役を問う。 設計の時点では正しく、 便を起こすまでの間に別の着地で変わった事実も 2 件ある。

CTX2

現物 — 器の閉包は字面の下界で、 名の役を数える道具が無い

器の write-set の閉包は touches の型を字面で探し (literal 構築・match の arm・件数 pin・const slice の宣言・variant 構築)、 自ら下界と書く。 別名 (use … as)・Self の構築・glob の取り込みを見ず、 fn 形の touches は宣言の file だけを数えて呼び手を数えない。 上界は構文木が要り、 構文木の crate は実行時の依存 0 本 (SRS NFR3) と A3 に当たるので設計 contract-source.md §11 が却下した。 受付の 1 行の検査は起動の列の候補でも撃たれ、 断りは待ちの理由 admission になる。 審査の材料の outside.txt は、 lens が shell も cargo も撃てないことを理由に、 契約が名指す write-set の外の item を字面で束ねている。 vessel 宣言の任意 key と行の欄はどちらも閉じた列で、 未知の key と欄は宣言と doc の区間を読めなくする。 rust-analyzer は repo の toolchain の component に無い。

CTX3

試し — SCIP に構文の分類を重ねた形が最も正しく、 素の grep は事実を持っていたが埋もれた

失敗の事実 44 件から作った 74 問 (採点 53 問・正解の site 249) で、 道具 8 つを同じ規則で採点した。 SCIP (rust-analyzer) に構文の分類を重ねた形は 49 問が合格し、 site の recall 0.968・precision 0.780、 組み立て・参照・呼び手・歯・可視性の 211 site では recall 0.995・precision 0.972 で、 同名の別 symbol を出した数は 0 だった。 SCIP だけでは precision が半分で、 doc の link・文字列の取り込み・Self の literal・test の役・source の可視性の字が出ない。 名の単語の grep は 43 問が合格し事実の 88 % を持っていたが、 precision 0.023 で 1 問に数百〜千数百の行を出した。 compiler の試し撃ちは 20〜39 問で、 それだけが答えた問いは 0。 既製の graph 3 つは 9〜16 問で、 literal を 1 つも引けなかった。 索引 1 本は wall 約 30〜105 秒・peak RSS 約 2.5 GB で増分は無く、 同じ base の 2 回の出力は byte で同一、 network を切った中で最後まで通った。 規則 3 つは同じ bench の落ちを見てから足したので、 新しい問いでは割り引いて読む。

CTX4

射程 — 索引の形と置き場と表と 3 つの使い場所を決め、 道具の採否は持ち主に聞く

持ち主は 2026-09-27 に Rust 専用の索引の道具を断り、 器が乗る言語を Rust・TypeScript・typed Python と React Native + Expo に決めた (裁定 user 2026-09-27T17:33Z)。 SCIP は 3 言語の indexer を持つ言語に依らない形式である。 vocabulary は、 seam を先に置き採否を測って決める外部依存の枠 (day-1 optional adapter) に graphify を置いている。 本 ADR が決めるのは、 (1) 索引を作る外の道具の宣言と、 器が読む形と、 鍵と置き場と量の上限、 (2) 行ごとの逆引きの表行ごとの使われ方の項目と列と母集団、 (3) 審査の材料・受付の索引の閉包・事実の欄と起動の列の測り直しの 3 つの使い場所。 外の道具を採ることは憲法 A3 の裁定が要り、 本 ADR は proposed で、 rules 行の値と置き場を消すことと合わせて SRS の追加 round で持ち主に聞く。 別の言語の indexer は、 その言語の消費側が宣言するときに決める。 ADR を書く条件のうち 2 (外部依存)・3 (on-disk の形)・4 (却下案を残す価値) に当たる。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 6 本のものさしです。 設計を書く時点で事実を件数と母集団つきで見せること。 足りない file と古くなった事実を、 並ぶ前と便を起こす前に機械で止めること。 器の依存を増やさず、 Rust 専用の形にしないこと。 測れないことを通すことに倒さず、 それでいて道具が壊れた時に全部を止めないこと。 足す前に消す物を名指すこと。 作った表を真実の置き場にせず、 器が作った物だけを消し、 外の道具を箱の中で撃つことです。

DR1設計を書く時点で、 code の事実を件数と母集団つきで見せ、 埋もれさせない CTX1・CTX3
DR2足りない file と古びた事実を、 列に並ぶ前と便を起こす前に機械で止める CTX1・CTX2
DR3器の binary の依存を増やさず (NFR3)、 言語の集合を Rust 専用の形に閉じない CTX2・CTX4
DR4測れないを通すに倒さない (C10) が、 道具が壊れた周に列の全部を止めない CTX2・CTX3
DR5足す物の前に消す物を名指す (C17.2) — 口 1・on-disk の形 1・rules 行 2・宣言の key 2・行の欄 1・材料の file 1 を足し、 手の数え直しの手順・outside.txt の item と要約の塊・graphify の候補を消す。 event の種類と待ちの理由の variant は足さない CTX2・CTX4
DR6導出値を真実の置き場にせず (C3)、 消すのは器が作った物だけにし、 外の道具は封じ込めの中で host の枠を取って撃つ (NFR6) CTX3・CTX4
03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 5 つ並べます。 外の道具の索引を器が読む案 (選んだ案) と、 選ばなかった 4 つです。 選ばなかった案は、 既製の code の graph を採る案・器の字の一致の走査を広げる案・構文木の部品を器に足す案・compiler に仮の編集を当てる試し撃ちを本命にする案です。

OPT1外の道具の SCIP と構文の役名の使われ方の種類の一致を器が読む code の索引名の使われ方の表と逆引きの表採用

vessel 宣言が SCIP を出す command と構文の役の一致を出す command を名乗り、 器が commit の木で箱の中で撃ち、 protobuf と JSON を自前の読み手で読んで平らな表にする。 表は行ごとの逆引きの表 (7 列・件数と母集団) として審査の材料に入り、 受付は索引で解いた別名や Self の構築の site を閉包に足し、 行の事実の欄を測る。 決め手は試し (CTX3)。

外の道具に名の使われ方の索引を作らせ、 器が自分の読み手で読んで表にする案です。 試しでは、 組み立て・参照・呼び出し・歯・可視性の問いで取りこぼしがほぼ無く、 余分な答えもわずかでした。 件数の横に母集団を出すので「0 件」と「測れていない」を分けられ、 器の依存も増えず、 言語は宣言の側に閉じます。 代わりに、 外の道具 2 つを入れる裁定が要り、 code が変わるたびに作り直す時間と memory を使い、 設定の file と文字列の流れは索引の外に残ります。

+ 利点

  • 組み立て・参照・呼び手・歯・可視性の問いで recall 0.995・precision 0.972 (DR1)
  • 件数の横に母集団と索引の外の件数を出すので、 0 件と測れていないを分けられる (DR1・DR4)
  • 別名と Self と glob の越しの site が受付の閉包に加わり、 名乗った事実が起動の時点で測り直される (DR2)
  • 器の binary に crate を足さず、 器が知るのは SCIP の形と役の語だけで、 言語は宣言の側に閉じる (DR3)
  • 設計の PR は code の木の鍵が main と同じで作り直さない (DR5)

− 欠点

  • 外の道具 2 つ (rust-analyzer と ast-grep) を host に入れる (A3 の裁定が要る)
  • 増分が無く、 code を変える着地 1 本ごとに 30〜105 秒と 2.5 GB を使う
  • toml や文字列を経由する流れは辺にならず、 影響範囲は上界しか出ない
  • 索引の閉包索引で数える閉包は CI に無く、 設計の PR の CI を通った行が行の審査と受付で断られる
OPT2既製の code の graph を 1 つ採る不採用

code-review-graph・graphify・codebase-memory-mcp のどれかを land ごとに撃ち、 その query を材料にする。 決め手は試し (CTX3)。

既製の code の graph の道具を 1 つ採って、 その問いの口を材料にする案です。 道具が口と保存の形を持ち、 器が作る物が少ない点で勝ります。 けれども試しでは 53 問のうち 9〜16 問しか通らず、 型の組み立ての場所を 1 つも引けませんでした。 名の字の一致で結ぶ作りは、 器の失敗の型そのものです。

+ 利点

  • 道具が問いの口と保存の形を持ち、 器が作る物が少ない
  • 多くの言語の文法を 1 つの道具が持つ

− 欠点

  • 53 問のうち 9〜16 問しか合格せず、 struct の literal を 1 つも引けない (DR1)
  • 名の一致で辺を結ぶ作りが、 器の失敗の型 (同名・別名・可視性) そのもの (DR2)
  • graphify は Rust で fn と同名の struct を 1 つの node に潰す (DR1)
OPT3字面の閉包を std の走査のまま広げる不採用

別名の表・impl の範囲・glob の展開・呼び手の関数の範囲・可視性の連鎖・test の文脈を、 器の字面の走査に足す。 決め手は見積りと言語の集合 (CTX2・CTX4)。

器が今持つ字の一致の走査を、 別名や範囲の追跡まで広げる案です。 外の道具も依存も要らず、 CI と受付が同じ判定を撃てる点で勝ります。 けれども、 Rust に閉じた構文の近似を何千行も書くことになり、 method を呼ぶ相手の型は型推論が要るので字では解けず、 言語を足すたびに書き直しになります。

+ 利点

  • 外の道具も新しい依存も要らない
  • CI と受付が同じ判定を撃てる

− 欠点

  • 1500〜3000 行の Rust に閉じた構文の近似になる (未実測) (DR3・DR5)
  • method の呼び出しの受け手の型は型推論が要り、 字面では解けず下界のまま残る (DR1)
  • 言語を足すたびに同じ量を書き直す (DR3)
OPT4構文木の crate を器に足す不採用

syn などの構文木の crate を器の binary に link して閉包と表を作る。 決め手は依存の制約 (CTX2)。

構文木を読む部品を器の本体に組み込む案です。 器の中で完結し、 CI も同じ判定を撃てる点で勝ります。 けれども、 実行時の依存を 0 本に保つ約束を破り、 以前の却下を覆します。 名の解決までは持たないので別名と method の相手は残り、 Rust に閉じます。

+ 利点

  • 器の中で完結し、 CI も同じ判定を撃てる
  • 構文の役は正確に取れる

− 欠点

  • 実行時の直接依存 0 本 (NFR3) を破り、 設計 contract-source.md §11 の却下を覆す (DR3)
  • 名の解決 (use の越し・型推論) は持たず、 別名と method の受け手は残る (DR1)
  • Rust に閉じる (DR3)
OPT5compiler の試し撃ちを本命にする不採用

item に #[deprecated] を付ける・struct に欄を足すなどの仮の編集を木に当て、 compiler の診断から site を集める。 決め手は試し (CTX3)。

code に仮の編集 (使うと警告が出る印を付ける・欄を足す) を当てて、 compiler の指摘から場所を集める案です。 追加の道具が要らず、 欄を足して壊れる場所は compiler が正確に知る点で勝ります。 けれども試しでは、 この方法だけが答えた問いは 0 で、 名前を変える形では後ろの使い手が全部黙り、 編集と指摘の読み方が言語ごとに違います。

+ 利点

  • 追加の道具が要らない (cargo は在る)
  • 欄を足して落ちる literal と網羅の match は compiler が正本

− 欠点

  • 53 問のうち 20〜39 問で、 試し撃ちだけが答えた問いは 0 だった (DR1)
  • import の改名は後ろの使い手を全部黙らせ、 全 site を引く道具にならない (DR1)
  • 編集の字と診断の読みが言語ごとに違う (DR3)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 外の道具が作った索引を器が自分の読み手で平らな表にし、 行ごとの逆引きの表を審査の材料に足し、 受付が索引で数えた閉包の不足と、 行が名乗った事実の食い違いで断ります。 起動の列は、 便を起こす時点でその事実を測り直します。

採用 — OPT1

器 SHALL code の事実を、 vessel 宣言が名乗る外の道具の出力から数える。 宣言は任意 key index-scip (1 行ごとに SCIP の file を出す command) と index-roles (1 行ごとに構文の役の一致を 1 行 1 件の JSON で出す command) の 2 つで、 どちらも無い repo は索引を持たない。 器は索引を作る commit を detach した木で宣言の command を封じ込めの箱の中で受付札を取って撃ち (時間の上限は rules 行 index.timeout_s)、 SCIP の protobuf の必要な欄と役の一致の JSON を std の読み手で読み、 occurrence に最も内側の役を結び、 SCIP に無い名は同じ字の occurrence を囲む定義から借り、 平らな表 (code の索引・schema 1) にして state dir に置く。 索引の鍵索引の指紋は code の木の鍵と宣言の字の digest で、 設計の PR は main の索引を使う。 置き場の合計が rules 行 index.cap_mb を越える周は、 撃ち中の鍵と anchor の HEAD の鍵を除き古い順に消す。 索引は導出値で、 無い・壊れた・形の違う索引は無いと読む。 役の語は閉じた 9 つ (literal・pattern・call・use・reexport・test・doclink・capture・vis) で、 どの構文がどの役かは宣言が名指す規則の file が言語ごとに持つ。 口 pipe index の build と show が前面で撃つ。 逆引きの表は、 行の touches の項目と、 節の名指しの型と関数を項目にし、 参照・呼び手・literal・pattern・歯・可視性の連鎖・その項目を touches に持つほかの行の 7 列を、 site と write-set の外の印と、 名の字が tracked file に現れる件数と索引の外の件数の母集団とともに出す。 表は行の審査と契約の審査の材料 index.txt に入る。 受付の 1 行の検査は、 索引を持つ周に字面の閉包と同じ 3 形 (literal・match・variant 構築) を解いた symbol で数え、 足りない file を write-set-incomplete で断る (索引の閉包)。 行は任意の欄 code-facts (code の事実の欄事実の名乗り) で code の事実を数で名乗れ、 行の審査・受付・起動の列はそれを各々の commit の索引で測り、 違えば断るか受付の理由 code-facts で待たせ、 測れない周は code-facts-unmeasured で待たせる。 名乗らない行は、 索引の撃ち中は index-building で待ち、 索引が無い周は字面の閉包に縮退する。 実装は設計 reverse-index.md の行で、 SRS の追加 round と A3 の裁定の後に起こす。

器は、 code の事実を外の道具の出力から数えます。 どの道具を撃つかは repo の宣言が名乗り、 名乗らない repo は索引を持ちません。 器は索引を作る commit の写しの上で、 宣言の道具を箱の中で memory の枠を取って撃ち、 出力を自分の読み手で読んで、 名の使われ方の平らな表 (code の索引) にして置き場へ置きます。 同じ code の木なら作り直さず、 置き場が上限を越えたら、 作り中と今の main の分を残して古い順に消します。 名の使われ方の種類は閉じた 9 語で、 どの書き方がどの種類かは言語ごとの規則の file が持ちます。 行ごとに、 触る型と節が名指す型と関数を項目にし、 参照・呼び手・組み立て・match・歯・可視性・その型を触るほかの行の 7 列を、 件数と母集団つきで出します (逆引きの表)。 表は審査の材料に入ります。 受付は、 索引が在る周に、 別名や自分の型の短縮の書き方の越しに型を組む file の不足を断ります。 行は code の事実を数で名乗れ、 行の審査・受付・起動の列はそれを測り、 違えば断るか待たせます。 索引が作り中なら待ち、 壊れて無い周は字の一致の閉包で続けます (名乗った行は待ちます)。 外の道具にしたのは、 試した 8 つの道具のうち、 言語に依らない索引の形式に構文の分類を重ねた形だけが、 組み立て・参照・呼び出し・歯・可視性の問いで取りこぼしがほぼ無かったからで、 器の本体に部品を足さずに済むからです。 器が形式を自分で読むのは、 依存を 0 本に保ち、 言語を足すのを宣言と規則の file だけにするためです。 件数に母集団を並べるのは、 素の字の検索でも事実の大半は手に入っていたのに、 余分な答えに埋もれて読めなかったと実測で分かったからです。 索引の閉包を字の一致の閉包と同じ形に限るのは、 閉包の意味を変えずに解ける場所だけを増やし、 CI の判定と食い違う所を最小にするためです。 事実を名乗る欄にしたのは、 設計の文の数を機械が判定に使わないためで、 便を起こす時点で測り直すのは、 設計の後に別の着地で事実が変わった例が在ったからです。 道具が壊れた周に名乗らない行を字の一致で続けるのは、 列の全部を止めないためで、 名乗った行だけは測らずに通しません。 試し撃ちを本命にしないのは、 それだけが答えた問いが無かったからです。
