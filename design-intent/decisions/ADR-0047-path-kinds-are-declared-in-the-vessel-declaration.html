設計判断記録 (ADR) scribe2 — path の種別の出所

path の種別は consumer が vessel 宣言で名乗る: guard の 4 種別の分類を固定 prefix から repo ごとの任意 key 3 本へ (key の不在は現行の固定値＝既存の consumer と本 repo は無変更・宣言 file 自身は常に code・不正な宣言は fail-closed で全 file を code にして doctor に typed な 1 行・glob は持たない・schema は 1 のまま)

席の編集を止める guard は、 編集先を 4 つの種別 (design-intent / 設計 doc / 歯 / code) に分けて権能と 1:1 で照合する。 いまの分類は器の中に固定で書かれた 3 つの prefix (design-intent/ ・ docs/design/ ・ crates/<crate>/tests/) で、 この配置は本 repo の配置である。 Rust でない consumer repo にはその段が無く、 全 file が code に落ち、 code の編集の権能を持たない orchestrator の席は 1 file も編集できない (実測)。 本 ADR は分類に属する path の集合を器の規則から外し、 対象 repo が自分の vessel 宣言 (.vessel.toml) の任意 key 3 本で名乗る形にする。 key を書かない repo は現行の固定値のままで、 既存の consumer も本 repo も 1 行も変えない。

この判断が約束すること (1 文サマリ)

「どの file が仕様で、どの file が設計 doc で、どの file が test で、どの file が本体 code か」の切り分けを、器の中に書いた固定の置き場所から、相手の repo が自分で名乗る宣言へ移します。名乗り先は相手の repo にもともと在る宣言 file（.vessel.toml）で、そこに「仕様の置き場」「設計 doc の置き場」「test の置き場」の 3 つを、先頭一致の一覧として書けるようにします。書かない repo はいままでどおりで、既存の相手も scribe2 自身も 1 行も変わりません。宣言 file 自身は必ず「本体 code」に数えるので、席が自分の柵を自分で広げることはできません。宣言が壊れている回は黙って既定へ戻さず、全部を「本体 code」として扱い（＝いちばん厳しい側へ倒し）、点検コマンドに 1 行で理由を出します。

01 背景 / なぜこの判断が要るか

いま何が問題か (本 repo の配置が器の規則になっている)

なぜこの判断が要るのかを、現物と実測と裁定から説明します。席の編集を止める仕組みは、編集先の file を 4 つの種類に分けて、その種類ごとに「してよいか」を照らし合わせます。その分け方は器の中に固定で書かれていて、中身は scribe2 自身の file の置き方そのものです。置き方の違う repo では、全部が「本体 code」に落ちて、席が 1 file も編集できなくなります。相手の repo には、もともと自分のことを名乗る宣言 file が在り、そこには「書かなくてよい項目」の形が既に 4 つ在ります。

CTX1

現物 — 分類は器の中の固定 prefix 3 本で、 中身は本 repo の配置

編集面の guard (ADR-0022 §2.3・設計 seat-roles.md §4) は、 編集先を repo root からの相対 path の prefix だけで 5 つの種別に分ける閉じた enum PathKind (design-intent / 設計 doc / 歯 / code / 対象 repo の外) を持ち、 種別と権能は 1:1 である (PathKind::capability)。 分類の本体 PathKind::of_relative は 3 つの prefix を const で固定して持つ: 1 段目が design-intent なら design-intent、 1 段目と 2 段目が docs / design なら設計 doc、 1 段目と 3 段目が crates / tests なら歯、 先頭が .. なら対象 repo の外、 それ以外はすべて code である。 この 3 つはいずれも scribe2 自身の repo の配置であって、 器が対象 repo に強制できる規則ではない。 歯 (role_guard_path_kind_classifies_by_prefix_only / role_guard_orchestrator_may_edit_teeth_but_not_src) も本 repo の配置を前提に書かれている。

CTX2

実測 — Rust でない consumer repo では orchestrator の席が 1 file も編集できない

orchestrator の席は ADR-0045 §2 (1) により src の編集の権能を持たない (行が持つのは歯の段に限った編集で、 名は edit-tests)。 分類が固定 prefix である以上、 Rust でない consumer repo — docs/design/ の 2 段も crates/<crate>/tests/ の段も持たない repo — では、 仕様の file も設計 doc も test も、 すべてが code に落ちる。 落ちた先の権能を行が持たないので、 その席は自分の repo の file を 1 つも編集できない (実測済み)。 これは guard の欠陥ではなく、 分類の値の出所が器の側に在ることの帰結である。 本 repo では同じ分類が正しく働くので、 本 repo だけを見ていると現れない。

CTX3

読み口が既に在る — 対象 repo は自分のことを vessel 宣言で名乗っている

対象 repo の root には marker の隣に tracked な宣言 file .vessel.toml が在り (ADR-0010 §2.1)、 「許してよい command」「どの便でも撃つ検証」を repo 自身が名乗っている。 読み手は器の中に 1 本だけで、 行単位の key = value を読み、 配列と scalar の層は rules manifest の loader と共有する (第 2 の parser を作らない)。 未知の key は断り、 必須 key の欠落・重複・型違いは行番号つきで全件積む。 書かなくてよい key (任意 key) の形は既に在り、 現に 4 つが載っている: 検出線の行の列・要件面の path・push 先の remote の名・CI の判定を読む 1 行 (ADR-0023 が要件面の path を任意 key として足した前例)。 任意 key の「無い」は key の不在で表し、 書いた空配列は従来どおり不備である。 宣言の schema は 1 で、 読み口は HEAD commit の tree を読む (作業ツリーは読まない＝commit されていない宣言は無いのと同じ)。

CTX4

guard は anchor を先に解いており、 宣言の置き場はそこから決まる

guard が権能を解く順は anchor (repo root・state dir) → pane → target → 登録 row → role → rules 行 → 権能で、 anchor がいちばん先に在る (設計 seat-roles.md §4)。 anchor は生成 hooks.json の shell 行が渡す --project から解き、 席が cd しても変わらない。 席の登録 row も 役割 × anchor を鍵に持ち、 anchor の値 (対象 repo の main checkout の path) を項目として持つ。 つまり「どの repo の宣言を読むか」は guard が既に持っている値から決まり、 新しい引数も env も要らない (C2.2)。 anchor を解けない周は現行どおり権能なし＝deny (fail-closed) である。

CTX5

裁定 — repo ごとに宣言する

user 裁定 2026-09-20 (対話面・逐語は台帳 s2-07l.491 の notes) は、 path の種別の分類を「repo ごとに宣言する」形に決めた。 分類の値をどこに書くか (宣言 file か rules 行か) と、 どの表現力を持たせるか (prefix か glob か) は本 ADR が決める。 新しい consumer repo の最初の宣言 file を誰が書くかは導入の口の設計に属し、 本 ADR の範囲外である (未実装)。

CTX6

憲法の向き

C1 は規律を manifest と型に置き、 器の外の散文を規則の置き場にしない。 C10 は人が書いた宣言値と効力を持つ値を型で弁別し、 宣言値は実測を経てはじめて効力を持つと定める (host 固有の値は manifest 以外に置けない)。 C11 は失敗を境界ごとの enum で表し、 開くか閉じるかの極性を型に持たせる。 C16 は逸脱を編集の時点で止める。 C17 (決定はしご・ADR-0044) は「要るか → 既に在るか → 標準 library か入っている依存で足りるか → 1 行で書けるか → 最小実装」を宣言順に通り、 最初に成立した段で止まる。 C17.2 は走査・record・rules 行・仕掛けを足す提案に、 先に消すものを名指すことを求める。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (出所・無変更・非増殖・自分の柵・fail-closed)

判断を評価する 5 本のものさしです。repo の置き方はその repo の事実なので、その repo が名乗ること。いま動いている相手と scribe2 自身を 1 行も変えさせないこと。読み口も parser も規則の行も増やさないこと。席が自分を縛る柵を自分で広げられないこと。そして、宣言が読めない回に黙って既定へ戻さず、いちばん厳しい側へ倒して理由を名指すことです。

DR1repo の file の配置はその repo の事実であって器の規則ではない。 器は種別の集合 (閉じた enum) と権能の対応を持ち、 種別に属する path の集合は対象 repo が名乗る 憲法 C1 / C10・CTX1
DR2いま動いている consumer と本 repo の宣言を 1 行も変えさせない (key を書かない宣言は現行の分類のまま・schema の版も上げない) ADR-0010 §2.1 / ADR-0023 (任意 key の前例)
DR3読み口・parser・rules 行・走査を増やさない。 既に在る宣言 file と 1 本の reader と既に在る任意 key の形で済ませる 憲法 C17 の段 2・C17.2 / ADR-0044
DR4席が自分の柵を自分で広げられない。 分類の宣言を書き換える編集そのものが、 便の審査と gate か user の手を通る側に落ちる 憲法 C16 / SRS FR45・ADR-0010 §2.4
DR5宣言が読めない・矛盾する周は黙って既定へ戻さない。 いちばん厳しい側 (全 file が code) へ倒し、 理由を typed な語で名指す 憲法 C10 / C11・SRS NFR4
03 検討した選択肢 / 5 つの形

それぞれの利点と欠点を並べる

候補を 5 つ並べます。相手の repo の宣言 file に先頭一致の一覧を 3 つ足す案、同じ宣言をワイルドカードや正規表現で書けるようにする案、分類を器の規則の行に持つ案、置き方の違う相手の席に本体 code の編集を許す案、そして中身を見て言語を当てて自動で分類する案です。

OPT1vessel 宣言の任意 key 3 本 (repo 相対の prefix の配列)・key の不在は現行の固定値・宣言 file 自身は常に code採用

対象 repo の .vessel.toml に flat な任意 key を 3 本足す (design-intent の置き場 / 設計 doc の置き場 / 歯の置き場)。 値は repo 相対の prefix の配列で、 dir は末尾 /・単一 file は完全一致とする。 key を書かない宣言は現行の固定値 (本 repo の配置) のままで、 既存の consumer も本 repo も 1 行も変わらない。 読み口は既に在る 1 本 (行単位の key = value・配列の層は rules manifest と共有) で、 任意 key の形も既に在る (検出線・要件面・remote・CI の行)。 guard は登録 row の anchor の宣言を読んで分類し、 宣言 file 自身は常に code の種別に落とす。

相手の repo が自分の宣言 file に「仕様はここ」「設計 doc はここ」「test はここ」を、先頭一致の一覧として書けるようにします。書かなければいままでどおりです。読み込む部品も書き方も、いま在るものをそのまま使います。宣言 file そのものは必ず「本体 code」に数えるので、席が自分で自分の柵を広げることはできません。

+ 利点

  • 分類の値の出所が repo の側へ移る (DR1)・置き方の違う repo でも席が仕事を始められる (CTX2 の実測が解ける)
  • key の不在＝現行の固定値ゆえ、 既存の consumer と本 repo の宣言は無変更で schema も 1 のまま (DR2)・跨版で読み口が割れない
  • 足すのは既に在る宣言 file の任意 key 3 本だけで、 読み口も parser も rules 行も走査も増えない (DR3)
  • 宣言 file 自身が常に code ゆえ、 席は自分の柵を自分で広げられない (DR4)・変更は便の審査と gate か user の手を通る

− 欠点

  • prefix しか書けないので、 種別が dir の段で分かれていない repo (同じ dir に設計 doc と code が混ざる形) は表せない
  • 宣言を書き間違えた repo は fail-closed で全 file が code になり、 席が止まる (doctor の 1 行を読むまで理由が分からない)
OPT2glob / 正規表現で宣言する不採用

同じ 3 本の key に、 prefix でなく glob (docs/**/*.md) か正規表現を書けるようにする案。 表現力は上がるが、 宣言の読み口に pattern の parser と評価器を足すことになり (行単位の key = value と配列の層だけで済んでいた読み口が 1 段深くなる)、 「どの pattern がどの種別に当たるか」の曖昧さ (重なり・優先順・最長一致) を器が決めることになる。 いま解こうとしている形 — 種別ごとの dir を名乗る — は prefix で足りる。 決定はしごの段 3 / 段 4 (入っている依存で足りるか・1 行で書けるか) で止まる。

同じ宣言をワイルドカードや正規表現で書けるようにする案です。細かく書ける代わりに、読み取る部品が増え、複数の書き方が同じ file に当たったときにどちらを採るかを器が決めることになります。いま必要なのは「この dir から下」なので、先頭一致で足ります。

+ 利点

  • dir の段で分かれていない配置も表せる・拡張子だけで種別を分ける repo にも当たる

− 欠点

  • 宣言の読み口に parser と評価器を足す (DR3)・重なりと優先順の曖昧さを器が決めることになる・prefix で足りる (C17 の段)
OPT3rules manifest の行に持つ不採用

分類の値を器の rules manifest の行 (裁定 id つき) に置き、 consumer ごとに host の面で上書きする案。 だが rules 行は器の規則の置き場であって、 「この repo のどの dir が設計 doc か」は規則ではなく対象 repo の事実である。 器の規則の行に repo 固有の配置を積むと、 consumer が増えるたびに器の行が増え、 裁定 id を打つ相手も「その repo の配置」になる (C5 の裁定の意味が薄まる)。 宣言 file は既にこの分担で作られている — 値は repo が名乗り、 器の行は上限だけを持つ (ADR-0010 §2.1)。 同じ分担をここでも取る。

分類を器の規則の行に書く案です。規則の行は「器がどう振る舞うか」の置き場で、「この repo のどの dir が設計 doc か」は相手の repo の事実です。相手が増えるたびに器の行が増え、承認の意味も薄まります。同じ分担は宣言 file の側に既に在ります。

+ 利点

  • 値が裁定 id つきで rules-diff に載る・器の側で全 consumer の分類を一望できる

− 欠点

  • 器の規則に対象 repo の事実を積む (DR1)・consumer ごとに器の行が増える (DR3)・ADR-0010 の分担 (値は宣言・行は上限) と逆向き
OPT4consumer の席に src の編集の権能を与える不採用

分類は固定のまま、 置き方の違う repo の席には edit-code を与えて動かす案。 1 行で済むが、 ADR-0045 §2 (1) の役割分担 — orchestrator は契約・設計・落ちる歯を書き、 実装は自分で行わない — を崩す。 しかも崩し方が静かで、 「置き方が違うから」という理由で権能が増え、 その repo では席が本体 code を直接書けるようになる。 種別の分類が壊れている問題を、 権能を広げて見えなくしているだけで、 分類は壊れたままである。

分け方はそのままにして、置き方の違う相手の席には「本体 code を編集してよい」を与えて動かす案です。1 行で済みますが、席の役割分担（席は実装を自分で行わない）を、置き方の違いを理由に崩すことになります。分け方が壊れている問題は残ったままです。

+ 利点

  • 変更が rules 行 1 つ分で済む・実装の便が要らない

− 欠点

  • ADR-0045 §2 (1) の役割分担を崩す (DR4)・分類の壊れを権能で覆い隠す・「置き方が違う」が権能を増やす理由になる
OPT5分類を言語の検出で自動化する不採用

repo の中身 (build file・拡張子の分布・慣習の dir 名) から言語と配置を当て、 種別を自動で決める案。 宣言を書かせずに済むが、 推測は黙って外れる——外れた周に席が止まる (厳しい側へ外れる) か、 本来 code の file が設計 doc として通る (緩い側へ外れる) かのどちらかで、 どちらも「測っていない値が効力を持つ」形である (C10)。 さらに検出のための走査を器に足すことになり、 C17.2 の「足す提案は先に消すものを名指す」に対して消すものが無い。

repo の中身を見て言語と置き方を当て、自動で分ける案です。宣言を書かなくて済みますが、当て推量は外れたときに黙って外れます。厳しく外れれば席が止まり、緩く外れれば止めるはずの編集が通ります。どちらも「測っていない値が効いている」形です。

+ 利点

  • consumer が宣言を書かなくてよい・新しい repo でもそのまま動く

− 欠点

  • 推測が黙って外れ、 緩い側へ外れると guard が空洞化する (DR5 / C10)・検出のための走査を器に足す (C17.2 に対して消すものが無い)
04 採用した判断 / どの形を選ぶか

選んだ形と、 それが守る要件 (cross-doc 照会)

選んだ案と、それが要件書のどの要件を支えるかを示します。相手の repo の宣言 file に先頭一致の一覧を 3 つ足し、書かない repo はいままでどおりにし、宣言 file 自身は必ず本体 code に数え、宣言が壊れている回はいちばん厳しい側へ倒して理由を 1 行で出します。編集の時点で止める執行（FR45）、権能と種別の 1:1（FR41）、不正な入力を黙って落とさないこと（NFR4）に対応します。

採用 — OPT1

対象 repo の vessel 宣言 (.vessel.toml) SHALL 任意の flat key 3 本 (design-intent-paths / design-doc-paths / tests-paths) を受け、 値 SHALL repo 相対の prefix の配列である (dir は末尾 /・単一 file は完全一致・既に在る配列の層をそのまま使う)。 key を書かない宣言 SHALL 現行の固定値 (本 repo の配置) で分類され、 既存の consumer と本 repo の宣言 SHALL 1 行も変わらない。 宣言 SHALL NOT glob・正規表現を持つ (prefix で足りる・決定はしご C17)。 編集面の guard SHALL 登録 row の anchor の宣言を読んで種別を決め、 宣言 file 自身 SHALL 常に code の種別である＝席 SHALL NOT 自分の柵を自分で広げ、 宣言の変更 SHALL 便 (審査と gate) か user の手を通る。 宣言が不正な周 (.. を含む・絶対 path・空文字・種別の間で prefix が重なる) SHALL fail-closed で全 file を code の種別として扱い、 doctor SHALL typed な 1 行で理由を出す＝器 SHALL NOT 黙って既定へ戻る (憲法 C10 / SRS NFR4)。 宣言の schema SHALL 1 のままで (key の追加と不在＝既定は版を上げない)、 新旧どちらの読み口も同じ宣言を読める。 種別の集合 (閉じた enum) と種別ごとの権能の 1:1 SHALL 不変で、 変わるのは種別に属する path の集合の出所だけである。 新しい consumer repo の最初の宣言 file を誰が書くか SHALL 導入の口の設計が決め、 本 ADR SHALL NOT それを決める (未実装)。 発効 SHALL 宣言の任意 key 3 本と guard の読み口が land した版とし、 本 ADR SHALL それまで proposed のまま何も拘束しない。

相手の repo が自分の宣言 file に、「仕様の置き場」「設計 doc の置き場」「test の置き場」の 3 つを先頭一致の一覧で書けるようにします。書かない repo はいままでどおりで、既存の相手も scribe2 自身も 1 行も変わりません。ワイルドカードや正規表現は持たせません。編集を止める仕組みは、その席が登録されている repo の宣言を読んで分け方を決めます。宣言 file そのものは必ず「本体 code」に数えるので、席が自分の柵を自分で広げることはできず、書き換えるには便（審査と検査）か user の手が要ります。宣言が壊れている回は、黙って元の分け方に戻さず、全部を「本体 code」として扱い（いちばん厳しい側）、点検コマンドが理由を 1 行で出します。宣言の版は上げないので、古い読み口でも新しい読み口でも同じ file が読めます。種類の数も、種類ごとに何をしてよいかも変わりません。変わるのは「どの file がどの種類か」を誰が決めるか、だけです。 分類が器の中に固定で書かれている限り、その中身は scribe2 自身の置き方であって、相手の repo の事実ではありません（CTX1）。置き方の違う repo では全部が「本体 code」に落ち、本体 code の編集の権能を持たない席は 1 file も編集できません（CTX2）。これは guard の不具合ではなく、値の出所が間違っている形です。相手の repo はもともと自分のことを宣言 file で名乗っていて、そこには「書かなくてよい項目」の形も読み口も既に在ります（CTX3）。だから足すのは任意の項目 3 つだけで、読み込む部品も規則の行も増えません。書かない回を現行の固定値にするのは、いま動いている相手と scribe2 自身を 1 行も変えさせないためで、版を上げないのも同じ理由です。宣言 file 自身を必ず「本体 code」に数えるのは、そうしないと席が「自分が編集してよい範囲」を自分で書き足せてしまい、止める仕組みが自分で外せる柵になるからです。壊れた宣言で元の分け方へ黙って戻さないのは、戻した瞬間に「読めなかった」という事実が消え、間違った分け方で動いていることに誰も気づけないからです。先頭一致だけに絞るのは、いま要るのが「この dir から下」であって、それ以上の書き方を足すと読み取る部品と曖昧さが増えるからです。

この判断が正当化する要件 (cross-doc 照会 → SRS-SCRIBE2-MVP)

FR45claim権能で守られた操作を編集の時点で止める形は不変で、 分類の値の出所だけが対象 repo の宣言へ移る。 宣言が読めない周は権能なしの側へ倒れるので、 「止める点が在る」という要件の中身は弱まらない。
FR41claim権能の一覧は rules 行が持ち、 種別と権能の 1:1 も不変である。 本 ADR が決めるのは「歯の path 種別」等が指す path の集合を誰が名乗るかで、 行の値にも種別の集合にも触れない。
NFR4claim不正な宣言 (..・絶対 path・空文字・種別をまたぐ重なり) を黙って落とさず、 全 file を code として扱ったうえで doctor に typed な 1 行を出す＝「黙って落とす件数 0」の側に立つ。

照会先: SRS-SCRIBE2-MVP — SRS: 設計 → 契約 → 実装 → 検証 → land を、 人の手を借りずに 1 本通す器（MVP）

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなることと、代わりに引き受けることです。置き方の違う repo でも席が動けるようになり、分け方の出所が相手の repo へ移り、いま動いているものは 1 行も変わらず、席が自分の柵を広げられない形が保たれます。代わりに、書ける形が先頭一致だけであること、宣言を間違えた repo は席が止まること、分類が repo ごとに違うので歯が本 repo の配置だけを測れなくなること、そして新しい repo の最初の宣言を誰が書くかを先送りにすることを引き受けます。

✓ 良い結果

  • ●Rust でない consumer repo でも orchestrator の席が自分の仕様と設計 doc と歯を編集できる (CTX2 の実測が解ける)・器の配置を相手に押し付けない
  • ●分類の値の出所が対象 repo の宣言へ移り、 器の側は種別の集合と権能の 1:1 と上限だけを持つ (ADR-0010 の分担と同じ形)
  • ●key の不在＝現行の固定値ゆえ、 既存の consumer と本 repo の宣言は無変更・schema は 1 のまま＝跨版で読み口が割れない
  • ●宣言 file 自身が常に code ゆえ席は自分の柵を広げられず、 宣言の変更は便の審査と gate か user の手を通る (DR4)・読み口も rules 行も走査も増えない

⚖ トレードオフ・代償

  • ●書けるのは prefix だけ。 種別が dir の段で分かれていない repo (同じ dir に設計 doc と code が混ざる形) は表せず、 その repo は dir を分けるか全 file を code として扱うことになる
  • ●宣言を書き間違えた repo は fail-closed で全 file が code になり、 席が止まる。 理由は doctor の 1 行に出るが、 席の側の deny 文は「権能でない」としか言わない (読む先が 2 つに分かれる)
  • ●分類が repo ごとに変わるので、 歯は「本 repo の配置で正しいか」だけを測れば足りるという前提を失う (宣言の値から分類が導かれる形を歯が測ることになる)
  • ●新しい consumer repo の最初の宣言 file を誰が書くかは決めない (導入の口の設計・未実装)。 それまでは新しい repo に宣言を置く手が user の側に残る
06 改訂関係と原則 / この判断の位置づけ

版の系譜と、 行き着く原則 (照会終端)

この ADR が版の系譜のどこに在るかと、判断が最後に行き着く原則です。既存の ADR は 1 本も置き換えません。宣言 file の分担（値は相手が名乗り、器の行は上限だけを持つ）と、席の役割分担の上に乗ります。行き着く原則は「相手の repo の形は相手の事実であって、器の規則ではない」です。

照会終端 — PRIN-CONSUMER-DECLARES-ITS-OWN-SHAPE (本 ADR)

対象 repo の形 (どの dir が何か) は、 その repo の事実である。 器は種別と上限と極性を持ち、 値はその repo に名乗らせる——名乗らない周は器の既定で動き、 名乗りが読めない周は最も厳しい側へ倒す。

本 ADR の判断はこの原則に行き着く (これ以上は遡らない照会終端)。 憲法 C10 (宣言値と効力を持つ値を型で弁別し、 宣言は実測を経てしか効かない) と C1 (規律は器の中に置く) を、 「repo 固有の事実をどちらの側に置くか」の形で持ったものである。 器の既定を他人の repo の規則にしない。

07 用語集 / この文書で使う専門語

本文に出てくる専門語のやさしい説明

本文に出てくる専門語を、やさしい言葉で説明します。

path の種別path kind
編集先の file を分ける閉じた分類 (design-intent / 設計 doc / 歯 / code / 対象 repo の外)。 種別ごとに要る権能が 1 つ決まっていて、 編集面の guard は編集先の種別を引いてから席の権能と照らす。 分類は repo root からの相対 path の先頭一致だけで決め、 file の中身や名前の語彙では判定しない。
vessel 宣言vessel declaration
対象 repo の root に marker の隣として置く tracked な file (.vessel.toml)。 その repo が「許してよい command」「どの便でも撃つ検証」などを自分で名乗る宣言値で、 器はここに上限を掛けて便ごとに凍結する。 本 ADR はここに path の種別の宣言を 3 本足す。
任意 keyoptional key
宣言 file の key のうち、 書かなくてよいもの。 「無い」は key の不在で表し (書いた空配列は不備)、 書かない宣言は器の既定で動く。 既に検出線の行・要件面の path・push 先の remote・CI の行の 4 つが任意 key で、 本 ADR の 3 本も同じ形である。
prefix の宣言prefix declaration
repo 相対の path の先頭一致で集合を表す書き方。 末尾に / を付けた項目はその dir の配下全部を指し、 付けない項目は file の完全一致を指す。 ワイルドカードも正規表現も持たない。 器の中では write-set の allowlist が同じ形を既に使っている。
fail-closedfail closed
解けない・読めない周に「通す」ではなく「止める」側へ倒す極性。 ここでは、 宣言が不正な周に現行の既定へ戻すのでなく、 全 file を code の種別として扱う (code の権能を持たない席は止まる)。 極性は型が持ち、 全 guard の一覧は器が生成する。
anchoranchor
席が仕える対象 repo の main checkout。 席の登録は役割と anchor を鍵に持ち、 guard は権能を解く最初の段で anchor を解く。 本 ADR の guard は、 この anchor の宣言 file を読んで種別を決める (新しい引数も env も要らない)。
