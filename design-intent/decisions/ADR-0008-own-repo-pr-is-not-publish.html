ADR-0008 — 自 repo への branch push と PR 作成は憲法 A4.2 の「出す」ではない (A4.3 の可逆)

§1. Context

自分の repo に枝を押して「見てください」の札 (PR) を立てる操作に、 これまで人の承認を要求していました。 憲法を読み直すと、 承認が要るのは取り消せない操作だけで、 この操作は取り消せます。

憲法 A4.2 は「操作が不可逆 (destroy / publish / 追加課金) のとき」だけ C7 の対話面で先に確認せよと定め、 A4.3 は「merge・自 repo への dispatch・依存なしの code 変更は A4.2 の目的において可逆と扱う」と定める。 一方 pipeline の設計 doc は --pr-cmd を「公開の口」と呼び、 前提に「run に承認 event が在る」を足していた (§5.4)。 加えて §5.5 は「3 クラスの判定は契約の自己申告に加え、 seam の使用からの導出を 1 つ持つ」と定めていた。 これは ADR ではなく実装時の設計裁定 (2026-09-10) である。

この読みの下で、 自 repo (すでに公開されている本 repo) へ branch を push して PR を出すだけの便が「出す」に分類され、 1 便ごとに人の承認を消費していた (記録時点の実測: 同日 3 便で承認 6 回)。 承認が安く大量に要求されると、 承認そのものが儀式化して「本当に不可逆な操作の前で止まる」機能が薄まる——A4.2 が守ろうとしているのはその機能である。 ∴ 「出す」の範囲を条の解釈として確定する必要がある。 本 repo の作法は憲法条の解釈が要る便は実装前に ADR を書くと定めるので、 ここへ記録する。

§2. Decision

決めることは 3 つです。 「出す」とは何か、 では機械はどうやって見分けるのか、 そして今回は決めない範囲はどこかです。

本 ADR は A4.2 の「出す」(publish) の範囲の解釈だけを記録する。 憲法本文・rules 表・SRS はいずれも書き換えない (A4.3 が既に答えているため、 解釈で足りる)。

§2.1 「出す」は repo の外へ出す操作

「出す」は、 自分の repo の外へ情報を出すことです。 自分の repo に枝を押して PR を立てるのは、 どちらも後から閉じられるので含みません。

A4.2 の「出す」は repo の外へ出す操作を指す (MUST): 他 repo への push、 外部サービスへの送信、 release / tag の公開、 公開 URL の発行。 自 repo への branch push と PR 作成は A4.3 の「自 repo への dispatch」として可逆であり、 Ask-first の対象外である (MUST NOT be gated on approval)。 可逆性の根拠は機構にある: この形は main を 1 byte も動かさず、 branch も PR も後から閉じられる——A4.3 が merge を可逆と呼ぶのと同じ理由で、 merge の手前の操作も可逆である。

本 repo が既に PUBLIC であることは判定を変えない。 PR は公開 repo の中で起こる出来事であり、 「repo の外へ出す」ではない——PUBLIC 面へ書く情報そのものの規律 (逐語・host 名・口座名を tracked file へ書かない) は本 ADR とは別の面で、 そちらは不変である。

§2.2 機構 — 判定は契約の自己申告だけ

機械は「この便は消す / 出す / 使うに当たる」と契約が自分で名乗った分だけ止めます。 道具を使ったかどうかから推測するのはやめます。

--pr-cmd は承認 event を前提としない (MUST NOT require)。 3 クラス (消す / 出す / 使う) の判定は契約の自己申告 (classes) だけとし、 設計 §5.5 の「seam の使用からの導出」は廃止する。 導出を残せない理由は、 それが操作の可逆性ではなく道具の名前で止めていたことにある——同じ seam に他 repo へ push する道具を渡しても、 自 repo へ PR を出す道具を渡しても、 導出は同じ判定を出す。 ∴ 正しく止まる形にはならない。

classes に publish を名乗る契約は従来どおり spawn の手前で Blocked となり、 承認 event を受けるまで進まない (SRS FR15 / FR16・AC5 は不変)。 承認の受理面 (C7 の対話面・逐語を event へ記帳する) も ADR-0005 のまま変えない (supersede しない)。

§2.3 射程外

この記録は範囲の読み方だけを決めます。 憲法の文そのものを直すことも、 機械が操作の中身を見て判定することも、 ここでは決めません。

次は本 ADR の決定ではない (MUST NOT be read as such): 憲法条文の改訂 (A2 の手続きを要する・本 ADR は条文を 1 文字も変えない)、 操作の中身から 3 クラスを判定する enforcer の実装 (A4 の機構欄・次の版)、 push 先が自 repo かを機械が弁別すること (remote の解決は道具側にあり core は道具を知らない・MVP は自己申告)、 「出す」以外の 2 クラス (消す / 使う) の範囲 (本 ADR は publish の範囲だけを扱う)。

§3. Consequences

良い点は、 承認を求める回数が減って、 本当に取り返しがつかない操作の前でだけ止まるようになることです。 弱い点は、 見分けが契約の自己申告に頼るので、 名乗り間違いを機械が見つけられないことです。

Positive: 自 repo への PR を出す便が承認を消費しなくなる (記録時点の実測では同日 3 便で 6 回消費していた)。 承認要求が不可逆な操作に集中するので、 A4.2 が守ろうとしている「止まる」機能が摩耗しない。 判定の面が 2 つ (自己申告 + seam からの導出) から 1 つ (自己申告) へ減り、 同じ操作が経路によって違う判定を受ける余地が消える。

Negative: 名乗り間違いを機械が捕まえられない。 classes を空にした契約が --pr-cmd に他 repo へ push する道具を渡せば、 器は止めずに通す (弁別は §2.3 で射程外へ置いた enforcer の領分)。 ∴ MVP では契約を書く側の規律に依存する——起票時に「repo の外へ出るか」を見て classes を名乗る運用が要る。 また Land から承認の導出値を落としたので、 将来 enforcer を入れる周には land 側へ判定の材料を渡し直す設計が必要になる。

§4. Alternatives Considered

3 つの案を退けました。 いまのまま承認を求め続ける案、 機械に push 先を調べさせる案、 憲法の文そのものに書き足す案です。

案 (i) 現状維持 (1 便 1 承認): 却下。 利点は実在する——承認 event が残るので「誰が何を許したか」の記録が便ごとに揃い、 判定を間違える余地が無い (安全側へ倒れる)。 しかし A4.3 が自 repo への dispatch を明示的に可逆と定めているため、 可逆な操作に Ask-first を課す形は条と矛盾する。 加えて承認の要求が大量に出ると承認が儀式化し、 不可逆な操作の前で止まる機能そのものが薄まる (§1 の実測)。

案 (ii) --pr-cmd の文面や remote の URL から自 repo かを機械が判定する enforcer: 却下。 利点も実在する——自己申告に頼らず「repo の外へ出るか」を機械が測れるので、 名乗り間違い (§3 Negative) を塞げる。 しかし remote の解決は道具側にあり (seam に渡るのは sh -c の 1 行で、 push 先を決めるのは道具である)、 core は道具を知らない設計を採っている。 ここで文面を parse すると、 器が道具の方言を追いかける実装を抱え込み、 道具を変えた日に静かに誤判定する。 ∴ 判定の面は次の版の enforcer (A4 機構欄) へ置き、 本 ADR は範囲の解釈だけを確定する。

案 (iii) 憲法 A4.2 の「出す」の範囲を条文へ明文化する: 却下。 利点は最も強い——解釈を ADR に置くより条文に置いた方が、 読む側は 1 か所で完結する。 しかし憲法条文の改訂は A2 の user 裁定の手続きを要し、 かつ A4.3 がすでに「自 repo への dispatch は可逆」と答えている。 答えの在る条へ言葉を足す改訂は、 手続きの費用に見合う情報を増やさない (同じ内容が 2 か所に載り、 片方が古くなる面が生まれる)。 ∴ 解釈の記録で足りる。

§5. Trace

出所は 3 件です。 承認は要らないという確認、 設計の記録が先に承認を前提していたこと、 そして承認の受け方を決めた別の記録との関係です。

  • 裁定: 自 repo への PR は「出す」に当たらない旨を 2026-09-10 に確認した。 本 repo は public のため、 確認の逐語・席や台帳の識別子・host 名は本 file に載せない (出所は日付で指す)。
  • 先行記述: 設計 doc の pipeline §5.4 / §5.5 が承認を前提とする読みを書いて land していた (2026-09-10 の実装時の裁定)。 本 ADR はその読みを覆すものであり、 同じ PR で設計 doc の当該記述を改訂する。
  • 関連: ADR-0005 (承認の受理面 = C7 の対話面) は不変で supersede しない——本 ADR が変えるのは「何が承認を要するか」だけであり、 「承認をどう受けるか」は変えない。
  • 拘束条件: A1 (3 クラス) と A4 (A4.2 不可逆だけ Ask-first / A4.3 merge・自 repo への dispatch は可逆)、 C7 (対話面)。 要件は SRS FR11 (land) / FR15 (承認の停止) / FR16 (承認の再開) / AC2 (自己ホスト 1 便) / AC5 (無承認の通過 0)。
