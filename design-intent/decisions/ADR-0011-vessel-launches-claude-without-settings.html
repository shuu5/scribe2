§1. Context

前の記録 (ADR-0009) は、 実装役を起こすとき「起動した人の設定は読まず、 相手の repo の設定だけ読む」と決めました。 ところが相手の repo の設定 file は、 審査される PR 自身の中身です。 そこに「この command は聞かずに許す」と書けば、 器が置いた門番 (承認の問いに一律で断る hook) には問いが届かず、 「この場面でこの command を動かせ」と書けば、 器が許した覚えのない command が動きます。 審査役 (lens) に至っては、 起動した人の設定も相手の repo の設定も全部読んでいました。

ADR-0009 §2.1 は runner を --setting-sources project と --allowedTools <allowlist> で起こすと定めた (MUST)。 目的は「user / local の settings を継承しない」ことであり、 project を読むこと自体は目的ではなかった。 実装は 2026-09-10 に land し、 ADR-0010 §2.4 が allowlist の出所を凍結した写しへ移した際も起動 flag は「ADR-0009 §2.1 のまま不変」とした。

同日の便 (宣言の凍結) の lens review が、 この project が穴であることを指摘した (L4)。 runner の cwd は便の worktree であり、 worktree は審査対象の PR 自身の checkoutである。 Claude Code は project source として <cwd>/.claude/settings.json を読むので、 契約の write-set に .claude/ を含めた便が permissions.allow に Bash(*) 相当を書いて land すれば、 それ以後の全便の runner は宣言の外の command を承認要求なしに撃てる。 器の PermissionRequest hook (vessel-hook §6.5) は「承認の問い」にだけ答える機構であり、 allow 規則で問いが出ない経路は素通りする——ADR-0009 §2.1 が「明示 allow 以外は fail-closed」と呼んだ形は、 allow の出所が器だけであるときにだけ成り立っていた。 同じ file の hooks は SessionStart / PreToolUse 等で任意の command を起動する口でもあり、 こちらは allowlist の外側で checkout が runner の process を動かす経路である。

lens の起動を実測すると、 --setting-sources を渡していなかった (Command を組む関数は runner だけがこの flag を足していた)。 既定はすべての source (user・project・local) を読むので、 lens は起動口座の settings と checkout の settings を両方継承し、 同じ diff が口座ごとに違う道具・違う hook の下で審査される形になっていた。 ADR-0009 §2.1 は runner だけを名指しており、 lens はその視野の外にあった。

直す前に「読まない起動形」が実在するかを実 binary で測った (§5)。 対象 dir の .claude/settings.json に SessionStart hook で marker file を作らせ、 --setting-sources project では hook が発火して marker が生成され、 --setting-sources "" (空) では init record から始まり hook が 1 度も発火しなかった。 空指定は既定 (全 source) へ化けない。 ∴ 決めるべきは「どの flag で、 どこで、 何に対して」であり、 ADR-0009 §2.1 が flag を逐語で MUST と書いている以上、 frozen な ADR を部分 supersede する新 ADR として記録する (本 repo の作法「既存 ADR は frozen・改訂は supersede」)。 3 クラス (消す / 出す / 使う) にも憲法条文の改訂 (A2) にも当たらないので user 裁定は仰がず、 2026-09-10 の裁定 (抜け道を構造で閉じる) の適用として planner が決めた。

§2. Decision

決めることは 4 つです。 器が起こす claude は起動した人の設定も相手の repo の設定も 1 つも読まない、 それを claude の起動命令を組む 1 か所に置いて実装役と審査役の両方に効かせる、 前の記録の flag の字面をこの形に改める、 そして「相手の repo の設定 file を器が覗いて危ない行を探す」形は採らない、 です。

本 ADR は C11 (C11.2 の極性は型・allow を返す経路を作らない) と C16 (逸脱は編集時に止め、 事後検証で代替しない) の適用を記録し、 起動形を 1 か所に置く形は C2 の趣旨 (1 つの決まりは 1 つの関数・1 つの列挙に置き、 散文で二重に持たない) に倣う (C2 の条文が名指すのは選択・除外・routing であり、 起動形はその適用対象ではない——根拠は §2.1 自身の MUST である)。 憲法本文は書き換えない。 読みは次のとおり: 器が claude に与える権限の出所は器だけである (ADR-0009 §2.1 の趣旨)。 settings file は権限 (allow) と process の起動 (hooks) の両方を運ぶ入力であり、 その出所が起動口座であれ checkout であれ、 器の外にある。 ∴ 器が起こす claude は user / project / local の settings を読まない (Claude Code が常に適用する managed settings は §2.4)。 runner については、 これは「明示 allow 以外は fail-closed」を、 allow の出所を器に限ることで成り立たせる条件である (lens の境界は §2.2)。

§2.1 起動形 — Command を組む 1 か所で user / project / local の settings を切る

claude を起こす命令を組み立てる関数は器に 1 つしかありません。 そこで「起動した人の設定と相手の repo の設定は読まない」と「repo に置かれた外部ツール (MCP) の設定も読まない」を毎回付けます。 実装役も審査役も、 この関数を通らずに claude を起こすことはできません。

器が claude を起こす Command を組む関数 (記録時点では headless::build・runner と lens が共有する唯一の構築点) は、 --setting-sources "" (空 = user / project / local のいずれも読まない) と --strict-mcp-config を毎回渡す (MUST)。 flag は呼出側 (runner / lens) でなくこの関数に置く (MUST): 呼出側に置くと lens のように「足し忘れた側」が既定 (全 source) へ落ちる。 器が claude を起こす新しい経路を足すときも、 この関数を通す (MUST・第 2 の構築点を作らない)。

同じ関数は --settings (settings の追加読込) と --restricted (組込み tool の除去 mode) を渡さない (MUST NOT)。 前者は settings を消さず足す flag であり (§4 案 (b))、 後者は Bash を外して --tools の名指しを要求し、 かつ settings / git / tool 設定 file への書込みを人の承認へ倒すので、 無人の席では構造的に止まる (§4 案 (a))。 権限を丸ごと外す --dangerously-* 系を渡さないこと (記録時点の歯が runner と lens の両方で測る) は不変。 runner について、 --allowedTools に凍結した写しの allowlist を Bash(<cmd>:*) で渡すこと (ADR-0009 §2.1・ADR-0010 §2.4) と --plugin-dir に器が写した plugin を載せること (設計 pipeline §5.2 / §6) は不変。 両者について --permission-mode を毎回明示すること (設計 pipeline §6) は不変。 lens の起動形 (記録時点: --allowedTools も --plugin-dir も渡さない) は本 ADR では変えない (§2.2)。

--strict-mcp-config は「--mcp-config で渡した server 以外を読まない」flag である。 記録時点の実測では checkout の .mcp.json は --setting-sources "" だけでも load されなかった (§5) が、 その挙動は project MCP server の承認状態という settings 側の状態に依っている。 本 ADR は settings 経路に依らず MCP の出所も器に限る belt として、 同じ関数で毎回渡す (MUST)。 器は --mcp-config を渡さない (記録時点・MCP server を器が与える決定は本 ADR に無い)。

§2.2 ADR-0009 §2.1 の起動 flag を部分 supersede する

前の記録が「相手の repo の設定だけ読む」と書いた flag の字面を、 「設定はどこからも読まない」に改めます。 それ以外——器が権限を与えること、 許す command の渡し方、 門番の hook が一律に断ること——は前の記録のままです。

ADR-0009 §2.1 の「runner は claude を --setting-sources project と --allowedTools <allowlist> を付けて起こす (MUST)」は、 本 ADR により「runner は claude を settings を 1 つも読まない起動形 (§2.1) と --allowedTools <allowlist> を付けて起こす」と読む (SHALL be read as)。 「user / local の settings を継承しない (MUST NOT inherit)」は「user / project / local の settings を継承しない」へ拡張される。 同節の残り——allowlist の形 Bash(<cmd>:*)・PermissionRequest hook の一律 deny (allow を返す経路を作らない・C11)・write-set の fence は gate の照合が担うこと——と、 ADR-0010 §2.4 が定めた「allowlist は凍結した写しから組み manifest を読まない」は不変 (MUST remain)。 ADR-0010 §2.4 (normative) の一文「--setting-sources project と PermissionRequest hook の一律 deny は ADR-0009 §2.1 のまま不変」も、 flag の部分を同じく部分 supersede する (SHALL be read as 「§2.1 の起動形と PermissionRequest hook の一律 deny は不変」)——hook の一律 deny は不変のまま。 ADR-0009 §5 の実測行にある --setting-sources project の字面は決定時点の記録として残し、 書き換えない。

本 ADR は lens を同じ起動形の適用対象に加える (ADR-0009 §2.1 は runner だけを名指していた)。 ただし lens の権限の境界は runner と同じではない: 記録時点の lens は --allowedTools を渡さず、 --plugin-dir も載せない (器の PermissionRequest hook は lens の session に無い)。 本 ADR の後、 lens の tool 権限の出所は --permission-mode の値と、 Claude Code が headless (-p) で答え手の無い承認要求をどう扱うかの既定だけになる (いずれも本 ADR は変えない・§2.4)。 本 ADR が lens について決めるのは「口座と checkout の settings が lens の権限と hook を広げる経路を断つ」ことまでであり、 lens に器の plugin を載せるか・組込み tool を絞るかは別の決定である (§2.4 候補)。

§2.3 intake が settings を字面で検査する fallback は採らない

「相手の repo の設定 file を器が読んで、 危ない行が在れば便を断る」という形も考えましたが、 採りません。 それは設定を読んでしまった後で追いかける検査で、 しかも起動した人の設定までは見えません。 読まない、 が答えです。

intake (あるいは gate) が checkout の .claude/settings.json を parse し、 permissions.allow に Bash(...) が在れば rc 1 で拒む形は、 本 ADR の決定に含めない (MUST NOT be read as a fallback)。 理由は 3 つ: (1) それは settings が効いた後の事後検証であり、 C16 は逸脱を編集時 (ここでは起動時) に止めることを求める。 (2) 字面の検査は allow の書き方 (Bash(*) / Bash / 別の tool 名 / hooks の command) を列挙し続ける形になり、 器が Claude Code の settings schema を追いかける第 2 の parser になる。 (3) user / local の settings は checkout に無く、 intake からは見えない——lens の穴はこの形では閉じない。 §2.1 の起動形は入力そのものを断つので、 列挙も parser も要らない。 「読まない起動形が将来の版で受理されなくなる」場合は、 runner / lens の rc が claude の rc を写す (設計 §6) ので便が Failed として見える形で落ちる。 「空指定を既定へ読み替える版」が出た場合は見えない——これは §3 の残る弱点として記録し、 §5 の実測を検出線の候補として残す。

§2.4 射程外

組織が配る管理者設定 (これは claude が常に読みます)、 相手の repo の CLAUDE.md や skill のような「読ませる文章」まで切ることや、 組込み tool の一覧を絞ること、 環境変数の継承のしかた、 門番 hook の極性を変えること、 宣言 file の形を変えることは、 ここでは決めません。

次は本 ADR の決定ではない (MUST NOT be read as such): managed settings (host / 組織が配布する settings・Claude Code が --setting-sources の値に依らず常に適用する第 4 の source・本 ADR の起動 flag では切れず、 §1 の脅威〔checkout と口座〕の外にある)、 checkout の CLAUDE.md・.claude/skills・.claude/agents 等のprompt 面の入力を切ること (それらが権限や process を運びうるかを本 ADR は測っていない・runner は checkout を読んで実装する役であり、 切る / 切らないの決定は別の論点)、 組込み tool の集合を --tools で絞ること (候補・別便)、 子 process の環境変数の継承 (ADR-0004 §2.4 と設計 §6 の裁定のまま)、 PermissionRequest hook の極性 (C11・一律 deny のまま)、 --permission-mode の値、 plugin の写し ({plugin_dir}) の扱いと plugin 自身の hooks (それは器の hooks である)、 vessel 宣言の schema (ADR-0010)、 器が MCP server を与えること (--mcp-config)、 憲法条文の改訂 (A2)。

§3. Consequences

良い点は、 審査される PR が自分の権限を広げたり、 器の知らない command を動かしたりできなくなること、 審査役の判定が起動した人の設定に左右されなくなること、 直す場所が 1 か所で済むことです。 弱い点は、 器自身の repo に置いた設定 file も実装役には効かなくなること (これは意図どおりです)、 組織が配る管理者設定までは切れないこと、 「空 = 読まない」という claude 側の意味に依っていて、 その意味が黙って変わると気付けないことです。

Positive: checkout の .claude/settings.json は runner にも lens にも効かないので、 PR が permissions.allow や hooks で自分の便や以後の便の権限・process を広げる経路が入力の段で消える (ADR-0010 §2.3 の「自己拡張の閉塞」が settings 面でも成り立つ)。 起動口座の settings も読まないので、 同じ diff が口座ごとに違う道具・違う hook の下で審査される経路が閉じる (lens の判定の再現性)。 runner について「明示 allow 以外は fail-closed」の allow の出所が器だけになり、 ADR-0009 §2.1 の形が条件付きでなく成り立つ (lens は allow も器の hook も持たないので、 この文は lens には及ばない・§2.2)。 flag が Command を組む 1 関数に在るので、 新しい起動経路を足しても足し忘れが起きない。 変更は引数 2 つで、 event log・契約・宣言・manifest のいずれにも触れない。

Negative: 器自身の repo (自己ホスト) の .claude/settings.json も runner / lens には効かない——runner の権限は宣言と器からしか来ないという設計の帰結であり、 開発 session の settings と runner の権限は別物になる (意図どおりだが、 開発者が settings で runner の挙動を変えられると期待すると外れる)。 checkout や口座の MCP server も使えない (器が与える決定は §2.4 の外)。 managed settings は切れない (§2.4)。 「空 = 読まない」は claude CLI の意味に依る: 受理されなくなれば rc≠0 で便が Failed になり見えるが、 空を既定へ読み替える版が出ると黙って穴が開き直る。 fake の歯は argv の字面しか測れないので、 実 binary で marker が生成されないことを測る §5 の手順が唯一の証明であり、 実装の便はそれを記録する。 版ごとに繰り返す検出線 (CI 外・課金なしで撃てる) は候補に留まる。

§4. Alternatives Considered

4 つの案を退けました。 claude の「制限 mode」を使う案、 器が作った設定 file を「追加で」読ませる案、 相手の repo の設定 file を器が覗いて危ない行を探す案、 そして今のまま門番の hook に頼る案です。

案 (a) --restricted を使う: 却下。 利点は user / project / local の settings を無視することが flag の定義に含まれ、 file tool を作業 dir に閉じる副次効果もあること。 しかし同じ flag が Bash を含む「command を実行する組込み tool」を --tools で名指ししない限り外し、 settings / git / tool 設定 file への書込みを「人か設定済みの承認 handler」の承認へ倒す。 無人の runner はそこで構造的に止まり、 何を名指すかという新しい列挙 (組込み tool の一覧) を器が抱える。 目的 (settings を読まない) に対して足す変更が大きく、 版ごとに意味が動く面も広い。 ∴ settings だけを切る flag を選ぶ (§2.1)。

案 (b) --settings <器が生成した最小 file> を渡す: 却下。 利点は「器が settings を与える」という形が ADR-0009 §2.1 の趣旨に近く見えること。 しかし --settings は settings を追加で読む flag であり、 project も user も消えない (checkout の allow と hooks はそのまま効く)。 器が与える必要のある settings も記録時点には無い (権限は --allowedTools・hook は --plugin-dir で既に与えている)。 ∴ 渡さない (§2.1 MUST NOT)。

案 (c) intake / gate が checkout の settings を字面で検査して拒む: 却下 (§2.3)。 事後検証・第 2 の parser・user / local が見えない、 の 3 点。 fallback としても置かない——置くと「読まない起動形」が外れたときに字面検査が黙って主役になり、 C16 の極性が事後側へ倒れる。

案 (d) 現状維持 (project を読み、 PermissionRequest hook の一律 deny に頼る): 却下。 利点は変更が無いこと。 しかし hook は「承認の問い」にだけ答える機構で、 allow 規則で問いが出ない経路と hooks による process 起動には届かない (§1)。 write-set の照合 (gate) は .claude/ を write-set に含めた便を止められず、 land した settings は以後の全便に効く。 lens に至っては全 source を継承していた。 ∴ 入力を断つ (§2.1)。

§5. Trace

出所は、 審査役 (lens) の指摘と、 claude を実際に起動して「設定を読んだかどうか」を測った結果です。 測り方は、 相手の repo の設定 file に「起動したら印を残せ」と書いておき、 印が残るかを見る、 というものです。 課金は発生させていません。

  • 指摘: 2026-09-10 の便 (vessel 宣言の凍結・ADR-0010 の実装) の lens review が、 runner の --setting-sources project が checkout の settings を読む穴であること (L4) を申し送り、 planner が bead に起票した。 本 ADR はその設計の記録である。
  • 実測 (起動形・2026-09-10・Claude Code 2.1.267): 対象 dir の .claude/settings.json に SessionStart hook として marker file を作る command を置き、 口座 dir は空の tmp・API key は無効値 (API は 401 で止まり課金しない) で claude -p を --output-format stream-json --verbose --permission-mode acceptEdits で起動した。 --setting-sources project: stream に hook_started / hook_response (SessionStart) が各 1 record・marker 生成。 --setting-sources "": 先頭が init record・hook_started 0 record・marker なし。 --setting-sources "" + --strict-mcp-config: 同じ。 いずれも api_retry 8 record の後に authentication_failed で終わる。 限界: この実測は --plugin-dir を渡していない＝器の plugin の hook が --setting-sources "" の下でも発火することは測っていない (実装の便が同じ手順を --plugin-dir 込みで撃ち、 stream に器の hook の hook_started が現れることを確かめる)。
  • 実測 (MCP・同日・同版): 対象 dir に .mcp.json (marker を作る command を server として登録) を置き --setting-sources "" で起動すると、 init record の mcp_servers は空・marker なし。 --strict-mcp-config を足しても同じ。 ∴ 記録時点では settings 経路だけで閉じているが、 §2.1 は belt として flag を毎回渡す。
  • 実測 (器の実装・記録時点): claude の Command を組む関数は 1 つで、 -p・--permission-mode・(streaming のとき) --output-format stream-json --verbose・--plugin-dir・cwd・口座 env を組む。 runner はその上に --setting-sources project と --allowedTools を足し、 lens は何も足さない。 既存の歯は runner の argv に --setting-sources→project の対が在ることを、 runner と lens の両方の argv に --dangerously 系が無いことを測る。 fake claude は argv を 1 引数 1 行で写すので空文字は空行になる——実装の便の歯は flag と値の対で測る (flag の存在だけを見る歯は値が project でも緑になる)。
  • 先行記述: ADR-0009 §2.1 (flag の逐語 MUST)・§5 (実測行)・ADR-0010 §2.4 (「--setting-sources project と hook の一律 deny は不変」)・設計 doc pipeline §6 (runner 行)・vocabulary (runner / lens / allowlist / headless)。 本 ADR は同じ PR で設計 doc と vocabulary を改訂し、 ADR-0009 / ADR-0010 の本文は frozen のまま (被参照 link は folio の生成)。
  • 拘束条件: C11 (C11.2・極性は型・allow を返す経路を作らない)・C16 (逸脱は編集時に止める・事後検証で代替しない)・C2 は趣旨の参照 (§2)。 ADR-0009 §2.1 / §2.2・ADR-0010 §2.3 / §2.4。 要件は SRS FR5 (runner) / FR9 (lens)。 本 repo は public のため席・台帳の識別子・host 名・口座名は本 file に載せない (出所は日付で指す)。
