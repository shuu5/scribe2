§1. Context

便を 3 本同時に流したとき、 いちばん後に着地した便が 7 時間かかりました。 便そのものの大きさで説明できるのは審査 (gate) 1 周の 82 分だけで、 残りは「他の便が先に着地するたびに審査をやり直す」「着地の後に同じ木へ同じ審査をもう一度撃つ」「変異検査を 1 本ずつしか走らせない」という器の作りの費用でした。 user の裁定の要旨は、 並列を上げてよいが memory がいっぱいになって process が殺される事故を防ぐ仕組みが要ること、 複数の project でそれぞれ便を流すこともあること、 かといって資源を余らせるのもよくないこと、 の 3 点でした (逐語は台帳)。 この記録はその形を決めます。

記録時点 (2026-09-12) の現物: gate は verify 行を sh -c で 1 本ずつ撃ち (pipe/gate.rs の run_line_captured・gate と land の main 実測で同じ 1 本)、 変異検査は xtask mutants-diff が cargo-mutants を --in-diff / -p / -o で呼ぶ (--jobs を渡さない＝並列度 1)。 変異 1 本の費用 = 増分 build (実測 2 s) + package の test suite 1 周 (壁時計 34 s・30 s の実待ちを持つ歯 10 本が床・台帳 s2-07l.151)。 land は squash の後、 tmp worktree を切って gate と同じ verify を全行撃つ (land.rs の verify_main・設計 pipeline.md §5.4 手順 3)。 並列 3 便の実測 (台帳 s2-07l.143): 先着 21 分 / 2 本目 1 時間 40 分 (追随 1 回) / 後着 7 時間 13 分 (追随 3 回・stale 2 回・gate 82 分 × 4 周 + main 実測 78 分)。 器は子 process の memory / CPU を制限せず、 host の空き memory も測らない。 本 host は cgroup v2 で user scope に memory / cpu / pids の controller が委譲され、 systemd-run --user --scope -p MemoryMax=… で上限が効く (実測 2026-09-12)。 state dir は project ごと (<NAME>-v2-state / <NAME>-v2-state-<project>) で、 同じ host の state dir は 1 つの親の下に置かれている。

憲法の向き: C1 / C5 は閾値を rules 行に裁定 id 付きで持つ。 C2.2 は env を読まず、 置き場を NAME 定数から導く。 C6 は起動口を 1 つに限り、 Budget を Precheck の測定からしか作れない形を求める (資源の枠も同じ形が望ましい)。 C10 は宣言値・測定値・実効値を型で分け、 宣言値を実効に上げるのは測定を通してだけとする。 C11.2 は境界に極性を持たせ、 ADR-0014 §2.1 は guard の定義を持つ。 C12.4 は変異の生存を検出線とし deny gate にしない (昇格は裁定)。 C12.6 は main を常に緑に保つ。 C3 は host・口座・席・lease・退役の状態を 1 つの DB に置く (受付の札がこの対象かは §5 で読む)。 C3.4 は完了条件を 1 つの完了 enum の値で表し、 待つ実装を 1 つに限る。 N1 は器が管理する物を不可逆に消さない。 user の裁定 (2026-09-12・会話面・逐語は台帳 s2-07l.153 の notes): 3 点の推奨でよい・1 (並列度) は memory 枯渇の kill を予防・対策する機能が前提・複数 project / 複数 pipeline の同時走行に対応・余らせず使い切る・実装コストが高すぎるなら報告。 続く裁定 (同日): 設計の選択を planner に委ねた (要旨)。

§2. Decision

§2.1 変異検査の並列度は rules 行の上限 (宣言値) を実測で下げた実効値で渡し、 宣言値をそのまま渡さない

「何本まで同時に走らせてよいか」は規則の値として持ちますが、 それをそのまま使いません。 実際に走らせる本数は、 その瞬間の host の空き memory を測って決めた本数との小さい方です。 本数は宣言 file の検証行に穴として置き、 器が実効値を埋めて撃ちます。 環境変数では渡しません。

器 SHALL 変異検査の並列度の上限を rules 行 (gate.mutants_jobs・kind は Int・値は裁定 id 付き・C5・本 ADR は値を決めない) で持ち、 実効値 SHALL min(上限, §2.3 の受付が配った枠) とする (C10: 上限は宣言値・空き memory は測定値・渡す本数は実効値)。 宣言 file の共通 verify が置ける穴 SHALL {base} と {jobs} の閉じた集合とし (ADR-0010 の宣言の内側)、 器 SHALL {jobs} を実効値で置換して撃つ。 {jobs} を持たない行 SHALL 受付を通らない (枠を取らない)。 器 SHALL NOT 並列度を env で子 process に渡さない (C2.2 の精神・裏口を作らない)。 xtask の mutants-diff は --jobs N を受け cargo-mutants にそのまま渡す (値を持たない)。 受付 (§2.3) が実装されるまで、 器 SHALL 実効値を 1 とする (上限を実効に上げるのは受付の測定を通してだけ)。

§2.2 器が起こす子 process は cgroup の scope で封じ、 溢れたときに死ぬのはその scope だけにする。 封じられない host は並列度 1 で進む

審査の検証行、 実装役、 審査役の process は、 それぞれ memory の上限付きの箱 (cgroup の scope) の中で走らせます。 上限は 2 種で、 変異検査の箱は「本数 × 1 本ぶんの memory」、 それ以外の箱 (他の検証行・実装役・審査役) は「host 全体から席のぶんを引いた残り」です。 箱の中で memory が溢れたら、 殺されるのはその箱の中の process だけで、 対話中の席や他の便、 他の project は生き残ります。 箱を作れない host では、 箱なし・1 本ずつで走らせ、 そのことを記録に残します。 便を止めることはしません (実装役の箱が溢れた周だけは、 その便を理由付きで終端し、 新しい便で起こし直します。 着地後の実測の箱が溢れた周は、 変更は main に載ったまま、 便を「測れなかった」で終端します)。

器 SHALL verify 行 (gate と main 実測の共通の 1 本)・runner・lens の子 process を、 host の systemd-run --user --scope で作る transient scope の内側で起動し (ADR-0017 §2.2 の「host の binary を子 process で呼ぶ」と同じ形・依存の追加ではない)、 scope に memory の上限 (MemoryMax・MemoryHigh は付けない＝係数を持たない) と CPU の重み (rules 行 gate.cpu_weight・席は既定の重み) を付ける。 上限 SHALL 2 種とする: {jobs} を持つ行は 実効 jobs × rules 行 gate.job_memory_mb、 それ以外 ({jobs} を持たない verify 行・runner・lens) は MemTotal − host.reserve_memory_mb (host の予約分だけを守る箱・行ごとの値を持たない)。 CPU に上限 SHALL NOT 付けない (memory だけが硬い資源)。 scope の内側で kernel が process を殺した周 (scope の memory.events の oom_kill が 1 以上・包みは systemd の OOM 停止の対象から外す〔OOMPolicy=continue・既定の stop では包みが終端行を出す前に止められる・2026-09-12 実測〕。 それでも包みが死んだ周は signal 死〔record の 255〕を代理とする)、 器 SHALL その verify 行を rc に依らず「測れなかった」に倒す (gate は INCONCLUSIVE・main 実測は main-unmeasured・赤に化けさせない・gate の INCONCLUSIVE と land の main-unmeasured の既存極性〔FR9 / AC3・測り直しは FR14〕)。 runner の scope が殺された周は verify 行の極性の外で、 便 SHALL 閉じた理由 (enum の variant 1 つ・現物の runner-rc と同じ終端の段) で終端し、 起こし直しは新しい便で行う (設計 §4.2)。 lens の scope が殺された周は FR9 の既存極性のまま INCONCLUSIVE とする (stdout が parse できない周と同じ・道具を揃えて同じ便を撃ち直せる〔FR14〕)。 器 SHALL memory.peak と memory.events を scope の内側で読ませて record に jobs peak_mb を残す (包みの sh -c が行の終了後に自分の /proc/self/cgroup の path〔scope の内側ではそれが scope 自身〕から読んで stdout の終端に固定形で出し、 器は pure な parser で剥がす。 transient scope は最後の process の終了で消えるので外からは読めない〔2026-09-12 実測〕・env を読まない・C2.2。 memory.peak の無い kernel は peak_mb を欠く＝0 と書かない)。 gate.job_memory_mb の宣言値を上限にそのまま使うのは既存の rules 行 (gate.token_cap 等) と同じ慣行で、 その宣言値 SHALL peak の測定が溜まった後に裁定で置き換える (C10: 宣言値を実効に上げるのは測定を通してだけ)。 systemd-run が無い・scope を作れない周、 器 SHALL 封じ込めなし・並列度 1 で進み、 record に confined=false reason=<閉じた enum の名> を記す (止めない・理由は自由文にしない・C3.3)。 封じ込め (Confinement: Confined / Unconfined(reason)) は行為を止めうる判定を持たない (縮退するだけ) ので ADR-0014 §2.1 の guard ではなく、 極性一覧に SHALL NOT 載せない (可視化は record の confined=)。 §2.3 の受付と同じ扱いである。

§2.3 受付は host 単位で、 project をまたいで空き memory を受付札で分け合う。 枠が無ければ待ち、 待ち切れなければ並列度 1 で進む

「いま何本走らせてよいか」は host 単位の受付が決めます。 受付は project ごとの置き場の 1 つ上 (同じ host の置き場が集まる親) に在るので、 別の project の便とも枠を分け合えます。 受付は毎回、 host の空き memory を測り、 席のために残す分を引き、 1 本ぶんの memory で割って「配れる本数」を出します。 配った枠は「受付札」という小さな file で表し、 すでに配った札の合計も数えます (配った直後はまだ memory を使っていないので、 空きだけ見ると 2 つの便が同じ枠を取ってしまうためです)。 枠が無ければ待ち、 待つ上限を超えたら 1 本で走らせて記録に残します。 0 本で走らせることも、 便を断ることもしません。

器 SHALL 受付の置き場を <state_dir の親>/<NAME>-host/slots/ とし (NAME 定数から導く・env を読まない・C2.2。 同じ host の state dir が 1 つの親の下に在る運用が前提で、 親を分けた project は別の受付になる＝§2.7)、 枠 SHALL 受付札 (file 1 つ・<pid>-<run>.slot・内容は schema / pid / run / jobs / ts) で表す (語彙の lease は fleet の割当であり本 ADR の札とは別の実体・§5)。 生きている札 SHALL /proc/<pid> の実在 ∧ その process の起動時刻が札の ts 以前 (pid の再利用を弁別) で判定し、 死んだ札と読めない札 (schema / 数値の壊れ) は次の受付が回収して record に slot=reclaimed:<n> を残す (黙って落とさない・止めない・NFR4。 札は器が管理する「物」ではなく受付の一時的な印で、 N1 の対象外・§5)。 受付 SHALL fleet の lock と同じ実装 (lock file 方式・acquire 1 本・受付の置き場に lock file を 1 つ持つ〔event log の lock file は state dir ごとで共有できない〕・retry と stale は rules 行 fleet.lock_retry_ms / fleet.lock_stale_ms・第 2 の lock 実装を持たない・C6.3) の内側で毎回測る (C10): avail = MemAvailable − host.reserve_memory_mb、 by_avail = floor(avail / gate.job_memory_mb)、 by_token = floor((MemTotal − host.reserve_memory_mb) / gate.job_memory_mb) − Σ 生きている札の jobs、 free = min(by_avail, by_token)。 配る枠 SHALL min(gate.mutants_jobs, free) とし、 free = 0 の周は lock を離して待つ。 待ち SHALL 完了 enum に variant 1 つ (Completion::SlotFree・受付の置き場と要る枠を運ぶ) を足して唯一の wait 実装を通し (C3.4・第 2 の poll loop を持たない・周期は唯一の wait 実装が持つ定数のまま〔rules 行の意味を二重にしない〕)、 rules 行 gate.slot_wait_s を超えたら 1 で進んで record に slot=degraded を記す。 器 SHALL NOT 0 で走らせない・便を断らない。 測れない周 (/proc/meminfo が読めない・lock が取れない) SHALL 1 で進み slot=unmeasured を記す (縮退・従来の費用)。 verify 行の終了で札 SHALL 消す。 受付は行為を止めうる判定を持たないので guard ではなく、 極性一覧には載せない (§2.2 の封じ込めと同じ)。 rules 行 (gate.mutants_jobs / gate.job_memory_mb / host.reserve_memory_mb / gate.slot_wait_s / gate.cpu_weight) は契約が裁定 id 付きで manifest に足すまで本 ADR の予定行であり、 C14.2 の相互参照は行が在って初めて成立する (ADR-0018 §4 と同じ扱い)。 host.reserve_memory_mb は v2 では host に依らない 1 値で、 host 差は行の改訂で吸収する (C10.2 の host 固有値も manifest に置く形と同じ)。

§2.4 main 実測は木の hash が gate の木と一致する周に検出線を撃ち直さない。 deny する行は撃ち直す

審査を通った木と、 着地して main になった木は同じ木です (器はそれを毎回確かめています)。 同じ木に同じ変異検査をもう一度撃っても新しいことは分からないので、 着地後の実測では「検出線」(落ちても止めない行・変異検査) を撃ちません。 test / lint / 依存監査のように「落ちたら止める」行は撃ち直します。 審査は便の作業 dir で走り、 着地後の実測は追跡された file だけの木で走るので、 環境が違うからです。 木が違っていたら全部撃ちます。

宣言 file SHALL detection-verify (検出線の行の列・穴は {base} {jobs}) を任意の key として持てる (無ければ③は空・既存の 3 key は必須のまま・未知 key は従来どおり拒む＝ADR-0010 §2.1 の部分 supersede・§2.6)。 gate SHALL ① write-set の照合 → ② common-verify → ③ detection-verify → ④ 契約の verify の順で撃つ (ADR-0009 §2.4 の順序に③を挿す・§2.6)。 ③の行 SHALL ②と同じく intake が凍結した写しから取る (HEAD の宣言を読み直さない・ADR-0010 §2.4)。 検出線の rc≠0 SHALL 従来どおり赤に数える (「測れていない」の印・測れなかったを通ったに化けさせない)。 検出線の rules 行 (R-C12-1) が deny に昇格した周 (C12.4 の裁定)、 その行 SHALL 同じ便で detection-verify から common-verify へ移す (deny する行は撃ち直す側に居る)。 verify.jsonl の record SHALL schema 1 のまま任意 field (kind / jobs / peak_mb / confined / reason / slot / skipped / tree) を足せる (古い読み手は無視する・ADR-0017 §2.1 の event と同じ足し方・§2.6)。 gate SHALL verdict.json に tree (gate を撃った HEAD の ^{tree} の sha) を残す (schema 1 のまま field を足す)。 land の main 実測 SHALL その record を verify-main.jsonl (gate と同じ record 形・別 file・gate の周の n と重ねない) に書き、 git rev-parse <new>^{tree} が verdict の tree と一致する周に③を撃たず skipped=detection tree=<sha> を記し、 ①②④ は従来どおり撃つ。 一致しない周と tree の無い verdict の周 SHALL 全部撃つ。

§2.5 着地は gate 済みの便を先に通す (機構は後続の設計)

審査を通った便が着地を待っている間に別の便が先に着地すると、 待っていた便は出発点がずれて審査をやり直します。 これを防ぐため、 審査済みの便が在る間は他の便の着地を待たせます。 待たせる上限や詰まりの解き方は、 衝突の起こし直し (ADR-0019) が実装された後に別の設計で決めます。

器 SHALL Gated ∧ verdict PASS の run が在る間、 他の run の land を待たせる (先に gate を通った便を先に着地させる)。 順序の判定・待ちの上限 (rules 行・裁定 id 付き)・詰まりの解き方・追随 (ADR-0019 §2.2) との関係は、 台帳 s2-07l.147 の設計が s2-07l.146 の land 後に決める。 本 ADR は原則だけを持つ。

§2.6 ADR-0009 §2.3 / §2.4 と ADR-0010 §2.1 / §2.3 / §2.4 / §2.5 を部分 supersede する

先の記録は「審査は 3 段の順で撃つ」「着地後の実測も同じ順で全部撃つ」「宣言 file の鍵は 3 つで穴は 1 つ」「審査の記録の形は変えない」「変異検査の置き場は共通 verify」と決めていました。 この記録はそれぞれを、 「検出線の段を 1 つ挿した 4 段」「木が同じなら検出線の段は撃たない」「鍵は 3 つ必須 + 1 つ任意・穴は 2 つ」「記録は版を上げずに項目を足せる」「変異検査は検出線の列に置く」と読み替えます。 それ以外の文は変えません。

ADR-0009 §2.4 の「gate は ①write-set の照合 → ②共通 verify 各行 → ③契約 verify 各行 の順で撃ち、 verify.jsonl の record 形は変えない」は、 本 ADR により「① → ② → ③ detection-verify 各行 → ④ 契約 verify 各行 の順で撃ち、 record は schema 1 のまま任意 field を足せる」と読む (SHALL be read as)。 同 §2.4 の「land の main 実測も同じ順序で撃つ」は「同じ順序で撃つが、 木の hash が gate の木と一致する周は③を撃たない (§2.4)」と読む。 ADR-0010 §2.1 の「key は 3 つですべて必須 … {base} は便の base に置換される唯一の穴」は「必須の key は 3 つ・detection-verify は任意の 4 つ目・共通 verify と検出線の穴は {base} と {jobs}」と読み、 同 §2.4 の「順序を変えず (①→②→③) … record 形 … は不変」は上と同じ読み替えに従う。 同 §2.3 (2) の「穴は {base} だけである」は「穴は {base} と {jobs}」と読み (SHALL be read as)、 同 (2) の検査 (先頭語が宣言の allowlist に在る・制御文字を含まない・repo 外の path を持たない) SHALL detection-verify の各行にも同じ基準で掛ける (共通 verify と同じ 1 関数・宣言に allowlist を迂回する行を置けない)。 ADR-0009 §2.3 の「Rust repo の共通 verify (§2.4) に cargo xtask mutants-diff --base {base} を置く」と ADR-0010 §2.5 の同旨の括弧は「宣言 file の detection-verify に置く (共通 verify から外す・§2.4)」と読む (SHALL be read as)。 ADR-0009 / ADR-0010 の他の文 (allowlist の上限・intake の拒否〔穴の集合を除く〕・宣言は HEAD から読む・非 Rust 実行物の deny) は変えない。

§2.7 射程外

この記録が決めるのは「並列度の実効値」「封じ込め」「host 単位の受付」「main 実測の検出線の省略」「着地の順序の原則」だけです。 host をまたぐ受付、 置き場の親を分けた project 同士の統合、 CPU の上限、 便の同時本数の上限、 30 秒の実待ちの歯の改修は別に決めます。

次は本 ADR の決定ではない (MUST NOT be read as such): 複数 host にまたがる受付 (受付は host 単位)、 state dir の親を分けた project 同士の受付の統合 (運用で親を揃える・doctor の検査項目は移行後の epic)、 CPU の上限と swap の制御、 cargo の -j (cargo-mutants の内側)、 便の同時本数の上限 (admission control・口座の自律制御 s2-07l.142 と併せて別途)、 30 秒の実待ちを持つ歯の改修 (s2-07l.151)、 検出線の deny 化そのもの (C12.4 の裁定・本 ADR は昇格時の置き場だけを決める)、 検出行の値 (total / caught / missed …) の記録 (s2-07l.152・§2.2 の行に相乗りする)、 --pr-cmd の子 process の封じ込め (host の gh を呼ぶだけ)。

§3. SRS との関係 (正本は SRS)

この記録が仕える要件は、 審査 (FR8 / FR9)、 着地 (FR10 / FR11)、 追随 (FR34)、 審査役の予算 (NFR1)、 読めない記録の扱い (NFR4) です。 「host の資源を枯渇させない」という要件は要件書にまだ無いので、 次の版 (v0.7) の材料として user の手番に出します。

本 ADR が仕える要件は SRS v0.6 が正本である: FR8 / FR9 (gate の機械検証と lens・§2.1 / §2.4)・FR10 / FR11 (land の前提と squash・§2.4 / §2.5)・FR34 (追随・§2.5)・NFR1 (lens の予算・§2.2 の scope は予算の器ではなく memory の箱)・NFR4 (読めない store は rc 2・受付の置き場は真実を持たない印の置き場で NFR4 の store ではなく、 読めない札は回収して record に残し rc を変えず縮退する＝§2.3)。 FR11 の「main で verify を再実走し」の verify は deny する行 (①②④) と読み、 検出線の省略 (§2.4) はその内側である (v0.7 で FR11 の文言に「deny する行を」を添える材料として user の手番に出す)。 FR8 の「1 本でも rc が 0 でなければ FAIL」は走った行の赤を指し、 §2.2 の「測れなかった」(scope の OOM) は現物の gate が既に持つ「測れなかったは赤より先」の側 (AC3 の偽 PASS 0 件は保たれ、 測り直しは FR14) と読む。 「器は host の memory を枯渇させない (封じ込めと受付)」の NFR は SRS v0.6 に無く、 planner が v0.7 の材料 (planner state dir) として user の /folio-architect 手番に出す。 要件の文面はここには写さない。 rules 行の値・受付札の file 形・scope の引数は §2 と現物が持ち SRS は持たない。

§4. Consequences

良い面は、 変異検査が上限 4 で最大およそ 4 倍速くなること、 memory が溢れても席や他の便が死なないこと、 別の project の便とも枠を分け合えること、 着地後の実測から変異検査 1 周ぶんが消えること、 そして 1 本ぶんの memory の値を実測で更新していけることです。 悪い面は、 host の systemd に依ること (無ければ 1 本ずつ)、 受付の置き場という host 単位の物が 1 つ増えること、 規則の行が 5 つ、 宣言 file の鍵が 1 つ、 記録の項目が増えることです。 止める仕組みの一覧は増えません。

Positive: 変異検査の壁時計が実効 jobs ぶん縮む (上限 4 で最大およそ 4 倍・実測は契約で取る)。 memory の溢れが scope の内側に閉じ、 席・他の便・他の project の process は kernel の OOM で選ばれにくい ({jobs} 行の合計は受付が守り、 それ以外の箱の合計は便の同時本数〔§2.7〕が守る)。 受付が project をまたぐので、 複数 project の便が同じ host で同時に走っても合計が守られる。 main 実測から検出線 1 周 (実測 75 分) が消える。 peak_mb の測定が溜まり、 gate.job_memory_mb を宣言値から測定値へ置き換える材料になる (C10)。 縮退 (並列度 1) は従来の費用と同じで、 実装役の箱の溢れ (§2.2・理由付きの終端) と着地後の実測の「測れなかった」(main-unmeasured・変更は main に載ったまま) 以外のどの失敗も便を止めない。

Negative (受け入れるコスト): systemd-run と cgroup v2 の user 委譲に依る (無い host は封じ込めなし・並列度 1・記録に残る)。 host 単位の置き場 (<NAME>-host/slots/) が state dir の外に 1 つ増え、 state dir の親を揃える運用が前提になる。 rules 行 5 つ・RuleKind 5 variant・宣言 file の鍵 1 つ (detection-verify) と穴 1 つ ({jobs})・verify.jsonl / verify-main.jsonl の任意 field 8 種 (kind jobs peak_mb confined reason slot skipped tree)・verdict.json の field 1 つ (tree)・完了 enum の variant 1 つ (SlotFree) が増える。 極性一覧は増えない (封じ込めも受付も guard ではない)。 main 実測の record を別 file に書き始める。 受付の測定は `MemAvailable` に依るので、 host の他の process が急に memory を使った周は scope の上限が守る (受付は追わない)。 `gate.job_memory_mb` の初期値は宣言値で、 実測が溜まるまで並列度が保守的に出る。 検出線を main 実測で省くので、 gate と main 実測の「同じ順序・同じ関数」は条件付きになる (ADR-0009 §2.4 の部分 supersede・§2.6)。 host の予約分を守る箱は「行が予約分まで食う」周にだけ効き、 その周は測れなかったに倒れる (§2.2)。

§5. Alternatives Considered

6 つの案を退けました。 並列度を焼くだけの案は合計を見ません。 検査の範囲を絞る案は検出の質を落とします。 着地後の実測を全部省く案は環境の違いを見落とします。 受付を project ごとの DB に置く案は host をまたげません。 箱の path を環境変数から組む案は憲法に反します。 memory が足りなければ便を断る案は、 資源の少ない host で便が 1 本も流れません。

(A) xtask に --jobs 4 を焼く。 却下: 合計を見ないので複数 gate / 複数 project で溢れる。 user 裁定で不採用 (防御が前提)。

(B) 変異検査の test suite を絞る (unit だけ・package を狭める)。 却下: 変異の kill 判定が弱くなり検出線の質が落ちる。 30 秒の実待ちの解消 (s2-07l.151) で 1 変異の費用は同じ以上に下がる。

(C) main 実測を全部省く (lossless の実測が在るので)。 却下: gate は run の worktree (untracked を含む) で撃ち、 main 実測は tracked だけの木で撃つ。 untracked に依って通った便を main 実測が捕まえる価値は残る。 省くのは検出線だけ (§2.4)。

(D) 受付を fleet DB (C3) に置く。 却下: DB は state dir ごと＝project ごとで project 横断にならない。 受付札は C3 が列挙する「host・口座・席・lease・退役の状態」の lease (語彙: 席が口座や host を占有する期限付きの割当) ではなく、 host 内・pid 寿命の予約の印である。 札は判定に効く (Σ 札の jobs が by_token の入力) が真実の置き場ではない: 札が失われても結果は「過剰に配る」側に倒れ、 その最悪は §2.2 の封じ込めが scope の内側に閉じる (席は死なない)。 つまり札は安全側の予約であって、 C3 が per-host directory に置くなと言う「真実」ではない、 と読む。 札の削除は N1 (器が管理する物を不可逆に消さない) の対象外である＝札は管理する物ではない。 この読みは本 ADR の C3 の解釈であり (ADR を書く条件 1)、 憲法の条文は動かさない。 user の裁定 (2026-09-12・逐語は台帳 s2-07l.153) は設計の選択を planner に委ねたもので、 この読みへの異議は supersede ADR で受ける。

(E) cgroup の path を XDG_RUNTIME_DIR から組む・受付の置き場を HOME / TMPDIR から組む。 却下: env を読む (C2.2)。 cgroup は /proc/self/cgroup から、 置き場は state dir の親から導く。

(F) memory が足りない周は便を断る (fail-closed)。 却下: systemd の無い host や memory の少ない host で便が 1 本も流れない。 縮退 (並列度 1) は従来の費用と同じで安全側。 「止めない」は record (confined= / slot=) の上で選ぶ。
