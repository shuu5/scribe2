設計判断記録 (ADR) scribe2 — 逼迫の門の窓

逼迫の門のモデル別窓は役割の model の窓だけを数える — 5 時間窓と 7 日窓は今のまま全部、 モデル別 7 日窓は群の席の役割の model の行だけで逼迫を判じる (ADR-0055 と ADR-0069 の窓の読みを部分 supersede)

口座が上限に近いかは 3 つの窓 (5 時間・7 日・model ごとの 7 日) で判じる。 今の門は model ごとの窓を「どの model でも」数えるので、 席を Opus で走らせても Fable の窓が埋まった口座は上限扱いのまま、 移り先にも使えず、 今の口座なら移動を起こす。 本 ADR は model ごとの窓を席の役割の model の窓だけに絞り、 移り先の並べ方 (ADR-0069 の残量の鍵) と同じ読みに揃える。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「席」は人と AI が話す 1 つの session、 「群」は同じ口座の候補を共に使う project の集まり、 「逼迫」は口座が上限に近いこと、 「役割の model」は席の役割ごとの既定の model です。 口座が上限に近いかは 3 つの窓 (5 時間・7 日・model ごとの 7 日) で判じます。 今の門は model ごとの窓を「どの model でも」数えるので、 持ち主が席の既定を Opus に替えても、 Fable の窓が埋まった口座は上限扱いのまま移り先にならず、 今の口座なら移動を起こします。 同じ日の実測では、 口座 6 つのうち 4 つが Fable の窓は 95 以上なのに 7 日窓には余裕がありました。 この記録は、 model ごとの窓を席の役割の model の窓だけに絞り、 移り先の並べ方 (残量の鍵) と同じ読みに揃えると決めます。 5 時間窓と 7 日窓は今のまま全部数えます。 持ち主は 2026-09-26 にこの形を裁定しました。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを、 経緯 (門は 3 窓の全部を閾値で断る)・事象 (席の既定を Opus に替えても Fable の窓で群が止まる)・機序 (判定の関数が model の名を見ずに数える)・これまでの決まり・この判断の範囲の 5 つから説明します。 移り先の並べ方 (ADR-0069 の残量の鍵) は既に役割の model の窓だけを読んでいて、 門と並べ方とで読みが食い違っていました。

CTX1

経緯 — 門は 3 窓の全部を閾値で断る (ADR-0055・ADR-0069)

ADR-0055 は群の逼迫口座が上限に近いことを 5 時間窓・7 日窓・モデル別窓のいずれかが閾値の rules 行の値以上である状態と決めた。 ADR-0069 は移り先の門移り先に使える条件も 3 窓の全部を閾値で断り、 実データのモデル別の行は Fable だけなので Fable が 95 以上の口座は候補に入らないと書いた。 同じ ADR-0069 の残量の鍵候補を並べる物差しは、 モデル別窓model ごとの 7 日枠を役割の model席の既定の model (rules 行 seat.model.<役割>) の行だけで読む。 門と鍵とで、 モデル別窓の読みが食い違っている。

CTX2

事象 — 席の役割の既定を Opus に替えても、 Fable の窓で群が止まる

2026-09-26、 持ち主は orchestrator の既定の対を opus / xhigh に替えると裁定した (設計 seat-roles.md §28)。 同じ日の実測で、 口座 6 つのうち 5 つの Fable の窓が 95 以上で、 そのうち 4 つは 7 日窓が 50 から 92 だった (口座名は台帳)。 usage API使用率を返す外部の口 は Fable の窓しか返さない。 今の門のままでは、 席が Opus で走る群もこの 4 口座を移り先にできず、 今の口座なら逼迫と読んで移動や断りを起こす。

CTX3

機序 — 門の 1 関数は model の名を見ずにモデル別窓の行を数える

逼迫の判定は 1 つの pure な関数 (口座の最新の実測の行を窓の閾値と比べ、 どれかが閾値以上なら越えた窓の最大の 1 つ) で、 群の移動の判定・移り先の門・先の群の逼迫・席の turn の 1 行・管理 tick の口座の門上限の席を促さない条件の 5 か所が呼ぶ。 モデル別窓の行は model の名を持つのに、 関数は名を読まない。 役割の model の集合を読む関数 (群の置き場の席の登録 row の役割ごとの rules 行の表示名) は既に在り、 鍵だけが使っている。

CTX4

憲法と既存の決定の向き (本 ADR の解釈)

C2 (同じ事実の読みは 1 本) から、 モデル別窓をどの model で読むかは門と鍵で 1 つにし、 役割の model の集合を読む既存の関数を門でも使う。 C17 (決定はしご) から、 新しい rules 行も新しい計測も足さず、 既に在る集合を判定の関数へ渡すだけにする。 C1 (既定を出さない) から、 役割の行が無い周は集合を空に読み替えず、 今の typed な止まり方 (判定は読めない・予約は行なし) に倒す。 ADR-0058 の口座の門は「閾値を越えた口座」とだけ書き窓を名指さないので、 同じ関数を通して本 ADR に従う。

CTX5

射程 — 動かすのはモデル別窓の読みと、 呼び手が渡す集合だけ

動かすのは (1) 判定の関数がモデル別 7 日窓を役割の model の表示名の集合に在る行だけで数えること (集合が空ならモデル別窓を数えない)、 (2) 役割 1 つの model を読む関数を 1 つに切り出すこと、 (3) 5 つの呼び手が判じる群 (tick は自席の役割) の集合を渡すこと。 動かさないのは、 5 時間窓と 7 日窓の読み・閾値の rules 行 3 本と値・残量の鍵・予約の規則 (ADR-0069・ADR-0074)・便用の口座選定 (ADR-0042)・usage の計測と実測の行の形・event の種類。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 4 本のものさしです。 席を走らせる model の上限だけが群を止めること (使わない model の窓は移動を起こさない)。 門と並べ方のモデル別窓の読みを 1 つにすること。 使う model の上限は今のまま守ること (役割の model の窓が閾値以上の口座は断る)。 足すものを最小にすること (新しい rules 行・計測・状態を足さない)。

03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 4 つ並べます。 モデル別窓を役割の model の窓だけ数える案 (選んだ案)、 今のままどの model の窓も数える案、 モデル別窓を門から外す案、 席の登録 row に残る起動の model で数える案です。 選ばなかった 3 つは、 役割の既定を替えた意味が群に届かない・使う model の上限を守れない・読みが 2 つになる、 という理由で退けました。

判定の関数に、 群の席の役割の model の名の集合を渡す案です。 model ごとの 7 日窓は、 名が集合に在る行だけを閾値と比べます。 5 時間窓と 7 日窓は今のまま全部比べます。 席が Opus で走る群は Fable の窓で止まらず、 7 日窓に余裕のある口座へ移れます。 門と並べ方が同じ集合を読み、 役割の model が Fable の群は今のまま Fable の窓で断られます。 足すのは関数の引数 1 つと、 役割 1 つの model を読む関数 1 つです。 代わりに、 usage API が Opus の窓を返さない間は Opus の群の門が 5 時間窓と 7 日窓だけで判じ、 呼び手と既存の歯の fixture が動きます。 持ち主の裁定で選びました。

04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 判定の関数は役割の model の名の集合を受け、 model ごとの 7 日窓は名が集合に在る行だけを閾値と比べます。 5 時間窓と 7 日窓は今のまま全部比べます。 呼び手は判じる群の集合を渡し、 管理 tick は自席の役割 1 つの集合を渡します。 支えるのは FR38 (群の逼迫の通知と移動) の根拠と FR27 (管理 tick) への主張です。

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなること 3 つと、 代わりに引き受けること 3 つです。 良くなるのは、 Opus で走る群が Fable の窓の埋まった口座へも移れること、 門と並べ方の読みが 1 つになること、 役割の model が Fable の群は今のまま守られることです。 引き受けるのは、 usage API が Opus の窓を返さない間は Opus 固有の上限が見えないこと、 判定の関数の呼び手と既存の歯の fixture が動くこと、 役割の行を欠く規則の写しでは群の判定が逼迫を測る前に読めないと判じることです。

✓ 良い結果
