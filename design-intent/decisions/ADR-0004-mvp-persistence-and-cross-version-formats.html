§1. Context

MVP を小さく切り直したとき、 「状態をどこに、 どんな形で置くか」を決めないと契約が書けなくなりました。 憲法は状態の置き場を「SQLite 1 file」と例示しますが、 この repo は外部 crate を 1 本も持たない (依存 0 本) と決めていて、 SQLite を今すぐ入れると矛盾します。 加えて、 前の版と次の版が共有する 5 つの接点 (所属の目印・観測・台帳・停止・審査結果) の file の形と、 設定を環境変数で受け渡してよいかも、 契約より先に決める必要がありました。 本 ADR はその決定の記録です。

MVP 切り直し (user 裁定 2026-09-09) により、 SRS の到達点は toy repo 5 便 + 自己ホスト 1 便に絞られ、 契約は 5 本 + 不足 3 本に分かれた (docs/design/ の 4 設計)。 各契約が同じ on-disk 面を読み書きするため、 形式は契約に先立って 1 箇所で決める必要がある。 拘束条件は次の 4 つである。 (1) C3 は fleet の状態を「host 列を持つ 1 つの database file」に置くと定め、 機構欄は SQLite 1 file を例示する。 (2) NFR3 と C13 は実行時の直接依存 0 本 (許可リストの外は歯が落とす) を定め、 依存の追加は A3 の user 確認を要する。 (3) C2.2 は環境変数の直読と新しい env seam の新設を禁じる。 (4) 器 SPEC §12.2 (要件カタログ R-O3) は跨版契約を 5 面 (所属 marker / 観測 export / 台帳 adapter / 停止 1 コマンド / oracle) と定め、 版番号に依らず固定する。 CLAUDE.md の「ADR を書く条件」のうち 1 (憲法条の解釈) と 3 (schema・on-disk 形式・跨版契約) に当たる。

§2. Decision

決めたことは 5 つです。 (1) 状態は「1 行 1 出来事を末尾に足していく JSONL の file 1 つ」に置き、 SQLite は次の版で依存の確認を経てから入れます。 (2) 前の版と共有する 5 つの接点の file の形を固定します。 (3) 契約 file と規則の値の file は、 標準ライブラリだけで読める小さな TOML の形にします。 (4) 環境変数を読みません (HOME も読みません)。 置き場は引数と、 repo に紐づけた git の local 設定で渡します。 (5) file の形には版番号を付け、 壊す変更は版を上げて行います。

§2.1 永続面 = 追記だけの JSONL 1 file (C3 の MVP 解釈)

「1 つの database file」を、 MVP では「追記だけの JSONL 1 file」と読みます。 各行に host 名を持たせるので、 憲法が求める「host 列」も満たします。 SQLite は次の版で、 依存の追加を user に確認してから入れます。

D-1: scribe2 SHALL keep the fleet state of the MVP in exactly one append-only JSONL file, <state_dir>/fleet/events.jsonl, in which every line is one event carrying a host field, and SHALL derive the current position of every run and seat only by replaying that file.

D-1.2: IF a line of the event log cannot be parsed, THEN scribe2 SHALL report every such line with its line number and SHALL NOT skip it silently.

解釈
C3 の規範文が求めるのは「1 つの file」「host 列」「per-host の dir / TSV / cache に真実を置かない」の 3 点であり、 storage engine は機構欄の例示である。 JSONL 1 file は 3 点を満たす。 SQLite 化は依存許可リスト (C13 / A3) を経た v3 の手番とし、 その際も event log は消さず投影元として残す (跨版 面 2 の path を固定するため)。
機構
lock file (events.jsonl.lock・create_new・stale 30 s で除去し warn) を伴う O_APPEND の 1 行 write。 reader は fail-closed (NFR4)。 型は EventKind (閉じた 8 variant) と Stage (閉じた 8 variant)。 設計は docs/design/fleet-event-log.md。
出所
器 SPEC v0.4.6 §4 (MVP の state store は std の JSONL・SQLite は v3)・SRS FR3

§2.2 跨版 5 面の v2 側の形

前の版と次の版が共有する 5 つの接点のうち、 MVP で作るのは 4 つ (所属・観測・停止・審査結果) です。 台帳の接点は「bead の id を文字列で持つだけ」に留め、 台帳への書き込みは MVP の外です。

面v2 側の形 (MUST)SRS
1 所属repo root の固定名 .vessel。 中身は 2 行・LF・この順・末尾改行・余白なし: name=<NAME> / version=<N>。 不在・読めない・parse 不能は「黙る」側へ倒すFR19 / FR24
2 観測<state_dir>/fleet/events.jsonl (schema 1) と <NAME> fleet export (stdout 1 行目が schema header・read-only・lock を取らない)FR3
3 台帳MVP 外。 event と契約は bead id を文字列で持つだけで、 台帳 (bd) の read / write を行わないSRS scope out
4 停止<NAME> pipe stop --all 1 コマンド・冪等。 rc = 0 (全部止まった / 対象なし)・1 (残った)・2 (state が読めない)FR13
5 oracle<state_dir>/fleet/verdicts.jsonl に land ごと 1 行 {"schema":1,"run","bead","sha","verdict","evidence","ts"} を append。 evidence は verdict.json の pathFR12

path・file 名・rc 語彙は版番号に依らず固定する (R-O3)。 面 5 は要件カタログ R-O3 では「oracle 再 gate」(前の版が次の版の land を独立に gate し直す面) だが、 ADR-0003 により前の版が再 gate する形は無くなった。 v2 が固定するのは verdict を外へ出す面 (verdicts.jsonl) だけであり、 読み手が再 gate するかは読み手の版が決める。 <state_dir> は §2.4 のとおり repo ごとに git の local 設定で紐づける (env からも HOME からも導かない)。

§2.3 契約 file と rules manifest = TOML subset

契約 file と規則の値の file は、 どちらも小さな TOML の形にします。 読み手は標準ライブラリだけで書く自前の scanner で、 未知の key は拒みます。 数字を書く file は、 人が裁定 id を添えて手で編集できる形であることが大事です。

D-3: scribe2 SHALL read the contract file and the rules manifest as a TOML subset (top-level scalars, [[rule]] array-of-tables, string / integer / boolean values, string arrays) with a scanner written in the standard library only, and SHALL reject unknown keys, missing required keys and type mismatches by collecting every error with its line number.

契約 file
key = goal / done / size / owner / disposition / write-set / verify / req / design / classes (任意)。 req (SRS の要件 id・1 本以上) と design (設計 doc の repo 相対 path) は SRS FR2 の帰結として必須。 verify の各要素は 1 行で完結する。 設計は docs/design/pipeline.md §3。
rules manifest
rules/manifest.toml・schema = 1・行 = id / kind / value / enabled / ruling / ruled_at。 全行が user の裁定 id を持つ (C5・裁定の無い行は loader が拒む)。 憲法 §3 の行 id は manifest の行 id の接頭辞として一致する。 user 逐語の key は持たない (PUBLIC repo)。 tracked な manifest は build 時に binary へ埋め込む (include_str!) ので、 別 repo の worktree で走る gate も path に依存せず同じ規則を読む。 --rules <path> は test 用の override。 設計は docs/design/rules-manifest.md。
出所
C1 (manifest は TOML・未知 key 拒否・起動時 1 回読み)・FR17・xtask の既存 scanner (toml_lite) と同形

§2.4 env seam を持たない (C2.2 の適用)

「状態の置き場」や「触ってよい file の一覧」を環境変数で渡すのはやめ、 HOME も読みません。 置き場は、 その repo を器に紐づけるときに git の local 設定へ書いておき、 引数で上書きできます。 触ってよい file の一覧は作業場所の git の私有 dir に置いた file で、 実装役への情報は起動コマンドの穴埋めで渡します。

D-4: scribe2 SHALL NOT read any environment variable, SHALL take the state directory of a served repository from that repository's local git configuration key derived from NAME (written once by vessel init --state-dir) or from an explicit --state-dir argument, and SHALL pass every other location or policy as a command-line argument, a file under the worktree's private git directory, or a placeholder substituted into the runner command.

機構
vessel init --state-dir <dir> が git config --local <NAME>.stateDir <dir> を書く (key 名は NAME 定数から導出・C2.2 の「state directory は NAME から導く」の MVP 形)。 hook と pipe はそれを git config --get で読み、 fleet は --state-dir を必須にする (既定を持たない)。 guard の policy は <git-dir>/<NAME>/write-set.txt (worktree ごとに私有・tracked 面に触れない・git status を汚さない)。 runner cmd の {run} {worktree} {contract} {write_set} {base} を置換し、 scribe2 固有の env は 1 つも足さない (親の env はそのまま継承)。 hooks.json の command に書く ${…_BIN:-<NAME>} の展開は Claude Code 側の shell が行い、 scribe2 は読まない。 headless wrapper が子 process (claude) へ設定 dir を環境変数として渡す行為は SRS FR5「口座は環境変数で切替」の履行であり、 「読む」ではないため本条に触れない。
解釈
C2.2 は「env を直読しない」「新しい env seam を作らない」「state dir を NAME から導く」の 3 点を課す。 HOME を読んで既定を組む案は 1 点目に当たるため採らない (std に HOME を介さず home dir を得る API は無く、 依存 0 本のまま条文を字面どおり守る唯一の道は「読まない」である)。 repo ごとの git local 設定は tracked 面に無く、 key 名が NAME から導出されるので 3 点目を満たす。
出所
C2.2。 前の器で SCRIBE_* env が 533 種に増えて改名不能になった実測 (器 SPEC §7)。

§2.5 schema 版と互換性

JSONL の各行と TOML の先頭に schema の番号を持たせます。 field を足すだけの変更は同じ番号のまま、 読めなくなる変更は番号を上げて「新しい版」として行います。

D-5: scribe2 SHALL carry an integer schema field in every event line, every verdict line, every injection record and at the top of the rules manifest, SHALL treat the addition of an optional field as compatible within the same schema number, and SHALL treat any change that makes an existing line unreadable as schema-incompatible, to be carried out only as a new version (N4).

機構
reader は schema が自分の知る値でなければ行番号付きで error にする (fail-closed)。 初期値はすべて 1。
出所
N4 (schema 非互換は新しい版)・R-O3 (export の schema 版付き)

§2.6 本 ADR の射程外

依存 OSS の追加・削除は決めない (rtk / graphify の seam と依存予算は別 ADR)。 folio の位置は決めない (別 ADR)。 SQLite 化の時期と schema は決めない (v3 の A3 を通す周で新 ADR)。 憲法の条文も SRS の要件文も 1 字も変えない (本 ADR は C3 / C2.2 の解釈を記録する。 FR5「口座は環境変数で切替」は子 process への設定であり、 §2.4 と矛盾しない)。 口座・lease・退役・tmux 席の状態 (C3 の残りの列・C9) は MVP の event log に持たせない (SRS scope out)。

§3. Consequences

良い点は、 依存 0 本のまま今日から状態を永続でき、 process を殺しても続きが引けること、 環境変数の増殖を最初から塞げることです。 悪い点は、 file が追記だけなので大きくなり続けること、 同じ host の中でしか lock が効かないこと、 憲法 §3 の写しと manifest の drift をまだ機械が測れないことです。

Positive

  • 直接依存 0 本 (NFR3) を保ったまま fleet の永続面が手に入る。 cell の sandbox が crates.io を引けなくても build できる。
  • 現在地が replay で決まるため、 process を殺して別 process で resume できる (SRS AC4)。 席の記憶や散文を判定入力にしない (C3.3) 形が構造で決まる。
  • 跨版 5 面の path と rc 語彙が版番号に依らず固定され、 v2 が「前の版」になる日に同じ面をそのまま提供できる (R-O3)。
  • env を 1 つも読まないため、 改名 (NAME 定数の差替え) が env の洗い替えを伴わず、 test が env の漏れに左右されない。 manifest を埋め込むので gate がどの repo で走っても規則は 1 つ。
  • 契約 file と manifest が同じ scanner で読めるため、 形式の実装が 1 本で済む。

Negative

  • 無限追記: event log は圧縮も rotation も持たない。 1 便あたり 10 行程度ゆえ MVP では問題にならないが、 v3 で SQLite 化するか rotation を足す判断が要る。
  • lock は同 host 内のみ: 複数 host からの append は想定しない (C3 の host 列は「どこで起きたか」を記録するだけで、 cross-host の直列化は担わない)。 fleet を複数 host で共有する形は v3 の SQLite / 同期の手番。
  • drift の歯が無い: manifest が憲法 §3 の行 id と字面一致するよう設計したが、 §3 の HTML と manifest を突合する CI の歯 (C14.2) は本 ADR の時点で存在しない。 最小形 (xtask の閾値 const と manifest の値の一致) だけを rules manifest の契約に含める。
  • repo の初期化が要る: state dir は vessel init --state-dir を 1 回打った repo でしか解決しない。 未初期化の repo では hook は黙り、 pipe は rc 1 で止まる (fail-closed)。
  • manifest の版は binary の版: 埋め込みゆえ manifest を直しても再 build するまで効かない。 tracked file と binary の drift は「build して使う」運用で吸収する (test の override は --rules)。
  • guard の policy を git dir に置くため、 git を使わない repo では guard が不活性になる (git は core 依存ゆえ許容)。

Neutral

  • 本 ADR は user 裁定を要しない (依存の増減も条文改訂も無く、 C2.2 の例外も作らない)。 前提の MVP 切り直しは user 裁定 2026-09-09。 AI が提案した運用の数値 (停止の猶予・lock の再試行と stale 線・hook の timeout) は本 ADR では決めず、 C5 の手続き (user 裁定 id 付きの rules 行) で manifest に入る。
  • REORG 案が予約していた ADR 番号 (0004 = 依存予算・0005 = folio) は 0005 / 0006 へ繰り下がる。 番号は land 順で採る。

§4. Alternatives Considered

状態の置き場は 4 案、 受け渡しは 2 案、 file の形は 2 案を比べました。 いずれも「依存 0 本」「環境変数を増やさない」「壊れた行を黙って捨てない」の 3 つの物差しで決めています。

案内容理由採否
永続 案 1 SQLite を今入れるC3 の例示どおり rusqlite 等で 1 fileNFR3 (依存 0 本) と cell sandbox の crates.io 不達に衝突。 A3 の user 確認も要る却下 (v3 で再提案)
永続 案 2 per-run の JSON file を上書き<state_dir>/pipe/<run>/state.json を段ごとに置換置換 write は先行の印を消す (記帳は追記であること・要件カタログ R-I16)。 人由来 event の計数 (FR22) が成立しない却下
永続 案 3 lock 無しの append複数 process の同時 append を許す同 host の並列 write で行が interleave する却下
永続 案 4 lock 付き append-only JSONL 1 file本 ADR §2.1C3 の 3 要件を満たし依存 0 本。 fail-closed reader で NFR4採用
受け渡し 案 a env (<NAME>_STATE_DIR 等)state dir / write-set / run 情報を env でC2.2 (env 直読禁止・seam 新設禁止)。 前の器の env 533 種の再演却下

形式 案 ii TOML subset本 ADR §2.3C1 の例示 (TOML) と一致。 std だけの scanner が既に 1 本在る採用

§5. Trace

出所は、 憲法の C1 / C2 / C3 / C13 / N4 と、 SRS の FR3 / FR12 / FR13 / FR17 / FR19 / NFR3 / NFR4、 器 SPEC の v0.4.6 (MVP 切り直し) と §7 / §12.2 です。 決定は AI が行い、 前提の切り直しは user の裁定です。

  • 前提: MVP 切り直しの user 裁定 (2026-09-09・逐語は repo 外)。 器 SPEC v0.4.6 §4 (state store は std の JSONL・SQLite は v3)・§7 (marker の字面)・§12.2 (跨版 5 面)。
  • 憲法: C1 (manifest は TOML 1 file)・C2.2 (env 直読禁止)・C3 (1 つの file・host 列)・C6.3 (計測は append-only store 1 つ)・C11.2 (極性は型で)・C13 / A3 (依存の予算と確認)・N4 (schema 非互換は新しい版)。
  • SRS: FR3 / FR5 (口座は子 process の環境変数で切替) / FR12 / FR13 / FR17 / FR19 / NFR3 / NFR4。 要件カタログ R-O3 (5 面・版に依らず固定)・R-I16 (記帳は追記)・R-G10 (破損入力は loud)。
  • 設計 doc: docs/design/fleet-event-log.md / docs/design/rules-manifest.md / docs/design/vessel-hook.md / docs/design/pipeline.md。 契約はこれらを pointer で指す (SRS FR2)。
  • 関連 ADR: ADR-0003 (前の版を oracle にしない = 跨版 5 面は「v2 が前の版になる日」のために実装する)。
  • 記録した日: 2026-09-09 (決定日と同日)。
