本 ADR は IETF RFC 2119 および RFC 8174 / BCP 14 に定義される MUST / SHALL / SHOULD / MAY のキーワード解釈規約に従う。 ADR は決定時点の記録であり、 改訂は新しい ADR による supersede で行う。

§1. Context

この器には「どの検査を、 どの順でやるか」の一覧が、 動いているコードと、 説明の文書の 2 か所にあります。 文書側の一覧は人が書き写したもので、 実際に動いている一覧より 3 つ少ないまま残っていました。 手で数えた一覧は必ず古くなります。 いっぽうコード側では、 一覧の並びがそのまま実行順になるという決まりなのに、 その並びが正しいことを機械が測っていませんでした。 どちらも「守られているはず」と思われていて、 誰も測っていなかった、 という話です。

ADR-0006 §2.1 は cargo xtask check が measure する tag を列挙し (記録時点で 11 本)、 §2.2 は各 tag が測るものを 1 行ずつ並べた。 2026-09-11 の実測 (main = e892fdc・判定行の現物) では、 判定行が並べる measure は 14 であった。 文書側の列挙は 3 本ぶん drift していた。

この drift は本件固有の事故ではない。 同じ形が独立に 2 度観測されている。 (a) measure を足す便の review が「文書の件数を直さないまま『本便で数え直した』と書いた」形を捕まえた。 (b) 設計文書の歯一覧が現物と 29 本ずれていることが記録された。 手で数えた列挙は必ず腐る——腐っても compile も CI も通るので、 腐ったことに気づく面が無い。

憲法 C1.2 は「規則の文書は型と manifest から導出し、 手書きの規範行を 0 にする」と定める。 列挙を文書へ写す形はこの条と正面から衝突する。 列挙を「更新する」対処は、 次の便で同じ drift を作り直すだけである。

別の面として、 憲法 C2 は「適用順は stage 列挙の宣言順だけから取り、 順序についての散文注記を持たない」と定める。 器はこれを「閉じた enum + 全 variant の const slice + 網羅 match」の形で実装しており、 対象は 3 面ある (pipe::gate::CHECKS / pipe::gate::VERDICTS / rules::ALL)。 ところが const slice の並びは手で書くので、 宣言順から静かにずれうる——ずれても compile は通り、 順序の注記は持たない方針ゆえ、 機械が測らなければ誰も気づかない。 記録時点で 3 面の並びはいずれも正しく、 それを測る歯は 1 本も無かった。

§2. Decision

§2.1 列挙の SSOT は機械側に置き、 文書は pointer だけを持つ

一覧の正本は動いているコードと、 それが出す実際の出力だと決めます。 文書は一覧を書き写さず、 「どこを見れば本物が分かるか」だけを書きます。 こうすると、 文書が古くなる余地そのものが無くなります。 項目が増えたり減ったりしても、 そのたびに新しい記録を立てる必要はなくなります。

器 SHALL 列挙の SSOT を機械側 (型と、 それを写す外形) に置く。 design-intent の文書 SHALL NOT 列挙を写す。 文書 SHALL 「どこを見れば現物が分かるか」の pointer を持つ (本件では cargo xtask check の判定行と、 それを組み立てる実装)。

本決定は ADR-0006 の次を supersede する: §2.1 (11 本の列挙)、 §2.2 (各 tag が測るものの列挙)、 §2.3 のうち「tag の増減は本 ADR を supersede する新 ADR で行う (MUST)」の規定。 文書が列挙を持たない以上、 measure の増減で差し替える列挙が存在しないためである。 measure の増減は通常の契約 (bead) で足りる (MAY)——ただし repo の「ADR を書く条件」に当たる便 (憲法条の解釈・外部依存・跨版契約・却下案を残す価値のある分岐) は従来どおり ADR を要する。 ADR-0006 §2.4 (ADR-0002 §2.2 の例示の訂正) は supersede しない——列挙ではなく実測の訂正記録だからである。

§2.2 C2「宣言順」の充足形

「並びがそのまま実行順になる」決まりを、 実際に守れている形として次のように定めます。 種類は閉じた型で数えきる。 全部の並びを 1 か所に書く。 場合分けは取りこぼしがあれば組み立てに失敗するようにする。 そのうえで、 並びが宣言した順のままであることを機械が測る。 最後の 1 つが今まで無かった部分です。

器 SHALL 憲法 C2 の充足形を次の 4 つの対で持つ: (a) 閉じた enum (variant の集合を型が閉じる)、 (b) 全 variant を並べた const slice (この並びが適用順序である)、 (c) 網羅 match (variant の追加が compile error になる)、 (d) const slice の並びが判別子の昇順 (0, 1, 2, …) と一致することを測る歯。

(d) の述語 SHALL crate 内に 1 つだけ置く。 3 面が別々の実装を持つと、 片方だけ緩む形で穴が開くためである。 述語は判別子の slice ではなく写像の関数を受け取り、 as を書く場所を呼び手の 1 行へ閉じる。

記録時点の対象は 3 面である: pipe::gate::CHECKS (機械検証の段・並びが適用順序)、 pipe::gate::VERDICTS (gate の 3 値)、 rules::ALL (規則種別の母集団)。 この 3 面という数を文書側の権威にしない (§2.1)——新しく (a)〜(c) の形を持つ面を足す便は、 同じ便で (d) の歯を足す (MUST)。

§2.3 pin が捕まえない形と、 それを捕まえる面

この測り方には、 はっきりした穴が 1 つあります。 種類を末尾に足して一覧へ入れ忘れた場合は見つけられません。 順番を入れ替えた・重複した・途中を抜いた場合は見つかります。 穴を承知で採るのは、 末尾の入れ忘れを捕まえる別の面が既にあるからです。 限界は、 主張と同じ場所に書いておきます。

(d) の歯が捕まえるのは「並べ替え」「重複」「中間の欠番」である。 enum の末尾に足した variant を const slice へ入れ忘れた形は捕まえない——残りの判別子が 0..len に収まるからである。

末尾の入れ忘れを捕まえる面は面ごとに異なる。 rules::ALL では manifest との parity である——行の kind は ALL を通して解決されるので、 ALL に無い variant の行は未知の kind として parse できず歯が落ちる (行を伴わない variant は、 配線されていない設定として C10.3 の面が扱う)。 pipe::gate の 2 面では網羅 match と外形である。 これらは本 ADR が作る面ではなく、 既に在る面である。

本 ADR の記録時点の限界: §2.1 が SSOT と定めた「判定行」は、 集合としても順序としても pin されていない。 xtask の歯は判定行に対して個別 token の contains を当てるだけで、 token の集合も並びも測っていない (2026-09-11 実測)。 したがって §2.1 は「文書が列挙を持たない」ことは達成するが、 「機械側が列挙を守っている」ことの担保は現時点で個別 token の存在までである。 判定行を外形として pin する面は別便で入れる。 本 ADR はこの不在を知ったうえで決めている——担保が既に在るかのように書かない。

§2.4 射程外

この記録が決めるのは「一覧をどこに置くか」と「並びをどう測るか」だけです。 それぞれの検査が何を測るか、 上限の数値、 出力の書式は、 ここでは決めません。

次は本 ADR の決定ではない (MUST NOT be read as such): 各 measure の実装と測定定義、 閾値の実値と置き場 (rules manifest と裁定 id が扱う)、 判定行の書式、 判定行を外形 snapshot として pin する面の設計 (別便)、 CI の job 構成。

§3. Consequences

良い面は、 文書が古くなる余地が消えること、 そして「並びが実行順」という決まりが初めて機械で測られるようになることです。 悪い面は、 一覧を読みたい人がコードか実行結果を見に行く必要があること。 もうひとつ、 末尾の入れ忘れという穴が残ることです。 どちらも承知のうえで選んでいます。

Positive: 文書側に drift しうる列挙が無くなる (C1.2 の向き)。 C2 の充足が測られる状態になる——記録時点まで、 並びの正しさは誰も測っていなかった。 measure の増減で ADR を立てる必要が消え、 記録の増殖が減る (憲法の順位「増殖の防止」)。

Negative (受け入れるコスト): 列挙を知りたい読み手は現物 (判定行または実装) を見に行くことになる。 文書だけで完結しない。 pointer が指す先が動いた便では pointer の更新が要る (列挙の更新より頻度は低い)。

Negative (残る穴): §2.3 の末尾入れ忘れ。 面ごとの別経路が受けるが、 1 つの歯で全部が守られるわけではない。 加えて §2.3 末尾のとおり、 判定行そのものが集合として pin されていない状態が当面続く。

§4. Alternatives Considered

4 つの案を退けました。 いちばん素直な「文書の一覧を今の数に直す」案は、 次の便で同じずれを作り直すだけです。 一覧を機械から自動生成する案は筋が通りますが、 生成の仕組みを 1 つ増やすぶん高くつきます。 並び順を文章で注記する案は決まりに反します。 何もしない案は、 ずれを抱えたまま「並びが実行順」を誰も測らない状態を続けることになります。

(A) 文書側の列挙を現物の数へ更新する (起票時の案)。 却下: 同じ drift が次の便で再発する。 実測で 2 度観測された形であり (§1)、 「今回は気をつける」は機械的な保証ではない。 C1.2 とも衝突したままである。

(B) 列挙を機械から生成して文書へ埋める。 却下ではないが本便では採らない: C1.2 の理想形ではあるものの、 生成物と生成器を 1 面ずつ増やす。 drift は消えず生成器へ移る (生成漏れは同じく静かである)。 現物 1 面を指す方が安く、 憲法の順位「増殖の防止」に沿う。 判定行を外形として pin する面 (§2.3) が入れば、 生成の是非を実測付きで再検討できる。

(C) 並び順を散文の注記で持つ (「この順で適用する」と文書に書く)。 却下: 憲法 C2 が明示的に禁じる形である。 加えて注記は測れないので、 本 ADR が塞ごうとしている穴をそのまま残す。

(D) 現状維持。 却下: 文書の 3 本 drift が残り、 C2 の充足が測られない状態が続く。 並びが静かにずれた周は、 段の実行順が変わっても誰も気づかない。

§5. Trace

出所は、 実際に検査を走らせて出力を数えたことと、 並びを測る歯を書いて「無い状態では落ちる」ことを確かめたことです。 担保が無いと分かった件は、 別の便の審査で見つかりました。

  • drift の実測 (2026-09-11・main = e892fdc): cargo xtask check の判定行を現物で数え、 文書側の列挙 (記録時点 11 本) との差を確認した。 判定行が並べる measure は 14 であった。
  • C2 の充足が測られていないことの実測 (同日): 3 面 (CHECKS / VERDICTS / ALL) の並びを判別子順と突き合わせる歯を検索し、 0 本であることを確認した。 並び自体は 3 面とも正しかった——測る面が無いだけである。
  • 歯の flip の実測 (同日): (d) の歯を先に置いた木で cargo nextest run --workspace が rc 101 (述語が存在しない compile error = 機能不在) で落ち、 述語を置いた後に 368/368 で通ることを実測した。
  • 述語の非空虚性 (同日): 並べ替え・中間の欠番・重複の 3 つの壊し方で述語が偽を返すことを歯にした。 真を返すだけの述語ではない。
  • 判定行が集合として pin されていないことの実測 (2026-09-11・別便の review): xtask の歯は判定行に対し個別 token の contains のみで、 順序も token 集合も測っていないことが確認された。 §2.3 末尾の限界はこの実測に基づく。
