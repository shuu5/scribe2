設計判断記録 (ADR) scribe2 — 起動の口を 1 つに

core は子 process を自分で起こさず、 何を起こすかの記述を差し替え口へ渡す — 実物は境界 crate の 1 か所に据え、 撃つ関数の純移動はやめる (ADR-0033 の実現方法の一部を置き換える)

ADR-0033 は、 子 process を撃つ関数を core から境界 crate へ純移動して、 core が process を起こさない形にすると決めた。 測り直すと、 撃つ関数は core の中の多くの file から呼ばれており (git の 3 関数だけで 16 file)、 core は境界 crate に依存できないので、 撃つ関数だけを移すと呼び手が compile できない。 本 ADR は、 core に「何を起こすかの記述」の型 1 つと「起こす役の差し替え口」の trait 1 つを置き、 実物は境界 crate の 1 か所で bin の main の先頭に据えると決める。 呼び手の呼び方と判定は変わらず、 core の本体の Command::new は 0 になり、 歯は偽の起こし役を据えて site を測れる。 代わりに core の行数は減らず (+150 行前後)、 ADR-0033 が見込んだ移す量 (3〜5 千行) は成立しない。 ADR-0033 は何が I/O かを core の Command::new が 0 であることで機械で決めると置いており、 本 ADR はそれを 2026-09-15 の裁定の物差しと読んで満たす。 撃つ関数と driver の関数は core に残り、 core の行数が減らない点が裁定の見込みと違う。 user は core の行数が減らないことを了解した上でこの形 (OPT1) で進めると裁定した (裁定 id user 2026-09-24T00:13Z)。

この判断が約束すること (1 文サマリ)

この記録で「core」は器 (scribe2) の本体の箱、 「境界 crate」は外の世界に触れる仕事を受け持つ別の箱、 「子 process」は器が git や tmux などの道具を起こすことです。 前の決定 (ADR-0033) は、 道具を起こす関数を本体の箱から外の箱へそのまま引っ越しさせ、 本体の箱が道具を自分で起こさないようにする、 と決めました。 実際に数え直すと、 道具を起こす関数は本体の箱の中の多くの file から呼ばれていました (git を起こす 3 つの関数だけで 16 file)。 本体の箱は外の箱を名指せない作りなので、 関数だけを引っ越しさせると呼んでいる側が組み立て (compile) できなくなります。 この記録は、 本体の箱には「何を起こすかの記述」と「起こす役を差し込む口」だけを置き、 実際に起こす役は外の箱の 1 か所に置いて、 実行 file が動き出す最初に差し込む、 と決めます。 呼んでいる側の呼び方と判定の code は変わらず、 本体の箱が道具を自分で起こす場所は 0 になり、 test は偽の起こし役を差し込んで、 どんな道具をどんな引数で起こしたかを測れます。 代わりに本体の箱の行数は減らず (150 行前後増える)、 前の決定が見込んだ移す量 (3〜5 千行) は成り立ちません。 前の決定は、 何が外の世界に触れる仕事かを「本体の箱が道具を起こす場所が 0」で機械的に決めると置いており、 この記録はそれを user が 2026-09-15 に決めた「本体を判定と型に絞る」の物差しと読んで、 満たします。 ただ、 道具を起こす関数と、 判定と起動が交互に並ぶ関数群は本体の箱に残り、 行数が減らない点が見込みと違います。 user は 2026-09-24 に、 行数が減らないことを承知の上でこの形で進めると決めました (裁定 id user 2026-09-24T00:13Z)。 この記録は、 受け入れられるまで何も拘束しない発効前 (proposed) の記録です。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを、 これまでの決定と実測と器の現物から説明します。 user は 2026-09-15 に、 本体の箱の行数の数え方から test の行を外すこと、 道具を起こす部分を外の箱へ分けて本体を判定と型に絞ること、 外の箱にも行数の上限を置くことを決めました。 前の決定 (ADR-0033) はその実現方法を「道具を起こす関数を外の箱へ移す」と書き、 移す量を 3〜5 千行、 引っ越しの便を 6 本ほどと見込みました。 最初の 2 便 (数え方の変更と、 外の箱の新設) は済んでいます。 数え直すと、 本体の箱で道具を起こす場所は 34 か所 (22 file) で、 設計の初版が数えた main の 33 か所から、 その約 48 分後に入った変更 1 つで 1 か所増えていました。 今は数を記録するだけなので、 増えるのを止めません。 また、 道具を起こす関数は本体の中の多くの file から呼ばれ、 包みの関数や claude の組み立て役は起動の組み立てそのものを受け渡ししていました。 本体の箱は外の箱を名指せない作りなので、 関数だけを引っ越しさせると呼んでいる側が組み立てできず、 呼んでいる側ごと引っ越しさせると、 判定まで外の箱へ押し出されます。 つまり、 判定を本体に残すか、 道具を起こす関数を本体から出すかの選択になります。 前の決定は、 何が外の世界に触れる仕事かを「本体の箱が道具を起こす場所が 0」で機械的に決めると置き、 「純粋かどうか」を物差しにする案は人の判断に頼るとして退けていました。 この記録は、 その「0」を user の決定の文面の物差しと読みます。 file の読み書きはどの案でも本体に残ります。 test の側では、 git が成功したのに何も返さなかった回を実物の git では作れず、 その回を弾く判定の一行が変異検査で生き残ったままです。

CTX1

経緯 — I/O 面を分ける決定と物差しは済み、 段 2 の形と行数の見込みの差が残る

2026-09-15 の user 裁定 (A2・2 問) は、 core器の本体の箱-lines (R-C4-1) の母集団を core の src の本体 (in-file の歯を除く) にすること、 子 process を起こす I/O 面を境界 crateprocess を起こす箱 へ分けて core を pure な判定と型に絞ること、 境界 crate にも行数の上限 (新しい rules 行・値は実測の +20%・同じ裁定 iduser の決定を指す印) を置くことを決めた。 ADR-0033 はそれを記録し、 実現方法を、 std の Command標準の起動の型 を構築する関数を境界 crate へ移すことと、 core が Command::new を 0 本しか持たないこと (deny) と書いた。 見込みは、 移す量が 3〜5 千行、 純移動中身を変えない移動の機械証明 (pipeline.md §5.3) で lens に渡せる、 純移動の便が 6 本ほど、 とした。 段 1 の 2 便 (core-lines の母集団を本体にする便・境界 crate を新設して bin と e2e の歯を移す便) は着地済みで、 core-spawn (core の src で Command::new を含む行の数) は数だけ出す検出線止めずに記録する線として動いている。 同じ日の後の裁定で R-C4-1 は一時 60,000 に緩められ、 リファクタリングを定期の枠で続けると決まった。 ADR-0033 は境界を散文でなく機械で決める (DR3) と置き、 何が I/O かを「core は Command::new を 0 本しか持たない (deny)」で決めると書き、 「pure かどうか」を物差しにする案 (判定を新しい crate へ出す案) を散文の判断として退けた。 本 ADR はその Command::new = 0 を裁定の文面の物差しと読む (本 ADR の解釈)。 file の読み書きはどの案でも core に残る。 本 ADR が採る案 (OPT1) はその物差し (本 ADR の読みでは core の本体の Command::new = 0) を満たす。 裁定と ADR-0033 の見込みと違うのは、 撃つ関数と driver の関数便を進める関数群 (判定と起動が交互に並ぶ関数群) が core に残って口越しに起こし、 core の行数が減らない点である。 ADR-0033 が見込んだ形 (撃つ関数を core に持たず、 境界は生の結果だけを返す) にいちばん近いのは driver の関数ごと移す案 (OPT2) だが、 それは判定を境界 crate へ押し出す。 段 2 の形について user に 2 つを問い、 裁定 (裁定 id user 2026-09-24T00:13Z) を得た。 1 つ目は、 core の行数が減らない (core +150 行前後・境界 +110 行前後・ADR-0033 が見込んだ 3〜5 千行の移動は成立しない) ことを了解した上で OPT1 で進め、 段 2 をやめる案 (OPT5) は採らない、 である。 2 つ目は、 R-C4-5 を足す時点 (下の supersession) を core-spawn を deny にする便と同じ便とし、 既存の裁定 id user 2026-09-15T10:07Z の範囲内と扱う (新しい A2 の裁定は要らない)、 である。 逐語は非公開の作業記録簿 (台帳 s2-07l.198 の notes) に在る。

CTX2

実測 — 撃つ site の数と、 検出線が増加を止めないこと

main 9f516d3 (2026-09-24) の core の src で Command::new を含む行は、 本体 (core-lines と同じ切り方) が 34 行 / 22 file、 歯の区間test の区間が 10 行 / 8 file である。 設計 §9 の初版が同じ日に数えた main b82be74 では本体が 33 行 / 21 file で、 その約 48 分後に着地した便 1 本 (s2-07l.576・doctor の版の照合) が本体に 1 site を足した。 検出線は数を出すだけなので増加を止めない (実例はこの 1 件)。 道具別には git が最も多く、 systemctl・tmux・sh・systemd-run・kill・bd・自分自身の bin・claude・curl・hostname・cargo・CI の照会が続く。 歯の区間の 10 行は、 git の fixture を作る helper と、 死んだ pid を作る true の起動と、 包みの歯が渡す引数である。 core の行数は段 1 の母集団の変更の後に 44,118 / 60,000 (main 8ca0dc9・設計 §9 の実測。 9f516d3 では 44,657) で、 余地は段 1 で戻っている。 台帳の notes には、 変異検査の A/B (撃墜 11・生存 1・母集団 12) で生き残った 1 本が記録されている。 それは口座の導入先の HEAD の読み (git が成功して stdout が空の周を空 sha として弾く guard) で、 歯が実 git を撃つので「成功して空」の周を作れない。

CTX3

現物 — 撃つ関数は core の中から呼ばれ、 core は境界 crate を名指せない

main 9f516d3 で、 pipe/mod.rs の git の 3 関数 (bytes・ok・1 行の読み) は core の他の 16 file から呼ばれる。 seat/mod.rs の tmux に届く公開関数 (送る・pane を読む・pane の前面が shell かを見る・target を解く) は core の他の 10 file から呼ばれる。 pipe/confine.rs の包み (sh の行や Command を memory の囲いに入れる関数) は Command を値で受けて返し、 他の 5 file から呼ばれる。 headless/mod.rs の claude の構築点は Command を組んで返し、 包みへ渡す。 core の Cargo.toml は実行時の依存を 1 つも持たず、 境界 crate は core に依存する (向きは境界 → core の一方向)。 したがって撃つ関数だけを境界 crate へ移すと、 core に残る呼び手関数を呼ぶ側が compile できない。 呼び手ごと移すと、 land・gate・train・follow などの driver の関数 (判定と子 process の起動が交互に並ぶ関数群) が丸ごと境界 crate へ動き、 判定が境界へ押し出される。 core に残る関数の本文も変わるので、 純移動の機械証明 (名と本文の hash で「中身を変えていない」を示す仕組み) も使えない。 xtask の claude-spawn-points (deny) は、 claude の構築の字面が headless/ の中で mod.rs に 1 つだけ在ることを求める。

CTX4

憲法と既存の決定の向き (本 ADR の解釈)

C4 は core の大きさなどの上限を CI の deny で守り、 上限の変更を A2 (user 裁定) に限る。 C13.2 は derive macro を境界 crate に閉じることを求める。 本 ADR はこれを、 core が境界 crate に依存しない構成を前提にした条と読む (条文そのものは依存の向きを言わない)。 C17 は変更のたびに決定はしご足す前に通す 5 段 (要るか・既に在るか・std で足りるか・1 行で済むか・最小の実装か) を順に通し、 C17.2 は仕組みを足す前に消すものを名指すことを求める。 C12.4 は変異の生存を検出線として記録する。 ADR-0033 は境界を散文でなく機械 (Command::new の有無) で決める (DR3) と置き、 境界 crate の関数は「引数 → 子 process → 生の結果」だけを返し、 判定は core の純関数に残り、 歯は stub で撃てる、 と帰結 (CSQ-P3) に書いた。 ADR-0001 の実行 file 1 つは不変である。 ADR-0033 の「core は Command::new を 0 本しか持たない」は、 歯の区間を数えるかを書いていない。 本 ADR はこれを、 core-lines と同じ切り方で「core の src の本体は 0 本」と読む (歯の区間の量は R-C4-3 が縛る)。 C1 は rule value (閾値・発効の印・裁定 id など) を manifest の 1 file に置くことを求め、 C1.2 / N2 は規則を散文だけで持たないことを求める (ADR-0033 の DR3 の根)。 claude-spawn-points (1 つだけ) と ADR-0033 が deny と置いた core-spawn (0 本) は、 rules 行裁定つきの規則の行を持たない xtask の構造の検査である。 本 ADR はこの型の検査を C1 の rule value と読まない (本 ADR の解釈)。

CTX5

材料 — std の Command の面は数えられ、 site ごとの差し替えの先例が在る

core の site が std の Command に対して呼ぶ面は数えられる (数は src 全体の字面の件数)。 builder の面は new・arg・args・current_dir・env・env_remove・stdin・stdout・stderr・process_group・get_program・get_args・get_envs で、 終端は output (26 か所)・spawn (15)・status (4)・exec (1・席の起動の行) である。 exec と process_group のために unix の CommandExt を use する file が 5 つ在る。 hook/host_guard.rs は git の program の path を判定の場の引数に持ち、 歯が偽の git で呼出回数を数える。 headless の構築点も claude の program を引数に受ける。 これらは site ごとに program を差し替える先例で、 口は site ごとに別々である。 core の歯は nextest の下では歯ごとに別の process で走るが、 変異検査の道具は baseline を常に、 mutant の歯を的の歯の名が無い周に、 cargo test で同じ process の複数 thread で走らせる。 process 全体に効く偽物を歯が据えると、 並んで走る他の歯に漏れる。 境界 crate の e2e の歯は core の lib を同じ process で呼ぶものを持つ (seat の recent の git の読みを直に呼ぶ歯 2 本は、 実 git が撃てないと dirty の行と not-a-repo の判定が落ちる)。

03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 6 つ並べます。 本体に記述と差し込み口だけを置いて外の箱の 1 か所が起こす案、 道具を起こす関数を呼んでいる側ごと外の箱へ移す案、 関数だけを前の決定どおりに引っ越しさせる案、 道具ごとに専用の口を作る案、 この段をやめて数を記録するだけの線のまま残す案、 本体の箱が外の箱に頼る向きに変える案です。 却下した 5 案にも利点を並べ、 退けた決め手が現物か分析かを各案に書きます。 呼んでいる側ごと移す案は本体の行数を数千行減らせ、 前の決定が見込んだ形 (道具を起こす関数を本体に持たない) にいちばん近い点で、 関数だけを移す案と向きを変える案は本体の行数が減る点で、 道具ごとの口の案は引数の形を型で強く縛れる点で、 この段をやめる案は費用が 0 で新しい仕組みを足さず、 増加の歯止めや生き残りの対処も口なしでできる点で、 選んだ案に勝ちます。

OPT1起動の記述何を起こすかの記述と差し替え口起こす役の差し込み口 — core は何を起こすかを組むだけで、 境界 crate の実物 1 つが撃つ採用

core に std の Command と同じ builder の面と 4 終端を持つ起動の記述の型 1 つと、 4 終端と 1 対 1 の method を持つ差し替え口の trait 1 つを置く。 実物は境界 crate の 1 file に置き、 bin の main の先頭で据える。 core の各 site は構築の字面と use の行だけを置き換える。 歯は cfg(test) の実物で今のまま動き、 新しい歯は記録する stub記録する偽の起こし役 を据えて site を測る。 core の本体の Command::new が 0 になったら core-spawn を deny にし、 同じ便で R-C4-5 を足す。 決め手は分析 (呼び手を動かさずに ADR-0033 の 0 本を実現できる形のうち、 面が最小で便を並列に流せる形)。

本体の箱には「何を起こすかの記述」の型と「起こす役を差し込む口」だけを置き、 実際に道具を起こす役は外の箱の 1 か所に置いて、 実行 file が動き出す最初に差し込む案です。 記述の型は標準の起動の型と同じ呼び方を持つので、 本体の各場所は組み立ての書き出しと読み込みの行だけを書き換え、 呼び方も判定も変えません。 test は偽の起こし役を差し込んで、 どんな道具をどんな引数で起こしたかと、 返った結果をどう読んだかを測れます。 本体の箱で道具を起こす場所は 0 になり、 検査で固定できます。 口を置く 1 便の後は、 書き換えの便を並べて流せます。 代わりに、 本体の箱の行数は減らず (150 行前後増える)、 道具を起こす関数と判定を並べる関数群は本体に残るので、 前の決定が見込んだ形にはなりません。 起こして流しながら読む起こし方では、 偽物は実物を起こさないので失敗だけを返します。 差し込んだ口という状態が 1 つ増えて差し込み忘れると全部が止まり、 test の区間には本物の起動が残り、 中身の書き換えなので「中身を変えない引っ越し」の証明は使えません。 決め手は分析で、 呼んでいる側を動かさずに前の決定を実現できる形のうち、 足す面が最小で便を並べて流せる形でした。

+ 利点

  • core の本体の Command::new が 0 になり deny で固定され、 何が I/O かが機械で決まる (DR1)
  • 呼び手の呼び方と判定が変わらず、 判定は core に残る。 関数の引数の数・順・戻りの形も変わらない (型の字面 Command が起動の記述に替わる所はある・DR2)
  • 歯が記録する stub で起動の引数を測れ、 output と status の周は結果の読みも測れる。 空 sha の生存変異を殺す歯が書ける (DR3)
  • 口を置く 1 便の後は、 site の置換 5 便が write-set を交えずに並列で流れる (各 S・DR4)
  • 依存 OSS を足さず、 std の型を写すだけで済む (DR5)

− 欠点

  • driver の関数と git の 1 行の読みなどの撃つ関数は core に残り、 口越しに子 process を起こし続ける。 ADR-0033 が見込んだ形 (撃つ関数を core に持たず、 境界は生の結果だけを返す) にはならない (裁定 id user 2026-09-24T00:13Z で了解済み)
  • 記録する stub は実 process を起こさないので、 spawn の終端は失敗だけを返す (std の Child は std の外から作れない)。 spawn の 15 site の成功の周は stub で測れず、 cfg(test) の実物を撃つ歯が持つ (DR3)
  • core の行数は減らない (起動の記述と差し替え口で +150 行前後)。 ADR-0033 が見込んだ移す量 (3〜5 千行) は成立しない
  • process 全体の状態 (据えた口) が 1 つ増え、 据え忘れた bin や e2e の test binary は全 site が撃てなくなる
  • 歯の区間には cfg(test) の実物と fixture の起動が残る
  • site の本文が変わるので純移動の機械証明は使えず、 各便の lens は置換の diff を読む
OPT2driver の関数ごと境界 crate へ移す不採用

撃つ関数を呼ぶ land・gate・train・follow などの driver の関数を、 呼び手ごと境界 crate へ移す。 core には呼ばれない判定と型だけが残る。 決め手は分析 (閉包ごと移せば判定が境界へ押し出され、 判定を残そうと切れば切り方が散文になる)。

道具を起こす関数を呼んでいる land や gate などの関数群 (driver の関数) を、 呼んでいる側ごと外の箱へ移す案です。 本体の箱の行数が数千行の単位で減り、 道具を起こす関数を本体に持たないという前の決定の見込みにいちばん近い案です。 新しい型も口も足さず、 移す file の多くは中身を変えずに済みます。 けれども driver の関数の中では判定と道具の起動が交互に並んでいます。 呼ばれる関数を丸ごと移せば切れ目は組み立ての都合で機械的に決まりますが、 判定を含む数千行が外の箱へ出て、 外の箱の上限はその判定ごと認めることになります。 判定を本体に残そうと人が切れば、 どこで切るかを文章で判断することになり、 境界を機械で決めるという前の決定の物差しに反します。 どちらかを引き受けることになり、 1 便も多くの file を跨いで大きくなって並べて流せません。 決め手は分析です。

+ 利点

  • core の行数が数千行の単位で減り、 ADR-0033 が見込んだ形 (撃つ関数を core に持たない) にいちばん近い
  • 新しい型も trait も足さない。 移した file の多くは中身を変えずに済む

− 欠点

  • driver の関数の中では判定と起動が交互に並ぶ。 撃つ関数を呼ぶ閉包ごと移せば境界は compile で機械的に決まるが、 判定を含む数千行が境界 crate へ押し出され、 境界 crate の上限 (R-C4-5) はその判定ごと実測 +20% で認めることになる。 判定を core に残そうと人が切れば、 切り方が散文の判断になる (ADR-0033 の DR3 に反する)。 どちらか一方を引き受ける (DR1 / DR2)
  • 1 便が多くの呼び手を跨いで L 級になり、 並列に流せない (DR4)
OPT3撃つ関数だけを境界 crate へ純移動する (ADR-0033 の見込みの 6 便)不採用

git・tmux・systemd・claude・curl などを撃つ関数を module ごとに境界 crate へ純移動し、 純移動の機械証明で lens に渡す。 決め手は現物 (core に残る呼び手が compile できない)。

道具を起こす関数だけを、 前の決定の見込みどおり 6 便に分けて外の箱へ引っ越しさせる案です。 前の決定の文面どおりで新しい決定が要らず、 「中身を変えない引っ越し」の機械の証明が使えるので審査は要約を読むだけで済み、 本体の行数もその分減ります。 けれども本体の箱は外の箱を名指せない作りなので、 本体に残る呼んでいる側 (git の 3 関数だけで 16 file、 tmux の関数で 10 file) が組み立てできません。 組み立てを通すには呼んでいる側ごと移すしかなく、 それは上の driver の関数ごと移す案になります。 決め手は現物です。

+ 利点

  • ADR-0033 の文面どおりで、 新しい決定が要らない
  • 純移動の機械証明が使え、 lens は要約だけを読む
  • core の行数が撃つ関数の分だけ減る

− 欠点

  • core は境界 crate に依存できないので、 core に残る呼び手 (git の 3 関数だけで 16 file・tmux の関数で 10 file) が compile できない (DR2)
  • 呼び手の compile を通すには呼び手ごと移すしかなく、 それは driver の関数ごと移す案になる
OPT4道具ごとの typed な口 (git・tmux・systemctl など) を core に置く不採用

起動を 1 つの型でなく、 道具ごとに閉じた method の集合 (git の口・tmux の口・systemctl の口…) で表し、 境界 crate が各口を実装する。 決め手は分析 (子を流しながら読む site に結局 spawn の口が要り、 全道具の口を定義する最初の便が大きくなる)。

起動を 1 つの型で表す代わりに、 git 用・tmux 用・systemctl 用のように道具ごとに専用の口を作り、 外の箱が各口を実装する案です。 起こせる引数の形が型で閉じるので、 記述の型より強く縛れ、 test の偽物も道具ごとに小さく書けます。 けれども、 子の出力を流しながら読む場所 (審査役の起動・便の起動・台帳の読み) は起こした子そのものを持ち続けるので、 どの道具の口にも汎用の起動の口が要り、 結局は記述の型と同じ面が残ります。 全部の道具の口を最初の便で定義するとその便が大きくなり、 後から道具ごとに足すと口の定義 file を複数の便が触って並べて流せません。 行数も記述の型より増えます。 決め手は分析です。

+ 利点

  • 撃てる引数の形が型で閉じ、 起動の記述より強く縛れる
  • 歯の偽物も道具ごとに小さく書ける

− 欠点

  • 子を流しながら読む site (headless の lens・pipe の spawn・seat の台帳の読み) は Child を持つので、 どの道具の口にも汎用の spawn が要り、 結局起動の記述と同じ面が残る
  • 全道具の口を最初の便で定義すると、 その便が大きくなる。 道具ごとに後から足すと、 口の定義 file を複数の便が触って write-set が交わる (DR4)
  • 道具ごとの method と実装が増え、 行数も起動の記述より多い (DR5)
OPT5段 2 をやめ、 core-spawn を検出線のまま残す不採用

core の余地は段 1 で戻ったので、 起動の site には触らず、 core-spawn は数だけを出す線のまま置く。 決め手は分析 (core が process を直接起こす構造が残り、 歯が差し替え口で起動を撃てない)。 目的と価値の選択でもあり、 裁定 id user 2026-09-24T00:13Z は OPT1 を採り本案を採らないと決めた。

本体の行数の余裕は最初の便で既に戻ったので、 この段はやめて、 道具を起こす場所の数を記録するだけの線のまま残す案です。 費用が 0 で、 新しい仕組みも足さず、 「そもそも要るか」を最初に問う決まりに最も素直です。 選んだ案でも行数は減らないので、 行数という元の目的はもう果たされています。 場所が増えるのは、 今の数を上限にする規則の行 (user の決定が要る) で口なしに止められ、 生き残っていた変異も、 git の出力を値で受ける判定と git を起こす部分に関数を分ければ口なしで捕まえられます。 けれども、 本体が道具を直接起こす作りはそのまま残り、 本体が道具を起こす場所を 0 にするという前の決定は実現せず、 それを取り下げる別の決定が要ります。 test が口に偽物を差し込んで起動を測ることはできず、 分けた場所のほかは場所ごとに分割か専用の口を 1 つずつ足すことになります。 決め手は分析で、 何を大事にするかの選択でもあるので user に尋ね、 user はこの案を採らないと決めました (裁定 id user 2026-09-24T00:13Z)。

+ 利点

  • 費用が 0 で、 新しい仕組みも足さない (決定はしごの最初の段「要るか」に最も素直)
  • core の行数の目的は段 1 で既に果たされ、 OPT1 でも行数は減らない
  • site の増加は、 core-spawn を今の数で上限にする形 (ratchet) で口なしに止められる (rules 行なので A2 の裁定は要る)
  • 空 sha の生存変異は、 HEAD の読みを「git の出力を値で受ける pure 関数」と「撃つ面」に分け、 pure 側に歯を足せば口なしに殺せる (台帳 s2-07l.198 の notes に在る手)

− 欠点

  • core が process を直接起こす構造が残る。 ADR-0033 の決定 (core の Command::new が 0・deny) は実現せず、 それを取り下げる別の ADR が要る (DR1)
  • 歯が差し替え口で起動を撃てない。 pure 分割や自前の口で測れるのは手を入れた site だけで、 site ごとに 1 つずつ足すことになる (OPT1 は全 site で口が 1 つ・DR3)
OPT6core を境界 crate に依存させる不採用

撃つ関数を境界 crate へ移し、 core の呼び手は境界 crate を use して今の形のまま呼ぶ。 決め手は分析 (今の構成では境界 crate が core に依存しているので依存が循環し Cargo が build を拒むが、 それは bin を別の crate へ移すか、 撃つ関数を std だけの葉の crate に置いて core がそれに依存すれば切れる。 どちらの形でも core は撃つ関数を直に呼び続け、 歯は実 process を撃つ・DR3)。

道具を起こす関数を外の箱へ移し、 本体の箱のほうが外の箱に頼る向きに変えて、 呼んでいる側は今の形のまま呼ぶ案です。 呼び方が変わらず、 関数は中身を変えずに引っ越しでき、 本体の行数もその分減ります。 外の箱は実行 file を持ち、 既に本体に頼っているので、 今の作りのまま向きを逆にすると頼り合いが輪になって組み立てができません。 ただしこの輪は、 実行 file を 3 つ目の箱へ移す (済んだ最初の便をやり直す) か、 道具を起こす関数を標準の部品だけで作る小さな箱に置いて本体がそこに頼れば切れます。 退ける理由は輪ではなく、 どちらの形でも本体が道具を起こす関数を直に呼び続けるので、 test が偽物を差し込めず実物を起こし続けることです。 実行 file を移す形では、 この記録の読みでは、 本体が外の箱に頼らないというこの器の作りの前提も崩れます。 決め手は分析です。

+ 利点

  • 呼び手の呼び方が変わらず、 撃つ関数は純移動で移せる
  • core の行数が撃つ関数の分だけ減る

− 欠点

  • 境界 crate は bin を持ち core に依存しているので、 依存が循環して build できない。 循環を切るには、 bin を 3 つ目の crate へ移す (着地済みの段 1 を組み直す) か、 撃つ関数を std だけの葉の crate に置いて core がそれに依存するか、 の構成の変更が要る
  • どちらの形で循環を切っても core は撃つ関数を直に呼び続けるので、 core の歯は差し替えられずに実 process を撃ち、 site を偽物で測れない (DR3・退ける決め手)。 bin を移す形では core の依存に境界 crate が入る (本 ADR の読みでは C13.2 の前提が崩れる・補助の理由・DR1)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 本体の箱には、 標準の起動の型と同じ呼び方を持つ「何を起こすかの記述」の型を 1 つ置き、 実際に起こす段になったら、 その記述を「起こす役を差し込む口」へ渡すだけにします。 本番では、 外の箱が持つ本物の起こし役を、 実行 file が動き出す最初に 1 回だけ差し込みます。 外の箱の test も本体の code を同じ process で呼ぶので、 そうした test が最初に呼ぶ共通の関数 1 つで、 同じ本物を 1 回だけ差し込みます。 差し込まれていないときは「できない」を返し、 今ある「道具を起こせなかった」ときの扱いにそのまま落ちます。 本体の箱の各場所は、 組み立ての書き出しと読み込みの行だけを書き換え、 呼び方も判定も変えません。 test では、 何も差し込まなければ今までどおり本物が動き、 新しい test は、 起こした道具と引数を覚えて決めた結果を返す偽物を、 その test の中だけに差し込んで測ります。 全部の場所を書き換え終えたら、 本体の箱で道具を起こす場所が 1 つでも在れば落とす検査に変え、 外の箱で標準の起動の型を組む file が 2 つ以上になっても落とす検査を足し、 同じ便で外の箱の行数の上限を規則の行に足します。 要件書では、 1 つの変更を小さく保つ要件 (NFR2) の根拠になり、 実行時に外部の部品に頼らない要件 (NFR3) と、 器の子 process を memory の囲いの中で走らせる要件 (NFR6) の形を変えず、 見張りの口が git を何回起こすかを test で測る要件 (NFR5) と同じ測り方を全部の場所へ広げる根拠になります。
