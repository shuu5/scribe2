設計判断記録 (ADR) scribe2 — 上限の許可

上限の許可 — user の発話に結んだ裁定を器が照らしてから、 rules 行が名指す消費の上限を bead 1 つに限り有限の値へ上げる記録を event log に持ち、 その bead の gate の照合と lens だけが読む

器の消費の上限は、 user が見ていない間に token が大量に使われないための既定の守りである。 正当な作業が上限に当たったとき、 今は manifest を PR で上げて戻すか、 写しの manifest を --rules で渡すしかない。 前者は重くほかの作業の上限も緩め、 後者は誰が許したかを確かめず、 記録も残らず、 lens に届かない。 本 ADR は、 user の発話に結んだ裁定を器が照らしてから、 名指された上限の行を bead 1 つに限って有限の値へ上げる記録 (上限の許可) を event log に 1 件書き、 その bead の gate の照合と lens だけがその値を読み、 期限・着地・取り消しで切れると決める。 上限を外す形は持たない。 新しい rules 行 2 本の値は、 持ち主の裁定 id (user 2026-10-01T01:05Z 項 permit-rows・user 2026-10-01T01:24Z 項 permit-max-h) と共に manifest に置くと決める。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「便」は 1 件の仕事の約束 (bead) を実装して main に入れる 1 回の流れ、 「上限」は 1 回の検査に渡す量などの数の守りです。 上限は、 user が見ていない間に token が大量に使われないための守りなので、 ふだんはそのまま残します。 けれども正当な作業が上限に当たったとき、 今は設定を PR で上げて戻すか、 写しの設定をその場で渡すしかなく、 前者は重くてほかの作業も緩み、 後者は誰が許したかが残らず、 検査役 (lens) にも届きませんでした。 この記録は、 user が chat で答えた言葉を器が確かめてから、 その作業 1 つだけ上限を有限の値まで上げる記録 (上限の許可) を残し、 期限か着地で自然に元へ戻すと決めます。 上限を外す形は持ちません。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 4 つから説明します。 今日の便が上限に当たり、 今の 2 つの手ではその作業だけに絞れなかった経緯・作業 1 つを縛る上限の行が 7 行で、 1 つの値を 2 つの process が別々に読んでいる現物・user の許しを器が確かめる今の仕組みとその穴・憲法をどう読み何を決めるかという範囲です。

CTX1

経緯 — 正当な作業が上限に当たったとき、 今の 2 つの手はどちらも作業 1 つに絞れない

2026-10-01 の便は、 verify が全部緑のまま、 gate の予算の照合で diff 215431 byte が cap 150000 (rules 行 gate.token_cap) を超えて Gated INCONCLUSIVE に止まった。 user が一時の上げを許し、 席は写しの manifest を --rules で渡して撃ち直した。 gate の照合は写しで通ったが、 lens は別の process で cap を読み直し (lens の起動の行は --rules を持たない)、 埋め込みの 150000 で再び断った。 着地の権能を持たない席は、 列の手動の 1 周に写しの --rules を渡す形しか持たず、 列は渡された道具を起こす便の全部へ写すので、 起こされうる契約 7 本を hold にしてから回した。 前例の一時の上げは、 manifest を上げる PR・binary の入れ替え・戻す PR の対 (2 組) で、 上げている間はほかの便の上限も緩む。 同じ契約の撃ち直し (追随・再 gate・新しい便) は同じ大きさの diff を何度も gate に掛けるので、 上限に当たった契約は撃ち直しのたびに同じ上限に当たる。 同じ便の消費の 4 値の和は約 6,531 万 token で検出線 R-C6-1 の 2,500 万を越えたが、 pipe show が超過の 1 行を出すだけで便は止まらない。

CTX2

現物 — 作業 1 つの消費だけを縛る上限は 7 行で、 gate.token_cap の読み手は 2 つの process に割れている

rules manifest の 85 行は、 便か bead 1 つの消費を縛る 7 行 (gate.token_cap・R-C6-1・review.same_kind_stop・pipe.follow_retries・pipe.land_wait_s・pipe.ci_wait_s・gate.slot_wait_s)、 host と群で分け合う 18 行 (1 つを上げるとほかの作業の取り分が減る)、 構造の 20 行 (C4・C13・C12 の門と台帳の形で、 CI は main の manifest で測る)、 上限でない 40 行に分かれる。 gate.token_cap は、 gate の予算の照合 (gate と追随の再 gate) と、 gate が起こす lens・契約の審査の lens・先撃ちの lens・行の審査の lens・memo の lens が別々に読む。 R-C6-1 は pipe show の表示だけが読む。 runner の起動には消費の上限の読み手が無く、 turn の上限の rules 行も無い。 便 524 本のうち消費の 4 値の和が 2,500 万以上は 13 本 (2.5 %) で、 gate の予算の照合で止まった形は verdict の写し 545 本のうち 5 本 (bead 4 つ・撃ち直しで上書きされるので下界) だった。

CTX3

現物 — user の許しを確かめる仕組みのうち、 席が字を渡せないのは発話の記帳と裁定の結びだけで、 そこにも穴が 3 つ在る

承認の口 pipe approve は、 席が渡した逐語が空でないことしか確かめず、 発話 event人が打った字の記録 と照らさない (fleet record も便の形の kind を actor human で書ける)。 発話の記帳の hook は prompt が model に読まれる前に逐語を書き、 seat ruling bind は記帳済みの発話と開いた台帳の問い台帳に立てる問いを結んで逐語を event から写すので、 普通の口では席が字を渡せない。 ただし、 席の Bash が器の hook の発話の記帳の枝を直に撃つ形を止める guard が見当たらず (穴 1)、 event log は席の権能 edit-outside の内側の file で (穴 2)、 どの発話を結ぶかは席が選ぶ (穴 3)。 裁定面の答えの口は経路 gui の発話を書くが、 承認の受理面ではない (C7・ADR-0087)。 --rules の差し替えは渡した file を丸ごと読み、 pipe gate は役割の guard の表に無く、 どの manifest を読んだかを event に残さない。 置き場は AI と同じ OS の user が書けるので、 改ざんを不可能にはできない。

CTX4

射程 — 許可を値の宣言でなく実行時の記録として読み、 対象の線・照合・単位・置き場・読み手・見え方を決める

C1 は規則の値を manifest 1 file に置き、 実行時はそこからだけ読むと定める。 本 ADR は、 許可を値の宣言でなく、 承認 event が便ごとに 3 クラス操作を開けるのと同じ実行時の記録として読み、 許可の値を manifest の値の宣言でなく裁定を出所に持つ実行時の記録として、 manifest の値と別の型で持つ (C10)。 C5 により、 新しく足す rules 行 2 本は新しい裁定 id裁定を指す番号 を要る。 C7・C7.2・A1 により、 上げの許しは対話面承認を受ける唯一の窓口の chat の経路の裁定に限り、 subscription の窓の token の消費も A1 の「使う」に入る側で読む。 A2 により、 構造の上限 (C4・C13) は作業ごとの許可の対象にしない。 C6.2 は便が R-C6-1 を越えたら器が止めると書くが現物は表示だけで、 停止は同じ epic の次の設計が持つ (推奨で進める既定の裁定 user 2026-09-28T00:54Z の適用)。 上限を外す (上限なし) 形は持たない (裁定 user 2026-10-01T00:38Z)。 要望は、 user が問いに短く許すと答えるだけで作業 1 つの上限が上がり、 設定 file の書き換えも binary の作り直しも要らない形である。 ADR を書く条件のうち 1 (C1・C7・C10 の解釈)・3 (event の kind と形・run dir の写し・rules 行の kind・跨版)・4 (却下の分岐) に当たる。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 6 本のものさしです。 既定の上限を守りとして残し、 ほかの作業の上限を動かさないこと。 user の許しを器が記録済みの言葉で確かめ、 AI の席が字を渡す口では許しを作れないこと。 許しを作業 1 つに結び、 同じ作業の撃ち直しのたびに user を呼ばず、 自然に切れること。 設定の書き換えも本体の作り直しも要らず、 検査の 2 つの読み手に同じ値が届くこと。 いつ誰の言葉で上げたかが後から見えること。 記録の置き場を 1 つに保ち、 足す前に消す物を名指すことです。

DR1既定の上限を、 見ていない間の大量消費を止める守りとして残し、 ほかの作業の上限を動かさない CTX1・CTX2
DR2user の許しを器が記帳済みの発話で確かめ、 席が字を渡して許しを作れない形にする CTX3・CTX4
DR3許しを作業 (契約) 1 つに紐づけ、 同じ契約の撃ち直しのたびに user を呼ばず、 期限か着地で自然に切れるようにする CTX1
DR4設定 file の書き換えと binary の作り直しを要らない形にし、 gate の照合と lens の 2 つの読み手に同じ値を届ける CTX1・CTX2
DR5作成と使用を event と一覧に出し、 いつ誰の言葉で上げたかを後から引けるようにする CTX1・CTX3
DR6真実の置き場を event log 1 つに保ち (C3)、 足す物の前に消す物を名指す (C17.2) — event の kind と形 1 つ・口 1・rules 行 2・RuleKind の分けの match 1・run dir の写し 1・hook の断り 1 を足し、 上げて戻す PR の対と、 pipe gate・pipe land・pipe resume に --rules を渡す応急の形を消す CTX1・CTX4
03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 9 つ並べます。 user の言葉に結んだ裁定を器が確かめてから記録に残す案 (選んだ案) と、 選ばなかった 8 つです。 選ばなかった案は、 設定を PR で上げて戻す今の前例・写しの設定を渡す応急の形を正式にする案・記録を別の置き場に置く案・承認の記録や別の画面の答えを根拠に加える案・上限を外す形も許す案・構造の上限も作業ごとに上げる案・許可を便 1 本ごとに結ぶ案・user の言葉に値の数字を求める案です。

OPT1発話に結んだ裁定を器が照らし、 event log の上限の許可作業 1 つだけの上限上げを名指された bead の gate と lens だけが読む採用

席が台帳の問いに bead・行・値・期限を字のまま書いて user に聞き、 user が chat で答えた発話を seat ruling bind で問いに結ぶ。 席が許可の口に bead・行・値・期限・裁定 id を渡すと、 器は閉じた 10 の照合を上から照らし、 通る周だけ event log に許可の event を 1 件書く。 その bead の便の gate の照合と lens だけが許可の値を cap に読む。 決め手は現物の読み (CTX2・CTX3)。

席が問いに「この bead の、 この上限を、 この値まで、 この時刻まで」と字のまま書いて user に聞き、 user が chat で答えた言葉を問いに結びます。 器は行・値・期限・裁定とその言葉・作業の着地を 10 の項目で確かめてから許可を記録に 1 件残し、 その作業の検査だけが許可の値を読みます。 上げが効くのは作業 1 つで、 AI の席が字を渡す口では許しを作れず、 設定も本体も触らず、 検査の 2 つの読み手に同じ値が届き、 作成と使用が一覧に出ます。 代わりに、 置き場の改ざんを不可能にはできず、 user が何に「よい」と言ったかまでは測れず、 最初の許可の前に本体の入れ替えが要り、 最初に効くのは検査役に渡す量の上限 1 行の 2 つの読み手だけです。

+ 利点

  • 上げが効くのは bead 1 つで、 ほかの便・host 全体の読み・CI の門は manifest の値のまま (DR1・DR3)
  • 根拠は hook が記帳した発話と結びの口が書いた裁定 event裁定を結んだ記録 だけで、 席が逐語を渡す口を根拠にしない (DR2)
  • manifest も binary も触らず、 gate の照合と lens の両方に run dir の写しで同じ値が届く (DR4)
  • 作成と使用が event・判定の文・pipe show・pipe dispatch ls に出て、 裁定 id から逐語を引ける (DR5)
  • 置き場は event log 1 つで、 上げて戻す PR の対と、 pipe gate・pipe land・pipe resume に --rules を渡す応急の形を消せる (DR6)

− 欠点

  • 置き場は AI と同じ OS の user が書けるので改ざんを不可能にはできず、 跡と一覧で見せるまでになる
  • 問いの後に user が別の話題で言った「よい」を結ぶ形と、 user が問いの本文を読んだかは測れない
  • event の kind を足すので、 最初の許可の前に PATH の binary の入れ替えが要る
  • MVP は gate.token_cap の 2 つの読み手だけで、 契約の審査・先撃ち・行の審査・memo の lens は manifest の値のままで、 ほかの作業ごとの行を対象に足すには読み手を足す後継の決定が要る
OPT2manifest を PR で上げ、 着地の後に戻す (今の前例)不採用

上げる PR・binary の入れ替え・戻す PR の対で、 上限を一時に上げる。 決め手は前例の重さと効く範囲 (CTX1)。

今の前例どおり、 設定の値を上げる PR を出し、 本体を入れ替え、 着地の後に戻す PR を出す案です。 新しい仕組みが要らず、 値の変更が裁定つきで設定に残り、 どの検査も同じ値を読む点で勝ります。 けれども、 便 1 本のために PR 2 本と本体の入れ替えが要って重く、 上げている間はほかの作業の上限も緩み、 戻し忘れを器が止めません。

+ 利点

  • 新しい仕組みが要らず、 値の変更は C5 の裁定 id つきで manifest に残る
  • CI の門と受付と gate が同じ値を読む

− 欠点

  • PR 2 本と binary の入れ替えが要り、 便 1 本のためには重い (DR4)
  • 上げている間はほかの便の上限も緩む (DR1・DR3)
  • 戻し忘れを器が止めない (DR3)
OPT3--rules の写しを正式の口にする不採用

席が写しの manifest を書いて pipe gate や列の 1 周に --rules で渡す今の応急の形を、 そのまま正式の手にする。 決め手は今日の実測 (CTX1・CTX3)。

今日の応急の形 (写しの設定を書いて、 command にその場で渡す) を、 そのまま正式の手にする案です。 すでに在って足す code が無く、 その command 1 つにだけ効き、 設定を変えずに済む点で勝ります。 けれども、 誰が許したかを器が確かめず、 どの設定を読んだかも残らず、 別の process で動く検査役には届きません。 列の手動の 1 周に渡すと起こす便の全部へ写り、 作業 1 つに絞れません。

+ 利点

  • 今すでに在り、 足す code が無い
  • command 1 つにだけ効き、 manifest を変えずに済む

− 欠点

  • 誰が許したかを器が確かめず、 どの manifest を読んだかも記録に残らない (DR2・DR5)
  • 読み手が 2 つの process に割れていて、 lens に届かない (DR4)
  • 列の 1 周に渡すと起こす便の全部へ写り、 作業 1 つに絞れない (DR3)
OPT4許可を event log の外 (host の面か state dir の別 file) に置く不採用

host の面 (host.toml) に作業ごとの例外の表を置く (ADR-0093 の型)、 または state dir に許可の file を足す。 決め手は真実の置き場の数 (CTX4)。

許可を、 host ごとの設定の面に例外の表として置くか、 状態の置き場に別の file を足して置く案です。 host の面には裁定つきの例外を置いた前例が在り、 記録の file の形を変えずに済む点で勝ります。 けれども、 host の面に作業の id が毎日出入りすることになり、 どちらの形でも記録の file と真実が 2 か所に分かれ、 作成と使用の順序が食い違いえます。

+ 利点

  • host の面には裁定つきの例外を置いた前例が在る
  • event log の形を変えない

− 欠点

  • host の面は host 固有の値の面で、 作業の id が毎日出入りし、 期限と着地で切る読み手を面の読みに足すことになる (DR6)
  • どちらも event log と真実が 2 か所になり、 作成と使用の順序が log と食い違いうる (DR6)
OPT5承認 event か裁定面の答えを根拠に加える不採用

pipe approve が書く承認 event、 または裁定面の答えの口が書く経路 gui の裁定を、 許可の根拠に加える。 決め手は根拠の偽れなさと承認の受理面 (CTX3・CTX4)。

便の承認の記録や、 別の画面 (裁定面) から来た答えも、 許可の根拠に加える案です。 照らす項目が少なく、 user が chat を開かずに許せる点で勝ります。 けれども、 承認の記録の言葉は AI の席が渡す字なので、 AI が許しを作れてしまいます。 裁定面は承認を受ける面ではなく、 承認を受ける面を 2 つにするのは憲法を変える側の話です。

+ 利点

  • 承認 event は便の不可逆操作の承認と同じ形で、 足す照合が少ない
  • 裁定面から答える user は、 対話の session を開かずに許せる

− 欠点

  • 承認 event の逐語は席が渡す字で発話 event と照らさないので、 席が許しを作れる (DR2)
  • 裁定面の答えの口は承認の受理面でなく (C7・ADR-0087)、 対話面を 2 つにする読みは憲法の改訂の側にある (DR2)
OPT6上限を外す (上限なし) 形も許す不採用

有限の値への上げに加えて、 bead 1 つの上限をまるごと外す許可も持つ。 決め手は持ち主の裁定 user 2026-10-01T00:38Z (CTX4)。

数の上げだけでなく、 その作業の上限をまるごと外す許可も持つ案です。 要る大きさが読めない作業でも 1 度の許しで済む点で勝ります。 けれども、 見ていない間の大量消費を防ぐという動機と真っ向からぶつかり、 問いに数を書かないので user が数を見て許す形になりません。 持ち主はこの形を持たないと裁定しました。

+ 利点

  • 要る大きさが読めない作業でも、 1 度の許しで撃ち直しを止めない

− 欠点

  • 見ていない間の大量消費を防ぐという動機と真っ向からぶつかる (DR1)
  • 問いの本文に数を書かせないので、 user が数を見て許す形にならない (DR2)
OPT7構造の上限 (C4・C13) も作業ごとに上げる不採用

file の行数や CI の時間などの構造の上限の行も、 bead 1 つに限って上げられるようにする。 決め手は A2 と CI の測り方 (CTX2・CTX4)。

file の行数や CI の時間など、 構造の上限も作業ごとに上げられるようにする案です。 そうした作業も同じ 1 つの口で許せる点で勝ります。 けれども、 構造の閾値を変えるのは憲法が grill と裁定を求める事項で、 作業ごとの許しでは代えられません。 また CI は main の設定で測るので許可が CI に効かず、 受付と CI の判定が食い違うだけになります。

+ 利点

  • 構造の上限に当たる正当な作業も、 同じ 1 つの口で許せる

− 欠点

  • 構造の閾値の変更は A2 の grill と裁定 id を要る事項で、 作業ごとの許しで代えられない (DR2)
  • CI の門は main の manifest で測るので許可が CI に効かず、 受付の余地と CI の門が食い違うだけになる (DR4)
OPT8許可を便 1 本ごとに結ぶ不採用

許可の単位を bead でなく便 1 本にし、 その便が終わったら切る。 決め手は撃ち直しの回数 (CTX1)。

許可を作業 (bead) でなく、 便 1 本ごとに結ぶ案です。 効く範囲がもっと狭く、 便が終わればそれで切れる点で勝ります。 けれども、 同じ約束の撃ち直し (追随・再 gate・新しい便) は同じ大きさの差分に何度も当たるので、 撃ち直すたびに user を呼ぶことになります。

+ 利点

  • 効く範囲が bead より狭い (DR1)
  • 便の終わりで切れるので、 期限を置かなくても切れ目が在る (DR3)

− 欠点

  • 同じ契約の撃ち直し (追随・再 gate・新しい便) は同じ大きさの diff に何度も当たるので、 撃ち直しのたびに user を呼ぶ (DR3)
OPT9user の発話に値の数字を含めることを求める不採用

許可の口が、 結んだ発話の逐語に許可の値の数字が在ることも照らす。 決め手は要望との釣り合い (CTX3・CTX4)。

許可の口が、 結んだ user の言葉の中に許可の値の数字が在ることまで確かめる案です。 問いの後に別の話題で言った「よい」を結ぶ穴を詰められる点で勝ります。 けれども、 user が許すたびに数字を打つことになり、 短く許すと答えるだけで済む形を求めた要望に反します。 この穴を詰める次の手として残します。

+ 利点

  • 問いの後に user が別の話題で言った「よい」を結ぶ形 (穴 3 の残り) を詰められる (DR2)

− 欠点

  • user が許すたびに値の数字を打つことになり、 短く許すと答えるだけで済む形を求めた要望に反する (CTX4)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 席が問いに bead・行・値・期限を字のまま書いて user に聞き、 user が chat で答えた言葉を問いに結びます。 器は、 行・値・期限・裁定とその言葉・作業の着地を 10 の項目で確かめてから、 その作業 1 つの許可を記録に 1 件残します。 その作業の検査だけが許可の値を読み、 ほかの作業は設定の値のままです。

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなること 4 つと、 代わりに引き受けること 6 つです。 良くなるのは、 正当な作業が PR なしでその作業だけ通れること、 AI の席が字を渡す口では許しを作れず許可から user の言葉をたどれること、 検査の 2 つの読み手が同じ値を読むこと、 効いている許可と使った検査が見えることです。 引き受けるのは、 置き場の改ざんを不可能にはできないこと、 user が何に「よい」と言ったかまでは測れないこと、 本体の入れ替えの手番、 最初は 1 行の 2 つの読み手だけに効くこと、 runner の消費はまだ縛らないこと、 撃ち直しは今の手のままであることです。

✓ 良い結果

  • ●正当な作業が上限に当たったとき、 PR も binary の入れ替えも無く、 その bead の便だけが user の許した値で gate を通れる
  • ●席が逐語を渡す口では許しを作れず、 許可は裁定 id から user の逐語へたどれる
  • ●gate の照合と lens が同じ値を読み、 pipe gate・pipe land・pipe resume に --rules を渡す応急の形が無くなる (列の手動の 1 周に渡す --rules は本 ADR の断りの外で、 扱いは後継の決定が持つ)
  • ●効いている許可と、 許可の値を使った gate の周が、 一覧と event で見える

⚖ トレードオフ・代償

  • ●置き場は AI と同じ OS の user が書けるので改ざんは不可能にならず、 器が持つのは普通の口の閉じ・跡・一覧まで (それ以上は別の OS の user か署名が要る)
  • ●問いの後に user が別の話題で言った「よい」を結ぶ形と、 user が問いの本文を読んだかは測れない (発話に値の数字を求める照合を次の手として残す)
  • ●event の kind を足すので、 最初の許可の前に PATH の binary を入れ替える手番が要る
  • ●MVP は gate の 2 つの読み手だけで、 契約の審査・先撃ち・行の審査・memo の lens と、 ほかの作業ごとの 6 行は後の行に残る (行を対象に足すには、 その行の読み手と SRS FR111 の直しを足す後継の決定が要る)
  • ●runner の消費は縛らず (R-C6-1 は表示だけ・turn の上限は無い)、 動機に一番効く守りは同じ epic の次の設計を待つ
  • ●許可の記帳は便を自動で測り直さず、 撃ち直しは席の今の手のまま
