設計判断記録 (ADR) scribe2 — 席の役割と便の配送 (orchestrator / dispatcher)

席の役割は orchestrator 1 つで、 便の起動・着地・merge は器の dispatcher が行う (planner / 管理席の 2 役割と席の自律機能を廃止・SessionStart の注入は短い 1 本・session を跨ぐ記憶は台帳・runner には憲法の散文を注入しない)

席は 2 役割 (planner / 管理席) と、 それを保つための自律機能 (作業記憶の退避と復元・管理 tick・cap guard と強制 cycle・heartbeat・statusline・席間の連絡・hook 集合の食い違いの検知) を 1 週間で積み、 席 1 つの起動に 256 行 / 20,616 字を注入するに至った (うち憲法の全文が 74%)。 本 ADR は席の役割を orchestrator 1 つ (人と話す唯一の席) にし、 便の起動・着地・merge を器の dispatcher に移し、 席の自律機能を削除する。 session を跨ぐ記憶は台帳 (metadata / status / 依存) が構造で持ち、 文脈の圧縮は Claude Code の /compact で足りる。 SessionStart の注入は約 11 行に縮み、 runner には憲法の散文を 1 行も注入しない。

この判断が約束すること (1 文サマリ)

席の役割を「人と話す席」1 つ（orchestrator）にし、便を起こす・着地させる・merge する仕事は器の dispatcher が台帳から読んで行います。席が自分を保つために積んだ仕組み（作業記憶の退避と復元、管理 tick、上限の guard と強制 cycle、heartbeat、statusline、席どうしの連絡、hook 集合の食い違いの検知）は消し、session を跨ぐ記憶は台帳の構造に置き、文脈の圧縮は Claude Code の /compact に任せます。session の開始で注入する文は約 11 行に縮み、実装役には憲法の文章を注入せず、書いてよい file と撃ってはいけない command を hook で止めるだけにします。消してから dispatcher を足す順で進めます。

01 背景 / なぜこの判断が要るか

いま何が問題か (席が自分を保つために機構を積み、 注入が憲法の全文になった)

なぜこの判断が要るのかを、現物の計測と 2 本の調査と裁定から説明します。席 1 つの起動で 256 行の文を注入し、その 4 分の 3 が憲法の全文でした。planner の指示文 14 行のうち、文でしか運べない役割の特性は 5 行だけで、7 行は管理席との中継や復元の手順でした。席を保つ機構（退避と復元、tick、guard、heartbeat、連絡）は 1 万行を超え、契約に溜まる文の 6 割は「機械が引ける事実の写し」と「門を黙らせる防御文」でした。無いのは、席を 1 つにして機構を消すという決定です。

CTX3

調査 — なぜ席に機構と散文が溜まったか (prose-root-cause §1〜§3・role-injection §1)

契約 5 本 25,208 字の分類 (prose-root-cause §1・母集団 5 本): repo から機械で引ける事実の写し 36% / 門と lens を黙らせる防御文 25% / test を撃てば分かる事実 15% / 人の意図 16% / 手順 8%。 散文が伸びた根は「同じ事実を設計 § → 契約表の行 → 台帳の acceptance → 契約 file の 4 か所に写す構造」で、 写しの食い違いを lens が指し、 planner が次の焼き直しで防御文を足す輪が 1 日ごとに回った (同 §2・防御行の字数は 09-10 → 09-16 で 6 倍)。 審査の非 PASS 54 件 (母集団 161 run) の型は、 契約の中の自己矛盾 18 / verify が done を測れない 18 / write-set の閉包の外 10 / § との不一致 7 / 材料不足 1 で、 「散文が足りない」型は 0。 runner の質問 20 件は 20 件とも write-set の閉包の話で、 「何を作るか分からない」は 0 (同 §3)。 席の側も同型で、 席が黙る・文脈が溢れる・口座が上限に当たる、 の 1 つ 1 つに機構 (tick・guard・cycle・backoff・強制の窓) を足してきた。 一方 Claude Code の仕組み (role-injection §1・verified): 作法 file は system prompt ではなく user message として届き、 途中で注入した文は圧縮で要約に飲まれ、 圧縮のたびに原文が戻るのは SessionStart の hook だけ。 plugin の hooks.json から system prompt 層へ書く正規の経路は無い。 したがって注入の強さは置き場所ではなく「短さ・席ごとの限定・機械が測った値で穴を埋める・圧縮で戻る」の 4 つから来る。

CTX4

裁定 — 管理席を消し、 席の自律機能を消し、 注入を短くする

CTX5

憲法の向き

C7 / R-C7-1 は承認を受け取る対話面をちょうど 1 つと定め、 C7.2 は承認 event が逐語を運ぶ。 A1 / A4.2 は 3 クラス (消す / 出す / 使う) と不可逆の操作の前に user へ聞くことを求め、 機械の面をほとんど持たない (人と話す席にだけ文で運ぶ価値がある)。 N2 / C1.2 は散文にしか無い規則を規則と認めず、 C14 は規律を文書と manifest の 2 面で持つ。 C2.2 / C3 は設定と状態の置き場を manifest と 1 つの DB に限る (席の退避物・直命の表・heartbeat の file は状態の置き場を増やしていた)。 C9 は席の停止の検知と再開を器に求め、 その面は管理 tick と cycle が担っていた = 本 ADR は C9 の解釈 (席 = orchestrator 1 つ・便の driver は dispatcher が起こし直す) を持つ (ADR を書く条件 1)。 C16 / C16.2 は in-loop の guard を要求し、 write-set guard・command guard・role guard がそれである。 C17 (ADR-0044・proposed) は機構を足す提案に先に消すものを名指させる = 本 ADR は「消す → dispatcher」の順を持つ。 憲法の順位 2 位は増殖の防止。

03 検討した選択肢 / 5 つの形

それぞれの利点と欠点を並べる

候補を 5 つ並べます。席を orchestrator 1 つにして自律機能を消し dispatcher に起動と着地を移す案、2 役割を残して文だけ削る案、作業記憶を器の機構でなく文書として残す案、役割を project の作法 file にだけ書く案、そして介入の印と観測を備えた dispatcher を先に作る案です。

OPT1席の役割は orchestrator 1 つ・席の自律機能は削除・便の起動と着地と merge は最小の dispatcher・SessionStart は約 11 行・runner には憲法を注入しない採用

Role は Orchestrator の 1 variant (閉じた enum のまま)。 権能は answer / approve / go / edit-design-intent / edit-design-doc / edit-contract / edit-outside + tests/ に限った edit-code (落ちる歯 = 実行できる acceptance を書く)。 launch / merge は dispatcher (機械) が持ち、 relay は消える。 作業記憶・tick・guard・cycle・heartbeat・statusline・席間の連絡・hook 集合の検知は削除し、 /compact と台帳で代える。 順序は「消す → dispatcher」。

人と話す席を 1 つだけにし、便を回す仕事は機械に渡し、席が自分を保つために積んだ仕組みを全部消す案です。文脈が溢れたら Claude Code の /compact を使い、次の session は台帳を読めば続きが分かるようにします。session の開始で注入する文は約 11 行に減り、実装役には憲法の文章を渡さず、書いてよい file と撃ってはいけない command だけを hook で止めます。

+ 利点

  • src 7,215 + 歯 4,240 + skill 279 ≒ 11,700 行と rules 行 10 本と skill 2 本が消え、 状態の置き場 (退避物・直命の表・heartbeat・tick-stamp・強制の印) が消える (DR2 / C2.2 / C3)
  • 人と話す席が 1 つになり、 中継 (planner ↔ 管理席) の手順 7 行と席間の連絡の経路が要らなくなる (DR1)
  • 注入は席の同一性 3 行 + 憲法の効く部分 5 行 + 役割の特性 3 行に縮み、 runner は 0 行 (DR5)。 残る規律は hook と行が持つ (DR3)

− 欠点

  • 席の停止の自動検知と自動の立て直し (C9 の席の面) は消え、 orchestrator の再起動は user が器の口 (seat launch) を撃つ。 便の側は dispatcher の driver の起こし直しが担う
  • SRS の FR 20 本超が廃止候補になり、 改訂は /folio-architect の段で user が行う (本 ADR は候補を列挙するだけ)
OPT22 役割 (planner / 管理席) を残し、 指示文と憲法の注入だけを削る不採用

注入は 20 行に入る (調査 §2.4 の含意) が、 中継・報告・席間の連絡の 7 行と、 管理席が便を見守るための tick・heartbeat・cycle は残る。 CTX3 の輪 (席が黙る → 機構を足す) の根は 2 席の間の中継そのもので、 文を削っても機構は減らない。

席は 2 つのまま、注入する文だけを短くする案です。手軽ですが、席どうしの中継と、席を見守る仕組みがそのまま残ります。溜まった仕組みの根は「席が 2 つあって、片方がもう片方を見守る」形そのものなので、文を減らしても仕組みは減りません。

+ 利点

  • code の変更が小さい (雛形 2 枚の書き換えだけ)・既存の ADR-0016 / 0022 の形を保つ

− 欠点

  • 機構 11,700 行と rules 行 10 本が残る (DR2 に反する)・管理席の中継が残るので runner の質問と gate の判定は席を経由し続ける (ADR-0034 §1 の待ちが残る)
OPT3作業記憶を器の機構でなく文書 (skill の散文と markdown の退避物) として残す不採用

前の版の形。 退避物は規則の置き場ではないと決めていた (作業記憶の語彙・N2) が、 pointer の無い命令行が暫定行として溜まり (ADR-0018 §2.2 の対策が要った)、 復元の brief の 5 slot (FR67) が手順として指示文に載った。 台帳が metadata / status / 依存を構造で持つなら、 文書の退避物は台帳の写しになる。

作業の記憶を器の仕組みでなく、文章の file として残す案です。前の版がこの形で、文章の中に「命令」が溜まって規則のように振る舞う問題が出ました。台帳が状態と依存を構造で持てば、文章の記憶はその写しになるだけです。

+ 利点

  • 器の code は要らない・/compact の要約より多くの文脈を運べる

− 欠点

  • 散文の命令行が規則になる穴 (N2・台帳 s2-07l.176 の型)・台帳と退避物の 2 か所に状態を持つ (C3 / DR2)・写しの食い違いが lens の finding と防御文を生む (CTX3 の輪)
OPT4役割の規律を project の作法 file (CLAUDE.md) にだけ書き、 hook の注入も guard も持たない不採用

公式 docs (調査 §1.1 / §1.2・verified): 作法 file は system prompt の後ろの user message として届き、 遵守は保証されない (advisory)。 圧縮の後に原文が戻るのは SessionStart の注入だけで、 作法 file は project root の分しか戻らず、 席ごとに内容を変えられず、 機械が測った値 (target・権能の行・台帳の現在地) で穴を埋められない。 執行力は hook にしか無い (「hooks are deterministic」)。

役割の決まりを project の作法 file に書くだけで済ませる案です。作法 file は「お願い」として届くもので守られる保証が無く、席ごとに内容を変えられず、機械が測った値を埋め込めません。文脈を圧縮した後に元の文がもう一度入るのは session 開始の hook だけです。止める力は hook にしか無いので、この案は弱すぎます。

+ 利点

  • 器の code が要らない・登録の無い session にも同じ文が載る

− 欠点

  • 執行力が無い (DR3・C16 の in-loop guard を欠く)・席ごとに絞れず穴も埋まらない (DR5)・散文の規則になる (N2)・置き場所の強さの差は docs に定量が無い (「hook だから強い」とも言えないが、 作法 file は明確に弱い側)
OPT5介入の印 (first / hold / release) と観測 (dispatch ls・rebrief の DATA) を備えた dispatcher を先に作り、 その後に席を減らす不採用 (保留)

ADR-0034 §2 の全体像。 だが介入の印は「planner が列の順を動かす口」で、 orchestrator 1 席なら priority の書き換え (台帳) で足りる可能性が高く、 観測の DATA は rebrief (削除対象) に載せる設計だった。 先に機構を足すのは C17 と CTX4 の「削る側」に反する。 最小の dispatcher (台帳から ready の列を導き、 起こし、 着地させる) で始め、 印と観測は必要が実測で出たときに足す。

便を回す機械に「順番を動かす印」と「いま何を待っているか見る画面」を最初から付ける案です。席が 1 つになれば順番は台帳の優先度で動かせ、見る画面は消す予定の仕組みの上に載っていました。先に足すのは「削る側」の向きに反するので、最小の形で始めて、要ると分かってから足します。

+ 利点

  • ADR-0034 の設計 (dispatcher.md §2〜§6) をそのまま使える・急ぐ便の扱いが最初から在る

− 欠点

04 採用した判断 / どの形を選ぶか

選んだ形と、 それが守る要件 (cross-doc 照会)

選んだ案と、それが要件書のどの要件を支えるかを示します。席の役割は orchestrator 1 つ、便の起動・着地・merge は器の dispatcher、席の自律機能は削除、SessionStart の注入は約 11 行、runner には憲法の散文を注入しません。残すのは write-set guard・command guard・role guard・3 クラスの承認 event・口座の選定と役割の実効の口座です。改稿後の配送構造（FR30）、権能の行（FR41）、dispatcher の起動と着地（FR68）に対応します。

この判断で良くなることと、代わりに引き受けることです。1 万行を超える機構と rules 行 10 本と skill 2 本が消え、人と話す席が 1 つになり、注入は約 11 行に縮み、便は着地の直後に次が起きます。代わりに、席の自動の立て直しが無くなること、要件書の 20 本超の改訂を user の手で行うこと、削除の便が着地するまで dispatcher を起こせないこと、消した後に「要る」と分かった機構は実測を添えて足し直すことを引き受けます。
