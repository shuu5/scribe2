§1. Context

便が 1 往復する間に、 器が構造として持っているのは受付の交差の判定・実装役の書ける範囲の見張り・実装後の審査・着地の順序だけで、 残りは席の判断と文章と手写しでした。 なかでも契約は同じ内容を 3 回写していました——設計 doc の文章、 台帳の受入条件の文章、 そして管理席が手で書く契約 file です。 写すたびに落ちが出て、 書ける範囲の抜けが 5 回、 設計そのものの穴が 2 回、 実装が終わってからの審査で初めて見つかりました。 台帳の側には、 設計の中身を持ったまま行き場のない memo が 40 本たまりました。 着地の後始末 (押す・CI の結果を確かめる・台帳を閉じる) も席の手順で、 「着地したのに閉じていない」「閉じたのに CI が赤」のずれを目で見て直していました。 加えて、 この器を別の project で使う段になって、 その project の要件の一覧がこの repo と同じ形とは限らないことが分かりました。 user は 3 つの論点を裁定し、 契約の正本を設計 doc の機械が読む表へ移し、 実装前の審査を必須とし、 着地の終端を器に持たせることを決めました。 この記録はその形を決めます。

記録時点 (2026-09-13) の現物: 便の一周の手順 15 のうち器が構造で持つのは 5 つ (受付の排他 FR39・実装役の write-set guard FR20・gate FR9・着地の CAS と順序 FR12 と ADR-0021 §2.5)。 契約は 3 段の写し (設計 doc の散文 → 台帳の受入条件の散文 → 契約 file の手写し) で、 write-set の落ち 5 例と設計の inline 2 件がそれぞれ別の段で生まれた。 台帳は open 57 件・うち memo 51 件で、 設計本文を持つ memo は 40 件。 契約 file は受付が --contract で受け取る手書きの入力 (ADR-0004 §2.3) で、 その parser が受理する array-of-tables は閉じた 2 種・空の配列を拒み・schema 版の印を必須とする。 契約 file の必須欄は 9 で、 設計 doc 側の欄との共通は 5 (1 対 1 ではない)。 台帳への口は復元の読み取り専用 1 点のみで write は無い (ADR-0018 §2.1 / §2.4)。 段の列に審査は無く、 受付の次は spawn。 着地は CAS で終わり終端を持たない。 対象 repo の宣言 file の key は必須 3 + 任意 1 (ADR-0010 §2.1・ADR-0021 §2.6)。 SRS の最大 id は FR46 / AC20 / NFR6。 consumer 第 1 号の要件面は YAML で、 本 repo の design-intent/spec/srs.html に相当する file を持たない (既定 path を固定すると、 その repo の契約は全行が fail-closed で断られる)。 着地の後始末 (押す・CI の照合・記帳・close・binary の入れ替え) は管理席の手順の散文にしかない。

憲法の向き: C15 は台帳を task と裁定だけに限り、 C15.2 は規律との結線を id の参照だけに限って欠落を lint で拒む。 C16 は逸脱を編集時に止め後段の検証で代替せず、 C16.2 は in-loop guard を極性一覧に載せる。 C2 は選択・除外・routing を 1 enum の 1 関数とし、 順序を宣言順から取り、 新しい理由を variant 1 つで表す。 C2.2 は env を読まず新しい env seam を作らない。 C3.4 は完了条件を 1 つの enum の値に限り、 待ちの実装を 1 つに限る。 C10 は宣言値・実測値・導出値・有効値を型で分け、 宣言値は実測を経てだけ有効になる。 C10.3 は配線の無い設定を CI が拒む。 C1 / C5 は規則の値を manifest の行に裁定 id 付きで持ち、 C1.2 は生成文書に手書きの規範文を 0 とする。 C14 は規律を文書と manifest の 2 面に限る (契約表はそのどちらでもない入力データであり、 ADR-0010 §2 の前置が宣言 file について、 ADR-0017 §2.3 が口座の行について採った読みと同じ)。 N3 は host 固有の値で分岐しない。 N2 は散文にしか無い規則を規則と扱わない。 N1 は回復不能な削除を拒む。 A3 は依存の増減に承認を要し、 A1 は「出す」を対話面の承認に掛ける。 user の裁定 (2026-09-13・対話面・planner 席): 要旨は decided-by のとおり。

§2. Decision

§2.1 契約の正本は tracked な設計 doc の機械が読む表の 1 行。 欄の集合の正本は core の型で、 置き場は 2 形・読み手は拡張子で決める

契約 1 本の正本は、 設計 doc の末尾にある「機械が読む区間」の表の 1 行です。 表の書き方は器がすでに読んでいる規則の file と同じ狭い TOML で、 表の種類を 1 つだけ足します。 行がどんな欄を持つかは文章ではなく器の型が正本で、 器がその一覧を 1 枚の file に描き出し、 その file と器の出力が食い違えば CI が落とします——同じ一覧を文章に写すと必ずずれるからです。 契約の名前は「設計 doc の名前 # 行の名前」で、 doc の名前は一度決めたら変えません (file を改名しても名前は残ります)。 表の置き場は 2 つ許します——設計 doc の中の区間と、 後で別の道具が作る単独の file です。 どちらかは file の拡張子で決め、 知らない拡張子は「たぶんこちら」と倒さず断ります。 表は「規律」ではなく「入力のデータ」です。

器 SHALL 契約 1 本の正本を、 対象 repo の tracked な設計 doc が末尾に持つ機械が読む 1 区間 (marker 形は既存の憲法区間と同じ・設計 doc 1 本に区間は 0 か 1 つ) の表の 1 行とし、 台帳の受入条件と手書きの契約 file を正本から降ろす。 表の形式 SHALL rules manifest と同じ TOML subset (ADR-0004 C7.2・user の逐語を伴う) とする。 本 ADR 自身は契約表の行を 1 つも足さず、 最初の行を tracked な main へ着地させる便 SHALL その承認を先に得る (ADR-0017 §2.3 が「確認してから行う・本 ADR は行を足さない」の順序で置いた先例と同じ)。 2026-09-13 の裁定 Q1 は正本の置き場の裁定であり、 公開面の情報が増えることの承認とは別に扱う。

§2.2 器が base の表から契約 file を生成する。 手書きの契約 file は受けず、 台帳は pointer 1 行と adapter 1 つに閉じ、 欠落は doctor の lint が名指す

受付は「この設計 doc のこの契約」と台帳の番号と対象の repo を受け取り、 器が対象 repo の最新の main から表の行を読んで、 便の契約 file を作ります。 手で書いた契約 file を渡す口はなくします——残すと写しが元に戻るからです。 台帳の側に残るのは、 題・状態・裁定・そして設計 doc を指す 1 行だけです。 契約の直しは台帳ではなく設計 doc の PR で行い、 実装役の質問への回答で書ける範囲を広げる口は作りません。 器が台帳に触る口は 1 つにまとめ、 読みは読み取り専用、 書きは「閉じる」1 種だけです。 台帳が正しい形になっているかは、 器の点検 command の項目として数えます (件数と母数を同じ行に出します)。 CI は非公開の台帳に届かないので、 この点検は CI ではなく点検 command と管理の tick が担います。 すでに起票してある契約は今の形のまま流し、 新しい契約から切り替えます。

受付 SHALL 入力を設計 pointer (設計 doc の path と契約 id・--design)・台帳 id・対象 repo とし、 base (対象 repo の HEAD) の tree から行を読んで便の契約 file を生成する。 器 SHALL NOT 手書きの契約 file を受ける引数 (--contract) を持つ (口の廃止は跨版の CLI 契約を壊す変更であり外形 snapshot が動く・C12.5)。 生成時に固定値を埋める欄 SHALL 導出値であって宣言値ではない (C10)。 生成された契約 file SHALL 既存の受付の検査 (ADR-0009 §2.2・ADR-0010 §2.3) の対象であり続ける (基準と極性は不変・対象が手書き入力から生成物へ移るだけ)。 台帳の bead SHALL 題・状態・裁定の記帳・設計 pointer 1 行の受入条件だけを持ち (C15)、 器 SHALL NOT 台帳の本文を契約の入力にする。 契約の改訂 SHALL 設計 doc の改訂 (PR) と再受付で行い、 器 SHALL NOT 回答が write-set を広げる口を持つ (写しは生成物であり手で直さない・C16・§2.7 (vi) (vii))。 回答 SHALL 逐語のまま実装役へ届く形と記録の型を変えない (FR32・ADR-0016 §2.2 は不変で、 回答の効き目が「契約を変える」から「契約の読み方を補う」へ狭まる)。 器が台帳へ触る口 SHALL core の module 1 つ (ledger) に閉じ、 読み SHALL 読み取り専用の子 process・書き SHALL close 1 種だけとする (起票・受入条件の編集・裁定の記帳は席の仕事)。 台帳の binary の名 SHALL 定数・path SHALL PATH 解決とし、 env の seam を作らない (C2.2)。 台帳の子 process の待ち SHALL ADR-0018 §2.4 が規範として据え 同 §4 が予定行とした seat.ledger_timeout_s を使い、 第 2 の行を新設しない (C1・行 id の接頭辞は据え置く＝使い手が席の復元から器の終端へ広がるだけで、 改名は行の追加と廃止になる)。 器 SHALL NOT 台帳の binary を差し替える引数を持つ (歯は PATH に置いた偽の binary で代える・ADR-0017 §2.2 の CLI 引数の形は引数の面を増やすため採らない)。 復元の subcommand (ADR-0018 §2.4) SHALL 同じ module を通し、 第 2 の読み口を作らない (C2)。 台帳の binary を子 process で呼ぶこと自体の A3 の扱いは同 §2.4 が持ち、 本 ADR は write の範囲 (close 1 種) を 2026-09-13 の裁定 Q3 で受ける。 close SHALL 器の行為であり席の権能ではない (ADR-0022 §2.2 の権能の型に variant を足さない)。 器 SHALL 台帳の lint を doctor の項目 1 行として持ち (C3.2)、 設計 pointer が解けない open な契約と、 設計の中身を持つのに pointer を持たない memo を名指し、 件数と母集団を同じ行に出す (0 件と「測れていない」を弁別する)。 CI SHALL NOT 台帳の lint を撃つ (private な台帳に届かない)。 C15.2 の「欠落を lint が拒む」 SHALL doctor の項目と管理の tick の pointer 注入 (FR43) で満たす読みとし、 本 ADR はその読みを記録する。 台帳の lint SHALL NOT guard として極性一覧に載る (行為を止めうる判定を返さない・ADR-0014 §2.1 の定義・計測を極性一覧に載せない ADR-0017 §2.2 に次ぐ 2 例目)。 memo の判定が台帳の本文の字面を入力にすること SHALL 限界として受け入れる (C3.3 は席の状態の判定入力の条であり、 ここでの判定は行為を止めない名指しである・ADR-0013 §2.3 の作法で限界を主張と同じ場所に置く)。 既に起票済みの契約 SHALL 今の形のまま流し、 本 ADR の land 以降に起票する契約から新しい形に切り替える (この分界が lint の母集団の起点になる)。

§2.3 書いてよい file の集合は、 行が宣言した閉じた型から器が導く。 導出は下界であり、 その限界は歯が固定する

行が「この閉じた一覧に値を 1 つ足す」と宣言したら、 器が対象 repo の最新の main を読んで、 その型を持つ file を集めます。 集め方は 4 つの形 (値を組み立てている所・網羅的な分岐の枝・件数を固定している所・一覧そのものの宣言) で、 文字の並びだけを見ます。 構文を解析する外部の部品は足しません。 読めない file や壊れた区間があれば、 通さずに断ります。 この集め方は「少なく見積もる」側で、 別名で書かれた形は拾えません。 拾えないことを歯 (test) で固定して、 限界を器の中に残します。 足りないときは、 足りない file を全部並べて断ります (1 つ目で止めません)。

器 SHALL 行が宣言した閉じた型 (touches の列) と base の tree から、 その型を運ぶ source file の集合を導出する。 導出 SHALL 字面の走査で行い (4 つの面・pure 関数・I/O は呼び手・property 検査を掛ける面・C12.7)、 器 SHALL NOT 構文木の crate を足す (A3 の依存を増やさない側の決定であり、 実行時の外部依存 0 の NFR3 に触れない)。 読めない file と区間の parse の失敗 SHALL 違反として扱う (fail-closed・NFR4)。 導出の結果 SHALL 下界であることを型と歯に残し (別名で現れる形を拾わない)、 限界 SHALL 本 ADR と歯に明記する (ADR-0013 §2.3)。 導出した集合が write-set に含まれない周 SHALL 契約を断る既存の閉じた型 Refuse に variant 1 つ (WriteSetIncomplete) を足して断り (ADR-0019 §2.1 の交差の理由と同じ enum・同 §2.1 の交差の定義と拒否の関数は不変)、 足りない file を全部名指す (1 件目で止めない・FR18 と同じ「全件・黙って落とさない」)。 閉包の不足の判定 SHALL 表の検査の境界 (§2.1 の 1 関数・極性一覧の表の検査の行) が持ち、 受付 SHALL その結果を Refuse の 1 variant として返す (判定の境界は 1 つ・返す enum も 1 つ・ADR-0019 §2.1 の関数 1 本に 2 つ目の判定を足さない)。 CI の入口と受付 SHALL 同じ導出関数を撃つ (C2・§2.1)。 下界の外に落ちた構築点 SHALL 実装役の質問 (FR31) として出し、 直しは §2.7 (vii) のとおり設計 doc の改訂に落とす (運用の注意書きにしない・N2)。

§2.4 受付の直後に契約の審査の段を置く。 飛ばす口は作らず、 測り切れない周は通さない

受付を通った便は、 実装役を起こす前に審査役が 1 回読みます。 読むのは 3 つ——生成された契約 file、 その契約が実装する設計の節、 そして要件の本文です。 差分は渡しません (まだ何も書かれていないからです)。 判定は便の段として記録に残り、 合格でない便は実装役を起こしません。 審査を飛ばす引数や環境変数は作りません。 予算を超えて読み切れなかった周は「合格」ではなく「測れなかった」に倒し、 その便も起こしません。 直すときは設計 doc を直して PR を通し、 もう一度受け付けます。 承認が要る便 (消す・出す・使う や閾値に触れる便) の関門は、 これまでどおり実装役を起こす直前に置きます。

器 SHALL 段の閉じた型に variant 1 つ (Stage::Reviewed) を足し、 その宣言順 SHALL 受付の段の直後とする (適用順は宣言順から取り、 順序を散文で書かない・C2・中間への挿入は ADR-0016 §2.2 に次ぐ 2 例目で ADR-0013 §2.2 の判別子順の歯が効く面・event の行は段の名を持つので schema 版は据置・ADR-0004 §2.1 の機構欄が写した段の件数は型の宣言に劣後する)。 器 SHALL 受付の直後に審査役を 1 回起こし (既存の 1 つの口に tracked な雛形を 1 枚足すだけで口を増やさない・起動形は ADR-0011 のまま)、 穴 SHALL 3 つ (生成した契約 file・設計の節の本文・要件の本文) に限り、 diff を渡さない。 判定 SHALL 既存の 3 値とし、 便の dir の file (実装後の審査の verdict と同型・一時 file から rename の atomic 書き) と段の event に残す。 spawn と resume の入口 SHALL 審査の段にあり、 判定が合格の便だけを実装役へ進め (FR4 の文は変えない・順序は本 ADR と設計 doc が持つ)、 合格でない便 SHALL 終端とし、 live な便の定義 (ADR-0019 §2.1) の終端に「審査の段で verdict が合格でない」を足す (§2.7 (viii)・判定は段の網羅 match のままで、 新しい段の arm が compile で強制される)。 器 SHALL NOT 審査を飛ばす引数・環境の口を持つ (C16・N2: 飛ばせる門を作って運用で埋めない・口の不在を usage が断る)。 予算 (NFR1) を超えた周 SHALL 合格ではなく「測れなかった」に倒す (FailClosed・FR9 の極性)。 承認の関門 (契約が持つ class の印) SHALL 審査の後・実装役の起動の直前に置き (読むだけの段を先に通し、 ADR-0008 §2.2 の「spawn の手前で Blocked」の位置を動かさない)、 承認の対話面と逐語の記帳先 SHALL 不変 (ADR-0022 §2.5・FR22)。 実装後の gate の 4 段 (ADR-0021 §2.6) SHALL 不変で、 本段はその前段ではなく受付の直後に立つ。

§2.5 着地の終端 (押す・CI の照合・台帳の close) を器が持つ。 着地の事実の正本は器の記録で、 commit の trailer はそこからの導出面

着地した便は、 そのあと器が 3 手を続けます——遠隔へ押す、 押した commit の CI の結果をその commit の id で確かめる、 台帳を 1 行の理由付きで閉じる。 CI が緑でなければ閉じません。 「結果を測れなかった」を緑と読み替えることもしません。 待ち時間の上限は規則の行に置き、 その行には裁定の印が付きます。 3 手はどれも便の記録に型付きで残ります。 「いつ何が着地したか」の正本はこの記録で、 commit の末尾に付ける 2 行 (どの契約か・どの要件か) は、 器が同時に書く写しです——外の道具が読む口はこの 2 行だけで、 2 行が無い commit は「まだ分からない」であって「まだ着地していない」ではありません。 途中で失敗した便は、 終端だけをやり直せます (何度撃っても同じ結果で、 着地そのものは巻き戻しません)。 器が自分の repo へ押すことは「出す」には当たりませんが、 それを理由に契約表を公開の場に置く判断 (§2.1) を素通りさせることはしません。

器 SHALL 着地 (既存の CAS・ADR-0021 §2.5) の後に 3 手 (遠隔への push・着地 commit の CI の結果の照合・台帳の close) を持ち、 各手を既存の終端 event の detail で弁別する typed な記帳とする (event の schema 版は上げない・FR12)。 CI の照合 SHALL 完了条件の閉じた型に 1 値 (Completion::CiResult) を足し、 唯一の待ちの実装だけが受ける (任意の述語を受ける入口を作らない・C3.4)。 結果 SHALL 既存の verdict と同型の閉じた 3 値の型で受け、 測れない周を成功に読み替えない (C10)。 待ちの上限 SHALL rules 行 1 本 (pipe.ci_wait_s・裁定 id 付き・C1 / C5) とし、 行が無い周 SHALL 規則の error とする (行は本 ADR ではなく契約が manifest に書く・ADR-0018 §4 の予定行と同じ扱いで、 C14.2 の相互参照は行が manifest に在って初めて成立する)。 成功でない周 SHALL NOT close する (FailClosed・記帳して非 0 で終わる・C12.6「main は常に緑」)。 器自身が撃つ子 process (遠隔の操作・forge の CLI・台帳の binary) SHALL runner の allowlist の対象外とする (allowlist は宣言が名乗ってよい上限であり runner に与える権限を縛る・ADR-0010 §2.2。 器が host の道具を子 process で呼ぶ先例は ADR-0017 §2.2・上限に語を足す C5 の裁定を要しない・宣言の command 行の検査は不変)。 forge の CLI を子 process として採ること SHALL A3 の対象とし (ADR-0017 §2.2 の HTTP client・ADR-0018 §2.4 の台帳の binary と同じ扱い・crate は増えず NFR3 は不変)、 承認 SHALL 対話面で得た approval event とし、 器 SHALL NOT 承認の前に、 その子 process を write-set に持つ契約 (契約表の contract-source#d) を受け付ける。 CI の照合の 1 行 SHALL 器の既定を持ち、 宣言 file の任意 key (ci-cmd) が差し替える。 遠隔の名 SHALL 同じく任意 key (remote) から読み、 無ければ器の既定を使う (§2.6)。 終端が読む宣言の値 SHALL 受付が凍結した写しから読み、 その周の作業木の宣言を読み直さない (ADR-0010 §2.4・便の実装が宛先を書き換えて別の repo へ押す経路を塞ぐ)。 着地の事実の正本 SHALL 器の記録 (追記だけの 1 file・ADR-0004 §2.1) とし、 squash commit の末尾の trailer 2 行 (契約 id・要件 id) SHALL 器が同時に書く導出面として扱う (名は NAME 定数から導出・C2.2・既存の便 id の trailer と 1 組に統合し、 同じ事実に carrier を 2 つ作らない)。 外部の道具が読む口 SHALL trailer 1 つに限り、 trailer を持たない commit SHALL 「まだ分からない」と読む (「未着地」と区別する・trailer の導入前の commit と弁別できないため)。 自 repo への PR の形 (--pr-cmd) SHALL trailer も記録も持たない恒久の穴として明示する。 終端の再実行 SHALL 冪等な口 1 つ (pipe land --terminal-only・便を名指す) で行い、 着地そのもの SHALL NOT 巻き戻す (N1・退役は可逆な移動)。 着地 commit SHALL 便の記録の任意の項目として残し (ADR-0021 §2.6 の「記録は任意 field を足せる」に乗る)、 自分の版が古い周に起動を断るかは §2.8。 器が自動で push すること SHALL ADR-0008 §2.1 により「出す」ではない (自 repo への反映であり可視性を反転しない) が、 それを理由に §2.1 の判定を素通りさせない。 本 ADR が足す止め口 3 つ (表の検査・審査・終端) SHALL 生成される極性一覧に in-loop / FailClosed として載り (C11.2 / C16.2・ADR-0014 §2.1 の定義「行為を止めうる判定を返す境界」)、 同じ検査を CI の入口から撃つ周も境界は 1 つ＝行も 1 つとする。 行の依存宣言 SHALL 解決と輪の無さを数えるだけとし、 着地の順序 SHALL ADR-0021 §2.5 のまま (器は依存宣言で順序を強制しない)。

§2.6 consumer の要件面は宣言 file の任意 key で受け、 読み手は拡張子で分ける。 宣言が無ければ器の既定、 既定も解けなければ断る

契約の行は「どの要件のためか」を要件の id で持ち、 器は受付でその id が本当に在るかを測ります。 ところが要件の一覧の形は repo ごとに違います——この repo は HTML の見出しに id が付いていて、 別の repo は YAML の項目として id が並びます。 そこで、 対象の repo が自分の宣言 file の任意の項目で「私の要件の一覧はこの file」と名乗り、 器は file の拡張子で読み方を決めます。 名乗りが無ければ器の既定の file を見ます。 その既定も無い repo は、 検査を黙って飛ばすのではなく受け付けません。 repo の名前や機械の名前で処理を分けることはしません——分かれ道は「宣言された値」と「拡張子」だけです。 遠隔の名前と CI の確かめ方も同じやり方で名乗ります。 名乗った値は、 受付が「本当に在るか」を測ってから使います。 便の途中で値が書き換わらないよう、 受付の時点で写しに凍らせ、 終端もその写しを読みます。 この記録は「必要なこと」を決めるだけで、 実際に効くのは宣言を読む部分を触る契約が着地したときです。

器 SHALL 契約表の要件 id の実在の検査先を、 対象 repo の宣言 file の任意 key 1 つ (requirements・宣言値) から取る。 本 ADR が足す任意 key の名と集合の正本 SHALL core の閉じた列 (と、 そこから描く生成物) とし、 本 ADR は要件面の path (requirements) と終端が読む値 (§2.5) を名指すだけで列を写さない (ADR-0013 §2.1。 未知 key の拒否・空の配列と空要素の拒否・不備の全件行番号付きの報告は ADR-0010 §2.1 のまま不変・§2.7 (iv))。 読み手 SHALL path の拡張子で形を決め (.html は id が anchor として在ることを見、 .yaml は id の欄が並ぶことを見る)、 列に無い拡張子 SHALL typed に断る (fail-closed・NFR4)。 宣言が無い周 SHALL 器の既定の path を使い、 既定の path が base の tree に無い周 SHALL 契約を断る (明示の既定 + fail-closed であり、 検査を飛ばす fallback ではない・ADR-0010 §4 が退けた「宣言し忘れが黙って効く」形を採らない)。 code SHALL NOT consumer の名・repo の名・host 固有の値で分岐する (N3)。 分岐の入力 SHALL 宣言値と拡張子だけとする。 器 SHALL NOT 新しい env の seam を作る (C2.2・値は宣言 file から来る)。 宣言値 SHALL 受付の実在の実測を経て有効になる (C10 の宣言値 → 実測値 → 有効値)。 足した任意 key SHALL 他の宣言値と同じく受付が便ごとに写しへ凍結し、 終端 SHALL その写しを読む (ADR-0010 §2.4・便の実装が宛先を書き換えて別の repo へ押す経路を塞ぐ)。 任意 key SHALL 読み手と同じ便で足す (配線の無い設定を CI が拒む・C10.3)。 本 ADR SHALL 必要条件だけを与え、 十分条件 SHALL 宣言を読む module を write-set に持つ契約 (設計 doc の契約表の contract-source#d) の done が持つ (本 ADR の land だけでは consumer は受け付けられない。 記録時点の同行の done は要件面の解決を持たず、 その句と設計 doc §2 の検査先の記述は本 ADR と同じ便で本節へ揃える)。 器 SHALL NOT 契約の行ごとに要件面の path を持たせる (同じ値が全行に写る・§5 (I))。 器 SHALL NOT 押す宛先が自 repo であることを機械で弁別する (ADR-0008 §2.3 の射程外を動かさない・宣言は対象 repo の PR として review を通り、 凍結の写しが便の自己拡張を塞ぐ・残る限界は §4)。

§4. Consequences

良い面は、 契約が 3 回写されなくなり (写しは器が作る生成物になり)、 書ける範囲の抜けと設計の穴が実装の前に出ること、 着地の後始末が目視から記録へ移ること、 そして別の project でも「宣言 1 行」で受け付けられるようになることです。 悪い面は、 型と行と段と止め口が増えること、 CI の結果を待つ間その project の次の着地が待たされること、 設計 doc の PR を通さないと契約を直せなくなること、 器の外にある門 (文書の検査) が手元でしか撃てないこと、 席が手で台帳を閉じる経路は今も止められないこと、 そして書ける範囲の導出が「少なく見積もる」側に留まることです。

Positive: 契約の正本が 1 つになり (設計 doc の行)、 台帳と便の契約 file は pointer と生成物になる (C15 の充足形・3 段の写しの drift 源が消える)。 書ける範囲の不足と設計の穴が受付と審査で止まる (C16 の in-loop・実装後の gate まで持ち越さない)。 着地の終端が typed な記帳になり、 「着地したのに閉じていない」「閉じたのに CI が赤」が記録で判定できる (FR22 の人由来 event を増やさない・ADR-0022 §2.7 の向きの実例)。 外部の道具は trailer 1 つと tracked な生成物 (欄の schema) だけを読めばよく、 欄の追加は本器の版上げで済む (他 repo の判断記録に縛られない)。 consumer は宣言 file の任意 key だけで受け付けられ、 code は consumer ごとに分岐しない (N3)。 CI と受付が同じ関数を撃つので、 検査の 2 実装が生まれない (C2)。

Negative (受け入れるコスト): 閉じた型に variant が 5 つ (契約を断る理由に 2・段・完了条件・規則の種類に各 1)・止め口が 3 つ (極性一覧に 3 行)・rules 行 1 本・core の module が 5 つ (表・閉包・審査・台帳の adapter・台帳の lint)・雛形 1 枚・tracked な生成物 1 file・CI の job 1 つ増える (非 Rust 実行物の検出線が動く・ADR-0009 §2.5)。 着地は gate 済みの便を先に通す規律 (ADR-0021 §2.5) と CI の実時間の待ちが重なり、 1 便の待ちが後続の着地を塞ぐ (並列度の実効値が落ちる。 終端だけを別に撃てる冪等な口が逃げ道で、 順序と待ちの機構は後続設計)。 契約の小さな直しにも設計 doc の PR が要る (審査と CI を毎回通る・起こし直しの周は審査を再度通り、 承認の関門を通った後でも審査で止まりうる第 2 の門になる)。 便ごとに審査役の呼出しが 1 回増える (予算は既存の cap の内側・超過は「測れなかった」で落ちる)。 書ける範囲の導出は下界で、 別名の形は拾えない (拾わないことを歯で固定するが、 穴は残る＝質問と設計 doc の改訂で解く)。 席が手で台帳を閉じる経路は編集時に止まらない (器の subcommand ではないので ADR-0022 §2.3 の guard の対象外・post-hoc の lint が名指すだけ・C16 に対する限界として明記する)。 memo の判定が台帳の本文の字面を入力にする (C3.3 と擦れる・guard ではなく名指しに留まる形で受け入れる)。 押す先が自 repo かを機械は弁別しない (ADR-0008 §2.3 の射程外は動かさない。 宣言の写しを便ごとに凍結することで便の自己拡張だけを塞ぐ)。 自 repo への PR の形は trailer も記録も持たない恒久の穴で、 外部の道具では「まだ分からない」に留まる。 公開面に契約の題と done の文が出る (A1 の判定は §2.1)。 既に起票済みの契約は古い形のまま流れるので、 移行の間は 2 つの形が併存する (lint の母集団は本 ADR の land 以降)。 v0.8 の要件 id が SRS に入るまで、 本 ADR の参照と最初の契約は待つ。

§5. Alternatives Considered

10 の案を退けました。 台帳を正本のままにする案は、 台帳が機械の読める形式を持たないので成り立ちません。 欄の一覧を文書に書く案は、 規則を文章に戻します。 別の記法を使う案は、 同じ種類のデータに 2 つ目の文法を足します。 構文を解析して「多めに」集める案は外部の部品が 1 つ増えます。 審査を人が回す案・任意にする案は、 飛ばせる門を門と呼ぶことになります。 後始末を席に残す案・台帳を閉じてから CI を見る案は、 ずれを目視に頼るか赤い着地を閉じます。 commit の末尾を正本にする案は、 直すのに歴史を書き換える必要が出ます。 要件の一覧の場所を器に固定する案や project の名前で処理を分ける案は、 形の違う project を門前払いにするか、 器が特定の相手を知ってしまいます。 契約の行ごとに書かせる案は同じ値を全行に写します。 契約の共通の決まりを各契約に手書きする案は、 先の記録がすでに退けています。 (設計 doc §11 の却下案と重なる案は同じ理由で退け、 設計に固有の残りは同 §11 だけが持ちます。)

(A) 契約の正本を台帳に置いたまま入口の検査だけ足す。 却下: 台帳は機械が読む形式を持たず (自由文)、 器が読むには adapter が要り、 規律を台帳に置く形へ逆行する (C15)。 入口の検査だけでは写しの各段の drift (実測 5 例・2026-09-13) と設計の inline が残る。 裁定 Q1。

(B) 欄の集合と値域を文書 (本 ADR か設計 doc の散文) の正本として持つ。 却下: 規則が散文に戻り (N2)、 生成文書に手書きの規範行が生える (C1.2)。 列挙の正本は機械側 (ADR-0013 §2.1)。 外部の道具の schema を正本にする案も、 器の版上げが他 repo の判断記録に縛られるので採らない (擦り合わせ 2026-09-13・合意記号 G-b)。

(C) 契約表の形式に別の記法 (YAML / JSON) を使う。 却下: 同じ種類のデータに 2 つ目の文法を足し、 受理域が広く fail-closed に保ちにくい。 既存の subset は未知 key と空配列を拒む形で既に fail-closed であり、 種類を 1 つ足すだけで足りる (C2)。

(D) 書ける範囲の集合を構文木で求めて上界にする。 却下: 外部の crate が 1 つ増え (A3)、 実行時の外部依存 0 の NFR3 に触れる。 字面の下界 + 限界の歯 + 質問の record で足りる (§2.3)。 逆に「宣言だけ受けて検査しない」案は、 今日の実害 (抜けが受付を通る) をそのまま残す。

(E) 契約の審査を席の運用として人が回す、 または任意の段にする。 却下: 散文にしか無い規則になり (N2)、 編集時に止める条を後段の運用で代替する (C16)。 飛ばせる門は門ではない。 予算の超過も合格ではなく「測れなかった」に倒す (FR9 と同じ極性)。 裁定 Q2 = must (2026-09-13)。

(F) 着地の後始末を席の手順に残す、 または台帳を閉じてから CI を見る。 却下: 前者はずれ (閉じ忘れ・赤いまま閉じた) を目視に頼り (N2)、 後者は赤い着地が閉じる (C12.6)。 CI を待たない案は「測れなかった」を成功に化かす (C10)。 台帳へ crate の依存で触る案は A3、 台帳の file を直読する案は形式が私物で壊れる。 裁定 Q3。

(G) 着地の事実の正本を commit の trailer (または台帳の notes) に置く。 却下: trailer を正本にすると訂正に commit の書き換えが要り、 器の記録と二重になる。 台帳の notes は private で外から読めない。 両方を正本にする案は同じ事実に carrier を 2 つ作る。 擦り合わせ (2026-09-13・合意記号 G-d) で「正本は器の記録・trailer は読む口」に確定した (§2.5)。

(H) consumer の要件面を器の既定 path 1 つに固定する、 または宣言が無いとき既定で黙って動く fallback を持つ、 または consumer の名で分岐する。 却下: 固定は形式の違う consumer を fail-closed で全部断り採用できなくし (実測: consumer 第 1 号の要件面は YAML で本 repo と同じ file を持たない)、 黙る fallback は宣言し忘れが静かに効き (ADR-0010 §4 が同型の案を退けている)、 名での分岐は host 固有の値による分岐と同じ極性に触れる (N3)。 採るのは「任意 key + 拡張子で読み手を決める + 明示の既定 + 解けなければ断る」(§2.6)。

(I) 要件の一覧の path を契約の行ごとに書かせる。 却下: 同じ値が repo の全行に写り、 1 か所を直し忘れると行ごとに検査先が食い違う。 repo に 1 つの値は repo の宣言 file が持つ (ADR-0010 §2.1 の「値は対象 repo の性質」の 2 例目・§2.6)。

(J) 契約の共通の決まりを契約側に手書きする (各契約に同じ規律の文を書く)。 却下: ADR-0009 §2.4 と ADR-0010 §2.1 が既に退けた形の再演で、 同文が契約の数だけ増える。 共通の規律は宣言 file と器が持ち、 契約表の行は「この便に固有の値」だけを持つ。
