設計判断記録 (ADR) scribe2 — 案件の局面と継ぎ目

案件の部品の局面は器の 1 つの関数で決めて state dir の 1 file に書き、 器の知らせ・裁定面・席が同じ file を読む — 局面の出力を観測の面の 1 種に足し (版の欄・読み手の約束・書き直しの契機の 2 層・呼ぶ向き・受付の断りの event)、 器の便でない着地は発端の trailer と merge の門で案件へ結ぶ (ADR-0004 §2.2 の面 2 と ADR-0023 §2.5 の 1 文を部分 supersede)

案件の部品が一生のどこにいて、 次に誰が動くかを、 今は器の中の数か所 (待ちの理由・終端の語・settled・doctor の lint)・消費側の画面 2 つ・席の頭が別々に判じ、 互いに食い違い、 どこにも出ない段も残る。 本 ADR は、 判じ手を器の 1 つの関数にし、 その出力を state dir の 1 file に書き、 器の知らせ・裁定面・席がその file を読むだけにする形と、 器の便でない着地を発端の trailer で案件へ結ぶ形を決める。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「席」は器が立てる対話の AI の session、 「便」は契約 1 本を実装して main へ入れる 1 回の走り、 「台帳」は作業と裁定を記録する beads、 「裁定面」は消費側の project が持つ、 user が答えを書き込む画面です。 memo か台帳の問いを根にして、 そこから辿れる発話・問い・契約・便・着地のひとまとまりを「案件」、 その一つ一つを「部品」と呼び、 部品がいま一生のどこにいるかを「局面」、 次に動くべき者を「手番」と呼びます。 今は局面の判定が器の中の数か所 (待ちの理由・終端の語・settled・doctor の lint)・消費側の project の画面 2 つ・席の頭の中に分かれて互いに食い違い、 CI の結果待ちや受付の断りのように、 どこにも出ない段も残っています。 本 ADR は、 局面を器の 1 つの関数だけで決め、 その結果を器の置き場 (state dir) の 1 file (lifecycle.json) に書き、 器の知らせ・裁定面・席がその file を読むだけにして、 古い結果は古いと示す形を決めます。 席が長く放っている部品の数もこの file が持ち、 知らせはそれを読むだけです。 この file は前の版と次の版が共有する観測の面に加わるので、 ADR-0004 の観測の面の欄を部分的に置き換えます。 あわせて、 器の便を通らない着地 (設計の変更の PR など) に、 どの memo や問いから来たかを示す発端の trailer を求め、 merge の時点の門と CI で確かめます。 自 repo への PR の形を trailer の無い穴とした ADR-0023 の 1 文も、 この形で置き換えます。 要件 FR90・FR92・FR94 を支え、 user の裁定 2026-09-28T12:46Z と 13:14Z の方向に沿います。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 6 つで示します。 局面の判定が 4 か所に分かれて食い違い、 どこにも出ない段があること (事象)。 観測の面と、 置き場の file を周が書いて管理 tick が数える型が既に在ること (現物)。 継ぎ目の機械の確かめが 2 本しかなく、 器の便でない着地が案件へ結ばれないこと (現物)。 user の裁定の方向と、 消費側の席が出した条件 (裁定)。 憲法と既存の決定の向き。 動かすものと動かさないものの射程です。

CTX1

事象 — 案件根から辿れる束の部品一生を追う単位が一生のどこにいるかの判定が 4 か所に分かれて食い違い、 どこにも出ない段が残る

案件の部品 (発話・台帳の問い・memo・契約・便・契約表の行・要件・epic) が一生のどこにいて次に誰が動くかを決める判定は、 今 4 か所 (器・消費側の画面 2 つ・席の頭) に在る。 1 つ目は器の中の数か所で、 起動の列の待ちの理由 (WaitReason・閉じた型)・便の終端の周の通知の語を決める dispatcher の alarm_word・終端に達した便を列から外す settled が別々に判じ、 doctor の台帳 lint の (vi) (memo を名指すのに辺の無い契約) と (viii) (辿れる契約が全部閉じた開いた memo) も別の判じ手を持つ。 2 つ目は器の外で、 消費側の project の 1 つが画面を 2 つ持ち、 それぞれ器の語を写して局面一生のいまの位置を自前で計算する。 2 つの画面は互いにも器とも食い違う (受付と実装中を区別しない・CI の結果を待つ便を着地に畳む・止めた便の扱いが画面ごとに違う)。 3 つ目は席の頭の中で、 圧縮で消える。 どこにも出ない段も在る: 受付の断りは起動の log の散文だけで event にならず、 CI の結果を待つ便と着地したが台帳で閉じていない契約は無音で、 契約表の行に bead が無いことと要件に行が 1 本も無いことを数える者はいない。 2026-09-28 には席が CI 待ちの便を 0 本と数え違えた。

CTX2

現物 — 観測の面外が読む器の記録は event log と export の 2 つで、 置き場の file を周が書き管理 tick が数える型が既に在る

ADR-0004 §2.2 は前の版と次の版が共有する 5 つの面を固定し、 面 2 (観測) を <state_dir>/fleet/events.jsonl と fleet export に置いた。 §2.5 は行と file に整数の schema を持たせ、 欄を足す変更は同じ番号・読めなくなる変更は新しい版とする。 ADR-0023 §2.5 は着地の commit の trailer を外部の道具が読む唯一の口とし、 trailer を持たない commit は「まだ分からない」と読み、 自 repo への PR の形 (--pr-cmd) を trailer も記録も持たない恒久の穴とする。 未反映の裁定 (FR84) と床の検査 (FR85) には、 dispatch の周が置き場の file を書き、 管理 tick がその file だけを読んで alarm の語を決める (台帳も git も撃たない) 型が在る。 管理 tick は既に event log の全部を読む。 器の plugin の hooks.json の hook は SessionStart・PreToolUse・PermissionRequest・UserPromptSubmit・Stop・PreCompact の 6 つで PostToolUse は無く、 plugin の hooks.json の matcher は道具の名でしか絞れない (command の字面で絞る「if」は設定の hook だけが持つ・2026-09-28 の実測)。 NFR5 は道具 1 回の呼出しの hook を binary 2 回以内・各 2.0 秒以内・重い I/O なしに縛り、 NFR6 は封じ込めの外で走る器の子 process を 0 本にする。 台帳の現在地の読み (status 級) は 1 回約 0.35 秒 (ADR-0045 の実測) で、 負荷の高い時は 2 秒を越え、 event log は 7 MB を越える。 起動の列は周期の timer を持たない (FR68)。

CTX3

現物 — 継ぎ目の機械の確かめは 2 本だけで、 器の便でない着地は案件へ結ばれない

機械が今確かめる継ぎ目は、 設計 pointer の無い契約を起こさないこと (FR68) と、 契約表の行の要件 id が SRS に在ること (契約表の検査) の 2 本である。 器の便は着地の commit に run: と契約と要件の trailer を書き (契約と要件の trailer の名は NAME から導く接頭辞を持ち、 run: は literal)、 案件の便と着地が結ばれる。 設計の変更 (SRS・ADR・設計 doc の PR の squash) と手の merge は bead も trailer も持たず、 どの memo や問いから来たかが main に残らない。 CI の main-provenance は main への push の時だけ撃ち、 HEAD が PR の squash (件名の末尾の (#N)) か run: の trailer を持つことを確かめる。 PR の段の CI は squash の本文を見られない (本文は merge の時に決まり、 merge する者が差し替えられる)。 器の hook の入口は既に席の道具の呼び出しの gh pr merge の command を読み、 着地の列の窓が閉じている間は断る (設計 vessel-hook §14)。

03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 8 つ並べます。 器の 1 つの関数の出力を 1 つの file に書き、 器の便でない着地を発端の trailer と merge の門で結ぶ案 (選んだ案)、 消費側が器の語を写して自前で判じる今の形、 読むたびに器の命令を撃つ案、 局面の移りを event として記録する案、 閉じた bead を窓で入力から落とす案、 設計の変更も器の便にする案、 発端の trailer を任意にする案、 PR の段の CI で本文を確かめる案です。 後ろの 3 つは、 器の便でない着地の結び方の候補です。

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなること 5 つと、 代わりに引き受けること 9 つです。 良くなるのは、 皆が同じ語を見ること、 無音だった段と席の放置が見えて席へ押し込まれること、 切り替えの線より後の死角が「当てはまらない」として数えられること、 読む側が軽いこと、 設計の変更も案件へ結ばれることです。 引き受けるのは、 版を跨ぐ約束が増えること、 file が書き直しの間は古いこと、 書き直しが重いこと、 語と表と規則の値の手入れ、 合図の届かない席、 merge の門の限り、 消費側への先の知らせ、 断りの event による記録の伸び、 切り替えの線より古い誤りが見えないままになることです。
