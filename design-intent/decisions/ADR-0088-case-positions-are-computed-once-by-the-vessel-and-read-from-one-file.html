設計判断記録 (ADR) scribe2 — 案件の局面と継ぎ目

案件の部品の局面は器の 1 つの関数で決めて state dir の 1 file に書き、 器の知らせ・裁定面・席が同じ file を読む — 局面の出力を観測の面の 1 種に足し (版の欄・読み手の約束・書き直しの契機の 2 層・呼ぶ向き・受付の断りの event)、 器の便でない着地は発端の trailer と merge の門で案件へ結ぶ (ADR-0004 §2.2 の面 2 を部分 supersede)

案件の部品が一生のどこにいて、 次に誰が動くかを、 今は器の中の 3 か所・裁定面 2 つ・席の頭が別々に判じ、 互いに食い違い、 どこにも出ない段も残る。 本 ADR は、 判じ手を器の 1 つの関数にし、 その出力を state dir の 1 file に書き、 器の知らせ・裁定面・席がその file を読むだけにする形と、 器の便でない着地を発端の trailer で案件へ結ぶ形を決める。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「席」は器が立てる対話の AI の session、 「便」は契約 1 本を実装して main へ入れる 1 回の走り、 「台帳」は作業と裁定を記録する beads、 「裁定面」は消費側の project が持つ、 user が答えを書き込む画面です。 user の発話から memo・問い・契約・便・着地・画面への反映までのひとまとまりを「案件」と呼び、 その部品がいま一生のどこにいるかを「局面」、 次に動くべき者を「手番」と呼びます。 今は局面の判定が器の中の 3 か所・消費側の project の画面 2 つ・席の頭の中に分かれて互いに食い違い、 CI の結果待ちや受付の断りのように、 どこにも出ない段も残っています。 本 ADR は、 局面を器の 1 つの関数だけで決め、 その結果を器の置き場 (state dir) の 1 file (lifecycle.json) に書き、 器の知らせ・裁定面・席がその file を読むだけにする形を決めます。 この file は前の版と次の版が共有する観測の面に加わるので、 ADR-0004 の観測の面の欄を部分的に置き換えます。 あわせて、 器の便を通らない着地 (設計の変更の PR など) に、 どの memo や問いから来たかを示す発端の trailer を求め、 merge の時点の門と CI で確かめます。 要件 FR90 と FR92 を支え、 user の裁定 2026-09-28T12:46Z と 13:14Z の方向に沿います。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 6 つで示します。 局面の判定が 4 か所に分かれて食い違い、 どこにも出ない段があること (事象)。 観測の面と、 置き場の file を周が書いて管理 tick が数える型が既に在ること (現物)。 継ぎ目の機械の確かめが 2 本しかなく、 器の便でない着地が案件へ結ばれないこと (現物)。 user の裁定の方向と、 消費側の席が出した条件 (裁定)。 憲法と既存の決定の向き。 動かすものと動かさないものの射程です。

CTX1

事象 — 案件1 件の一生の束の部品が一生のどこにいるかの判定が 4 か所に分かれて食い違い、 どこにも出ない段が残る

案件の部品 (発話・台帳の問い・memo・契約・便・契約表の行・要件・epic) が一生のどこにいて次に誰が動くかを決める判定は、 今 4 か所に在る。 1 つ目は器の中で、 起動の列の待ちの理由 (WaitReason・閉じた型)・便の終端の周の通知の語を決める dispatcher の alarm_word・終端に達した便を列から外す settled が別々に判じ、 doctor の台帳 lint の (vi) (memo を名指すのに辺の無い契約) と (viii) (辿れる契約が全部閉じた開いた memo) も別の判じ手を持つ。 2 つ目は器の外で、 消費側の project の 1 つが画面を 2 つ持ち、 それぞれ器の語を写して局面一生のいまの位置を自前で計算する。 2 つの画面は互いにも器とも食い違う (受付と実装中を区別しない・CI の結果を待つ便を着地に畳む・止めた便の扱いが画面ごとに違う)。 3 つ目は席の頭の中で、 圧縮で消える。 どこにも出ない段も在る: 受付の断りは起動の log の散文だけで event にならず、 CI の結果を待つ便と着地したが台帳で閉じていない契約は無音で、 契約表の行に bead が無いことと要件に行が 1 本も無いことを数える者はいない。 2026-09-28 には席が CI 待ちの便を 0 本と数え違えた。

CTX2

現物 — 観測の面外が読む器の記録は event log と export の 2 つで、 置き場の file を周が書き管理 tick が数える型が既に在る

ADR-0004 §2.2 は前の版と次の版が共有する 5 つの面を固定し、 面 2 (観測) を <state_dir>/fleet/events.jsonl と fleet export に置いた。 §2.5 は行と file に整数の schema を持たせ、 欄を足す変更は同じ番号・読めなくなる変更は新しい版とする。 ADR-0023 §2.5 は着地の commit の trailer を外部の道具が読む唯一の口とし、 trailer を持たない commit は「まだ分からない」と読む。 未反映の裁定 (FR84) と床の検査 (FR85) には、 dispatch の周が置き場の file を書き、 管理 tick がその file だけを読んで alarm の語を決める (台帳も git も撃たない) 型が在る。 管理 tick は既に event log の全部を読む。 器の plugin の hooks.json の hook は SessionStart・PreToolUse・PermissionRequest・UserPromptSubmit・Stop・PreCompact の 6 つで PostToolUse は無く、 plugin の hooks.json の matcher は道具の名でしか絞れない (command の字面で絞る「if」は設定の hook だけが持つ・2026-09-28 の実測)。 NFR5 は道具 1 回の呼出しの hook を binary 2 回以内・各 2.0 秒以内・重い I/O なしに縛り、 NFR6 は封じ込めの外で走る器の子 process を 0 本にする。 台帳の全部の読みは 1 回約 0.35 秒 (ADR-0045 の実測) で、 負荷の高い時は 2 秒を越え、 event log は 7 MB を越える。 起動の列は周期の timer を持たない (FR68)。

CTX3

現物 — 継ぎ目の機械の確かめは 2 本だけで、 器の便でない着地は案件へ結ばれない

機械が今確かめる継ぎ目は、 設計 pointer の無い契約を起こさないこと (FR68) と、 契約表の行の要件 id が SRS に在ること (契約表の検査) の 2 本である。 器の便は着地の commit に run: と契約と要件の trailer を書き (名は NAME から導く接頭辞を持つ)、 案件の便と着地が結ばれる。 設計の変更 (SRS・ADR・設計 doc の PR の squash) と手の merge は bead も trailer も持たず、 どの memo や問いから来たかが main に残らない。 CI の main-provenance は main への push の時だけ撃ち、 HEAD が PR の squash (件名の末尾の (#N)) か run: の trailer を持つことを確かめる。 PR の段の CI は squash の本文を見られない (本文は merge の時に決まり、 本文を直しても撃ち直されない)。 器の hook の入口は既に席の道具の呼び出しの gh pr merge の command を読み、 着地の列の窓が閉じている間は断る (設計 vessel-hook §14)。

CTX4

裁定 — 器の整理と見せ方を 1 対 1 にし、 局面の計算を器の 1 か所にまとめ、 裁定面は描くだけにする

user は 裁定 id user 2026-09-28T12:46Z で、 user の発話から画面への反映までの一生を器・裁定面・user で整理し直し、 器の整理と見せ方を 1 対 1 にし、 LLM の席にも死角を残さない方向を決めた (memo s2-07l.739)。 裁定 id user 2026-09-28T13:14Z は、 局面の計算を器の 1 か所にまとめ、 裁定面は描くだけにする推奨を採った (問い 3)。 その推奨は消費側の席の意見を入れた形で、 器が局面の出力を state dir の file に書き (台帳か event が動いた周と管理 tick の周)、 裁定面と席はその file を読むだけにし、 読みの道に process を起こさない (消費側の台帳の読みは負荷の高い時 2 秒を越える)。 出力は版の欄を持ち、 知らない局面の語は「まだ分からない」、 出力が無いか器が古い周は「測れない」と描き、 便の生の時刻の列は event log のまま、 出力は state dir ごとに 1 つとする。 一生の段の表 (user に示した 25 段) の全部を出力に入れ、 裁定面は台帳を中身の表示 (問いの本文・notes) にだけ読む。 仕分け済みの発話の行き先 (どの memo・どの裁定・会話) も画面に出す (問い 1・裁定 id user 2026-09-28T13:12Z)。 逐語は台帳にだけ在る。

CTX5

憲法と既存の決定の向き — 判定は 1 つの関数・真実は導出物に置かない・編集の時点で止める・消すものを先に名指す

C2 は選定・除外・routing を 1 つの enumeration の上の 1 つの関数にし、 適用の順を enum の宣言順だけから取り、 順の散文を持たず、 新しい理由は変種 1 つで表すと定める。 C3 は真実を host ごとの dir・TSV・cache に置かず、 C10.2 は報告と一覧を生成物だけにする。 C16 は仕様からの逸脱を編集の時点で止め、 事後の確かめで代えない。 C17.2 は走査・記録・rules 行・仕組みを足す前に消すものを名指させ、 N2 は散文にしか無い規則を規則と認めない。 C5 は rules 行の値に user の裁定 id を要る。 ADR-0045 は観測を実測で要ると分かってから足すとし、 2 つの画面の食い違いは実測である。 FR65 は発話 event の逐語を一覧へ運ばない。 FR27 は管理 tick の alarm を置き場の file だけから決め (台帳も git も撃たない)、 合図を送らない周の席 (梯子の列が尽きた席・合図を止めた席) には alarm も届かない。 doctor の出力の key は裁定面が読むので、 key を変える便の前に消費側へ知らせる約束が在る (memo s2-07l.692)。

CTX6

射程 — 動かすのは観測の面の 1 種・判じ手の寄せ・受付の断りの event・発端の trailer と merge の門merge を止める門の 4 つ

動かすのは、 (1) 局面の関数と、 その出力の file (観測の面の新しい 1 種・版を跨ぐ形・読み手の約束・書き直しの契機)、 (2) 便の終端の周の通知の語・doctor・管理 tick の alarm (語 owned席の手番の放置の知らせ)・session の開始の事実行の判じ手を局面の関数へ寄せること、 (3) 受付の断りの event の kind、 (4) 器の便でない着地の発端部品を生んだ上流の trailer と merge の門と main-provenance の広げ、 の 4 つで、 要件は SRS 版 0.29 の FR90・FR92 と FR27・FR42・FR44・FR51・FR68・NFR5 の改訂が持つ。 動かさないのは、 event log の schema 版と既存の kind・fleet export・起動の列の判定と待ちの理由・受付の判定・便の段・着地の手順・既存の trailer・発話の仕分けの形 (FR88)・memo の局面の条件と処置 (FR91)・rules 行の値 (裁定 id を待つ) である。 判定の HOW (関数の個数・呼ぶ向き・書き手の直列化・file の欄) は本 ADR と設計 doc の領分で、 SRS は、 どの読み手も同じ判定の結果を使って自前の判定を持たないこと・書きかけの file を見せないこと・古い入力の書きを残さないこと・版を持つことの WHAT を持つ。 局面の語の一覧と一生の段の表との対応・局面 (契約の待ちでは理由も) から手番次に動く者の番への対応・misfitどこにも当たらない の理由の閉じた一覧は設計 doc の 1 節が正本で、 欄の名と JSON の形・入力の印の形と古さの比べ方も設計 doc が持つ。 ADR を書く条件のうち 1 (C2・C3・C16 の読み)・3 (file・event の kind・trailer は版を跨ぐ形)・4 (却下案を残す価値のある分岐) に当たる。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 6 本のものさしです。 局面を決めるのは器の 1 つの関数だけで、 皆が同じ語を見ること。 読む側に process も台帳の読みも載せないこと。 版を跨いでも読み手が壊れず、 古さと測れなさが見えること。 どの部品も局面か「当てはまらない」のどちらかに出て、 無音の段が残らないこと。 継ぎ目の欠けは編集の時点で止めること。 足すものを最小にし、 消すものを名指し、 真実を出力に置かないことです。

03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 8 つ並べます。 器の 1 つの関数の出力を 1 つの file に書き、 器の便でない着地を発端の trailer と merge の門で結ぶ案 (選んだ案)、 消費側が器の語を写して自前で判じる今の形、 読むたびに器の命令を撃つ案、 局面の移りを event として記録する案、 閉じた bead を窓で入力から落とす案、 設計の変更も器の便にする案、 発端の trailer を任意にする案、 PR の段の CI で本文を確かめる案です。 後ろの 3 つは、 器の便でない着地の結び方の候補です。

OPT1器の 1 つの関数が局面を導いて state dir の 1 file に書き、 読み手は file を読むだけにする。 器の便でない着地は発端の trailer と merge の門で結ぶ採用

器は 1 つの関数で案件の部品 9 種ごとに局面・手番・since・理由・結びを導き、 <state_dir>/fleet/lifecycle.json局面を書いた 1 file を丸ごと入れ替えて書く。 全部の書き直しは dispatch の周と器の台帳の書きの直後で、 席の道具の呼び出しの台帳の書きと器の便でない merge は門が古さの印出力が古いという目印を置いて次の全部の書き直しが消し、 event log と時刻で決まる部分は管理 tick の周と発話 event の記帳の直後に書き直す (台帳も git も撃たない)。 器の知らせ・doctor・事実行・裁定面は局面の語をこの関数か file から得る。 受付の断りを event にし、 器の便でない着地の commit に発端の trailer を要り、 merge の門と main-provenance で確かめる。 決め手は裁定 12:46Z・13:14Z (問い 3 の推奨と消費側の条件) と分析 (OPT2〜OPT8 の欠点)。

選んだ案です。 器は 1 つの関数で、 案件の部品 9 種 (発話・台帳の問い・memo・契約・便・契約表の行・要件・epic・器の便でない着地の commit) ごとに、 いまの局面・次に動くべき者 (手番)・その局面に入った時刻・理由・つながり (どの発話や memo から来て、 どの契約と便と commit へ進んだか) を導きます。 どの局面にも当たらない部品は「misfit (当てはまらない)」と理由の語で出します。 結果は state dir の lifecycle.json に、 書きかけを見せないよう丸ごと入れ替えて書き、 版の欄と「何を元に作ったか」の目印 (入力の印) を持たせます。 書き直すのは、 便の周と器が台帳を書いた直後 (全部) と、 管理 tick の周と発話の記録の直後 (event log と時刻で決まる部分だけ) です。 席が自分で台帳を書いた後と、 器の便でない merge で main が動いた後は受ける仕組みが無いので、 門が「古い」という印を置き、 次の全部の書き直しで直ります (便が走らない間は長く古いままになりうる限界を受け入れます)。 器の知らせ・doctor・事実行・裁定面は、 この結果を読むだけです。 受付の断りは event にし、 器の便でない着地の commit には発端の trailer を求め、 merge の門と CI で確かめます。 皆が同じ語を見て、 読む側も軽く、 死角が残りません。 代わりに、 版を跨ぐ約束が増え、 file が古い間があり、 書き直しが重く、 語と表の手入れが要り、 merge の門は形しか見ず消費側の repo にも効き、 断りの event で記録が伸びることを引き受けます。 user の裁定 12:46Z と 13:14Z (消費側の席の条件を入れた推奨) に沿う案です。

+ 利点

  • 判じ手が 1 つで、 器の知らせ・裁定面・席が同じ語を見るので、 器の整理と見せ方の 1 対 1 が作りの上で保たれる (DR1)
  • 読み手は file を 1 回読むだけで、 process も台帳の読みも読みの道に載らない (DR2)
  • 版の欄と読み手の約束で、 古い読み手は新しい語を「まだ分からない」と描き、 file が無いか読めない版の周は「測れない」と出す (DR3)
  • 窓を表示にだけ掛けるので、 閉じた bead を要る判定 (行の bead・未反映の裁定・引き金の依存) が誤らない (DR4)
  • どの局面にも当たらない部品は misfit で出て、 無音だった CI 待ち・閉じ損ね・受付の断り・席の手番の放置が局面と年齢と alarm の語 owned で見える (DR4)
  • 器の便でない着地は merge の時点で止まり、 画面や端末の merge も CI が事後に名指す (DR5)
  • alarm_word と doctor の (vi)(viii) の自前の判定を消して足し、 file は導出物で真実を持たない (DR6)

− 欠点

  • 跨版の面が広がる (file 2 つ〔lifecycle.json と古さの印〕・版の欄と欄の名・局面の語・手番の値・event の kind 1・trailer 1)。 語を消すか意味を変えるには版を上げ、 裁定面を先に直す手が要る
  • file は書き直しの間は古い。 席の道具の呼び出しの台帳の書きと器の便でない merge は受ける hook が無いので、 門が置く古さの印で読み手が「古い」と描くだけで、 次の全部の書き直しまで出力は直らない。 dispatch の周は timer を持たないので、 便が走らない間は長く古いままになりうる (受け入れる限界)
  • 全部の書き直しは台帳の全部・event log・main の設計 doc と SRS と trailer を読むので、 dispatch の周と器の台帳の書きの直後が重くなる。 発話 event の記帳の直後の書き直しは hook の中で file を読み書きし、 NFR5 の重い I/O の線に近づく
  • 局面の語は 40 前後になり、 語と手番と一生の段の表との対応を設計 doc で保つ手が要る。 rules 行が増え (lifecycle.closed_window_h と局面ごとの lifecycle.age_h)、 値の裁定までは owned が出ない
  • merge の門は席の道具の呼び出しの command の字面しか見ず、 CI は台帳に届かないので、 発端の id は形しか確かめない。 打ち違えても形が合えば通り、 misfit でだけ見える。 本文を渡せない merge の形 (rebase) は断られる
  • merge の門は marker が器の名を言う repo の全部で効くので、 消費側の repo の席の merge も発端の trailer を要る
  • 受付の断りは断った周ごとに 1 件記帳するので、 同じ契約が周ごとに断られると event log が伸びる
OPT2裁定面が器の語を写して自前で局面を判じる (今の形)不採用

器は語 (待ちの理由・便の段・終端の語) と記録を出すだけにし、 裁定面と席はそれを写した自前の表で局面を決める。 決め手は分析 (既に食い違っている) と裁定 13:14Z。

今の形のまま、 器は語と記録を出すだけにして、 裁定面と席がそれを写した自前の表で局面を決める案です。 器に新しい約束も仕組みも足さず、 画面ごとに自由に畳め、 器の版が上がっても写しを直すまで画面は動き続ける点で勝ります。 けれども、 判定が器・画面 2 つ・席の頭の 4 か所に分かれ、 今すでに食い違っています。 器の語が増えるたびに全部の写しを直す手が要り、 直し漏れは無音で、 器の側にも出ない段 (受付の断り・CI 待ち・閉じ損ね) はどの写しも作れません。 user の裁定 13:14Z も判定を器の 1 か所にまとめる推奨を採ったので退けました。

+ 利点

  • 器に新しい跨版の面も書き直しの仕組みも足さない
  • 消費側は画面ごとに要る粒度で自由に畳める
  • 器の版が上がっても、 写しを直すまで裁定面は今の形のまま動く

− 欠点

  • 判じ手が器・画面 2 つ・席の頭の 4 か所になり、 今すでに互いに食い違っている。 1 対 1 は作りの上で保たれない (DR1)
  • 器の語が増えるたびに写しの全部を直す手が要り、 直し漏れは無音 (DR3)
  • 器の側にも出ない段 (受付の断り・CI 待ち・閉じ損ね) は、 どの写しも作れない (DR4)
OPT3読むたびに器の命令を撃って局面を得る (file を持たない)不採用

案件の一覧の口だけを器に置き、 読み手は読むたびにそれを撃つ。 決め手は分析 (画面の読みに process と台帳の読みが乗る) と裁定 13:14Z が採った消費側の条件。

file を持たず、 読む側が読むたびに器の命令を撃って局面を得る案です。 結果がいつも最新で、 file の書き手の順番付けや入れ替えの仕組みが要らず、 約束が命令の出力 1 つで済む点で勝ります。 けれども、 画面を読むたびに器の process と台帳の全部の読み (混んだ時は 2 秒を越える) が乗り、 消費側の席が出した「読む道に process を起こさない」条件に反します。 管理 tick と hook は台帳を読めないので同じ語を得られず判定が分かれ、 読む側の数だけ同じ計算が重なるので退けました。

+ 利点

  • 出力はいつも今の台帳と event log から導かれ、 古さが無い
  • file の書き手の直列化・丸ごとの入れ替え・古い書きの捨ての仕組みが要らない
  • 跨版の形が命令の出力 1 つで済み、 file の置き場を約束しない

− 欠点

  • 画面の読みのたびに器の process と台帳の全部の読み (負荷の高い時 2 秒超) が乗り、 消費側の条件に反する (DR2)
  • 管理 tick と hook は台帳を撃てないので同じ語を得られず、 判じ手が分かれる (DR1・DR2)
  • 読み手の数だけ同じ計算が重なる
OPT4局面の遷移を event として記帳し、 読み手は event log から局面を読む不採用

部品が局面を移るたびに器が event を 1 行記帳する。 決め手は分析 (台帳の書きの多くは器を通らず取りこぼす)。

部品が局面を移るたびに器が event を 1 行記録し、 読む側は event log から局面を読む案です。 局面の履歴が時刻つきで残り、 観測の面が増えず、 読む側が既に持つ道を使える点で勝ります。 けれども、 台帳の書きの多く (席や裁定面の書き) は器を通らないので移りを取りこぼし、 取りこぼしは無音です。 局面は他の記録から導ける値なので、 記録すると同じ値の置き場が 2 つになり、 判定を変えると過去の記録と食い違うので退けました。

+ 利点

  • 局面の履歴が時刻つきで残り、 年齢と遷移の順を後から数えられる
  • 観測の面が event log 1 つのまま増えない
  • 読み手は既に event log を読む道を持つ

− 欠点

  • 台帳の書きの多く (席の bd の書き・裁定面の書き) は器を通らないので遷移を取りこぼし、 取りこぼしは無音 (DR4)
  • 局面は台帳と event log と main から導く値で、 記帳すると同じ値の置き場が 2 つになる (C3・DR6)
  • 判定を変えると過去の event と食い違い、 読み手が導き直す手を持つことになる (DR1)
OPT5閉じた bead を窓で入力から落として判定を軽くする不採用

判定の入力を、 開いた bead と閉じてから lifecycle.closed_window_h 以内の bead に絞る。 決め手は分析 (判定が大量に誤る)。

判定を軽くするために、 閉じてから一定の時間 (窓) を過ぎた bead を入力から落とす案です。 台帳の読みと判定が軽く、 出力が小さく、 落とす範囲が規則 1 本で説明できる点で勝ります。 けれども、 窓の外で閉じた契約を見失うので、 審査の模擬では「bead の無い契約表の行」が本当は 5 行なのに 87 行と出ました。 窓より古い「文書に写していない裁定」も出力から消えて要件 FR84 の知らせと食い違い、 引き金の判定も誤るので退けました。 選んだ案では、 窓はclose した部品を出力に載せるかの表示にだけ使います。

+ 利点

  • 台帳の読みと判定が軽くなり、 書き直しの時間が台帳の大きさに依らない
  • 出力が小さく、 読み手の描きも軽い
  • 落とす範囲が rules 行 1 本で説明できる

− 欠点

  • 行の bead の判定が窓の外で閉じた契約を見失い、 審査の模擬では bead の無い行が真の 5 行に対して 87 行になった (DR4)
  • 窓より古い未反映の裁定が出力から消え、 FR84 の alarm と食い違う (DR4)
  • 引き金の依存・着地と、 辿れる契約が全部閉じたかの判定も窓の外の閉じを見失う (DR4)
OPT6設計の変更も器の便にして run: の trailer で結ぶ不採用

docs PR も契約と便にして、 着地の commit を器の trailer で結ぶ。 決め手は分析 (設計の変更を便にする形は別の memo の領分で、 手の merge は残る)。

設計の変更 (docs PR) も契約と便にして、 着地の commit を器の run: の trailer で結ぶ案です。 trailer の種類が増えず、 設計の変更も審査と gate を通り、 CI の今の確かめがそのまま効く点で勝ります。 けれども、 設計の変更を便にする形は別の memo (s2-07l.738.2) で扱う話で、 審査と gate の形を設計の変更に合わせる決定が先に要ります。 手の merge や画面からの merge は残り、 それらの発端は結ばれないので、 この記録では退けました。

+ 利点

  • trailer の種類が増えず、 main の commit は全部便の trailer で結ばれる
  • 設計の変更も審査と gate を通る
  • 既存の main-provenance の形がそのまま効く

− 欠点

  • 設計の変更を便にする形は別の memo (s2-07l.738.2) の領分で、 審査と gate の形を設計の変更に合わせる決定が先に要る (DR6)
  • 手の merge と画面の merge は残り、 それらの発端は結ばれない (DR4)
OPT7発端の trailer を任意にする不採用

付けた commit だけを案件へ結び、 無い commit は「まだ分からない」と読む。 決め手は分析 (設計の局面が画面に出ない)。

発端の trailer を任意にし、 付けた commit だけを案件へ結ぶ案です。 merge の門も CI の広げも要らず、 席の手順も消費側の repo への求めも増えず、 ADR-0023 の「trailer の無い commit はまだ分からない」の読みのままで済む点で勝ります。 けれども、 付け忘れが無音で、 設計の変更がどの memo や問いから来たかが画面に出ず、 継ぎ目の欠けを編集の時点で止める者がいない (憲法 C16 に合わない) ので退けました。

+ 利点

  • merge の門も CI の広げも要らず、 席の手順が増えない
  • 消費側の repo の merge に何も課さない
  • ADR-0023 の「trailer の無い commit はまだ分からない」の読みのまま

− 欠点

  • 付け忘れが無音で、 設計の変更がどの memo や問いから来たかが画面に出ない (DR4)
  • 継ぎ目の欠けを編集の時点で止める者がいない (C16・DR5)
OPT8PR の段の CI で PR の本文の trailer を確かめる不採用

PR の CI が本文の trailer の有無を見て落とす。 決め手は分析 (squash の本文は merge の時に決まる)。

PR の段の CI が PR の本文の trailer を見て落とす案です。 画面や端末からの merge にも同じ確かめが効き、 hook に command の読みを足さず、 PR の画面に赤が出て人にも見える点で勝ります。 けれども、 main に入る squash の本文は merge の時に決まるので PR の段の CI からは見えず、 本文を直しても CI は撃ち直されません。 PR の本文と squash の本文を合わせる手順が散文に残る (憲法 N2 に合わない) ので退けました。 選んだ案は、 merge の command を撃つ時点で本文を読む門と、 main に入った後の CI の確かめの 2 段にします。

+ 利点

  • 画面や端末の merge にも同じ門が効く
  • hook に command の字面の読みを足さない
  • PR の画面に赤が出て、 人にも見える

− 欠点

  • squash の本文は merge の時に決まり、 PR の段の CI はそれを見られない (DR5)
  • 本文を直しても CI は撃ち直されず、 直した後の本文を確かめない (DR5)
  • PR の本文と squash の本文を合わせる手順が散文に残る (N2・DR6)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 器は 1 つの関数で案件の部品 9 種ごとに局面・手番・時刻・理由・つながりを導き、 state dir の lifecycle.json を丸ごと入れ替えて書きます。 器の知らせ・doctor・session の開始の事実行・裁定面はこの結果を読むだけです。 受付の断りを event にし、 器の便でない着地の commit には発端の trailer を求め、 merge の門と CI で確かめます。

採用 — OPT1

本 ADR は局面の出力を ADR-0004 §2.2 の面 2 (観測) の中に 1 つの形として足し (面 2 の欄を部分 supersede し、 既存の path は変えない)、 C2 の「1 つの関数・宣言順」を局面と手番の判定に当てる。 (1) 器 SHALL 1 つの関数で、 案件の部品 9 種ごとに、 局面 (閉じた語・優先は enum の宣言順・便の段の値は全て写る)・手番 (user・seat・vessel・runner・ci・none)・since・理由 (既存の語をそのまま)・結び (発端・子の問い・昇格した契約・便・着地の commit・発話の行き先) を導き、 どれにも当たらない部品を misfit と閉じた理由の語で出す。 発話の部品は ts・session・行き先だけで逐語を持たない。 局面の語の一覧・局面と理由から手番への対応・misfit の理由の一覧の正本は設計 doc の 1 節。 全部の書き直しの入力は台帳の全部・event log・main の契約表と SRS と trailer で、 窓 (rules 行 lifecycle.closed_window_h) は close した部品の表示にだけ掛ける。 関数は起動の列の関数を呼び、 起動の列は関数を呼ばない。 (2) 出力 SHALL <state_dir>/fleet/lifecycle.json の 1 file で、 版の欄 (整数・語と欄を足すだけでは上げない)・局面の語の一覧・入力の印 (台帳の印・event log の長さ・main の sha)・生成の時刻を持ち、 一時 file からの rename で丸ごと入れ替え、 書き手は lock で 1 つずつ、 入力の印出力の元の目印が今の file より古い書きは捨てる。 file は導出物で真実を持たない。 (3) 全部の書き直し SHALL dispatch の周と器が台帳を書いた直後に撃ち、 管理 tick の周と発話 event の記帳の直後は台帳も git も撃たず、 event log の大きさに依らない読みで event log と時刻で決まる部分だけを書き直す。 起票の門が席の道具の呼び出しの台帳の書きを通した周と merge の門が器の便でない merge の command を通した周は、 同じ dir の lifecycle.stale に古さの印を書くだけで、 次の全部の書き直しがその入力より前の印を消し、 読み手は古さの印と入力の印で「古い」と描く。 (4) 便の終端の周の通知の語・doctor の未仕分けの発話と処置の待ちの memo の行・管理 tick の alarm・session の開始の事実行 SHALL 局面の関数と同じ判定の結果を使い写しの判定を持たない。 doctor の 1 行と事実行と alarm の語 owned は、 要件の部品を除き、 手番 seat の部品が局面ごとの rules 行 lifecycle.age_h を越えたものを数える。 (5) 読み手 (裁定面と席) は版の欄を読み、 知らない局面の語と欄を「まだ分からない」、 file が無いか読めない版の周を「測れない」と描き、 便の生の時刻の列は event log から読む。 出力は state dir ごとに 1 つ。 欄の名と JSON の形は設計 doc が持ち、 草稿を消費側の席に先に見せる。 (6) 受付 (FR68) が記帳する断りの event は kind IntakeRefused (key bead と refuse) で、 関数は入力として読むだけ。 (7) main に入る器の便でない commit SHALL 発端の trailer (名は NAME から導き本 repo では Scribe2-Source・値は bead の id) を 1 行以上持ち、 merge の門 SHALL 席の道具の呼び出しの merge の command が発端か run: の trailer を持つ本文を渡さない周を実行の前に欠けを名指して断り、 main-provenance SHALL その trailer の無い器の便でない commit を名指して落とす (どちらも形だけ・解けない発端はその commit の部品の misfit)。 (8) 消すもの: dispatcher の alarm_word の自前の判定と、 doctor の台帳 lint の (vi)(viii) のうち局面に代わる判定。 消費側の自前の局面の計算は消費側の行で外す。

局面の出力は、 前の版と次の版が共有する観測の面の中に 1 つの形として足します (ADR-0004 の観測の面の欄を部分的に置き換え、 既存の file の置き場は変えません)。 器は 1 つの関数で、 案件の部品 9 種 (発話・台帳の問い・memo・契約・便・契約表の行・要件・epic・器の便でない着地の commit) ごとに局面・手番・局面に入った時刻・理由・つながりを導きます。 局面は閉じた語で、 どれを優先するかは語を宣言した順だけで決め (憲法 C2)、 便の段の値は全部どれかの局面へ写ります。 理由には、 起動の列の待ちの理由・受付の断り・着地の終わり方・便の段の語をそのまま使います。 つながりには発端・子の問い・昇格した契約・便・着地の commit・仕分け済みの発話の行き先を載せ、 発話の部品は時刻と session と行き先だけで、 中身の字は載せません。 どの局面にも当たらない部品は misfit と理由の語 (edge-mismatch・reason-kind・unresolved-source など) で出します。 語の一覧・局面 (契約の待ちでは理由も) から手番への対応・理由の語の一覧は設計 doc の 1 節が正本です。 判定には台帳の全部・event log・main の契約表と SRS と trailer を使い、 窓 (規則の値
