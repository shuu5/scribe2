設計判断記録 (ADR) scribe2 — 席の口座の単位

席の口座を持つ単位は project の群で、群の宣言は host の面の 1 表・群の今の口座は host の根の記録 (役割 → 口座の ADR-0036 と役割の実効の記録の ADR-0041 を単位ごと置き換え・便用の選定は群の候補の口座を host 全体で外し・移動は新しい口座で新しい席を起こして機械の復帰に任せる・候補が無い周は移らず通知・初期化の口と鍵の欄は後続の ADR)

席の口座は project ごとの置き場に閉じていて、 複数の project の席を同じ口座にまとめる宣言も、 上限に当たった周にまとめて別の口座へ移す口も無い (実測 2026-09-19 = 席の口座が上限に当たり人が手で移した)。 本 ADR は口座を持つ単位を project の群に決め、 群の宣言と群の今の口座を host の面に置き、 便用の選定は群の候補の口座を host 全体で外し、 移動は新しい席を起こして機械の復帰に任せる形にする。 契機 (拍) と初期化の口と鍵の欄は本 ADR では決めない。

この判断が約束すること (1 文サマリ)

席（人と話す開発 session）がどの口座で立つかを、project 1 つずつでなく「project のかたまり（群）」ごとに決めます。どの project を同じかたまりにし、どの口座を候補にするかは、この machine に 1 つだけ在る宣言 file に書きます。いまそのかたまりがどの口座に居るかは、器が別の記録に書きます（人が書く宣言と、器が書く現状を分けます）。便（自動で走る実装の仕事）には、かたまりの候補になっている口座を 1 つも渡しません。口座が上限に近づいたら、かたまりごと別の口座へ移りますが、生きている対話を運ぶのではなく、新しい口座で新しい席を立てて、続きは器が台帳と git から組み直して渡します。移り先の候補が 1 つも無い回は、無理に移らず user に知らせます。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを、実測と現物と user の要求から説明します。席の口座が上限に当たって人が手で移した回が実際に在り、いま器には「どの project をまとめて同じ口座に置くか」を書く場所も、まとめて移す口もありません。前に決めた「役割ごとに 1 口座」は、役割が 1 つになった時点で分け方として働かず、しかも code には 1 行も入っていません。

CTX1

実測 — 席の口座が上限に当たり、 人が手で別の口座へ移した

2026-09-19 に席の口座が窓の上限に当たり、 user が手で別の口座へ移した (経緯の逐語は台帳 s2-07l.491 の notes)。 席が自分で判断して進む度合いを上げるほど、 上限で黙って止まる席は増える。 いまの器には、 止まった席を別の口座で立て直す口はあっても、 止まる前に移す判断も、 複数の project の席をまとめて移す単位も無い。

CTX2

現物 — 在るもの (口座の宣言・使用率の計測・閾値の行 1 本・便用の除外・口座を指定した起動)

口座 label の宣言は host の面 (state dir の host の manifest 1 file) の口座の表が持ち、 tracked の面と同じ loader・同じ 3 値 (無い = 0 宣言 / 読めた / 在るのに読めない = typed に止まる)・同じ拒否の形 (未知 key・型違い・両面の重複を行番号付きで全件) で読む (ADR-0026 §2.1・SRS FR57)。 口座ごとの窓の使用率は計測されて event log に残り、 session 用の閾値の rules 行が 1 本在る。 便用の口座選定は、 便の置き場 (anchor) の席の登録 row が持つ口座だけを候補から外す (置き場を共有する他の vessel の席の口座は候補に残す)。 席は口座を指定して起こせる。

CTX3

現物 — 無いもの (群の宣言・群単位の移動・host 全体の除外)、 および ADR-0036 / ADR-0041 が code に 1 行も無いこと

群の宣言・群単位の移動・移動の契機・host 全体での除外は、 どれも器に無い。 さらに ADR-0036 が決めた役割 → 口座の宣言 file と ADR-0041 が決めた役割の実効の記録は、 設計 doc と語彙には在るが code には 1 行も無い (実測 = その file 名は設計 doc にしか現れない)。 その 2 本が前提にしていた軸も残っていない — 席の役割は orchestrator の 1 つになり、 宣言と実効の記録を比べて席を移していた管理 tick は削除された (ADR-0045 §2 (2))。 つまり「役割ごとに 1 口座」は、 役割が 1 つになった時点で単位として働かない。

CTX4

要求 — user の 4 点と、 全口座が等価に交換できること

user の要求 (要旨・逐語は台帳 s2-07l.491 の notes) は 4 点である。 (1) 席の口座が上限に近づいたら自動で別の口座へ移す (2) 複数の project の席を同じ口座に置ける (3) project の群同じ口座にまとめて置く project のかたまりを作り、 群ごとに別の口座へまとめて置き、 上限が来たら群が一斉に同じ別の口座へ移る (4) 席の居る口座は便に使わない。 加えて、 全口座の設定は同一で等価に交換できることが前提である。 裁定は「実装の仕方は推奨の方法で」であり、 推奨は「移動 = 新しい口座で新しい席 + 機械の復帰」「段は宣言と点検 → 通知 → 自動の移動」であった。

CTX5

重い所 — 生きた対話を別の口座へ運ぶこと

要求 (1) の実装で唯一重いのは「生きた対話 session をそのまま別の口座へ移す」ことである。 対話の記録は口座ごとの置き場の下に在るので、 持ち越しには file の複写と起動行の再現が要る。 この host では全口座の置き場が 1 つの実体を共有しているため複写なしで持ち越せるが、 それは器の外の host の設定であって器が前提にできる形ではない (N3 = host 固有の値で分岐しない)。

CTX6

憲法の向き

C3 は状態の真実を 1 つの置き場に持ち host ごとの dir に真実を置かないことを、 C5 は rules 行の追加・変更に裁定 id を、 C10 は宣言値と実効値を型で分け昇格は測定を通すことを、 C10.3 は配線されていない設定を CI が拒むことを、 C17 は決定はしごと「足す前に消すものを名指す」ことを、 A1 は「使う」に当たる操作の承認を、 N3 は host 固有の値で分岐しないことを求める。 口座を消費する session を器が起こすことは A1 の「使う」に当たる。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 5 本のものさしです。口座を持つ分け方が 1 つに決まること、席の口座と便の口座が重ならないこと、移るのに生きた対話を運ばなくて済むこと、人が書く宣言と器が書く現状を分けて読み手の無い宣言を足さないこと、そして段階ごとに止められることです。

DR1口座を持つ単位が 1 つに決まり、 同じ単位の席がどの置き場からでも同じ口座に揃う CTX4 の要求 (2) / (3)・CTX3 (役割は単位として働かない)
DR2席の口座と便の口座が host 全体で交わらない CTX4 の要求 (4)・CTX2 (いまの除外は便の置き場の席だけ)
DR3移動が「生きた対話の持ち越し」を要らない (復帰の道は 1 本) CTX5・憲法 N3・圧縮 / 移動 / 異常終了が同じ復帰を通る
DR4宣言値と実効値を型と file で分け、 読み手の無い宣言を足さない 憲法 C10 / C10.3 / C17.2
DR5段で止められる (宣言と点検 → 通知 → 自動の移動) CTX4 の裁定・DR4 (段ごとに読み手が揃う)
03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 7 つ並べます。かたまりを分け方にする案、前の「役割ごと」を残す案、生きた対話を運ぶのを基準にする案、宣言を持たず起動のたびに選ぶ案、候補が無くても無理に移る案、導入の口や鍵の欄まで 1 本にまとめる案、そして便に渡さない口座を「いま居る 1 つ」だけに絞る案です。6 つ目は別の記録へ送ります。

OPT1口座を持つ単位を project の群にし、 宣言は host の面の 1 表・今の口座は host の根の記録・移動は新しい席 + 機械の復帰続きを人でなく器が組み立て直すこと採用

群 (名・置き場の列・候補の口座 label の順の列) を host の面の表 1 つで宣言し、 群の今の口座その群の席がいま実際に使っている口座は host の根の記録 1 件 (群ごとに高々 1 件) が実効値として持つ。 便用の選定は宣言のどの群の候補の口座も host 全体で外す。 上限に当たった周は群単位で 1 回だけ移り先を決め、 新しい口座で新しい席を起こして復帰は機械の注入に任せる。

project をいくつかのかたまりに分け、かたまりごとに「この口座を順に使う」という候補の並びを宣言します。宣言は人が書き、いまどの口座に居るかは器が別の記録に書きます。便にはかたまりの候補口座を渡しません。上限が近づいた回は、かたまり単位で 1 回だけ移り先を決め、新しい口座で新しい席を立てて、続きは器が組み直します。

+ 利点

  • 要求 (2) / (3) が単位 1 つで満たされ、 置き場が project ごとに分かれていても同じ群に入れられる
  • 要求 (4) が「宣言された候補の口座を便用から外す」1 つの規則になる
  • 移動の判定が host で 1 回・群単位・lock の内側に閉じるので、 同じ口座へ席が殺到する型が構造で消える
  • 圧縮・移動・異常終了が同じ 1 本の復帰を通る (実装が 1 本)
  • 宣言値 (候補の列) と実効値 (今の口座) が file も型も分かれる (C10)

− 欠点

  • host の根に実効の記録という置き場が 1 つ増える
  • 移動のたびに、 対話の文脈は機械が戻せるぶんしか残らない
  • 便が使える口座が群の候補のぶんだけ減る (今の口座 1 つだけを外す案は OPT7・却下)
OPT2役割 → 口座の宣言を残す (ADR-0036 の形のまま単位を役割にする)不採用

host の根に役割ごとの宣言 file を置き、 役割ごとに 1 口座を持つ。

前に決めた「役割ごとに 1 口座」をそのまま残す案です。書き直しは要りませんが、役割は 1 つになったので、全部の project の席が同じ 1 口座に集まることしか表せません。「かたまりごとに別の口座」という要求が書けず、そもそも code には 1 行も入っていません。

+ 利点

  • 既に決定記録と設計 doc と語彙が在る (書き直しが要らない)

− 欠点

  • 役割は orchestrator の 1 つになったので、 単位として働かない (全 project の席が 1 口座に集まる = 要求 (3) の「群ごとに別の口座」が表せない)
  • 宣言と実効を比べて席を移していた管理 tick が削除済みで、 移す軸が無い
  • code に 1 行も無いので「残す」の中身が無い (実測)
OPT3生きた対話を持ち越して別の口座へ移すのを基準の道にする不採用

対話の記録を複写し起動行を再現して、 同じ対話のまま別の口座で続ける。

生きている対話をそのまま別の口座へ持ち越すのを基準の道にする案です。文脈は 1 つも落ちませんが、対話の記録の置き場が共有されているかどうかは器の外の設定なので、それを当てにすると machine ごとの事情で動きが変わることになります。続きを戻す道も 2 本に分かれます。

+ 利点

  • 文脈が 1 つも落ちない
  • この host では置き場が共有されているので複写すら要らない

− 欠点

  • 置き場が共有かどうかは器の外の host の設定で、 器が前提にすると host 固有の値で分岐することになる (N3)
  • 復帰の道が 2 本になる (圧縮・異常終了は機械の復帰・移動だけ持ち越し)
  • 器が対話の記録を読む口を持つことになる (いまは 1 つも持たない)
OPT4群の宣言を持たず、 席が起きるたびに選定へ落とす不採用

席の口座は起動のたびに session 用の選定で決める。 宣言も記録も持たない。

かたまりの宣言を持たず、席を立てるたびにその場で空いている口座を選ぶ案です。いちばん小さくて済みますが、同じかたまりのはずの席がばらばらの口座に散り、席が立っていない間はその口座が便に取られます。

+ 利点

  • 置き場も表も増えない (いちばん小さい)

− 欠点

  • 同じ群のはずの席が別々の口座に散る (要求 (2) / (3) を満たさない)
  • 便用の除外便に渡してはいけない口座を候補から外すことが「いま席が居る口座」だけになり、 席が起きていない周は便に取られる (要求 (4) が周ごとに破れる)
  • 上限が来た周に群が一斉に移れない
OPT5妥協の移動 — 候補が無い周も閾値以上の口座へ群を移す不採用

移り先の候補が 1 つも無い周も、 いちばん余裕のある口座へ群を移して席を立てる。

移り先の候補が 1 つも無い回でも、いちばん余裕のある口座へかたまりごと移してしまう案です。席は止まりませんが、上限に当たっている口座へ移すだけなので止まる席が増え、移った先で便と口座が重なります。

+ 利点

  • 席が止まらない

− 欠点

  • 上限に当たっている口座へ群ごと移すので、 止まる席が増えるだけで解決しない
  • 移った先で便と口座が交わる (要求 (4) が破れる)
  • 「移った」という実効値が残るので、 次の周の判定が汚れる
OPT6初期化の口・consumer の rules の写しの廃止・外部 API の鍵の欄を同じ ADR に畳む不採用

導入を 1 command にする口 (host の面を作る口と置き場ごとの面を作る口・差分だけ出す形) と、 consumer が規則の写しを持たない形と、 外部 API の鍵を名乗る欄を、 本 ADR で一緒に決める。

かたまりの話と一緒に、導入を 1 コマンドにする口や、相手の repo が規則の写しを持たない形や、外部 API の鍵を名乗る欄まで、この 1 本で決めてしまう案です。まとまりは良くなりますが、1 つの記録が独立した 3 つの決定を抱えることになり、あとから片方だけ直せません。鍵の欄は読む側がまだ無いので、いま足すと「配線されていない設定」になります。別の記録へ送ります。

+ 利点

  • host の面と置き場の面を分ける話が 1 本にまとまる
  • 鍵の欄は 1 表で足りる

− 欠点

  • 1 つの決定記録が 3 つの独立した決定を持つことになる (後から片方だけ改訂できない)
  • 鍵の欄は読み手を持たないので、 いま決めて足すと配線されていない設定になる (C10.3)
  • 導入の口は本 ADR の群とは独立に決められる (依存が無い)
OPT7便用の除外を群の今の口座だけにする (候補の列の残りは便に開ける)不採用

便用の候補から外すのは「その群がいま居る口座」1 つだけとし、 記録が無い周は候補の先頭 1 つを外す。 候補の列の残りは便が使える。

便に渡さない口座を、かたまりの候補ぜんぶではなく「いまそのかたまりが居る 1 つ」だけに絞る案です。user の言い方にいちばん近く、便が使える口座もほとんど減りません。ただし便は口座を上限いっぱいまで使う側なので、候補の残りを便が先に使い切ってしまい、いざ移りたい回には移り先がどれも上限に近い、ということが起こります。つまり候補の列が逃げ道として働かなくなります。便に回せる量と逃げ道の広さは、候補をいくつ書くか（user が書く宣言）で調整できるので、この案で取り戻す必要はありません。加えて、外す口座を「器が書いた現状の記録」から決めることになるので、その記録が読めない回に何を外すかが決まりません。

+ 利点

  • user の要求 (4)「席の居る口座は便に使わない」の字面にいちばん近い
  • 便が使える口座が群ごとに 1 つしか減らないので、 便の容量が落ちない

− 欠点

  • 移り先になる候補を便が先に使い切る (実測 = 便用の選定の上限は 100 % の定数で、 便は口座を上限まで使う側の規則である。 一方で移り先の条件は閾値未満〔5 時間窓 85 ・ 7 日窓 95 ・ モデル別窓 95〕なので、 群が移りたい周には候補が全部閾値を越えている見込みが高い) ＝候補の列が逃げ道として働かない
  • 便の容量と逃げ道の釣り合いは、 候補の列の長さ (user が書く宣言値) で選べる。 この案で取り戻す必要が無い
  • 除外の規則が実効の記録の読みに依存する。 本 ADR は読めない記録を typed に止めると決めたので、 記録が読めない周の便用の除外が「止まる」か「黙って広がる」かの二択になり、 typed に決まらない (宣言値だけを読む OPT1 にはこの周が無い)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、それが要件書のどの要件を支えるかを示します。かたまりの宣言は machine ごとの宣言 file に 1 表として置き、いまの口座は別の記録が持ち、便の候補からはかたまりの候補口座を全部外し、移動は新しい席と器による続きの組み直しで行います。

採用 — OPT1
