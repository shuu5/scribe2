設計判断記録 (ADR) scribe2 — 箱の CPU の幅

箱の CPU の幅は受付の job 1 つの値段で閉じる — gate の verify 行を全部 host の受付に通し、 便と席の封じ込めの箱に CPU の上限 (CPUQuota) を付け、 host の core 数は cgroup の上限に左右されない 1 本で読む (ADR-0021 §2.2・ADR-0050・ADR-0072 を部分 supersede)

器が起こす子 process と席は memory の上限つきの箱で走るが、 CPU には重みしか無く上限が無い。 host の受付 (並列の枠) を通るのも変異検査の 1 行だけで、 gate の全件 test や clippy や契約の test、 runner の組み立て、 席の subagent の組み立ては、 1 本で host の core を全部取りにいく。 本 ADR は gate の verify 行を全部受付に通し、 便と席の箱に受付の job 1 つの値段の CPU の上限を付け、 core 数の読みを箱の上限に左右されない 1 本にすると決める。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「便」は契約 1 本を実装して取り込む 1 回の流れ、 「席」は人と AI が話す session です。 器が起こす作業 (検査の行・実装役・審査役) と席は、 memory の上限つきの囲い (箱) の中で走ります。 ところが CPU には「優先の重み」しか無く、 使える幅の上限がありません。 同時に何本走ってよいかを数える host の受付を通るのも変異検査の 1 行だけで、 全件の test や clippy、 契約の test、 実装役の組み立て、 席の組み立ては、 1 本で host の core を全部取りにいきます。 この記録は、 gate の検査の行を全部受付に通して同時の本数を数え、 便と席の箱に「1 本ぶんの core 数」(job 1 つの値段) の CPU の上限を付けると決めます。 32 core・値段の分母 4 の host なら 1 本は 8 core までです。 core 数は、 箱の上限に左右されない 1 本の読み口で数えます。 新しい設定の値は足さず、 既存の値と実測から幅を出します。 代わりに、 host が空いていても 1 本は 8 core までしか使わないことを引き受けます。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 6 つから説明します。 経緯 (CPU には重みしか無く、 前の記録が箱に上限を付ける案を退けたこと)・受付を通るのが変異検査の 1 行だけで全件の test が core を全部取りにいくこと・席と実装役の組み立てが縛られないこと・cgroup の上限の下で道具が core 数をどう読むかの実測・憲法の向き・この判断の範囲です。

CTX1

経緯 — CPU は重みだけで上限を持たず、 ADR-0050 は箱に上限を付ける案 (OPT6) を退けた

ADR-0021 §2.2 は器が起こす子 process を memory の上限つきの封じ込めの箱上限つきの囲いで走らせ、 CPU には重み (rules 行 gate.cpu_weight・値 50・席は既定の重み) だけを付けて上限を付けないと決め、 memory だけを硬い資源とした。 2026-09-20 の host の凍結 (変異検査の gate 6 本が同時に走り、 走行可能と待ちの process が積み上がった) の後、 ADR-0050 は core を硬い資源に加え、 受付 (並列の枠同時に走る数の枠) の枠に core の項を足し、 job 1 つの値段1 本ぶんの core 数 (実測の core 数を gate.mutants_jobs で割った thread 数) を器の 1 関数に置き、 行を撃つ前の遮断器を足した。 一方で「箱に CPU の上限を付けない形そのものは不変」とし、 scope に CPU の上限を付ける案 (OPT6) を、 上限は 1 本ずつを遅くするだけで積み上がる本数を減らさない、 遅くなった行が箱の中で長く居座り受付の枠を握ったままになる、 という理由で退けた。 ADR-0072 は席の起動行の頭に同じ語列の関数で memory の箱を付け、 席には CPU の重みを付けない (対話の席を便より軽くしない) と決めた。

CTX2

事象 — 受付を通るのは変異検査の 1 行だけで、 gate の全件 test も契約の test も core を全部取りにいく

受付を呼ぶのは gate の行の撃ち口の 1 か所で、 条件は vessel 宣言の行が穴 {jobs} を持つこと。 本 repo の共通 verify の 5 行 (全件 test・clippy・構造検査・依存の検査・入口の RED の検査) は {jobs} を持たず、 契約の verify 行は穴を持たないので、 どれも受付を通らない。 {jobs} を持つのは検出線 1 行で、 gate では撃たれない。 便の箱の語は MemoryMax と CPUWeight=50 と OOMPolicy だけで、 器は {jobs} を持たない行に並列度を渡さないので、 道具は既定の並列度 (core 数ぶんの thread) で走る。 遮断器は行を撃つ前の門で、 撃った後の 1 行が core を全部取ることは止めない。 消費側の席からの報告 (2026-09-29) では、 全テスト 1 回が CPU 1327 秒 (test の thread を 2 にすると 608 秒・組み立ては 80 秒で、 重いのは test の走行)、 gate の全件 test 1 行は受付の外で 158 秒・平均約 8 core を使った。

CTX3

事象 — 席の箱席を包む囲いには CPU の語が 1 つも無く、 席と subagent の組み立てと全テストは縛られない

席 (人と話す claude とその subagent の Bash) の箱は memory の上限だけを持つ。 消費側の席からの報告では、 席は起草の係ごとに repo の写しを作って試作を組み立て、 席の scope の合計が約 20 時間で 3022 core 分、 全テストの記録が約 70 回あった。 同じ報告は、 持ち主の要望として project 固有の知識でなく器の側で規制してほしいと伝えた (消費側の席の記録で、 器の裁定ではない)。 runner (実装役) の箱も同じく CPU の上限を持たず、 runner が撃つ組み立てと test は受付の外で走る。

CTX4

実測 — cgroup の上限の下で Rust の道具は thread を縮め、 affinity の列は上限に左右されず、 driver は席の箱の中に居る

本席の実測 (32 core の host・2026-09-29)。 systemd-run --user --scope -p CPUQuota=400% の中では、 Rust std の available_parallelism が 4 (cargo と nextest はこれで thread を縮める)、 nproc・/proc/stat の cpu の行・/proc/self/status の Cpus_allowed_list が 32。 taskset -c 0-5 の下の Cpus_allowed_list は 0-5 (6 本)。 CPUWeight=50 の中ではどれも 32 (重みでは thread は縮まない)。 CPU の上限の scope の中から systemd-run --user --scope で作った scope は外の scope の兄弟に置かれ、 外の上限を継がない。 dispatcher が起こした driver (pipe run の process) は、 それを撃った席の scope の中に居る。 したがって席の箱に上限を付けると、 driver の中で available_parallelism を読む受付と遮断器は、 席の幅を host の core 数と読み違える。 同じ読みは受付と遮断器の 2 か所に複製されている。

CTX5

憲法の向き (本 ADR の解釈)

C2 (経路は 1 本・env を読まない) から、 core 数の読み口core を数える口は 1 本にして複製を消し、 環境変数では渡さない。 C10 と N3 (host 固有の値は manifest か実測で、 host で code を分岐しない) から、 幅は host ごとの絶対値の宣言でなく、 実測の core 数と既存の rules 行から導く。 C5 (rules 行の変更は裁定 id つき) と C17 (足す前に要るか・既に在るかを問い、 何を消すかを名指す) から、 新しい rules 行を足さず、 既存の job 1 つの値段を使い回し、 受付の側の core 数の読みの複製を消す。

CTX6

射程 — 動かすのは受付の対象と箱の CPU の語と core 数の読みだけ

動かすのは (1) 受付を通る行の範囲 ({jobs} を持つ行だけ → gate の共通 verify・検出線・契約の verify の全部)、 (2) 便の箱と席の箱の語列に CPU の上限を足すこと、 (3) host の core 数の読み口。 動かさないのは、 受付の式と札の形と待ちと縮退と測れない周の扱い、 遮断器の判定と閾値、 箱の memory の上限の 2 種、 穴の置換、 CPU の重み (便は 50・席は付けない)、 席の起動の口と unit 名と起動の 1 行の字、 着地と intake の撃ち口が受付を通らないこと、 便の同時本数の上限 (ADR-0035)。 ADR を書く条件のうち 1 (ADR-0021 §2.2 と ADR-0050 の「不変」の読み替え) と 4 (ADR-0050 が退けた OPT6 を新しい事実で選び直す) に当たる。 SRS の改訂は伴わない (NFR6 と FR46 の範囲・FR59 は起動行の組み方の正本を決定記録に置く)。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 6 本のものさしです。 1 本が host を独り占めしないこと。 重い行が同時に何本走るかを host 単位で数えること。 道具の言語に依らないこと。 新しい設定の値を足さないこと。 取り込みと受け入れの検査を gate の後ろで待たせないこと。 core 数を、 読む側が居る箱の上限に左右されずに読むことです。

DR11 本が host を独り占めしない — 1 行・1 箱が使える core の幅に上限がある CTX2・CTX3
DR2同時の本数を数える — 重い行が同時に何本走るかを host 単位で数え、 走行可能の process の積み上がりを減らす CTX1・CTX2
DR3言語に依らない — 器は道具の言語ごとの知識 (thread の数を渡す環境変数など) を持たない CTX4・CTX5
DR4新しい値を足さない — 幅は既存の rules 行と実測の core 数から導く CTX1・CTX5
DR5着地と intake を止めない — 着地の実測と intake の base の実測を gate の札の後ろに並ばせない CTX6
DR6読み違えない — core 数の読みは、 読む process が居る箱の上限に左右されない CTX4
03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 8 つ並べます。 gate の検査の行を全部受付に通し、 便と席の箱に 1 本ぶんの core 数の上限を付ける案 (選んだ案) と、 選ばなかった 7 つです。 選ばなかった案は、 重みだけで分ける案・core の組を配る案・道具の thread の数を環境変数で渡す案・幅を新しい設定の値にする案・取り込みと受け入れの検査も受付に通す案・受付を通る行だけに上限を付ける案・席に受付を通す専用の口を用意する案です。

OPT1gate の verify 行を全部受付に通し、 便と席の箱に job 1 つの値段の CPU の上限を付ける採用

受付を gate の共通 verify・検出線・契約の verify の全部の行に広げ ({jobs} を持たない行は job 1 つ)、 便の箱に CPU の上限を付ける (受付が配った行は job 数 × thread 数、 それ以外の便の箱は job 1 つの値段)。 席の箱にも job 1 つの値段の上限を付け、 重みは付けない。 core 数は /proc/self/status の Cpus_allowed_list を数える 1 本で読む。 決め手は分析 (本数と幅の両方を閉じ、 新しい値を足さない)。

gate の検査の行を全部 host の受付に通し、 便と席の箱に 1 本ぶんの core 数の CPU の上限を付ける案です。 受付が配った行はもらった幅までを、 受付を通らない便の箱 (実装役・審査役・取り込みの検査) と席の箱は 1 本ぶんの core 数までを使えます。 core 数は、 この process が走ってよい core の一覧 (Cpus_allowed_list) を数える 1 本で読みます。 同時の本数と 1 本の幅の両方が閉じ、 上限の中の Rust の道具は thread の本数まで縮め、 言語に依らず効き、 新しい設定の値も足さない点で勝ります。 代わりに、 host が空いていても 1 本は 1 本ぶんの幅しか使えず、 Node と Python の道具は thread の本数が減らず、 受付を通らない箱と席の本数は数えず、 container の中では core を多く数え、 席の上限は起こし直した後から効きます。 分析で選びました。

+ 利点

  • gate の重い行の同時の本数が host 単位で数えられ、 受け付けた幅の和は core 数を越えない (DR2)
  • 1 行・1 箱・1 席の幅に上限が付き、 上限の中の Rust の道具は thread の本数そのものを縮める (DR1・CTX4 の実測)
  • 上限は CPU 時間の上限で、 道具の言語に依らず効く (DR3)
  • 新しい rules 行を足さず、 core 数の読みの複製を 1 本に消す (DR4・DR6)
  • 着地と intake の撃ち口は受付の外のまま待たない (DR5)

− 欠点

  • host が空いていても 1 行・1 箱・1 席は job 1 つの値段の幅しか使わない (32 core の host で 8 core)。 全件 test 1 行と席の組み立ては幅の分だけ長くなる
  • Node と Python の道具は cgroup の上限を読まず core 数ぶんの thread を立て、 上限で絞られる (上限にはなるが thread の本数は減らない)
  • 受付を通らない箱 (runner・lens・着地の実測・intake の base の実測) の本数は数えないので、 合計は core 数を越えうる (1 箱ずつは幅で閉じる)
  • cgroup の CPU の上限で絞られた container の中では、 Cpus_allowed_list は container の上限より多い core を数える
  • 今走っている席は起動行を読み直さないので、 席の上限は起こし直した後の席から効く
OPT2重みだけで分ける不採用

上限を付けず、 CPU の重み (席と便の比) だけを調整する。 決め手は実測 (重みでは道具の thread が縮まない)。

上限を付けず、 席と便の CPU の優先の重みだけを調整する案です。 host が空いているときに空いた core を全部使え、 箱の語列も変えずに済む点で勝ります。 けれども、 重みの中でも道具が読む core 数は 32 のままで、 thread の本数が縮まず、 順番待ちの process が積み上がる形が残ります。 混んだときに遅くなるだけで、 1 本が host を独り占めする形は止まりません。 退けました。

+ 利点

  • host が空いている周は、 どの箱も空いた core を全部使える
  • 箱の語列を変えずに済む

− 欠点

  • 重みの中でも道具が読む core 数は 32 のままで、 thread の本数が縮まず、 走行可能の process が積み上がる形が残る (DR2・CTX4)
  • 1 本が host を独り占めする形は、 混んだ周に遅くなるだけで止まらない (DR1)
OPT3affinity で core の組を配る不採用

taskset や AllowedCPUs で、 箱ごとに使える core の組を配る。 決め手は分析 (委ねられていない controller と配る勘定)。

箱ごとに使ってよい core の組 (0〜7 番など) を配る案です。 Rust 以外の道具も含め、 どの道具も core 数を小さく読む点で勝ります。 けれども、 core の組を配る仕組み (cpuset) は利用者の systemd に任されておらず効きません (実測)。 箱ごとに重ならない組を配る勘定も器が新しく持つことになります。 退けました。

+ 利点

  • Rust 以外の道具も含め、 どの道具も core 数を縮めて読む

− 欠点

  • user の systemd の manager に cpuset の controller が委ねられておらず、 AllowedCPUs は効かない (実測)
  • 箱ごとに重ならない core の組を配る勘定を器が新しく持つことになる (DR4)
OPT4道具の thread の数を環境変数で渡す不採用

CARGO_BUILD_JOBS や nextest の thread 数の環境変数を、 器が行や箱に渡す。 決め手は分析 (言語ごとの知識)。

道具ごとの thread の数の環境変数 (Rust の組み立ての並列度など) を器が渡す案です。 上限を付けずに thread の本数を直接決められる点で勝ります。 けれども、 道具の言語ごとの知識を器が持つことになり、 器が言語に依らない形が崩れます。 渡されない道具と、 席の subagent が撃つ command は縛られません。 検査の行は、 宣言の穴で thread の数を既に受け取れます。 退けました。

+ 利点

  • 上限を付けずに、 道具が立てる thread の本数を直接決められる

− 欠点

  • 道具の言語ごとの環境変数の知識を器が持つことになり、 器が言語に依らない形が崩れる (DR3)
  • 渡されない道具と、 席の subagent が撃つ command は縛られない (DR1)
  • 宣言の行は穴 {threads} で thread の数を既に受け取れる
OPT5幅を新しい rules 行にする不採用

箱や席の CPU の上限を、 絶対値か割合の新しい rules 行で宣言する。 決め手は分析 (host ごとの値と増殖)。

箱や席の CPU の上限を、 新しい設定の値 (rules 行) で宣言する案です。 席と便の幅を別々に決められる点で勝ります。 けれども、 core 数は host ごとに違うので、 絶対値で書くと host ごとに持ち主の裁定が要ります。 前の記録 (ADR-0050) の「枠のために新しい設定の値を足さない」にも反し、 既存の 1 本ぶんの core 数で足ります。 退けました。

+ 利点

  • 席と便の幅を別々に決められる

− 欠点

  • core 数は host ごとに違い、 絶対値の行は host ごとの裁定が要る (N3・DR4)
  • ADR-0050 の「枠のために新しい宣言値の rules 行を足さない」に反し、 既存の job 1 つの値段で足りる (C17・DR4)
OPT6着地の実測と intake の base の実測も受付に通す不採用

land の主実測・着地の列の候補の木・intake の base の実測も、 gate と同じく受付の札を取らせる。 決め手は分析 (着地と intake が待つ)。

取り込みの検査 (land の main での実測と、 並べて取り込む便の候補の木) と、 受け入れの検査 (intake の base での実測) も受付に通す案です。 host の重い行の本数を漏れなく数えられる点で勝ります。 けれども、 取り込みと受け入れが gate の札の後ろで、 受付の待ちの上限まで待つことになります。 取り込みは列で 1 本ずつ進むので、 待ちが列の全部の便に重なります。 退けました。

+ 利点

  • host の重い行の本数を漏れなく数えられる

− 欠点

  • 着地と intake が gate の札の後ろで、 受付の待ちの上限 (gate.slot_wait_s) まで待つ (DR5)
  • 着地は列で 1 本ずつ進むので、 待ちが列の全部の便に重なる
OPT7受付を通る行だけに上限を付ける不採用

受付が配った幅は上限で閉じるが、 受付を通らない便の箱 (runner・lens) と席の箱には上限を付けない。 決め手は分析 (runner と席が残る)。

受付が配った行だけに上限を付け、 受付を通らない便の箱 (実装役・審査役) と席の箱には上限を付けない案です。 席と実装役の組み立ては、 host が空いていれば core を全部使える点で勝ります。 けれども、 実装役の組み立てと test、 席の subagent の組み立てと全テストは、 gate の行と同じ重さで受付の外に残ります。 消費側の報告では、 席の囲いの合計が約 20 時間で 3022 core 分でした。 退けました。

+ 利点

  • 席と runner の組み立ては、 host が空いていれば core を全部使える

− 欠点

  • runner の組み立てと test、 席の subagent の組み立てと全テストは、 gate の行と同じ重さで受付の外に残る (DR1・CTX3)
OPT8席に受付を通す専用の口を用意する不採用

席と subagent が重い command を、 受付の札を取って上限つきの箱で撃つ器の口を足す。 決め手は分析 (使わない command が縛られない)。

席と subagent が重い command を撃つとき、 受付の札を取って上限つきの箱で撃つ器の口を新しく用意する案です。 席の重い command も受付の本数に数えられる点で勝ります。 けれども、 その口を使わない command は縛られず、 使うかどうかが散文の決まりに残ります。 subagent の command は器の見張りを通らないことがあり、 口へ寄せるよう強制できません。 退けました。

+ 利点

  • 席の重い command も受付の本数に数えられる

− 欠点

  • 口を使わない command は縛られず、 使うかどうかが散文の規律に残る (DR1)
  • subagent の Bash は hook を通らない周が在り、 口へ寄せる強制ができない
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 core 数は 1 本の読み口で数え、 gate の検査の行は全部受付を通り、 便の箱は受付が配った幅 (配らない箱は 1 本ぶんの core 数) を上限にし、 席の箱も同じ上限を持ちます。 支えるのは NFR6 (host の資源)・FR46 (囲いや枠が使えない host で止めずに進むこと)・FR59 (席の起動行の組み方) への主張です。

採用 — OPT1

器 SHALL host の core 数を 1 本の読み口で読み、 読み口 SHALL この process の /proc/self/status の Cpus_allowed_list の区間の列を数える (affinity と cpuset は数に効き、 cgroup の CPU 時間の上限は効かない。 Rust std の available_parallelism と環境変数を読まない。 読めない・形が違う・0 は読めない周とする)。 受付の core の項と遮断器の閾値 SHALL この 1 本を読み、 受付の側の読みの複製を消す。 gate SHALL 共通 verify・検出線・契約の verify の行を全部 host の受付に通し (write-set の照合の段は行を撃たない)、 穴 {jobs} を持たない行 SHALL 包めるかに依らず job 1 つを求める。 受付の式・札の形・待ち・縮退 (job 1 かつ thread 1)・測れない周の扱い SHALL NOT 変えない。 land の主実測・着地の列の候補の木・intake の base の実測 SHALL 受付を通さない。 便の封じ込めの箱 SHALL CPU の上限 (CPUQuota) を持ち、 値 SHALL 受付が配った行は job 数 × thread 数 × 100% (縮退と測れない周は 100%)、 それ以外の便の箱 (受付を通らない行・runner・lens・claude の包み) は job 1 つの値段 (実測の core 数を埋め込みの manifest の rules 行 gate.mutants_jobs で割った thread 数・1 の床) × 100% とする。 core 数を読めない周 SHALL 上限の語を置かない (止めない・縮退の側)。 箱の語列 SHALL 1 関数が MemoryMax → CPUWeight → CPUQuota → OOMPolicy の順で組み、 scope を試しに作る probe SHALL 受付を通らない便の箱の形で撃つ。 席の箱 SHALL 便の箱の既定と同じ job 1 つの値段の CPU の上限を持ち、 CPU の重み SHALL 今のまま付けない。 器 SHALL NOT 幅のために新しい rules 行を足さず、 gate.cpu_weight SHALL 便の箱に付けたままとする。

器は host の core 数を 1 本の読み口で読みます。 この process が走ってよい core の一覧 (Cpus_allowed_list) を数え、 cgroup の CPU の上限には左右されません。 受付と、 混んだ host で検査を待たせる仕組み (遮断器) はこの 1 本を読み、 受付の側の同じ読みの写しは消します。 gate は、 共通の検査・変異検査・契約の検査の行を全部受付に通し、 並列度の穴 ({jobs}) を持たない行 (全件の test や clippy、 契約の検査) は 1 本ぶんを求めます。 受付の計算・札・待ち・待ち切れないときの縮み方は変えません。 取り込みの検査と受け入れの検査は受付に通しません。 便の箱は CPU の上限を持ち、 受付が配った行はもらった本数 × thread 数ぶん (縮んだときは 1 core)、 それ以外の便の箱は 1 本ぶんの core 数 (core 数を設定の値 gate.mutants_jobs で割った数) までです。 core 数を読めないときは上限を付けずに進みます。 箱の語列は 1 つの関数が memory の上限 → CPU の重み → CPU の上限 → OOM の扱いの順で組みます。 席の箱も同じ 1 本ぶんの上限を持ち、 CPU の重みは今のまま付けません。 幅のための新しい設定の値は足さず、 便の箱の CPU の重みはそのまま残します。 前の記録 (ADR-0050) が箱に CPU の上限を付ける案を退けた理由は 2 つでした。 1 つ目は「上限は 1 本ずつを遅くするだけで、 積み上がる本数を減らさない」です。 今回は、 gate の重い行の本数を受付で数えるようにしたうえで上限を付けます。 さらに実測で、 上限の中の Rust の道具は読む core 数が上限の幅まで縮み、 立てる thread の本数そのものが減ると分かりました。 重みでは core 数が縮まず、 本数は減りません。 そのため 1 つ目の理由は成り立たなくなりました。 2 つ目の「遅くなった行が枠を握ったまま居座る」は引き受けます。 行の幅は札で払った値段と等しく、 受け付けた幅の和は core 数を越えないからです。 幅を新しい設定の値にしないのは、 core 数が host ごとに違い、 既存の 1 本ぶんの core 数で足りるからです。 core 数の読みを替えるのは、 器の運転役 (driver) が席の箱の中で走るからです。 席の箱に上限を付けると、 今の読み方では受付と遮断器が席の幅を host の core 数と読み違えます。 取り込みと受け入れの検査を受付に通さないのは、 取り込みの列を gate の札の後ろで待たせないためで、 幅の上限だけで閉じます。 環境変数で thread の数を渡さないのは、 器が道具の言語を知らずに済むようにするためです。 上限は CPU 時間の上限で、 どの言語の道具にも効きます。

この判断が正当化する要件 (cross-doc 照会 → SRS-SCRIBE2-MVP)

NFR6claimNFR6 (host の資源) の決定の側。 器の子 process は封じ込めの箱の中で走り、 並列度は host 全体の並列の枠から決める。 本 ADR はその枠を変異検査の行から gate の全部の verify 行へ広げ、 箱の CPU の幅を受付が配った幅 (配らない箱は job 1 つの値段) で閉じ、 core 数の読みを箱の上限に左右されない 1 本にする。 record の並列度・封じ込めの有無・縮退の理由の欄は変えない。
FR46claimFR46 (封じ込めか並列の枠が使えない host の縮退) の決定の側。 core 数を読めない周は CPU の上限の語を置かずに進み (止めない)、 受付の縮退と測れない周は job 1 かつ thread 1 のまま箱の上限を 100% とし、 CPU の controller を委ねない host は今の CPU の重みと同じく probe で縮退する (新しい失敗の形を足さない)。

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなること 4 つと、 代わりに引き受けること 7 つです。 良くなるのは、 重い行の同時の本数が数えられること、 1 本が core を全部取る形が無くなること、 言語に依らず新しい値も増えないこと、 席の箱の中の driver が core 数を読み違えないことです。 引き受けるのは、 host が空いていても 1 本は 8 core までしか使わないこと、 Node と Python の道具は thread の本数が減らないこと、 受付を通らない箱と席の本数は数えないこと、 受付の memory の勘定と箱の大きさがずれること、 container の中では core を多く数えること、 席の上限は起こし直した後から効くこと、 消費側の検査の行も受付で待つことです。

✓ 良い結果

  • ●gate の重い行が同時に何本走るかが host 単位で数えられ、 受け付けた幅の和は core 数を越えない
  • ●1 行・1 箱・1 席が host の core を全部取る形が無くなり、 上限の中の Rust の道具は thread の本数そのものを縮める
  • ●上限は道具の言語に依らず効き、 新しい rules 行は増えず、 core 数の読み口は 2 本から 1 本になる
  • ●席の箱の中に居る driver も、 host の core 数を読み違えない

⚖ トレードオフ・代償

  • ●host が空いていても、 1 行・1 箱・1 席は job 1 つの値段の幅しか使わない (32 core・gate.mutants_jobs 4 の host で 8 core)。 全件 test 1 行と席の組み立ては幅の分だけ長くなる
  • ●Node と Python の道具は cgroup の上限を読まず、 core 数ぶんの thread を立てて上限で絞られる (上限にはなるが thread の本数は減らない)
  • ●受付を通らない箱 (runner・lens・着地の実測・候補の木・intake の base の実測) と席の本数は数えないので、 合計は core 数を越えうる (1 箱ずつは幅で閉じる)
  • ●受付は {jobs} を持たない行の札も job 1 つの memory として数えるが、 その行の箱の memory は host の残りのまま (勘定と箱の大きさがずれる)
  • ●cgroup の CPU の上限で絞られた container の中では、 Cpus_allowed_list は container の上限より多い core を数える (器は user の session manager が在る machine を前提とする)
  • ●今走っている席は起動行を読み直さないので、 席の上限は binary を入れ替えた後に起こし直した席から効く
  • ●消費側の宣言の {jobs} を持たない共通 verify も受付の札を取り、 混んだ host では gate の行が受付で待つ (待ちの上限の後は job 1 かつ thread 1 で進む)
