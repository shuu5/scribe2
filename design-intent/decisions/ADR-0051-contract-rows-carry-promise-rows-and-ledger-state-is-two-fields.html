設計判断記録 (ADR) scribe2 — 契約と memo の形

契約表の行は約束の行から write-set と verify と done を導き、 台帳の memo と契約の状態は label と受入条件の 2 つの field で閉じる (新規の行は手書きの write-set と散文の対応表を持たず、 台帳の bead は契約表から生成した plan を席が撃つ・ADR-0023 §2.1 の「契約の正本は行 1 本」は不変)

契約の審査で落ちた 104 件の 87 % は、 write-set の閉包・名指しの実在・done と歯と verify の 1:1 という計算できる性質だった。 設計者 (AI) が散文の約束から write-set と verify と done を手で写す工程が、 その落ち方の全部の出所である。 本 ADR は約束を 1 行 1 約束の子行にして写す工程を器の導出に置き換え、 台帳の memo と契約の状態を 2 つの field の 4 象限で閉じ、 台帳の起票を契約表からの生成にする。

この判断が約束すること (1 文サマリ)

契約が審査で落ちた 104 件を数えたところ、87 % は「触る file の一覧が足りない」「名指した関数が無い」「約束と検証の行と完了条件の対応がずれた」という、機械で計算できる理由でした。原因は 1 つで、設計者（AI）が散文で書いた約束から、触る file の一覧・検証の行・完了条件を手で書き写しているからです。この記録では、約束を「1 行に 1 つ」の表にして、書き写す作業を器の計算に置き換えます。審査の lens には約束の 4 欄だけを渡し、見るのは「歯が中身を持つか」と「目標と完了条件が矛盾しないか」だけにします。台帳の側では、memo か契約かを「label が在るか」と「受入条件に設計への 1 行が在るか」の 2 つだけで決め、それ以外の組み合わせは壊れているとして doctor が名指します。契約の bead は設計書の表から機械が下書きを作り、人はそれを撃つだけにします。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを、実測と現物から説明します。審査で落ちた理由の 87 % は計算できる性質で、器には触る file の一覧を導く仕組みが既に在るのに、161 行のうち 151 行はその入力を人が手で埋めています。約束と検証の行と完了条件の対応は散文の規則で、器は測っていません。台帳では memo と契約の境が field に無く、memo を機械で引けません。

CTX1

実測 — 契約の審査で落ちた理由の 87 % は計算できる性質

run dir の残る全便の審査の FAIL と INCONCLUSIVE は 104 件で、 write-set の閉包が 51・名指しの不在が 17・done と約束の 1:1 の崩れが 11・verify の filter が 11・歯の空虚が 5・snapshot が 1・その他が 8 である (2026-09-21 の分類・逐語は台帳 s2-07l.510)。 実装席の問い 19 件のうち 16 件は write-set の不足である。 9 月 17 日以後は設計 doc の PR が 157 本に対して着地は 63 bead で、 1 bead の着地に平均 2 便を費やしている。 lens (LLM) の判断が要る理由は歯の空虚と goal の矛盾の 1 割強しか無い。

CTX2

現物 — 導出は在るが使われず、 設計者が閉包を欄で手書きしている

契約表の行の欄は 16 で、 tracked の 161 行のうち surfaces と creates と classes と opens を使う行は 0、 write-set は手書き (Declared) が 151・導出 (Derived) が 10 である。 導出そのものは land 済みで、 touches の閉包と歯の置き場と外形 pin と creates と also の和を取る。 しかし導出の入力 (touches / surfaces / tests / also) を設計者が手で埋める形なので、 設計者は結局 write-set と同じ閉包を別の欄で書いている。 閉包の穴は審査の lens と実装席の問いでしか見つからず、 直しは設計 doc の PR と再受付 (便 1 本ぶん) を費やす。

CTX3

現物 — 約束と done と歯と verify の 1:1 は散文の規則

各設計 doc の節は「約束 ↔ done ↔ 歯 ↔ verify」の対応を散文の段落で持ち、 器はそれを測らない。 done の字面の崩れ 11 件と verify の filter の誤り 11 件はこの写しの誤りである。 verify の filter は fn 名の部分一致なので、 裸の接頭辞が別の歯に当たって write-set を広げる事故も起きた。 insta の snapshot の名は歯の fn 名から導ける形が 15 本中 12 本で、 名付きの 3 本は fn 名から導けない。

CTX4

現物 — 台帳の memo と契約の境が field に無い

memo の弁別は label intake:memo、 契約の弁別は受入条件の設計 pointer の 1 行で、 両方在る形と両方無い形は禁じられていない。 memo の本文は自由文で出所も昇格の条件も書式が無く、 bd search は title だけを見るので議題に当たる memo を機械で引けない (user の指摘 2026-09-20)。 契約表の行から bead を起こすのは席の手で、 label の継承と edge の張り忘れが起きる — open 93 bead のうち本文で id を名指すのに edge の無い対が 91 あり、 label の体系を後から 76 bead に機械で足した (2026-09-21 実測)。

CTX5

現物 — bd 1.1.0 の型と field と lint

bd の型は built-in 9 と設定の custom 型で、 bd lint の必須節は built-in の型に固定され custom 型の節は測らない。 create の field は受入条件・設計・spec の id・外部参照・metadata (JSON)・依存 (10 種)・defer・見積・複数 bead を 1 回で作る graph を持つ。 器の台帳の口は読みが全件 JSON の 1 本、 書きが close の 1 種だけである (ADR-0045 §2 の dispatcher の着地)。 台帳 lint は契約表の行 e (contract-source.md §6) が pointer の解けない契約・pointer 無しの memo・本文を持つ契約の 3 欠陥を数える形で設計済み (未着地)。

CTX6

user の裁定と憲法の向き

user の裁定 (要旨・逐語は台帳 s2-07l.510 の notes) は「memo と契約の形は閉じ切る話で、 例外が生まれる開いた話ではない。 LLM に任せ切らず形をシステミックに作り、 beads の機能と合わせて先に設計する」で、 デメリット 5 つ (移行・可読性・新設の名指し・器の先行投資・緑への過信) の提示の後に案 A (約束を行に落とす) を是認した。 憲法は、 規則を散文でなく行に持つこと (C1)、 判定関数を 1 本にし散文の免除を持たないこと (C2)、 宣言値を測定なしに実効へ上げないこと (C10)、 bead が持つのは task と裁定だけであること (C15)、 足す前に消すものを名指すこと (C17)、 散文にしか無い規則を規則として扱わないこと (N2) を求める。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 5 本のものさしです。計算できる理由で落ちる工程を人の写しから器の導出に変えること、lens が見る面と器が測る面を重ねないこと、契約の正本を設計書の行 1 本のままにすること、memo と契約の状態を field の値だけで判定できること、そして着地済みの行と bead は書き換えないことです。

03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 6 つ並べます。約束を子行にして導出と生成に置き換える案、散文を残して閉包の計算だけ足す案、約束を台帳の bead の field に置く案、実装席の回答で触る file の一覧を広げる案、memo を beads の独自の型で名乗る案、器が台帳へ直接起票する案です。

OPT1約束を 1 行 1 約束の子行にして write-set と verify と done を導き、 memo と契約の状態を 2 field の 4 象限memo か契約かを 2 つの印の有無だけで決める表で閉じ、 台帳を契約表から生成する採用

契約表の行の下に約束の子行 (親の行 id・番号・約束の文・触る file・名指す識別子・歯の完全名・置き場・fixture の形・観測する結果) を置く。 子行を持つ行は手書きの write-set と done を持てず、 器が子行から導出の入力を組んで write-set を導き、 歯の完全名から verify の行を、 観測する結果から done を生成する。 lens には約束の 4 欄だけを渡し、 verdict の理由を歯の空虚と goal の矛盾とその他の 3 値に限る。 台帳では memo の識別を label の 1 つ、 契約の識別を受入条件の pointer 行の 1 つとし、 2 つの有無の 4 象限のうち 2 形を違反として lint が名指す。 台帳の bead は契約表の未着地の行から xtask が plan を出し、 席がそれを撃つ。 これから起きる memo は器の口 1 つ (便の終端か user の要望) が plan を出し、 起票は PreToolUse の guard が 4 節を要求し、 memo の close は着地の終端が行う (回り続ける周の入口と出口を器が持つ)。

契約の行の下に「約束の行」を置く案です。1 行が 1 つの約束で、約束の文・触る file・名指す関数や型・歯の名前・歯の置き場・試す材料の形・観測する結果を欄に書きます。器はこの欄から触る file の一覧を導き、歯の名前から検証の行を、観測する結果から完了条件を作ります。人が書き写す作業が無くなるので、写し間違いも無くなります。lens には約束の 4 欄だけを渡し、器が測った面は見せません。台帳では memo と契約を 2 つの印だけで決め、契約の bead は設計書の表から機械が下書きを作ります。これから起きる memo も器の口が下書きを作り、起票は hook が門になって形を確かめ、memo を閉じるのは着地の終端が行います。

+ 利点

  • 落ちる理由の 87 % を占める写しの工程散文の約束から write-set や検証の行を人が書き写す作業が消え、 1 bead あたりの便の数が下がる
  • 器が測る面 (閉包・実在・1:1) と lens が見る面 (空虚・矛盾) が重ならない
  • 契約の正本は行 1 本のまま (子行は同じ表の中・ADR-0023 は不変)
  • memo と契約の状態が 2 field で閉じ、 lint が違反を件数と母集団と id で名指す
  • 台帳の起票が生成になり、 label の継承や edge の張り忘れという手番の事故が消える
  • 着地済みの行と bead は触らない (新規と未着地だけが新形)

− 欠点

  • 約束の行契約が守る 1 つの約束を、 表の 1 行に書いたものの欄 9 つと parser の型 2 値・受付の断り 2 値・lint の項目 3 つ・xtask の口 1 つが増える
  • 新形と旧形の行が併存する期間、 受付と lint が 2 形を読む
  • 子行は散文より読みにくい (人が読む要旨は節の散文に残す二層になる)
  • 新設の識別子は着地の前は base に無いので、 write-set の + と同じ印と極性の 2 面が識別子にも要る
OPT2散文の節を残し、 閉包の計算だけを足す (案 B)不採用

約束の行を作らず、 手書きの write-set に対して閉包の計算を先に当てて不足を名指す。

設計書の散文はそのままに、触る file の一覧の不足を機械で先に見つける案です。移行は要りませんが、器には既に同じ仕組みが在って 151 行が使っていないのが現状で、入力を人が書く限り同じ理由で落ち続けます。約束と検証の行と完了条件の対応のずれも残ります。

+ 利点

  • 設計 doc の形が変わらず移行が要らない
  • 人が読む節がそのまま残る

− 欠点

  • 導出 (Derived) が既にこの形で、 151 行が使っていない — 入力の手書きが残る限り同じ理由で落ちる
  • done と歯と verify の 1:1 は散文のままで、 その 22 件は消えない
  • lens が閉包も見続けるので、 器と lens の面が重なったまま
OPT3約束を台帳の bead の field に置く不採用

約束の一覧を bead の受入条件か metadata に持たせ、 器が台帳を読んで導出する。

約束の一覧を設計書ではなく台帳の bead に持たせる案です。設計書の読み手を変えずに済みますが、契約の正本が設計書から台帳へ動いてしまい、CI が台帳に届かないので契約の検査が CI で回らなくなります。

+ 利点

  • 設計 doc の parser を触らない
  • beads の field をそのまま使える

− 欠点

  • 契約の正本が設計 doc の行から台帳へ動く (ADR-0023 §2.1 と FR47 に反する)
  • CI が台帳に届かないので、 契約表の検査が CI で回らなくなる (FR55)
  • 台帳の書きが close の 1 種から増える (ADR-0045 §2)
OPT4実装席の回答で write-set を広げる不採用

実装席の「write-set に file が足りない」の問いに席が回答し、 器が写しの write-set を広げて再開する。

実装席が「この file も触りたい」と聞いてきたとき、席が答えて器が一覧を広げる案です。便を捨てずに続けられますが、審査したときの契約と検査するときの契約が別物になり、設計書の穴も塞がりません。約束の行が先に穴を拾えば、この形の問いはほとんど起きなくなります。

+ 利点

  • 便を 1 本捨てずに続きから再開できる
  • 設計 doc の PR が要らない

− 欠点

  • 契約 file の sha が便の途中で変わり、 審査した契約と gate が測る契約が別物になる (C10・contract-source.md §7 の決定に反する)
  • 閉包の穴を設計の側で塞がないので、 同じ穴が次の便でも開く
  • 約束の行が閉包を先に拾えば、 この形の問いは字面走査の下界の外だけになる (16 件のほぼ全部が消える)
OPT5memo を bd の custom 型で名乗る不採用

設定に memo 型を足し、 label でなく型で memo を弁別する。

beads の設定に memo という型を足して、label ではなく型で memo を見分ける案です。型は 1 つしか付かないので見分けは強くなりますが、beads の節の検査は組み込みの型にしか効かず、結局 器の側で節を数えることになります。見分けの印が label と型の 2 つになって組み合わせも倍に増えます。

+ 利点

  • 型は 1 bead に 1 つなので label より排他が強い
  • bd の一覧が型で絞れる

− 欠点

  • bd lint の必須節も validate も built-in 型に固定で、 custom 型には効かない (節の検査は結局 器の lint が持つ)
  • 弁別の識別子が label と型の 2 つになり、 4 象限が 8 象限になる
  • 既存の 16 memo の型を書き換える手番が要る
OPT6器が台帳へ起票する不採用

xtask が plan を出すだけでなく、 器が bd を撃って bead と edge を作る。

下書きを出すだけでなく、器が台帳へ直接 bead と依存を書き込む案です。人の手番が 1 つ減りますが、器が台帳へ書く口が close の 1 種から増え、起票という「出す」側の操作を器が握ることになります。下書きと台帳のずれは doctor が数えれば足ります。

+ 利点

  • 席の手番が 1 つ減る
  • plan と台帳の drift が原理的に 0 になる

− 欠点

  • 台帳の書きの口が close の 1 種から増える (ADR-0045 §2・C15)
  • 起票は「出す」側の操作で、 起票の可否は席の判断 (憲法 A1 の 3 クラスに接する)
  • drift は lint が件数と母集団で名指せば足りる
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、それが要件書のどの要件を支えるかを示します。約束の行から触る file の一覧と検証の行と完了条件を器が導き、審査の lens は約束の 4 欄だけを読みます。台帳では 2 つの印の有無で memo と契約を決め、違反と節の欠けを doctor が数え、契約の bead は設計書の表から作った下書きを席が撃ちます。

採用 — OPT1

契約表 SHALL 行の子行として約束の行を持ち、 約束の行 SHALL 親の行 id・番号・約束の文・触る file・名指す識別子・歯の完全名・置き場・fixture の形・観測する結果の閉じた 9 欄とする (欄の集合の正本は core の型・文書は生成物 contracts/schema.toml を指す・ADR-0013 §2.1)。 約束の行を 1 つでも持つ行 SHALL 手書きの write-set と touches と surfaces と tests と also と creates と done を持たず、 持つ行 SHALL 受付と CI の契約表の検査が同じ語彙で断る。 器 SHALL 約束の行から導出の入力 (閉じた型に解ける識別子 → touches・+ の file → creates・.rs でない file → also・置き場 → tests・外形の歯と名付き snapshot の歯 → surfaces) を組み、 既存の導出の 1 本で write-set を導く (導出の 2 本目 SHALL NOT 作らない・C2)。 器 SHALL 歯の完全名を crate と scope で束ねて verify の行を生成し、 観測する結果を番号順に並べて done を生成し、 生成値 SHALL 契約 file にだけ載る
