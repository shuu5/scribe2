§1. Context

便を何本か同時に流すと、 2 本が同じ file を触っていたときに、 後から着地する便が main に追いつこうとして衝突します。 いまの器は衝突した便を「失敗」で止め、 その worktree を畳む口もありません。 user は「並列で速度を上げたいが、 review で範囲が広がって後から重なることは絶対にありうる。 誰がどう解くかを決めておかないと、 全部 admin に集まって詰まる」と問い、 planner の提案 (入口で重なりを排他し、 起きたら実装役に解かせ、 人は質問への回答でだけ関わる) を採り、 「本当に両方が働くかの歯は必須」と裁定しました。 この記録はその形を決めます。

記録時点 (2026-09-12) の現物: 便 1 本 = worktree 1 つ + runner 1 つ (FR4)。 runner は契約の write-set の外を編集できない (write-set guard・ADR-0009 §2.1。 ただし同 §2.1 が言うとおり fence は Bash では守れず、 構造の fence は gate の照合〔同 §2.4〕が担う)。 land は base が main の祖先なら worktree の branch を main へ rebase し、 RunStage stage=Implemented detail=rebase:<old>..<new> で段を戻して gate を撃ち直す (設計 pipeline.md §5.4)。 base の読み手 (base_of_run) はその rebase: 行の新しい側だけを base にし、 gate は <base>..HEAD の 2 点 diff を write-set と照合する。 rebase が衝突した周は git rebase --abort で木を戻し Failed detail=rebase-conflict で終端する。 pipe retire が畳めるのは Landed と Failed detail=rebase-empty だけで、 衝突で終端した便も gate FAIL で止まった便 (段は Gated のまま終端・pipeline.md §4) も畳めない (台帳 s2-07l.132)。 pipe stop --all は Live な席を持つ run にだけ RunStopped を書く (runner が終わった便は止まらない)。 intake は verify 行の形を検査する (ADR-0009 §2.2・Unfit は行 1 本の理由の閉じた enum で、 契約単位の拒否〔git repo でない・同じ秒の再 intake〕は散文の理由) が、 live な他の便の write-set と照合しない。 並列に 2 本を流した実測は歯の toy repo に在る (pipeline.md §9: 3 組 6 run で runner 2 本が同時に生き、 write-set が交わる 3 本目は stale base / CAS で止まった) が、 本番 repo の便は 1 本ずつで、 交差する契約を入口で断る判定と衝突を解く経路は無い。 便の途中で範囲が広がる経路は runner の質問 → planner の回答だけ (lens は読むだけ)。

憲法の向き: C2 は選択・除外・routing を 1 enum の 1 関数で持ち、 新しい理由は variant 1 つで表す。 C16 は逸脱を edit time で止め、 事後検証で代えない。 C6 は起動口を 1 つ (Budget を要する spawn) に限る。 C11.2 と ADR-0014 §2.1 は「行為 (編集・起動・merge・書込) を止めうる判定を返す境界」を guard と定め、 全 guard を極性一覧に載せる。 C3.3 は free text を判定の入力にしない向きを持つ。 C14.2 は文書に在って manifest に無い rules 行を drift と見る。 N1 は器が管理する物の不可逆な削除を拒み、 N1.2 は退役を可逆な move に限る。 ADR-0016 §2.5 は「契約の write-set の交差を intake で検査する形」を本 ADR の決定ではないと明記して残した。 user の裁定 (2026-09-12・会話面・逐語は台帳 s2-07l.143 の notes): planner の推奨 (入口で排他 + 起きたら runner が解く・人は質問経由のみ) でよい・歯は必須。 上限の値の裁定も同 notes (裁定 id 付き)。

§2. Decision

§2.1 intake は live な便 (終端でない run) の write-set と交差する契約を受け付けない (契約単位の拒否は 1 enum の 1 関数・C2)

便を受け付ける入口で、 まだ終わっていない便が触る file と重なる契約は断ります。 「終わっていない」とは、 着地も失敗も停止もしておらず、 審査で不合格にもなっていない便のことです。 断る理由は「契約を断る理由の一覧」(閉じた一覧) に足し、 判定は 1 本の関数です。 重なりの判定は path の集合の共通部分で、 dir はその配下の file を含みます。 放置された便が邪魔なら、 その便を 1 本だけ止める口で外します。 断られた契約は、 重なる便が終わってから出し直します。

pipe intake SHALL 契約の write-set を、 live な便の write-set (各 run の契約の写し) と照合し、 交差する周は受け付けない (run を作らず event を書かない)。 live な便 SHALL「終端でない run」と定義する: 終端 = 段が Landed / Failed / Stopped のいずれか、 または Gated で verdict が FAIL (verdict の読み手は既存の 1 本・pipeline.md §4「FAIL は終端」)。 判定は段の閉じた enum の網羅 match で書く (段が増えれば compile で気付く)。 交差の定義 SHALL path の集合の共通部分が空でないこととし、 末尾 / の dir はその配下の path を含む (正規化: 先頭の ./・重複する /・.. の畳み込みを write-set guard と同じ規則で行う・symlink は解かない＝実体が同じ file を別名で持つ 2 契約は見逃す側で、 その穴は編集時の guard が実体名で塞ぎ、 Bash の git 経路は ADR-0009 §2.1 の既知の穴のまま)。 契約 file が読めた後の契約単位の拒否 (git repo でない・同じ秒の再 intake・交差・写しを読めない) SHALL 閉じた enum 1 つ (Refuse・既存の散文の理由を variant に集め、 WriteSetOverlap と WriteSetUnreadable を宣言順の末尾に足す) を返す関数 1 本で持つ (引数の不足と契約 file 自体の parse error は従来の口〔rc 1 / rc 2〕のまま Refuse の外・C2)。 verify 行 1 本の理由 (Unfit) とは境界が違い、 同じ enum には足さない。 この境界は新しい guard (intake-refuse・InLoop / FailClosed) として極性一覧に 1 行増える (ADR-0014 §2.1)。 rc は交差 = 既存の拒否 (1)、 写しを読めない = 壊れた store (2・Gated run の verdict を読めない周も同じ「読めない」側で 2・NFR4)。 器 SHALL NOT 交差を許す flag を持たない。 live な便の write-set を読めない周 (契約の写しが無い・parse 不能) SHALL 受け付けない側へ倒す (fail-closed・「読めない」を「交差なし」に化けさせない)。 器 SHALL pipe stop --run <id> を持ち、 終端でない run 1 本に RunStopped を書いて live から外す (席が Live なら先に止める・終端の run には event を増やさず rc 1＝書込は冪等で rc は冪等でない)。 pipe stop --all の意味は変えない。

§2.2 land の rebase 衝突は終端にせず、 runner を起こし直して write-set の内側で解かせ、 gate をやり直す

入口で排他しても、 質問への回答で範囲が広がる周や、 dir 単位の write-set が実際には別 file を触る周に衝突は起きえます。 衝突したら便を失敗にせず、 木を衝突前に戻してから実装役をもう 1 回起こし、 「main が進んだので取り込んで衝突を解いてから続けよ」と契約に添えて渡します。 実装役は自分の write-set の中でだけ解き、 解けなければ木を元に戻して質問で止まります。 解けたら器が「出発点が進んだ」ことを記録し直してから審査 (gate) をやり直し、 通れば着地します。

land の追随 (設計 §5.4) で rebase が衝突した周、 器 SHALL git rebase --abort で木を戻し (戻せない周は Failed detail=rebase-abort-failed で終端し理由を stderr に残す)、 RunStage stage=Implemented detail=rebase-conflict:<base>..<main> を記帳して (終端の Failed にしない)、 §2.4 の判定が許す周は同じ run の worktree と契約で runner を起こし直す (C6 の 1 つの spawn 口・Budget は Precheck から・runner の起動形〔--runner〕を要し、 無い周は以後の event を書かず rc 1 で止まる＝rebase-conflict: の記帳は残る)。 起こし直しの stdin SHALL 契約の写しに「追随」節 (main の sha と「git rebase <main> を実行し衝突を write-set の内側で解いて commit せよ・解けなければ git rebase --abort で木を戻し〔commit を作らず clean のまま〕質問 record で止まれ」の定型) を付ける (ADR-0016 §2.2 の「回答」節と同じ置き場・順序は契約 → 回答 → 追随・定型の字面は prompt template が持つ)。 runner の終了後、 器 SHALL worktree の HEAD と main の merge-base を実測し、 記録済みの base より進んでいれば RunStage stage=Implemented detail=rebase:<old>..<merge-base> を記帳する (書く値は実測した merge-base であって現在の main ではない＝turn の間に main がさらに進んでいても 2 点 diff に逆向きの差分を載せない・base の読み手は既存の 1 本・gate は新しい base で diff を測る＝先着便の file を write-set の外と誤らない)。 木が rebase の途中のまま runner が終わった周は Failed detail=rebase-dirty で終端する (clean 前提を守る)。 その後は通常の spawn 完了と同じく Implemented → gate → land を通す (追随の rebase は再び走り、 解けていれば衝突しない)。 追随 turn の write-set の fence は gate の照合が担う (Bash 主体の turn ゆえ編集時の guard は効かない・ADR-0009 §2.1 / §2.4)。 runner が質問 record で止まった周は Questioned へ倒れ (木は clean・その turn で commit が増えていない＝§2.6 の読み替え。 便が base から持つ commit は起こし直しの前から在るので「base から 0 本」では測れない)、 planner の回答で再開する (FR31 / FR32)。 resume SHALL この段 (Implemented で最後の RunStage の detail が rebase-conflict: で始まり、 runner が起きていない周) からも同じ起こし直しを撃てる (同一 run の再 spawn の契機は ADR-0016 §2.2 の「回答済みの質問」に本項を足した 2 つ・§2.6)。

§2.3 人が関わるのは質問への回答だけ。 admin は中継と操作、 planner は契約の設計と回答。 手で merge する経路は持たない

衝突を人が手で直す道は作りません。 係の席 (admin) は便を流し・質問を届け・着地の操作をするだけ、 計画役 (planner) は契約の write-set を設計し、 質問に答えるだけです。 こうすると、 便を何本並べても人の手番は「質問に答える」の 1 種類に収まり、 admin に仕事が集まって詰まる形になりません。

器 SHALL NOT 衝突した worktree を席や人が編集して land する経路を持たない (gate 分離・C16: 逸脱は edit time で止める)。 管理席の仕事は ADR-0016 §2.1 の 3 つ (流す・中継する・land する) のまま増やさない。 planner SHALL 契約の write-set を「触る file でなく構造の連鎖」で設計し、 交差を入口で避ける (排他は planner の設計の穴を器が止める最後の線であって、 設計の代わりではない)。 回答で write-set を広げる周 (台帳 s2-07l.133) は、 広げた write-set で §2.1 の照合をやり直す (広げた結果 live な便と交差すれば、 回答は受け付けず planner に戻す)。

§2.4 起こし直しの回数は rules 行で上限を持ち、 その判定は guard で、 超えた便は Failed で終端して畳める

解けない衝突で実装役を無限に起こし直さないよう、 「何回まで起こし直すか」を規則の値として持ちます。 値が N なら起こし直しは最大 N 回で、 N+1 回目の衝突で便は「失敗」で終わります。 回数を記録から読めないときは「測れなかった」として別の理由で止め、 「上限に達した」とは区別します。 この判定は「起動を止めうる判定」なので、 器の止める仕組みの一覧に載せます。 失敗した便の worktree は可逆に畳めます (消しません)。 その後は計画役が契約の範囲を切り直して出し直します。 上限の値は user の裁定で決めます。

器 SHALL 1 つの run の衝突による起こし直し (再 spawn) の回数を rules 行 (pipe.follow_retries・kind は Int・値は裁定 id 付き・C5・本 ADR は値を決めない) で上限とする。 意味 SHALL「起こし直しの回数」とし、 k 回目の衝突の時点でそれまでの起こし直しが上限未満なら起こし直し、 上限以上なら Failed detail=rebase-conflict で終端する (値 N = 最大 N 回起こし直す)。 回数は event log の rebase-conflict: の RunStage 行数から導く (replay の導出値・別の状態を持たない・C3)。 この判定は起動を止めうる判定ゆえ guard であり、 器 SHALL 境界の閉じた enum (起こし直す / 上限到達 / 回数を読めない) と極性定数 (InLoop / FailClosed＝回数を replay から読めない周は起こし直さず Failed detail=follow-unmeasured + rc 2 で終端する。 上限到達の rebase-conflict + rc 1 とは分け、 「測れなかった」を「赤かった」に化けさせない〔設計 pipeline.md §5.4 の main-unmeasured と同じ極性・NFR4〕) を持ち、 極性一覧に 1 行増える (C11.2・ADR-0014 §2.1)。 rules 行は契約が裁定 id 付きで manifest に足すまで本 ADR の予定行であり、 C14.2 の相互参照は行が manifest に在って初めて成立する (ADR-0018 §4 と同じ扱い)。 pipe retire SHALL Failed detail=rebase-conflict の便と、 Gated で verdict が FAIL の便の worktree を可逆 move で畳める (N1 N1.2・台帳 s2-07l.132 の memo を本 ADR が吸収する)。 上限到達後の行き先 SHALL 器の外に置かない: 畳んだ後、 planner が契約の write-set を切り直して再 intake する (同じ bead の再 intake は live でない run とは交差しない)。 ADR-0016 §2.1 の手実装の例外に「衝突」は足さない。

§2.5 射程外

この記録が決めるのは「入口の排他」「衝突時の起こし直し」「人の関わり方」「回数の上限」だけです。 host をまたぐ便、 write-set を自動で分割する仕組み、 便の優先度や待ち行列、 同時に何本まで流すかの上限は別に決めます。

次は本 ADR の決定ではない (MUST NOT be read as such): 複数 host にまたがる便の排他 (event log は host ごと・v3)、 write-set の自動分割や契約の自動生成、 排他で断られた契約の待ち行列と再投入 (管理席か tick の運用・別途)、 同時に流す便の本数の上限 (admission control・口座の自律制御 s2-07l.142 と併せて別途)、 便を直列に流す運用 (同時に流さないという管理席の選択であり §2.1 の mode ではない)、 lens の指摘で範囲を広げる経路 (lens は読むだけで write-set を変えない・広げるのは planner の契約改訂)、 「追随」節の定型の字面 (prompt template の現物が正本)、 gate / lens FAIL 以外の理由で放置された run の自動掃除 (pipe stop --run は管理席の操作)。

§2.6 ADR-0016 §2.2 の質問判定と再 spawn の契機を部分 supersede する

先の記録 (ADR-0016) は「質問で止まるときは commit を作らない」「同じ便をもう一度起こすのは回答が届いたときだけ」と決めていました。 起こし直しでは便がすでに commit を持っているので、 前者は「この turn で新しい commit を作らない」と読み替えます。 後者には「衝突からの起こし直し」を 2 つ目のきっかけとして足します。 それ以外の文は変えません。

ADR-0016 §2.2 の「その周 SHALL NOT commit を作らない (record と commit が同時に在る周は質問ではなく実装の失敗)」は、 本 ADR により「その turn で commit を増やさない (spawn の時点の worktree の tip から新しい commit が無い。 record と新しい commit が同時に在る周は実装の失敗)」と読む (SHALL be read as)。 初回の turn では tip = base ゆえ従来の判定と同値で、 起こし直しの turn では便が既に持つ commit を数えない。 同 §2.2 の「resume SHALL Questioned から QuestionAnswered が在る周だけ同じ run を再 spawn する」は、 本 ADR により「Questioned から QuestionAnswered が在る周と、 §2.2 の衝突からの起こし直しの周だけ同じ run を再 spawn する」と読む (SHALL be read as)。 ADR-0016 の他の文 (質問 record の形・回答の権限・配送構造) は変えない。

§3. SRS との関係 (正本は SRS)

この記録が求めた要件は、 2026-09-12 に要件書 (SRS v0.6) へ入りました。 着地の前提の行 (FR10) が追いつけない便だけを止める形に改まり、 追随そのもの (FR34) が新しい行として加わっています。 要件の文面はここには置かず、 要件書の当該行を指すだけにします。

本 ADR が仕える要件は SRS v0.6 が正本である: FR4 (契約 1 本に worktree 1 つと runner 1 つ)・FR11 (審査合格と CAS の上での squash・§2.2 の起こし直しの後もこの内側)・FR14 (別 process からの resume・§2.2 の起こし直しは resume と同じ口)・FR30 (配送構造・§2.3)・FR31 (質問の停止・§2.2 / §2.3)・NFR4 (読めない store は rc 2・§2.1)。 FR10 (land の前提・追随できない周と verdict 非 PASS の周は何もしない) と FR34 (追随・rebase して gate をやり直し、 進んだ base と衝突を記帳し、 衝突は rules 行の上限までは終端にしない・上限で Failed) は SRS v0.6 (2026-09-12) が正本で、 本 ADR の §2.2 / §2.4 はその実装形である。 要件の文面はここには写さない。 intake の拒否の理由 (variant の名)・「追随」節の字面・rules 行の値は §2 と現物が持ち SRS は持たない。

§4. Consequences

良い面は、 便を並べても人の手番が「質問に答える」だけに収まること、 衝突が失敗ではなく実装役の 1 turn として処理されること、 衝突や不合格で止まった便を畳めるようになることです。 悪い面は、 実装役の起こし直しの分だけ口座の枠を使うこと、 入口の排他で契約が断られて出し直しの手間が増えること、 write-set を dir で広く取った契約ほど排他に掛かりやすいこと、 止める仕組みの一覧が 2 行増えることです。

Positive: 並列の便で人の手番が回答 1 種類に閉じる (ADR-0016 §2.3 の形を保つ)。 衝突が段の記帳 (rebase-conflict: を prefix に持つ RunStage) として残り、 回数が replay から読める。 契約単位の拒否が閉じた enum になり、 これまで散文だった理由 (git repo でない・同じ秒の再 intake) も variant として数えられる。 retire の前提が広がり、 Failed と gate FAIL の worktree が溜まらない (N1.2)。 放置された便を 1 本だけ外す口 (pipe stop --run) ができる。

Negative (受け入れるコスト): 起こし直しは runner の turn を増やし口座の枠を使う (上限は §2.4・枠の自律制御は s2-07l.142)。 排他は dir 単位ゆえ、 同じ dir の別 file を触るだけの契約も断られうる (出し直しは管理席の運用)。 symlink を解かないので、 実体が同じ file を別名で持つ 2 契約は入口で見逃す (編集時の guard が実体名で塞ぎ、 Bash の git 経路は既知の穴のまま)。 rules 行 1 つ・prompt template の節 1 つ・拒否理由の enum 1 つ (variant 2 つ + 既存の散文理由の分)・event の detail の prefix 1 種・極性一覧の行 2 つ・subcommand の flag 2 つ (stop --run・land / resume の --runner)・終端の detail 3 種 (rebase-abort-failed / rebase-dirty / follow-unmeasured) が増える。 ADR-0016 §2.2 の 2 文を読み替える (§2.6)。 Implemented の下位状態 (衝突からの起こし直し待ち) を detail の文字列 prefix で持つ (既存の rebase-empty と同じ形・C3.3 の向きとの緊張は受け入れる・段の variant を増やすと replay と fleet の閉じた enum を跨版で動かすため)。 並列 2 本の実地試験 (台帳 s2-07l.143) で追随と枠の減りを実測してから契約を流す。

§5. Alternatives Considered

5 つの案を退けました。 衝突した便を計画役が切り直す案は、 計画役が詰まります。 係の席が手で merge する案は、 審査の分離を壊します。 入口の排他だけで解く案は、 回答で広がる周に衝突が残ります。 全部を 1 本ずつ流す案は、 並列性がゼロです。 衝突を機械的な 3-way merge で解く案は、 意味の衝突を解けません。

(A) 衝突した便は planner が契約を切り直す。 却下 (部分採用): 意味を知る側が構造で切り直す強みは、 採用案でも「解けない周は質問で planner に戻る」(§2.2) と「上限到達後は切り直して再 intake」(§2.4) として残る。 すべての衝突を planner に戻す形は planner が律速になり並列を上げるほど悪化する (ADR-0016 §1 の実測と同型)。 採用案の口座枠のコスト (起こし直しごとの turn) と planner の待ち時間を秤に載せ、 機械が解ける衝突 (追随の rebase) は機械に解かせる側を採る。

(B) 管理席が worktree を手で merge して land する。 却下: gate 分離を破り (審査の後に人が編集)、 C16 (逸脱を edit time で止める) に反する。 席の仕事は 3 つのまま (§2.3)。

(C) 入口の排他だけを持ち、 衝突時の解消経路を持たない。 却下: 回答で write-set が広がる周 (s2-07l.133) と dir 単位の write-set が別 file を触る周に衝突が残り、 Failed の worktree が溜まる。

(D) 全便を直列に流す。 却下: 並列性がゼロで user の目的 (速度) に反する。 直列は「同時に流さない」という管理席の運用であって §2.1 の mode ではない (§2.5)。 直列でも回答で範囲が広がる周の衝突は残る。

(E) 衝突を器が 3-way merge の道具で自動解決する。 却下: 意味の衝突 (同じ関数を別々に直した) は道具で解けず、 道具が「解けた」と言う周を器は疑えない。 採用案でも誤った解決は gate が判定する点は同じだが、 解く主体が契約を読んだ runner であり、 解けない周を質問として人に返せる (道具には返す口が無い)。
