設計判断記録 (ADR) scribe2 — 契約表の置き場の宣言

契約表の置き場 — 既定 (設計 doc の dir の直下の markdown) に、 対象 repo の vessel 宣言の任意 key contract-tables が名乗る dir か file を足し、 契約表を数える器の読み手を全部 1 つの列挙の関数に通し、 受付は置き場の外を指す pointer を断る (ADR-0023 §2.1 の表の在りかの句を部分 supersede)

器の中で契約表を数える見張りの読み手は「表がどこに在るか」を 2 通りに決め打ちし、 表を設計 doc の dir の外の toml に置く repo では、 契約表の検査・局面の出力・走っている便の行を守る門・台帳の形の検査が表を見ない。 本 ADR は、 契約表の置き場を、 既定 (設計 doc の dir の直下の markdown) と、 その repo の vessel 宣言の任意 key contract-tables が名乗る dir か file の和とし、 表を数える読み手を全部 1 つの列挙の関数に通し、 受付は置き場の外を指す pointer を断ると決める。 key を書かない repo の数え方は今と同じだが、 走っている便の行を守る門は既定の置き場だけを守るように狭まる。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「便」は契約 1 本を実装して main へ入れる 1 回の走り、 「契約表」は便の元になる契約を 1 行ずつ並べた表です。 契約表は、 ふつう設計の文書 (docs/design/ のすぐ下の markdown) の末尾に置きますが、 表だけを持つ toml の file にも置けます。 1 行を指して読む入口は表がどこに在っても読めるので便は通りますが、 表を全部数えて見張る側 (表の検査・案件の今を書く file・走る便の行を守る門・台帳の形の検査) は、 表の在りかを 2 通りに決め打ちしています。 そのため、 表を別の dir の toml に置く隣の project では、 見張りが表を 0 本と数えます。 この記録は、 repo が自分の設定 file (vessel 宣言) に「表はここにも在る」と書けるようにし、 表を数える読み手を全部 1 つの関数に通し、 置き場の外を指す契約は後の行 (行 cg) で受付が断ると決めます。 書かない repo の表の数え方は今と同じですが、 走る便の行を守る門は既定の置き場 (すぐ下の markdown) だけを守るように狭まります。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 6 つで示します。 器の中に表の在りかの決め方が 3 通りあり、 表を数える見張りはそのうち 2 つを使っていること。 1 行を指して読む入口は場所を問わず、 表を数える見張りの側だけが在りかを決め打ちしていること。 表を toml に置く隣の project で、 見張りが表を 0 本と数えたという照会。 repo が自分の形を設定 file で名乗る口と、 項目を「足す」と「置き換える」の 2 つの先例。 表の形は決まっていたのに、 toml の表の在りかは決まっていなかったこと。 憲法の向きと、 この記録が動かす範囲です。

CTX1

現物 — 「表がどこに在るか」の定義が器の中に 3 通りあり、 表を数える見張りはそのうち 2 つを使う

契約表を読む器の読み手は、 表の在りかを 3 通りに定めている (main a6d4234c の現物)。 (1) 設計 doc設計を書いた文書 の dir (docs/design/) の直下の markdown: 契約表の検査表の全行を調べる口とその名の衝突の予想・宣言済みの新規 file (契約表の検査と受付便を受け入れる口の材料の両方)・runner に渡す「ほかの行の touches」節が 1 つの関数で読み、 局面の出力案件の今を書いた fileの行の読み手と台帳の形の検査は同じ絞り方を自前の写しで持つ。 (2) 設計 doc の dir の下の全部 (深さを問わず markdown か toml): live-row の門走る便の行を守る門だけが持ち、 設計 vessel-hook §15 がこの範囲を名乗る。 (3) 表の形の中身を持つ tracked file (場所を問わない): 行の審査の表の見分けと code の木の鍵が持つ。 表を数える見張りが使うのは (1) と (2) で、 (3) は中身で見分ける行の審査の側の定義として本 ADR の後も残る。 本 repo では 3 つが同じ 30 本 (全部が直下の markdown) を指し、 契約表の検査は docs=30 rows=478 と数える。 設計 doc の dir の下の toml と入れ子の dir は 0 本で、 表を持つ tracked file は設計 doc の dir の外に 0 本なので、 違いは見えていなかった。

CTX2

現物 — 1 行を pointer で引く口は場所を問わず、 表を数える見張りの側だけが在りかを決め打ちする

設計 pointer (表の file の path と契約 id の対) で 1 行を引く口は、 file の拡張子だけを見て形を決める (markdown は末尾の区間・toml は全文・ADR-0023 §2.1 の 2 形)。 受付の生成は pointer の doc を HEAD から読むだけで在りかを照らさず、 受付・preflight・列の候補・起動の列の事前の検査・行の審査・resume の取り直しがこの 1 本を呼ぶので、 表をどこに置いても便は起きて通る。 表の在りかを決め打ちするのは、 表を全部数える見張りの側 (契約表の検査・局面の出力・live-row の門・台帳の形の検査) だけである。 本 repo の contracts/schema.toml は欄の生成物 ([[field]] の表) で、 契約表の読み手は [[contract]] と [[promise]] のほかの表を断る。

CTX3

消費側の症状 — 表を toml に置く隣の project で、 見張りが表を 0 本と数える

契約表を contracts/ の toml に置く隣の project から、 局面の出力が契約の行と要件の部品を「表を読めない」と出し、 契約表の検査が docs=0 rows=0 と数え、 live-row の門が走っている便の行の書き換えを止めないと照会があった (台帳 memo s2-07l.738.42.2・2026-10-01)。 3 つとも、 CTX1 の (1) と (2) の定義の帰結として説明がつく。 同じ帰結として、 受付の名指しの実在の照らしが toml の行の新規 file を宣言済みと読まないこと、 名の衝突の予想が toml の行を見ないこと、 runner の「ほかの行の touches」節が toml の行を載せないことも導ける (器の code からの導きで、 その repo の code は読んでいない)。 2026-10-02 に数えると、 その repo の設計 doc の dir の下には、 直下の toml も入れ子の dir の表も 0 本だった。

CTX4

宣言の口と先例 — repo の形は vessel 宣言repo の設定 fileが名乗り、 任意 key書かなくてよい項目 には「足す」と「置き換える」の先例が在る

vessel 宣言 (.vessel.toml) は、 対象 repo が自分の形を器に名乗る tracked file で (ADR-0010)、 任意 key の集合は core の閉じた列が正本である (ADR-0023 §2.7 (iv))。 宣言の読み手は 1 本で、 未知の key を宣言全体の不備として断る。 path の種別の 3 key (ADR-0047) は repo 相対の prefix の配列で、 glob と正規表現を持たず、 書けば既定の分類を置き換える。 crate-roots の key (設計 contract-source §62) は固定の根に項目を足す。 宣言を名指した commit で読む口と、 既定だけの周・key の在る周・読めない周を閉じた 3 値で返す型にも先例が在る。 新しい key は、 古い binary が未知の key として断るので、 跨版版の違いをまたぐの形を持つ。

CTX5

予告されていた穴 — 表の 2 形は決まっていたが、 toml の表の在りかは決まっていない

ADR-0023 §2.1 は、 契約の正本を対象 repo の tracked な設計 doc が末尾に持つ機械が読む表の 1 行とし、 表の形を 2 つ (設計 doc の区間・表だけを持つ tracked な toml の全文) と決め、 読み手は拡張子で形を決めるとした。 けれども、 toml の表をどの dir に置くかは決めていない。 設計 contract-source §47 は、 契約表の検査の母集団に導出物の在りかを足すこと (在りかは消費側の宣言) を後続に残し、 前提の移行の仕事が取りやめで閉じた後も、 その 1 行だけが残っていた。

CTX6

憲法の向きと本 ADR の射程

C2 は選択と除外を 1 つの関数で行い、 新しい理由を enum の 1 値で足すことを求める。 C10 は宣言値と導出値を型で分け、 その読み (ADR-0047) では読めない宣言を既定に倒さない。 C16 は逸脱を編集の時点で止める。 C17 は足す前に消すものを名指すことを求める。 NFR4 は不正な入力を黙って落とさない。 本 ADR が動かすのは、 契約表の置き場表を置いてよい fileの定義・それを名乗る宣言の key・表を数える読み手の列挙・live-row の門の範囲・置き場の検査・受付が置き場の外の pointer を断ることの 6 つである。 1 行を pointer で引く口・表の 2 形と拡張子で形を決める読み手・契約 id の形・行の審査の中身による見分け・path の種別の key は動かさない。 SRS の字の直しは別の round が持つ。 ADR を書く条件のうち 1 (C2・C10 の読み)・3 (宣言の key と跨版の形)・4 (却下案を残す価値のある分岐) に当たる。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 7 本のものさしです。 表の在りかは repo が名乗ること。 書かない repo の数え方を 1 本も変えないこと。 表を数える読み手が全部同じ 1 つの決め方を使うこと。 設定 1 行で検査の範囲を狭められないこと。 読めない設定や打ち間違いを黙って「表 0 本」にしないこと。 古い本体と新しい設定が出会ったときの壊れ方を名指すこと。 走っている便の行を、 表がどこに在っても編集の時点で止めることです。

DR1出所 — 表の在りかは対象 repo の事実で、 repo が自分の宣言で名乗る (器の code にも規則の行にも決め打ちしない) CTX3・CTX4
DR2無変更 — key を書かない repo の検査の母集団は 1 本も変わらない CTX1・CTX4
DR31 つの定義 — 表を数える読み手は全部同じ 1 つの関数を通る (写しはずれる・C2) CTX1・CTX6
DR4狭められない — 宣言 1 行で器の検査の母集団を狭められない CTX4・CTX6
DR5fail-closed — 読めない宣言・何にも当たらない項目・打ち間違いを、 黙って「表 0 本」にしない (C10・NFR4) CTX3・CTX6
DR6跨版 — 古い binary と新しい宣言が出会ったときの壊れ方を名指す CTX4
DR7守り — 走っている便の行は、 表がどこに在っても編集の時点で止まる (C16) CTX2・CTX3・CTX6
03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 10 個並べます。 設定 file の書かなくてよい項目で表の置き場を既定に足し、 表を数える読み手を全部 1 つの関数に通す案 (選んだ案) と、 選ばなかった 9 つです。 選ばなかった案は、 contracts/ の toml を器が決め打ちで数える案・台帳の開いた契約が指す file だけを読む案・読み手ごとに置き場の一覧を持つ案・中身の印で表を見分ける案・設計 doc の編集の範囲を名乗る既存の項目を流用する案・項目にワイルドカード (glob) を許す案・項目が既定を置き換える案・走る便の行を守る門だけ今の広い範囲を残す案・受付で断らずに門が走る便の指し先を守る案です。

OPT1vessel 宣言の任意 key で置き場を既定に足し、 表を数える読み手を全部 1 つの列挙の関数表の file を選ぶに通す採用

対象 repo の vessel 宣言に任意 key contract-tables (repo 相対の dir か file の項目の配列) を足し、 既定 (設計 doc の dir の直下の markdown) との和を契約表の置き場とする。 契約表の検査・宣言済みの新規 file・runner の節・局面の出力の行・live-row の門・台帳の形の検査・受付の生成を 1 つの列挙の関数に通し、 各読み手は自分が読む commit の宣言を読む。 契約表の検査は何にも当たらない項目と doc id表の file の名 の重なりを名指し、 受付は置き場の外を指す pointer を断る。 決め手は repo の形を repo が名乗る先例と、 写しがずれた現物 (CTX1・CTX4)。

repo の設定 file (vessel 宣言) に、 書かなくてよい項目 contract-tables を足します。 値は repo の中の dir か file の一覧で、 dir はそのすぐ下の .md か .toml の file を、 file はその 1 つを指し、 既定 (設計 doc の dir のすぐ下の markdown) に足されます。 表を数える読み手は全部 1 つの関数を通り、 それぞれ自分が読む commit の設定を読みます。 表の検査は何にも当たらない項目と file の名の重なりを名指し、 受付は置き場の外を指す契約を断ります。 表をどこに置く repo でも 1 行で見張りに表を見せられ、 書かない repo の表の数え方は今と同じで、 読み手の範囲が揃い、 設定で設計 doc の表を外せず、 受付の断りが入った後は走る便の行が門の守る範囲に在ります。 代わりに、 古い本体は新しい項目を知らずに設定全体を断るので、 相手は本体を入れ替えてから書く順が要り、 読み手ごとに設定を読む手間が増えます。 項目を書かない repo では門の守る範囲が直下の markdown だけに狭まり、 受付の断りが入るまでの間はその外の行を門も受付も止めません (器の repo と隣の project の両方で、 外れる表は 0 本)。 設定を変える commit の中の表の変更は、 変更の前の設定で測ります。

+ 利点

  • 表の在りかを器が決め打ちせず、 どんな配置の repo も宣言 1 行で見張りの側に表を見せられる (DR1)
  • key を書かない repo の検査の数え方は 1 本も変わらず、 本 repo は 30 本のまま (DR2)
  • 表を数える見張りの読み手が全部同じ列を見るので、 検査と門と局面の出力の範囲が揃う (DR3)
  • key は既定に足すだけなので、 宣言で設計 doc の表を検査の外へ出せない (DR4)
  • 読めない宣言は既定に倒さず、 何にも当たらない項目と doc id の重なりを検査が名指す (DR5)
  • 宣言は PR と審査を通る tracked file で、 作業ツリーの一時の状態を読まない (DR1)
  • 受付の断りの着地の後は、 走っている便の行が置き場の中に在るので、 門は置き場だけを見て足りる (DR7)

− 欠点

  • 宣言の key が 1 つ増え、 古い binary は key を未知として宣言全体を断る (DR6)
  • 各読み手が自分の commit の宣言を読む費用 (git の子 process 1 回) が増える
  • 消費側は key を書く 1 手間を負い、 書く前に host の binary を入れ替える順が要る (DR6)
  • key を書かない repo の live-row の門は、 設計 doc の dir の下の全部から直下の markdown だけに狭まる (器の repo と隣の project の両方で、 外れる表は 0 本・2026-10-02 に数えた)
  • 門を狭める行から受付の断りの行までの間、 key を書かない repo の設計 doc の dir の下の toml と入れ子の dir の表を指す走る便の行は、 門も受付も止めない (DR7)
  • 宣言を変える commit と同じ commit の表の変更は変更の前の宣言で測り、 便が走る間に宣言から置き場を外すと門はその行を守らない (DR7)
OPT2決め打ちの dir (contracts/ の toml) を既定で数える不採用

宣言を足さず、 既定の在りかに contracts/ の toml を加える。 決め手は配置の決め打ちと本 repo の生成物 (CTX1・CTX2・CTX3)。

設定を足さず、 器が contracts/ の toml を既定で数える案です。 設定が要らず、 照会の repo には器の 1 行で効き、 新しい項目による版の違いの壊れ方も増えない点で勝ります。 けれども、 器が配置を決め打ちするので、 別の dir に表を置く次の repo には効きません。 また、 この repo の contracts/schema.toml は欄の一覧を書いた生成物で契約表ではないのに、 それを表と読んで器自身の表の検査が赤になります。

+ 利点

  • 宣言が要らず、 照会の repo には器の側の 1 行の変更で効く
  • key が増えないので、 跨版の壊れ方も増えない

− 欠点

  • 配置を器が決め打ちし、 別の dir に表を置く次の repo には効かない (DR1)
  • 本 repo の contracts/schema.toml (欄の生成物で契約表ではない) を表と読み、 器自身の契約表の検査が赤になる (DR2)
OPT3台帳の開いた契約の pointer が指す file だけを読む不採用

在りかを宣言せず、 台帳の open な契約が持つ設計 pointer の file を表の母集団とする。 決め手は bead の無い行と CI の届き方 (CTX1・CTX2)。

置き場を決めず、 台帳で開いている契約が指す file だけを表として読む案です。 設定も選び方の決まりも要らず、 今走っている契約の表はどこに在っても必ず見える点で勝ります。 けれども、 台帳に記録の無い行を数えられなくなり、 案件の今を書く file や台帳の形の検査がそうした行を名指せなくなります。 CI の表の検査は台帳に届かないので、 全行を調べる検査の数える範囲を作れません。 同じ commit の検査の結果が、 台帳の状態で変わることにもなります。

+ 利点

  • 宣言も列挙の規則も要らない
  • 今走っている契約の表は、 どこに置かれても必ず見える

− 欠点

  • bead の無い行 (局面の出力の row-unbeaded・台帳の形の drift) を数えられなくなる (DR5)
  • CI の契約表の検査は台帳に届かないので、 全行の検査 (FR55) の母集団を作れない (DR3)
  • 母集団が台帳の状態で変わり、 同じ commit の検査が台帳次第で違う結果になる
OPT4読み手ごとに置き場の列を持つ (今の形の延長)不採用

各読み手がそれぞれ key を読み、 自分の絞り方で表を数える。 決め手は今の写しのずれ (CTX1)。

各読み手がそれぞれ設定を読み、 自分のやり方で表を数える案で、 今の形を延ばしたものです。 直しを読み手ごとに小さく分けて先に着いたものから効かせられ、 読み手ごとに既定や倒れ方を変えられる点で勝ります。 けれども、 決め方の写しが読み手の数だけ残ります。 今まさに走る便の行を守る門だけが別の決め方を持ち、 検査と門の範囲が食い違っているのは、 この写しのずれです。 新しい読み手を足すたびに写す手間も要ります。

+ 利点

  • 差し替えの便を読み手ごとに小さく切れ、 先に着いた読み手から効く
  • 読み手ごとに既定や倒れ方を変えたいときに縛られない

− 欠点

  • 定義の写しが読み手の数だけ残る (DR3)
  • 今まさに live-row の門だけが別の定義を持ち、 検査と門の範囲が食い違っている (DR3)
  • 新しい読み手を足すたびに、 key の読みと絞り方を写す手が要る
OPT5中身で見分ける (表の marker を持つ tracked な markdown と toml を全部数える)不採用

宣言を持たず、 区間の marker か [[contract]] の表を持つ tracked な markdown と toml を全部表と数える。 決め手は fail-open と宣言値の型 (CTX1・CTX6)。

設定を持たず、 表の印 (区間の目印か契約の表の見出し) を持つ markdown と toml を全部表と数える案です。 設定が要らず新しい repo でもそのまま効き、 行の審査の見分け方と同じになる点で勝ります。 けれども、 印を打ち間違えた表は黙って数えから落ちます。 表の在りかが repo の宣言でなく器の推測になり、 見張りのたびに全 file を読む手間も要ります。

+ 利点

  • 宣言が要らず、 新しい repo でもそのまま効く
  • 行の審査の表の見分け (CTX1 の定義 3) と同じ形に揃う

− 欠点

  • marker の打ち間違いで表が黙って母集団から落ちる (fail-open・DR5)
  • 在りかが宣言値でなく推測になる (C10・DR1)
  • 見張りのたびに全 tracked file を読む費用が要る
OPT6path の種別の key design-doc-paths を流用する不採用

表の在りかを、 席が設計 doc として編集してよい path を名乗る key (ADR-0047) から読む。 決め手は 2 つの事実の違いと既定の違い (CTX4)。

席が設計 doc として編集してよい範囲を名乗る既存の項目 (design-doc-paths・ADR-0047) を、 表の在りかにも使う案です。 項目が増えず、 表を外に置く repo は席が表を編集するためにこの項目を既に書いている見込みが高い点で勝ります。 けれども、 「誰が編集してよいか」と「どこに表が在るか」は別のことで、 一方を変えると他方も動きます。 その項目の既定は今の数え方と違い、 置き換える意味の項目なので、 設定 1 行で設計 doc の表を検査の外へ出せてしまいます。

+ 利点

  • key が増えず、 跨版の壊れ方も増えない
  • 表を設計 doc の dir の外に置く repo は、 席が表を編集するためにこの key を既に名乗っている見込みが高い

− 欠点

  • 「誰が編集してよいか」と「どこに表が在るか」は別の事実で、 一方を変えると他方が動く (DR1)
  • その key の既定 (設計 doc の dir の下の全部) が今の母集団 (直下の markdown) と違う (DR2)
  • 置き換える意味の key なので、 宣言 1 行で設計 doc の表を検査の外へ出せる (DR4)
OPT7key の値に glob を許す不採用

key の項目に glob (例: contracts の下の toml の全部) を書けるようにする。 決め手は読み手の数と先例 (CTX4)。

項目にワイルドカード (glob) を書けるようにする案です。 入れ子の dir や拡張子の絞りを 1 つの項目で短く書け、 書き方の自由が広い点で勝ります。 けれども、 ワイルドカードを解く新しい部品が要り、 1 つの関数がそれを抱えます。 先頭の一致と完全な一致で足りるとした ADR-0047 の形から外れて項目ごとに書き方が分かれ、 dir と file の項目で足りるので、 最小の形で止まる憲法の決め方にも合いません。

+ 利点

  • 入れ子の dir や拡張子の絞りを 1 項目で短く書ける
  • 在りかの書き方の自由度が高い

− 欠点

  • glob を解く新しい読み手が要り、 列挙の 1 関数がそれを抱える (DR3)
  • ADR-0047 が prefix と完全一致で足りると決めた形から外れ、 宣言の key ごとに書き方が分かれる (DR1)
  • 決定はしご (C17) の「最小の形で足りるか」の段で、 dir と file の項目で足りる
OPT8key が既定を置き換える不採用

key を書いた repo では既定 (設計 doc の dir の直下の markdown) を数えず、 key の項目だけを置き場とする。 決め手は狭められないことと、 区間を持たない markdown の数え方 (CTX4・CTX6)。

項目を書いた repo では既定を数えず、 項目に書いた所だけを置き場にする案です。 既定の dir を表に使わない repo は置き場を項目だけで言い切れ、 ADR-0047 の項目と同じ「置き換える」意味に揃う点で勝ります。 けれども、 設定 1 行で設計 doc の表を検査の外へ出せてしまいます。 表を持たない markdown はもともと 0 行と数えるので既定を外す必要が無く、 既定を書き忘れると今の表が黙って数えから落ちます。

+ 利点

  • 既定の dir を表に使わない repo は、 置き場を key だけで言い切れる
  • path の種別の key (ADR-0047) と同じ「置き換える」意味に揃う

− 欠点

  • 宣言 1 行で設計 doc の表を検査の外へ出せる (DR4)
  • 表の区間を持たない markdown は 0 行と数えるので、 既定を外す必要がそもそも無い
  • 既定を項目に書き忘れると、 既存の表が黙って母集団から落ちる (DR5)
OPT9live-row の門だけは定義 2 (設計 doc の dir の下の全部) を残す不採用

表を数えるほかの読み手と受付は 1 つの関数に通すが、 live-row の門だけは今の広い範囲 (設計 doc の dir の下の全部) と置き場の和を守る。 決め手は定義の数と受付の断り (CTX1・CTX2)。

ほかの読み手と受付は 1 つの関数に通しますが、 走る便の行を守る門だけは今の広い範囲 (設計 doc の dir の下の全部) と置き場の和を守る案です。 項目を書かない repo でも入れ子の dir や toml の表を守り続け、 門を狭めてから受付の断りが入るまでの隙も無い点で勝ります。 けれども、 表の決め方が 2 本に戻って検査と門の範囲がまた食い違い、 受付が通さない場所の行を門だけが守る形になります。 受付の断りが入った後は走る便の行は置き場の中に在るので、 広い範囲は守る行を増やしません。 器の repo と隣の project の両方で、 門を狭めて外れる表は 0 本です。

+ 利点

  • 門の守りが最も広く、 key を書かない repo でも設計 doc の dir の下の toml と入れ子の dir の表を守り続ける
  • 門を狭める行から受付の断りの行までの隙が無く、 門の範囲が今より狭まる周も無い (DR7)

− 欠点

  • 表の定義が 2 本に戻り、 検査と門の範囲がまた食い違う (DR3)
  • 受付が通さない場所の行を、 門だけが守る形になる (DR3)
  • 受付の断りの着地の後は、 走っている便の行は置き場の中に在るので、 広い範囲は守る行を増やさない (DR7)
  • 器の repo と隣の project の両方で、 門を狭めて外れる表は 0 本である (2026-10-02 に数えた)
OPT10受付で断らず、 live-row の門を走っている便の pointer で守る不採用

受付は置き場の外を指す pointer も今どおり通し、 live-row の門は、 置き場でなく、 走っている便の設計 pointer が指す file を全部守る。 決め手は契約の正本の在りかと門の費用 (CTX1・CTX2)。

受付は置き場の外を指す契約も今どおり通し、 走る便の行を守る門は、 置き場でなく、 走っている便が指している file を全部守る案です。 受付の挙動が変わらず置き場の外を指す今の便も止まらず、 設定を変えている間や、 門を狭めてから受付の断りが入るまでの間にも走る便の行を守れる点で勝ります。 けれども、 表の検査や案件の今を書く file が見ない場所に契約の正本を置けてしまい、 表の決め方が 2 本に戻ります。 また、 門は markdown か toml を編集するたびに便の記録を読んで走っている便の指し先を集めることになり、 1 回の編集の手間が設計の見積で 10 ms 未満から 150 ms 前後に重くなります。

+ 利点

  • 受付の挙動が変わらず、 置き場の外を指す既存の便も止まらない
  • 宣言を変えている間も、 走っている便の行を守れる (DR7)
  • 門を狭める行から受付の断りの行までの隙も無い (DR7)

− 欠点

  • 契約表の検査と局面の出力が見ない場所に契約の正本を置けてしまい、 表の定義が 2 本に戻る (DR3・DR5)
  • 門は markdown か toml を編集するたびに便の記録 (event log) を読んで走っている便の pointer を集めるので、 1 回の編集の費用が設計 vessel-hook §15 の見積で 10 ms 未満から 150 ms 前後に上がる
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 表の置き場は、 既定 (設計 doc の dir のすぐ下の markdown) と、 repo の設定 file の項目 contract-tables が名乗る dir か file の和で、 項目は足すだけで既定を置き換えません。 表を数える読み手は全部 1 つの関数を通り、 それぞれ自分が読む commit の設定を読み、 設定を読めない回は既定に倒さずに止まるか厳しい側に倒れます。 走る便の行を守る門も同じ置き場だけを守るので、 項目を書かない repo では門の範囲が狭まります。 表の検査は、 何にも当たらない項目と file の名の重なりを名指します。 受付は置き場の外を指す契約を断り、 その断りは相手の repo が項目を書いた後に入れます。 支える要件は 7 つです。 要件書の字は、 FR47・FR55・FR90 を最初の行の前の改訂で、 FR53・FR54 を受付の断りの行の前の改訂で直し、 FR51 は揃えるだけです。

採用 — OPT1

器 SHALL 契約表の置き場を、 既定 (設計 doc の dir の直下の markdown・今の母集団) と、 対象 repo の vessel 宣言の任意 key contract-tables が名乗る項目の和とする。 key の値 SHALL repo 相対の項目の配列で、 末尾が / の項目はその dir の直下の、 拡張子が .md か .toml の file を、 ほかの項目はその path と等しい 1 file を指す。 宣言 SHALL NOT glob と正規表現を持つ。 key SHALL 既定に足し、 置き換えない。 key を書かない宣言と宣言 file を持たない repo SHALL 今と同じ母集団を持ち、 宣言の schema SHALL 1 のままとする。 項目の不備 (空・絶対 path・home の短縮記号・.. の段) SHALL key の行番号を名指す宣言の不備とする。 器 SHALL 契約表を数える全部の読み手 (契約表の検査とその名の衝突の予想・宣言済みの新規 file・runner の「ほかの行の touches」節・局面の出力の行・live-row の門・台帳の形の検査・受付の生成) を 1 つの列挙の関数に通し、 局面の出力の行の読み手と台帳の形の検査が持つ定義の写しと、 live-row の門の別の定義 (設計 doc の dir の下の全部) を消す。 各読み手 SHALL 自分が読む commit の宣言を読む (検査・宣言済みの新規 file・受付・台帳の形・門は HEAD、 runner の節は便の base、 局面の出力は main の sha)。 宣言を読めない周 SHALL 既定に倒さない: 検査は今と同じ rc 2、 局面の出力は declaration の語で止まって書き直さず、 台帳の形は unreadable の 1 行、 門は拡張子が .md か .toml の file を全部比べる側に倒し、 受付は置き場の外と同じ断りにする。 key を書かない repo の live-row の門 SHALL 既定の置き場だけを守る。 契約表の検査 SHALL 宣言した項目のうち tracked な file に 1 つも当たらない項目と、 置き場の file 名の stem (doc id) の重なりを名指して非 0 で止める。 受付の生成と、 それを呼ぶ全部の口 (受付・preflight・列の候補・起動の列の事前の検査・行の審査・resume の取り直し) SHALL pointer の file が置き場に無い契約を doc を読む前に typed に断り、 走っている便の行が置き場の中に在ることを受付で成り立たせる。 この断り SHALL 消費側が key を名乗り、 走っている便のうち置き場の外を指す便が 0 本と数えた後に着地する。 本 ADR は ADR-0023 §2.1 の「tracked な設計 doc が末尾に持つ表の 1 行」を「契約表の置き場の表の 1 行」と読み替える。 本 ADR SHALL NOT 1 行を pointer で引く口・表の 2 形と拡張子で形を決める読み手・契約 id の形・行の審査の中身による見分け・path の種別の key を変える。

表の置き場は、 既定 (設計 doc の dir のすぐ下の markdown) と、 repo の設定 file の書かなくてよい項目 contract-tables に書いた dir か file の和です。 項目は repo の中の相対の場所の一覧で、 / で終わる項目はその dir のすぐ下の .md か .toml の file を、 ほかの項目はその 1 file を指します。 ワイルドカードは持たず、 既定を置き換えず、 書かない repo の表の数え方は今と同じで、 設定の版も上げません。 空・絶対の場所・home の略記・親へ上る段を書いた項目は、 項目の行を名指して断ります。 表を数える読み手 (表の検査・宣言済みの新しい file・runner に渡す節・案件の今を書く file・走る便の行を守る門・台帳の形の検査・受付) は全部 1 つの関数を通り、 今ある写しと門だけの別の決め方は消します。 そのため、 項目を書かない repo では、 走る便の行を守る門が設計 doc の dir の下の全部でなく、 既定の置き場 (すぐ下の markdown) だけを守るように狭まります。 読み手はそれぞれ自分が読む commit の設定を読み、 読めない回は既定に倒しません。 表の検査は、 何にも当たらない項目と、 拡張子を除いた file の名の重なりを名指して止めます。 受付は、 置き場の外を指す契約を、 文書を読む前に断ります。 この断りは、 相手の repo が項目を書き、 置き場の外を指す走る便が 0 本になってから入れます。 1 行を指して読む入口・表の 2 つの形・契約の名の形・行の審査の見分け方・編集の範囲の項目は変えません。 表の在りかを repo の設定で名乗らせるのは、 それが repo ごとの事実だからで、 器が決め打ちすると次の配置の repo に効かず、 この repo の生成物を表と読み違えます。 項目を既定に足すだけにするのは、 設定 1 行で検査の範囲を狭められないようにするためで、 表を持たない markdown は 0 行と数えるので既定を外す必要がありません。 読み手を全部 1 つの関数に通すのは、 写しは必ずずれ、 現に門だけが別の決め方を持って検査と範囲が食い違っているからで、 選び方を 1 つの関数に置く憲法の線にも沿います (中身で見分ける行の審査の決め方は、 場所を問わないので残します)。 門を同じ決め方に狭めてよいのは、 受付の断りが入った後は走る便の行が置き場の中に在り、 狭めて外れる表が器の repo と隣の project の両方で 0 本だと数えた (2026-10-02) からで、 断りが入るまでの隙で守りから外れる行も同じ数え方で 0 本です。 門を走る便の指し先で守る形は、 編集のたびに便の記録を読む重さが要り、 表の検査が見ない場所に契約の正本を置けてしまいます。 読めない設定を既定に倒さず、 何にも当たらない項目と名の重なりを名指すのは、 黙って表 0 本に落ちる道を残さないためです。 台帳の指し先や中身の印で見分ける案は、 台帳に記録の無い行や印の打ち間違いを数えから落とし、 ワイルドカードは新しい部品が要るのに、 先頭の一致と完全な一致で足ります。

この判断が正当化する要件 (cross-doc 照会 → SRS-SCRIBE2-MVP)

FR47claimFR47 (契約の正本) の「tracked な設計 doc の契約表の 1 行」を、 契約表の置き場 (tracked) の契約表の 1 行と読むと主張する。 欄の形と 1 行だけから取る形は変えない (字の直しは最初の行の前の SRS の round)。
FR55claimFR55 (契約表の検査) の母集団を契約表の置き場の全 tracked な表とし、 何にも当たらない宣言の項目と doc id の重なりも名指して非 0 で止めると主張する (字の直しと受入の足しは最初の行の前の SRS の round)。
FR90claimFR90 (局面の出力) の入力の「main の設計 doc の契約表」を、 main の先端の vessel 宣言が名乗る契約表の置き場の表と読むと主張する。 宣言を読めない周は declaration の語で止まり書き直さない (字の直しは最初の行の前の SRS の round)。
FR54claimFR54 (設計 pointer の拒否) の解決しない理由に、 pointer の file が契約表の置き場に無いことを足すと主張する (字の直しは受付の断りの行 cg の前の SRS の round)。
FR51rationaleFR51 (台帳の lint) の、 解決できる設計 pointer を持たない open な契約を名指す形を保ち、 台帳の形の検査が数える表を同じ置き場に揃える (字は揃えるだけ)。
FR53rationaleFR53 (契約 file の生成) の、 記録した base の表から行を読んで契約 file を生成する形を保つ。 読む file は契約表の置き場の file で、 「base の設計 doc」を「base の契約表の置き場の file」とする字の直しは行 cg の前の SRS の round が持つ。
NFR4rationaleNFR4 (fail-closed) を保つ。 読めない宣言を既定に倒さず、 何にも当たらない項目と doc id の重なりを名指し、 黙って「表 0 本」に落とす経路を残さない。

照会先: SRS-SCRIBE2-MVP — SRS: 設計 → 契約 → 実装 → 検証 → land を、 人の手を借りずに 1 本通す器（MVP）

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなること 5 つと、 代わりに引き受けること 8 つです。 良くなるのは、 表を toml に置く repo でも見張りが表を見ること、 見張りの表の在りかの決め方が 1 つになり検査と門の範囲が揃うこと (中身で見分ける行の審査の決め方は残ります)、 項目を書かない repo の数え方が変わらないこと、 打ち間違いを表の検査が名指すこと、 受付の断りが入った後は走る便の行が門の守る範囲に在ることです。 引き受けるのは、 古い本体が新しい項目を断って設定を読む口が全部倒れるので入れ替えの順が要ること、 項目を書かない repo では門の守る範囲が直下の markdown だけに狭まること、 門を狭めてから受付の断りが入るまでの間はその範囲の外の行を門も受付も止めないこと (どちらも器の repo と隣の project で外れる表は 0 本)、 設定を変える commit の中の表の変更は変更の前の設定で測ること、 門と案件の file の書き直しが設定を読む手間、 受付の断りは相手が項目を書いて外を指す便が無くなった後でないと入れられないこと、 入れ子の dir や表でない toml を並べて書く手間、 要件書と用語集の字の直しです。

✓ 良い結果

  • ●表を toml に置く repo で、 契約表の検査・局面の出力・live-row の門・台帳の形の検査が表を見る
  • ●表を数える見張りの定義が 1 つになり (中身で見分ける行の審査の定義は残る)、 検査と門と局面の出力の範囲が揃う
  • ●key を書かない repo の検査の母集団は変わらない (本 repo は 30 本のまま)
  • ●打ち間違いの項目と doc id の重なりを契約表の検査が名指し、 黙って「表 0 本」にならない
  • ●受付の断りの着地の後は、 置き場の外を指す契約が便にならず、 走っている便の行は門の守る範囲に在る

⚖ トレードオフ・代償

  • ●古い binary は contract-tables を未知の key として宣言全体を断り、 宣言を読む全部の口 (受付・契約表の検査・局面の出力・close の門・席の権能 guard・gate) が宣言を読めない側に倒れる (席の権能 guard は repo の全 file を code と扱う)。 消費側が key を書くのは、 その host の PATH の binary を key を知る版に入れ替えた後で、 着地の知らせにこの順を書く
  • ●key を書かない repo の live-row の門は、 設計 doc の dir の下の toml と入れ子の dir の表を守らなくなる (器の repo と隣の project の両方で該当 0 本・2026-10-02 に数えた)。 そこに表を置く repo は key で名乗る
  • ●行 cd (門を狭める) から行 cg (受付の断り) までの間、 key を書かない repo の設計 doc の dir の下の toml と入れ子の dir の表を指す走っている便の行は、 門も受付も止めない (器の repo と隣の project の両方で 0 本・2026-10-02 に数えた。 隣の project の contracts/ の行は今も門の外なので、 その間に減る守りは無い)
  • ●宣言を変える commit と同じ commit の表の変更は、 変更の前の宣言で測る。 便が走っている間に宣言から置き場を外すと、 門はその置き場の行を守らない (宣言の変更そのものは便の審査と gate か user の手を通る)
  • ●門は markdown か toml の編集のたびに HEAD の宣言を 1 回読み (git の子 process 1 回・code と区間を持たない markdown の編集では読まない)、 局面の出力の全部の書き直しは main の木の全 path を 1 回読む。 宣言を読めない周の門は .md と .toml の file を全部比べるので、 その周だけ event log を読む回数が増える
  • ●受付の断りは、 消費側が key を名乗った後でないと着地できない (先に着地すると、 いま置き場の外を指す便の受付と resume の取り直しが全部断られる)。 着地の前に置き場の外を指して走り出した便は resume で止まるので、 着地の前にその便を 0 本にする
  • ●dir の項目は直下だけを読むので、 入れ子の dir は項目を並べて書く。 表でない toml を同じ dir に置く repo は file の項目で並べる (読めない表として契約表の検査が名指すので、 黙っては落ちない)
  • ●SRS の「設計 doc の契約表」の言い回しと、 用語集の「設計 doc」「契約」「設計 pointer」の字が動き、 その直しは user の SRS の round が持つ (FR47・FR55・FR90 は最初の行の前、 FR53・FR54 は行 cg の前)
06 改訂関係と原則 / この判断の位置づけ

版の系譜と、 行き着く原則 (照会終端)

この記録が版の系譜のどこに在るかと、 判断が最後に行き着く原則です。 この記録は ADR-0023 の 1 つの句を部分的に置き換えます。 契約の正本を「設計 doc の末尾の表の 1 行」とした句を「契約表の置き場の表の 1 行」と読み替え、 表の 2 つの形・形の決め方・契約の名の形は保ちます。 その句は user の裁定で決まったもので、 この記録は同じ 2 つの形の中の読み替えに留めます。 設定 file の項目の集合を決めた ADR-0010 は置き換えず、 編集の範囲を名乗る ADR-0047 とは別の事実として並べます。 走る便の行を守る門は user の裁定の下で足されましたが、 守る範囲は設計の値で、 それを狭めるのは user の常設の指示の下の orchestrator の決定です。 原則は ADR-0047 のもので、 repo の形はその repo の事実なので repo に名乗らせ、 名乗らない回は器の既定で動き、 名乗りが読めない回は最も厳しい側へ倒す、 です。

照会終端 — PRIN-CONSUMER-DECLARES-ITS-OWN-SHAPE (ADR-0047)
