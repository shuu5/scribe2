設計判断記録 (ADR) scribe2 — 台帳の形の写し

台帳の形の写し — hook の外の先読みの口が内容の鍵と組で台帳の 4 欄を写して置き、 台帳の形の門は鍵が今の store と字で等しい周だけ台帳を読まずに写しで測る

台帳の形の門は、 bd の書きの前に台帳を丸ごと 1 回読み、 崩れを増やす書きだけを断る。 読みの待ち上限は hook の予算 2.0 秒の全部で、 host が混む周は読みが 1.5〜27 秒かかって門が書きを断り続け、 崩れを直す書きも止まる。 本 ADR は、 席が hook の外で撃つ先読みの口が、 判定に要る 4 つの欄だけを、 台帳の中身の目印 (内容の鍵) と組で state dir に写して置き、 門は今の目印が写しの目印と字で等しい周だけ台帳を読まずに写しで測ると決める。 目印が違う・写しが無い周は今までどおり台帳を読むので、 写しは判定を変えず、 真実は台帳に残る (憲法 C3 の読み)。

この判断が約束すること (1 文サマリ)

この記録で「器」は scribe2 の本体、 「台帳」は作業と裁定を記録する bd の帳簿、 「門」は AI の席が道具を撃つ直前に器が挟む検問です。 台帳の形の門は、 台帳へ書く前に台帳を丸ごと 1 回読み、 崩れ (どこにも繋がらない作業や、 子が多すぎる親) を増やす書きだけを止めます。 けれども読みに使える時間は 2 秒しかなく、 計算機が混むと読みが 1.5〜27 秒かかって、 門は書きを止め続け、 崩れを直す書きまで止まっていました。 この記録は、 時間をかけてよい別の口 (先読みの口) が判定に要る 4 つの欄だけを、 台帳の中身の目印と一緒に写して置き、 門は今の目印が写しの目印と同じときだけ台帳を読まずに写しで判定すると決めます。 目印が違えば今までどおり台帳を読むので、 写しが判定を変えることはありません。

01 背景 / なぜこの判断が要るか

いま何が問題か (確定方式を決める力学)

なぜこの判断が要るのかを 4 つから説明します。 計算機が混む周に門が書きを止め続け、 直す書きまで止まった経緯・門の読みは 1 回きりで、 その時間のほとんどが台帳を開く費用であるという実測・台帳の中身の目印が読みでは動かず書きでは動くという実測・憲法をどう読み、 何を決めて何を変えないかという範囲です。

CTX1

経緯 — host が混む周、 台帳の形の門台帳の崩れを止める門が書きを断り続け、 直す書きも止まる

台帳の形の門 (設計 ledger-form.md §12) は、 起票の門で止まらなかった bd / bdw の 6 つの書きに台帳を 1 回読み、 根に着かない・溢れた親・親子の輪・根から外す書きを、 直す 1 行つきで断る。 読みの待ち上限は rules 行 hook.budget_ms (2000 ms) で、 その値は SRS NFR5 の 2.0 秒そのものである。 越えた周は ledger-timeout で断り (fail-closed)、 断り文の次の一手は撃ち直すことだけである。 host が混む周の全件の読みは 1.5〜27 秒 (2026-09-28〜10-01 の標本・1 分の load 14〜133) で、 撃ち直しも続けて断られ、 §12 の断り文が直し方として名指す書き (子 epic の作成・付け替え) も止まる。 orchestrator の観測と隣の project の席の申告から memo s2-07l.738.3 が立ち、 再発 3 の昇格条件は 2026-09-30 に満ち、 2026-10-01 の起票では create が 8 回断られた。

CTX2

現物 — 門の読みは 1 回で、 bd の 1 回は store を開く費用が支配する

門は 1 回の hook で全件の読み (bd の readonly の list の all) を 0 回か 1 回だけ撃ち (掛かる書きが在る周だけ・撃ち直しなし)、 判定が使うのは bead の id・status・型・parent-child の辺の 4 つの欄だけである。 減らせる余地は 1 回を 0 回にすることだけになる。 2026-10-01 (1 分の load 10〜15・台帳 971 本・全件の JSON 8.6 MB) に同じ load の下で各 10 回測った中央値は、 全件の読み 1.02 秒・起動だけ 0.11 秒・bead 1 件の show 1.22 秒・3 件の show 3.04 秒・node の包みを外した本体 1.13 秒で、 狭い読みも包みを外した読みも速くならない。 4 つの欄だけの写しは 121 KB で、 全件の出力の 1.4 % である。 plugin の hook の timeout は 10 秒で、 負荷の尾 (10.9〜27 秒) はこれも越える。 負荷の尾は load だけでは決まらず、 store の LOCK の取り合いと I/O の混みが足される。

CTX3

現物 — store の目次と追記の記録は、 読みで動かず書きで動く

bd 1.1.0 の embedded の store (dolt) は、 目次の file (manifest・ : で割った 1 行に版・lock・root・gc の世代と、 file 名と chunk 数の組) と、 名が全部 v の追記の記録の file (journal) を持つ。 読み (list と show) の前後で、 目次の字と journal の byte 長は動かず (更新時刻だけが同じ字の置き替えで動く)、 import・append-notes・create・close の書きでは目次の root と chunk 数と journal の長さが動いた (2026-09-28 の使い捨ての台帳・2026-09-30 と 10-01 の本 repo の store)。 局面の出力の台帳の印台帳の変化の目印 (ADR-0088) は目次の 1 file から root・世代・chunk 数を組み、 bd も git も撃たない。 ただし今の読み手は欄の位置が 1 つずれていて実物の目次を読めない (直しは別の設計の行 case-lifecycle.md の行 f が持つ)。 bd が書きの後に出す mirror (issues.jsonl) は、 どの時点の store の写しかを持たない。

CTX4

射程 — 写しを判定に使う読みと、 決めること・変えないこと

C3 は真実を cache に置かないと定め、 C10 は測った値を出所と組で持ち、 宣言の値を測りを経てだけ効く値にすると定め、 NFR5 は hook の呼出しを各 2.0 秒以内と重い I/O を持たないことで縛る。 ADR-0088 は導き出した局面の出力に真実を持たせない読みを記録したが、 その射程は台帳の中身を外す (局面と手番と理由と結びだけ) ので、 台帳の 4 つの欄を写して門の判定の材料にする本件にはそのまま使えない。 決めるのは、 (1) 写しを判定に使ってよい条件 (内容の鍵台帳の中身の目印)、 (2) 写しを書く者 (hook の外の先読みの口写しを先に作る口だけ)、 (3) state dir の file の形と版、 (4) 鍵が依る bd の振る舞いの記録と測り直しの時、 (5) 型を epic にするだけの update を読まずに通すこと、 (6) 却下の分岐。 変えないのは、 rules 行の値と数・SRS の文・§12 の判定と断りの語・台帳の書きの口・依存である。 ADR を書く条件のうち 1 (C3 の読み)・3 (state dir の file の形)・4 (却下の分岐) に当たる。

02 判断を縛る力 / 評価の軸

選択肢を測るものさし (安全・速さ)

この判断を評価する 5 本のものさしです。 混む周も、 写した後に誰も台帳へ書いていなければ書きが進むこと。 写しで測っても判定が変わらず、 写しが無いか古いときは今の読みに戻ること。 門の時間と処理を増やさないこと。 真実の置き場を台帳 1 つに保ち、 写しを消しても判定が変わらないこと。 足す物を最小にし、 代わりに消す物を名指すことです。

DR1負荷の周も、 写した後に台帳が書かれていない間は、 門が台帳を読まずに書きを測って進める CTX1・CTX2
DR2判定を変えない — 写しで測った判定は同じ時点に台帳を読んだ判定と同じで、 写しが無いか古い周は今の読みに戻る (C3・fail-closed) CTX3・CTX4
DR3hook の予算と I/O を増やさない — 子 process と binary の呼出しの数を増やさず、 hook に書きを足さない (NFR5) CTX2・CTX4
DR4真実の置き場を台帳 1 つに保つ — 写しは台帳の読み 1 回からしか作らず、 消しても判定が変わらない (C3・C15) CTX3・CTX4
DR5足す物を最小にし、 消す物を名指す — rules 行・guard・hook の event・依存を足さず、 負荷の間に断られ続ける撃ち直しの手番を消す (C17.2) CTX1・CTX4
03 検討した選択肢 / 3 つの確定方式

それぞれの利点と欠点を並べる

候補を 10 並べます。 選んだのは、 時間をかけてよい口が中身の目印と一緒に写しを置き、 門は目印が同じときだけ写しで判定する案です。 選ばなかったのは、 門の中で読み直す案・読みの待ち時間を延ばす案・狭く読むか bd の本体を直に撃つ案・bd が書き出す控えの file を読む案・局面の出力に欄を載せる案・門の側で写しを作る案・読めないときは通す案・古い写しで一部の書きを救う案・bd を常駐の server で動かす案の 9 つです。

OPT1先読みの口が内容の鍵と組で写しを置き、 門は鍵が等しい周だけ写しで測る採用

席が hook の外で撃つ先読みの口 (ledger prefetch) が、 内容の鍵 (台帳の印の root・世代・chunk 数と journal の長さ) を読みの前後で測り、 rules 行 seat.ledger_timeout_s の待ち上限で台帳を 1 回読み、 前後の鍵が等しい周だけ 4 つの欄の写しを鍵と組で state dir に置く。 門は掛かる周に今の鍵を測り、 写しの鍵と字で等しく、 payload の cwd が hook の root と同じ周だけ、 bd を起こさず写しで判定する。 型を epic にするだけの update は読まずに通す。 決め手は実測 (CTX2・CTX3)。

席が門の外で撃つ先読みの口が、 台帳の中身の目印を読む前と後で測り、 時間をかけて台帳を 1 回読み、 前後の目印が同じときだけ判定に要る 4 つの欄を目印と一緒に写して置きます。 門は、 今の目印が写しの目印と字で同じで、 作業場所が repo の根と同じときだけ、 台帳を読まずに写しで判定します。 混む周も写しの後に誰も書いていなければ書きが進み、 判定は変わらず、 門の処理も増えず、 写しを消しても判定は変わりません。 代わりに、 写しは誰も書いていない間だけ効き、 目印は bd の今の版の振る舞いに依り、 偽の写しを置けば門を欺け、 前提の直しが入るまでは効きません。

+ 利点

  • 負荷の周も、 先読みの後に台帳が書かれていなければ、 門が読まずに書きを測って通す (DR1)
  • 鍵が等しい周の写しは同じ時点の台帳と同じ判定を返し、 写しが無いか古い周は今の読みに戻る (DR2)
  • 写しで測る周は hook の子 process が 0 本で、 hook に書きを足さない (DR3)
  • 写しは台帳の読み 1 回の出力からだけ作り、 消しても判定は変わらない (DR4)
  • rules 行・guard・hook の event・依存を足さず、 断られ続ける撃ち直しを先読み 1 回と通る撃ち直し 1 回に置き換える (DR5)

− 欠点

  • 写しは先読みの後に誰も書いていない間だけ効き、 負荷の間に書きを続ける席は書きごとに 2〜3 手になる
  • 鍵は bd 1.1.0 の store の file の振る舞いに依り、 bd の版を上げるたびに測り直す
  • 写しは AI と同じ OS の user が書ける置き場に在り、 今の鍵を付けた偽の写しを置けば門を欺ける
  • payload の cwd が root と違う周は写しを使えず、 台帳の印の読み手の直しが着地するまで効きは 0
OPT2門の中で、 残りの hook の時間に 1 回撃ち直す不採用

1 回目の読みが待ち上限で切れた周に、 hook の残りの時間でもう 1 回読む。 決め手は予算の使い切り (CTX2)。

1 回目の読みが時間切れになったら、 門の残りの時間でもう 1 回読む案です。 新しい file も口も要らず、 一時の跳ねなら 2 回目が間に合う点で勝ります。 けれども、 読みに使える時間は要件が決めた 2 秒の全部で、 1 回目が切れた時点で残りが無く、 要件を書き換えないと撃ち直せません。 同じ混み方の下では 2 回目も切れます。

+ 利点

  • 新しい file も口も要らない
  • 一時の跳ねなら 2 回目が間に合うことがある

− 欠点

  • 待ち上限は NFR5 の 2.0 秒の全部で、 1 回目が切れた時点で残りが無く、 撃ち直すには NFR5 の改訂が要る (DR3)
  • 同じ負荷の下の 2 回目も切れ、 尾は hook の timeout 10 秒も越える (DR1)
OPT3門の読みの待ち上限を上げる不採用

rules 行 hook.budget_ms の値を上げるか、 門の読みだけに長い締め切りを持たせる。 決め手は値の裁定と負荷の尾 (CTX2・CTX4)。

門の読みの待ち時間を延ばす案です。 仕組みを足さず、 中ほどの混み方なら通る周が増える点で勝ります。 けれども、 設定の値の裁定と要件の書き換えが要り、 どの値も門そのものの打ち切り 10 秒を越えられず、 実測の 10.9〜27 秒の遅れを閉じません。 すべての席の道具の呼び出しを、 その間待たせることにもなります。

+ 利点

  • 仕組みを足さない
  • 中ほどの負荷なら通る周が増える

− 欠点

  • 値の裁定 (C5) と NFR5 の改訂が要る (DR5)
  • どの値も hook の timeout 10 秒を越えられず、 実測の尾 10.9〜27 秒を閉じない (DR1)
  • 全部の席の道具の呼び出しを、 最大でその間待たせる (DR3)
OPT4狭く読む、 または bd の本体を直に撃つ不採用

門が要る bead だけを show で読むか、 node の包みを外して bd の本体を撃つ。 決め手は 2026-10-01 の実測 (CTX2)。

門が要る作業だけを狭く読むか、 bd の包みを外して本体を直に撃つ案です。 出力の量が減り、 包みの起動の費用を除ける点で勝ります。 けれども、 bd の 1 回の時間は台帳を開く費用が占め、 狭い読みも本体も全件の読みより速くなりませんでした。 本体の置き場を計算機ごとに器が持つことにもなります。

+ 利点

  • 出力の量が減る
  • 包みの起動の費用を除ける

− 欠点

  • bd の 1 回は store を開く費用が支配し、 show 1 件 1.22 秒・3 件 3.04 秒・本体 1.13 秒で、 全件の 1.02 秒より速くない (DR1)
  • 本体の path を host ごとに器が持つことになる (C10.2)
OPT5bd の mirror (issues.jsonl) を読む不採用

bd が書きの後に出す台帳の写しの file を、 門が読む。 決め手は出所の印の有無 (CTX3)。

bd が書きの後に書き出す台帳の控えの file (mirror) を門が読む案です。 bd を起こさずに読め、 新しい file が要らない点で勝ります。 けれども、 その file はいつの台帳の写しかを持たず、 書き出しは器の外の道具の副作用で、 実測では書き 23 回のうち 15 回に書き出しが続きませんでした。 file の更新時刻は読みでも動くので、 新しさの目印にもなりません。

+ 利点

  • bd を起こさずに読める
  • 新しい file が要らない

− 欠点

  • mirror はどの時点の store の写しかを持たず、 書きの後の export は器の外の道具の副作用で、 2026-09-28 の 15 分の標本では書き 23 回のうち 15 回に export が続かなかった (DR2)
  • 更新時刻は読みでも動くので、 写しの新しさの印にならない (DR2)
OPT6局面の出力に 4 つの欄を載せて門が読む不採用

ADR-0088 の局面の出力 (lifecycle.json) に台帳の 4 つの欄を足し、 門はその出力を読む。 決め手は ADR-0088 の射程と書き直しの時 (CTX4)。

器がすでに書いている局面の出力に 4 つの欄を載せ、 門がそれを読む案です。 新しい file が要らず、 古さの目印もすでに持つ点で勝ります。 けれども、 局面の出力は台帳の中身を載せないと決めた記録の範囲の外で、 その読みを崩します。 しかも出力は器の決まった時にだけ書き直され、 席が書いた後は古い印が付くだけなので、 門が要る今の台帳の時に在ることが少ないのです。

+ 利点

  • 器がすでに書く file に載せられ、 新しい file が要らない
  • 入力の印と古さの印をすでに持つ

− 欠点

  • ADR-0088 の射程 (局面と手番と理由と結び) の外で、 台帳の中身を載せない読みを崩す (DR4)
  • 出力は便の周と器の書きの後にだけ書き直り、 席の書きの後は古さの印が付くだけなので、 門が要る今の台帳の周に在ることが少ない (DR1)
OPT7hook の中で写しを作る不採用

門が読めた周に写しを書く・切れた読みを子 process に続けさせて写しを書かせる・PostToolUse の hook で書きの後に写しを作る、 のどれかで、 写しを書く者を hook の側に置く。 決め手は hook の予算と process の積み重なり (CTX2)。

門の側で写しを作る案です (読めた時に書く・時間切れの読みを裏で続けさせる・書きの後の別の見張りで作る)。 席が先読みの口を撃つ手番が要らない点で勝ります。 けれども、 門が読めるのは混んでいない時なので写しが要らず、 混む時は読みが切れて書けません。 裏で続けさせると門の後に残る process が混む間に積み重なり、 台帳の取り合いを増やします。 書きの後の見張りで作ると、 道具 1 回あたりの見張りの呼び出しが増え、 書きのたびに全件を読みます。

+ 利点

  • 席が先読みの口を撃つ手番が要らない

− 欠点

  • 門が読めた周は負荷の無い周で写しが要らず、 負荷の周は読みが切れて書けないので、 書いて効く周がほとんど無い (DR1)
  • 切れた読みを続けさせると hook の後に生き残る process ができ、 負荷の間に積み重なって store の LOCK の取り合いを増やす (DR3)
  • PostToolUse で書くと道具 1 回の binary の呼出しが 3 本になり、 書きのたびに全件を読む (DR3)
OPT8読めない周と間に合わない周は書きを通す (fail-open)不採用

読みが切れた周は判定せずに書きを通す。 決め手は §12 の fail-closed と、 違反は減る向きにしか動かさない裁定 (CTX4)。

読めない時と時間切れの時は判定せずに書きを通す案です。 混む周も書きが止まらず、 仕組みが要らない点で勝ります。 けれども、 判断できない時は止めるという要件と、 崩れは減る向きにしか動かさないという持ち主の裁定に反し、 混む周だけ崩れを増やす書きが素通りします。

+ 利点

  • 負荷の周も書きが止まらない
  • 仕組みが要らない

− 欠点

  • §12 の fail-closed (NFR4) と、 違反は減る向きにしか動かさない裁定 user 2026-09-27T14:02Z に反し、 崩れを増やす書きが負荷の周だけ素通りする (DR2)
OPT9鍵の違う古い写しでも、 根に着いた epic への create は救う不採用

前の草稿の形で、 写しの後に台帳が書かれていても、 付け先が根に着いたままと見込める epic の create は古い写しで通す。 決め手は根に着いたままであることの根拠 (CTX3)。

写しの後に台帳が書かれていても、 根に着いたままと見込める epic への作成だけは古い写しで通す案です (前の草稿の形)。 混む間に子 epic を作る書きが、 先読みなしで通る点で勝ります。 けれども、 根に着いたままであることを門の働きに頼るので、 削除や門の無い session の書きで崩れます。 先読みの口が決まった 2 手の進み方を与えるので要りません。

+ 利点

  • 負荷の間に子 epic を作る書きが、 先読みなしで通る

− 欠点

  • 根に着いたままであることの保ちを門の ratchet に頼り、 delete と門の無い session の書きで崩れる (DR2)
  • 先読みの口が決まった 2 手の進み方を与えるので要らない (DR5)
OPT10bd を server の mode で動かす不採用

常駐の dolt の server に台帳を置き、 読みのたびに store を開く費用と store の LOCK をなくす。 決め手は射程 (CTX4)。

bd を常駐の server で動かし、 読むたびに台帳を開く費用と台帳の取り合いをなくす案です。 読みの費用そのものが下がる見込みがある点で勝ります。 けれども、 器の外の環境を変えることで、 常駐の process にすべての project の台帳の読み書きが依り、 持ち主の承認が要る類の変更です。 効きもまだ測っていません。

+ 利点

  • 読みの費用そのものが下がる見込みがある (未実測)

− 欠点

  • 器の外の環境の変更で、 常駐の process に全 project の台帳の読み書きが依り、 A1 の使うの類として user の承認が要る (DR5)
  • 効きを測っていない (DR1)
04 採用した判断 / どの方式を選ぶか

選んだ方式と、 それが守る要件 (cross-doc 照会)

選んだ案と、 それが要件書のどの要件を支えるかを示します。 門は、 今の台帳の目印が写しの目印と字で同じで、 作業場所が repo の根と同じときだけ、 台帳を読まずに写しの 4 つの欄で判定します。 写しを書くのは門の外の先読みの口だけで、 型を epic にするだけの書きは読まずに通し、 時間切れの断り文は先読みの口を次の一手として名指します。

採用 — OPT1

器の台帳の形の門 SHALL、 掛かる書きが在る周に、 hook の root の台帳の内容の鍵が台帳の形の写し判定に要る欄の写しの鍵と字で等しく、 payload の cwd を正規化した path が hook の root と等しい周に限り、 台帳を読まずに写しの 4 つの欄 (id・status・型・parent-child の辺の先と種別・辺の順のまま) で判定する。 判定・断りの語・直す 1 行・記録は同じ時点に台帳を読んだ周と同じで、 写しが無い・鍵が違う・崩れた・鍵が無い・cwd が root と違う周は今の読み (待ち上限 hook.budget_ms) に戻る。 内容の鍵は 1 行で、 写しの形の版・root の path・台帳の印の root と世代と chunk 数・journal の byte 長を並べ、 台帳の印が embedded の store の形で journal の長さを読める周だけ在る (store の無い台帳と server の mode の台帳は鍵が無く今の読みのまま)。 写しは導き出した値で、 真実は台帳に残る: 写しを作るのは台帳の読み 1 回の出力だけで、 台帳への 2 本目の口を足さず、 消しても判定は変わらない (C3・C10 の読み)。 写しを書くのは hook の外で席が撃つ先読みの口 (ledger prefetch) だけで、 hook は読むだけ。 先読みの口は rules 行 seat.ledger_timeout_s の待ち上限で台帳を 1 回読み、 読みの前後で鍵を測って等しい周だけ写しを書き、 書かない周は閉じた 7 語の理由で断る (台帳か state dir が壊れている 2 語は rc 2・ほかの 5 語は rc 1)。 写しは root ごとに state dir の直下の file 1 つで、 1 行目が鍵・2 行目が bd の list と同じ key の名の 4 つの欄の JSON 配列で、 一時 file からの rename で入れ替える。 形を変える版は鍵の頭の版を上げ、 知らない版は写しが無い扱いにする。 鍵が依る bd 1.1.0 の振る舞い (読みで目次の字と journal の長さが動かず、 書きで動く) は実測の事実として記録し、 bd の版を上げる便は読みと書きでの鍵の動きを測り直す。 型を epic にするだけの update (付け先を持たず型の値が epic の update だけが掛かる command) は、 どの台帳でも断られないので台帳を読まずに通す。 ledger-timeout の断り文は、 先読みの口を撃ってから同じ書きを撃ち直す一手を名指す。 rules 行の値と数・SRS の文・依存は変えない。

台帳の形の門は、 書きを判定するとき、 今の台帳の中身の目印 (内容の鍵) が、 先読みの口の置いた写しの目印と字で同じで、 作業場所が repo の根と同じときだけ、 台帳を読まずに写しの 4 つの欄で判定します。 判定・断りの語・直す 1 行・記録は、 同じ時に台帳を読んだときと同じです。 写しが無い・目印が違う・写しが崩れた・目印が無い・作業場所が根でないときは、 今までどおり 2 秒の待ち上限で台帳を読みます。 目印は 1 行で、 写しの形の版・根の場所・台帳の目次の値・追記の記録の file の長さを並べ、 台帳が bd の組み込みの store を持つときだけ在ります。 写しは導き出した値で、 真実は台帳に残ります。 写しを書くのは門の外で席が撃つ先読みの口だけで、 長めの待ち上限で台帳を 1 回読み、 読む前と後の目印が同じときだけ写しを書き、 書かないときは 7 つの理由の語で断ります (台帳か置き場が壊れているときは別の終わり方の番号を返します)。 写しは根ごとに器の置き場の file 1 つで、 1 行目が目印、 2 行目が 4 つの欄の並びです。 目印が依る bd の振る舞いは実測した事実として残し、 bd の版を上げるときに測り直します。 型を epic にするだけの書きは、 どの台帳でも止められないので読まずに通します。 時間切れの断り文は、 先読みの口を撃ってから撃ち直す一手を名指します。 設定の値・要件の文・依存は変えません。 目印が同じときだけ写しを使うのは、 実測で台帳の目次の字と追記の記録の長さが読みでは動かず書きでは動いたので、 目印が同じなら写した後に誰も書いていないと言え、 写しで判定しても台帳を読んだ判定と同じになるからです。 目印が違えば台帳を読むので、 写しは判定を変えず、 真実を台帳の外に置くことになりません。 写しを書く者を門の外の口に限ったのは、 門が読めるのは混んでいない時で写しが要らず、 混む時は読みが切れて書けないうえ、 門に書きの処理を足すと要件の時間の約束を崩すからです。 待ち時間を延ばす案と読み直す案を退けたのは、 要件の書き換えが要るうえ、 実測の遅れが門の打ち切り 10 秒も越えるからです。 狭い読みを退けたのは、 1 回の時間を台帳を開く費用が占め、 狭くしても速くならなかったからです。 bd の控えの file を退けたのは、 いつの写しかを持たず、 書き出しが続かないことが多かったからです。 型を epic にするだけの書きを読まずに通すのは、 門がその書きを止めるのは根の epic を epic でなくする時だけで、 型を epic にする書きはどの台帳でも止まらないからです。

05 結果 / 良い面とトレードオフ

この判断で何が良くなり、 何を引き受けるか

この判断で良くなること 4 つと、 代わりに引き受けること 6 つです。 良くなるのは、 混む周も写しの後に誰も書いていなければ書きが進むこと、 判定が変わらないこと、 門の処理が増えないこと、 型を epic にするだけの書きが読まずに通ることです。 引き受けるのは、 写しが効くのは誰も書いていない間だけであること、 目印が bd の今の版の振る舞いに依ること、 偽の写しを置けば門を欺けること、 作業場所が根でないときは使えないこと、 台帳の取り合いは減らないこと、 前提の直しが入るまで効かないことです。

✓ 良い結果

  • ●負荷の周も、 先読みの後に台帳が書かれていなければ、 門が bd を起こさずに書きを測って通し、 崩れを直す書きも進む
  • ●写しで測った判定は同じ時点に台帳を読んだ判定と同じで、 写しが無いか古い周は今の読みに戻るので、 fail-closed も減る向きにしか動かさない線も変わらない
  • ●写しで測る周は hook の子 process が 0 本になり、 hook に書きの I/O も binary の呼出しも足さない
  • ●型を epic にするだけの update は、 負荷の周も台帳を読まずに通る

⚖ トレードオフ・代償

  • ●写しは先読みの後に誰も書いていない間だけ効き、 負荷の間に書きを続ける席は書きごとに断り・先読み・撃ち直しの 2〜3 手になる
  • ●鍵は bd 1.1.0 の embedded の store の file の振る舞いに依る。 bd が置き場か形を変えれば鍵が無くなって今の読みに戻るが、 中身が変わるのに目次の root も journal の長さも動かない store が来れば鍵は偽になるので、 bd の版を上げる便が測り直す
  • ●写しは AI と同じ OS の user が書ける state dir に在り、 今の鍵を付けた偽の写しを置けば門を欺ける (門は事故を止める仕組みで、 意図した迂回を閉じない・改ざんは不可能にならない)
  • ●payload の cwd が root と違う周 (root の下の dir・別の worktree) は写しを使わない
  • ●写しは store の LOCK の取り合いそのものは減らさない (先読みの口も全件の読み 1 回)
  • ●台帳の印の読み手の直し (case-lifecycle.md の行 f) が着地するまで、 鍵が無く効きは 0 で、 写しの file は repo と state dir の組ごとに 1 つ残り消す口を持たない
