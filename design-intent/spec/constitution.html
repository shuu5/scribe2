本 constitution は IETF RFC 2119 および RFC 8174 / BCP 14 に定義される MUST / SHALL / SHALL NOT のキーワード解釈規約に従う。 規範文 (EARS) は機械層 (data-audience="machine") が正で、 人間向け要旨はその正確な要約である。

§1. Purpose — この憲法が何を決め、 どう読むか

scribe2 が版をまたいで守る「折れない線」を、 守り方の強さで Always / Ask-first / Never の 3 段に分けて置きます。 各条は「人が読む要旨」「機械が読む規範文 (正本)」「機械が検査できる形 (型 / lint / CI)」「出所 (どの裁定から来たか)」の 4 つを必ず併せ持ち、 数値は条文に書かず manifest の rules 行に置き、 その初期値を §3 に写します。 線どうしがぶつかったら、 場当たり修正の禁止 → 膨張防止 → compile 速度 の順位で決めます。

本 constitution は scribe v2「次の器」の design-intent の最上位文書であり、 条文の canonical WHAT かつ edit-SSoT である (folio ADR-0051 §3: flip しない doc は HTML が唯一の層)。 24 条の各条は (a) human 要旨、 (b) EARS 規範文 (canonical)、 (c) 機構 = 条を成立させる型 / lint / CI の形、 (d) 出所 = 裁定論点 id、 の 4 要素を持つ。 (c) を欠く条を置かない (散文だけの規則を残さない = N2)。 1 つの条は複数の規範文を持ちうる: 最初の規範文は条 id (例 C12)、 以降は条 id に連番を付す (例 C12.2)。 EARS pattern は各規範文の論理構造で決まり、 段 (Always / Ask-first / Never) とは独立である。 card の badge は最初の規範文の pattern を表し、 2 つ目以降の規範文の pattern は machine 層の各 block が持つ。 原本が執行主体を特定しない条は主語を scribe2 (system of interest) とし、 CI 等の執行機構は機構 dd に (導出) と明示する。 原本が CI を名指す条は scribe2 CI を主語にする。 数値 (閾値・件数・秒数) は条文に置かず rules 行 (manifest 内の値 1 行・裁定 id 付き) に置き、 本文書ではその初期値を §3 に写す。 改訂は A2 (利益の grill 検証を前置した user 裁定) のみで、 条文の改訂は新 ADR と本文の delta marker と裁定 id を伴う (N4)。

順位: WHEN two lines of this constitution conflict in a decision, scribe2 SHALL resolve the conflict in this order: prohibition of ad-hoc fixes first, prevention of growth second, compile speed third.

出所: 論点 1。 順位は条ではなく全条に先立つ決め方であり、 条 id の連番を持たない (§2 の一覧表にも含めない)。

§2.1 Always — いつも守る (C1〜C16)

例外なく常に守る 16 条です。 規則・経路・状態を「1 つ」に閉じ、 大きさと消費と依存に予算を置き、 失敗と値の出所を型で扱い、 歯は Rust の test だけにします。 規律は文書とデータの 2 面で持ち、 台帳はタスク専用で、 仕様からの逸脱は編集の時点で止めます。

C1 Ubiquitous 規則はデータ

規則の「種類」は閉じた型で、 「値」は repo 内の manifest 1 file に置きます。 人が読む説明は型と manifest から生成し、 手書きの規範文は 0 行です。 機械が実行時に読む規則はこの manifest 1 file だけです。

normative (machine)

C1: scribe2 SHALL represent every rule kind as a variant of one closed type with a mandatory exhaustive check implementation, SHALL keep every rule value (threshold, enabled flag, ruling id, ruling time, verbatim text) in exactly one manifest file inside the repository, SHALL keep only runtime state in the database, and SHALL read rules at run time only from that manifest.

C1.2: scribe2 SHALL derive human-readable rule documentation from the rule type and the manifest, and SHALL contain zero hand-written normative lines in that generated rule documentation.

機構 (型 / lint / CI)
enum RuleKind + trait Rule { fn check(&self, ctx) -> Verdict } を網羅 match で実装必須 (未実装 = compile error)。 値は manifest 1 file (TOML・schema_version・未知 key 拒否・起動時 1 回読み)。 DB は実行時状態だけを持つ。 人間向け doc は enum の doc コメント + manifest からの build.rs 生成物。 CI は生成 doc 中の手書き規範文の行数を数え、 0 行でなければ落とす。

論点 5
C2 Ubiquitous 経路は 1 本・語彙は 1 つ・名前は 1 定数

選定・除外・routing はそれぞれ 1 関数・1 enum で、 適用順は enum の並び順だけが決めます。 理由を足すときは enum に 1 値足すだけです。 設定は manifest 1 struct から読み、 env を直接読まず、 新しい env の口も作りません。 名前はすべて 1 つの定数から導きます。

normative (machine)

C2: scribe2 SHALL implement selection, exclusion and routing each as exactly one function over exactly one enumeration, SHALL take the application order solely from the declaration order of the stage enumeration, SHALL NOT carry a prose note on ordering, and SHALL express a new reason only as one new variant.

C2.2: scribe2 SHALL read configuration only from the manifest structure, SHALL NOT read environment variables directly, SHALL NOT introduce a new environment seam, and SHALL derive the plugin name, crate name, skill namespace, state directory, environment prefix and terminal-multiplexer server name from one NAME constant.

機構 (型 / lint / CI)
選定 / 除外 / routing = 各 1 関数 + 1 enum。 除外と適用順は宣言的で enum Stage の列挙順が唯一の適用順 (「適用点は X の後」の散文注記を持たない)。 設定 = manifest 1 struct・env 直読禁止・env seam を新設しない。 plugin 名 / crate / skill 名前空間 / state dir / env 接頭辞 / tmux server 名は NAME 1 定数から導出。

論点 8・SPEC §7
C3 Ubiquitous fleet の状態は 1 つ

host / 口座 / 席 / lease / 退役は 1 つの DB file (host 列付き) に置き、 host ごとの dir や TSV や cache に真実を置きません。 doctor 1 コマンドが全 host の版・口座・退役を照合します。 状態は型で運び、 端末の見た目や自由文を判定に使いません。 完了条件は 1 つの enum だけで表し、 待つ処理も 1 実装だけで、 その場限りの判定条件を書ける口は作りません。

normative (machine)

C3: scribe2 SHALL keep the state of hosts, accounts, seats, leases and retirements in exactly one database file carrying a host column, and SHALL NOT place truth in per-host directories, TSV files or caches.

C3.2: scribe2 SHALL provide one doctor command that reconciles version, accounts and retirements across all hosts.

C3.3: scribe2 SHALL carry seat state as a typed enumeration, and SHALL NOT use terminal rendering or free text as judgment input.

C3.4: scribe2 SHALL express completion conditions only as values of one completion enumeration, and SHALL provide exactly one wait implementation that accepts only those values, and SHALL NOT expose a wait entry point that takes an arbitrary predicate.

機構 (型 / lint / CI)
SQLite 1 file (host 列)。 doctor 1 コマンドが全 host の版・口座・退役を照合。 状態は enum SeatState で運ぶ。 完了条件は enum Completion の値でのみ表現でき、 待機 API は 1 実装 (引数型が Completion に閉じており、 その場で述語を書ける口を作らない)。
出所
論点 8
C4 Ubiquitous 大きさに上限

core・module・test の大きさと関数の粒度に上限を置き、 CI が実測します。 粒度の lint は #[allow] で黙らせられません。 上限の変更は A2 (利益の grill 検証を前置した user 裁定) でだけ行います。 判断に迷うときは「歯を足す」より「compiler に検査させる」を先に選びます。

normative (machine)

C4: scribe2 SHALL enforce upper bounds on core size (R-C4-1), module size (R-C4-2), the test-to-source line ratio (R-C4-3) and function granularity (R-C4-4) as CI-measured deny gates, SHALL NOT silence a granularity lint with an allow attribute, and SHALL change any such bound only through A2.

機構 (型 / lint / CI)
閾値 = §3 R-C4-1 (core 総行数) / R-C4-2 (1 module 行数) / R-C4-3 (test:src 行数比) / R-C4-4 (関数粒度 lint = 関数行数・複雑度・引数数)。 関数粒度 lint は deny で #[allow] による黙殺禁止。 CI が実測する。 判断規則 (A2 の審査観点): 「歯を足す」より「compiler に検査させる」を先に選ぶ。

論点 2
C5 Unwanted 規則変更 = manifest diff + 裁定 id

rules 行の追加や変更は、 user の裁定 id が付いていなければ merge できません。 CI が「裁定 id の無い rules 行の diff」を落とします。

normative (machine)

C5: IF a change adds or modifies a rules row without an accompanying user ruling id, THEN scribe2 CI SHALL reject the change.

機構 (型 / lint / CI)
rules 行の diff を CI が検査し、 裁定 id (ts) の無い diff を落とす。 裁定 id と裁定時刻は rules 行の値の一部 (C1)。 帰結として AI が場当たりで規則を生やすことはできない。

論点 5
C6 Ubiquitous 消費は害

Budget は Precheck の実測を使ってしか作れず、 起動口は Budget を受け取る 1 関数だけなので、 見積なしの起動は型の上で不可能です。 1 run の token 上限と検出線は rules 行に置き、 上限を超えたら人手を介さず止めます。 計測は 1 つの追記専用 store に残します。

normative (machine)

C6: scribe2 SHALL make a Budget constructible only by consuming a Precheck measurement, and SHALL expose exactly one spawn entry point, which requires a Budget.

C6.2: IF a run exceeds the per-run token ceiling (R-C6-1), THEN scribe2 SHALL stop the run without manual intervention.

C6.3: scribe2 SHALL record consumption in exactly one append-only store.

機構 (型 / lint / CI)
Budget は Precheck の実測を消費してしか作れず、 fn spawn(budget: Budget) が唯一の起動口 (帰結: 見積なしの起動は型で不能)。 計測は append-only store 1 つ。 上限と検出線の値は §3 R-C6-1。 C10 (値の出所を型で弁別) の応用。

論点 11
C7 Ubiquitous planner が唯一の対話面対話面は 1 つ

user の承認は、 ただ 1 つの対話面を通ったものだけを機械が受け取ります。 その対話面がどの席かは条文でなく rules 行 (R-C7-1) が決め、 今は開発 session が user と直接対話し、 受け取った承認は逐語を添えて記帳します。 他の経路で来た「承認」は承認として扱いません。

normative (machine)

改訂前の要旨: user の承認は planner を通った relay 印だけを機械が受け取ります。

C7: scribe2 SHALL accept a user approval only as a relay stamp issued through the planner.accept a user approval only through exactly one dialogue surface, and SHALL take the identity of that surface from the rules row R-C7-1 rather than from this article.

C7.2: scribe2 SHALL record every accepted approval as an approval event carrying the user's verbatim words.

機構 (型 / lint / CI)
承認 = planner 発行の relay 印のみを機械が受理する。承認の受理面は 1 つで、 どの席かは rules 行 R-C7-1 の値が決める (初期値 = user 直 = 開発 session)。 planner 席を戻すときは rules 行の値を変えるだけで条文は動かない。 受理した承認は fleet の approval event (approval.received・user の逐語付き) に記帳し、 会話の記憶を承認の根拠にしない。 A1 / A2 / A3 / A4 の承認はすべてこの経路を通る。

C8 Ubiquitous 版 N+1 は版 N の下で作られる版 N+1 は design-intent の下で作られる

器の開発を拘束するのは design-intent (憲法・ADR・要件 doc = folio 形式の tracked 文書) であり、 前の版の pipeline や oracle ではありません。 自己開発の可否を「前の版が成熟を測ったか」で決めません。 design-intent と食い違う編集は、 後の gate に回さず編集の時点で止めます (C16)。 design-intent の変更は必ず ADR か版付き文書として残します。

normative (machine)

改訂前の要旨: 器が自分自身を開発できるのは「成熟した版」だけです。 成熟の宣言は §3 の成熟条件がすべて成り立つことを機械が測り、 裁定 id を付けて行います。 自己開発が解禁されていない間は、 自分の repo への dispatch を拒みます。 立ち上げは 4 つの状態 (段 0 / 段 1 / 段 1-test / 段 2) を持ち、 機械が塞ぐのは最後の段 2 だけです。

C8: scribe2 SHALL permit self-development only for a version declared mature.be developed under its design-intent (constitution, ADRs, requirements) as the binding constraint, and SHALL NOT require a previous version to act as oracle or to hold stop authority.

C8.2: WHILE self-development is not enabled with a ruling id, scribe2 SHALL deny a dispatch onto its own repository anchor.C8.2: WHEN an edit conflicts with design-intent, scribe2 SHALL stop the edit at edit time rather than defer the judgement to a later gate of a previous version.

C8.3: scribe2 SHALL expose the maturity conditions as measured values through the doctor command.C8.3: scribe2 SHALL record every change to design-intent as an ADR or a versioned document.

C8.4: scribe2 SHALL attach a ruling id to every maturity declaration, and SHALL base every maturity declaration on all maturity conditions defined in R-C8-1 holding at once.

機構 (型 / lint / CI)
enum SelfDev { Disabled, Enabled { ruling_id } }。 dispatch は自 repo anchor を Enabled 以外で deny。 doctor selfdev が成熟条件を Measured<T> で出す。 bootstrap は 4 つの状態を持つ: 段 0 = v1 が v1 を自己開発 ／ 段 1 = v2 repo に v1 plugin の planner / admin を置いて v2 を開発 ／ 段 1-test = v2 repo 外の test project に v2 plugin を置いて試運転 ／ 段 2 = 成熟 + go の後に v2 repo 内の席を v2 plugin へ替えて自己開発。 deny が塞ぐのは段 2 だけ。 成熟条件の値は §3 R-C8-1。拘束条件の実体は tracked な design-intent/。 機械が守るのは (a) 契約 write-set の外への編集を編集時に止める in-loop guard (C16・PreToolUse) と (b) design-intent の validate / build が CI で緑であること。 改訂前の enum SelfDev / doctor selfdev / dispatch deny / bootstrap 4 状態は廃止 (前の版の存在を前提にした機構)。 §3 R-C8-1 は停止 (測らない・履歴として残す)。

C9 Event-Driven 口座の連続性

不変量は 2 本だけです: 「席の停止は人手を介さず検知し、 作業は resume され、 成果は失われない」 「口座は枠の終わりまで使い切る」。 数値と選定規則は rules 行に置きます。

normative (machine)

C9: WHEN a seat stops, scribe2 SHALL detect the stop without manual intervention, SHALL resume the seat's work, and SHALL preserve its results.

§4. 改訂の手続き — どう変えると何が起きるか

変えたいときはまず利益を grill で検証し、 user が裁定します (A2)。 閾値なら manifest の diff に裁定 id を付けて merge し (C5)、 条文なら新しい ADR と本文の delta marker と裁定 id を伴って同じ file の中で改訂します (N4)。 C4 / C13 以外の rules 行は A2 を通さず、 裁定 id 付きの diff (C5) だけで変えます。 したがって、 この file を書き換えるのは §3 の写しの更新・誤記の修正・ADR を伴う条文改訂の 3 つだけです。

本章は新しい規則を持たない。 手続きの正本は A2 (grill 検証 → user 裁定)・C5 (rules 行の diff + 裁定 id)・N4 (条文は新 ADR + delta marker + 裁定 id) である。 本 constitution の version は SPEC の版に追随する。 A2 / C5 / N4 の帰結として、 本 file の変更は §3 の写しの更新・誤記の修正・ADR を伴う条文改訂に帰着する。 改訂の trace は folio の delta marker (ins.delta / del.delta・data-delta-id) で本文に残す。
