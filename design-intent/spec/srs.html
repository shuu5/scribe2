01 ゴール / 絶対に避けたい 3 つの事故

「これが起きたら失敗」を先に決める

まず「これが起きたら失敗」を 3 つ先に決めます。人を待たせる・壊れたまま進む・記憶に頼る、の 3 つです。避けたい結果を共有してから要件を読むと、各要件が何を守るためのものか分かりやすくなります。

GOAL 1

人を待たせない

人の手番は 3 クラス承認だけ。 それ以外の段で pipeline が人の入力を待って止まらない。

GOAL 2

壊れたまま進まない

検証が落ちた便・PASS を名乗れない便は記帳して止まり、 黙って landmain への着地 しない。

GOAL 3

記憶に頼らない

現在地は永続面（event log追記だけの記録）から読め、 process が死んでも中断点から再開できる。

この文書の要件は、 どの事業ニーズから来たか

04 機能要件 / システムが必ずやること

「いつ・何をするか」を一つずつ決める

FR1禁止契約 file に必須 field（goal / done / write-set触ってよい file の列 / verify / size / owner / disposition）の欠落・複数行の verify・write-set 0 本が在るとき全件を行番号付きで集めて拒否し、 便を作らない契約の file に必須の 7 項目（goal / done / write-set / verify / size / owner / disposition）が欠けていたり、verify が複数行だったり、write-set が空だったら、問題を全部まとめて行番号付きで断り、便は作りません。契約が書き切れることを求めるニーズ（N-4）から来ています。欠けた契約を後の段で見つけると QA の周回が始まるので、入口で全件まとめて断る方が安いからです。必須 T
FR2恒常常時契約は SRS の要件 id と設計 doc設計 1 本の文書 を pointer で持ち、 設計 1 本から契約が複数出る形を保つ（適用対象は本 SRS を根拠に起票する契約・v1 由来の既存 bead は対象外）契約には「どの要件のためか」（SRS の要件 id）と「どの設計から来たか」（設計 doc）を必ず書きます。設計 1 本から契約が何本も出る、という形を崩しません。契約は小さく、しかし出どころは失わない、というニーズ（N-4）から来ています。要件 id と設計 doc を指していれば、契約を書き直すときも全部の bead が同じ形を保てます。必須 I
FR3恒常常時各段は fleet便と席の状態の全体 の event log を replay して現在地を読み、 段の終わりに event を 1 件追記する（process の記憶に状態を持たない）各段は自分の記憶ではなく、追記だけの記録（event log）を最初から読み直して現在地を知り、終わるときに記録を 1 行足します。process の中に状態を抱えません。記憶に頼らない、というニーズ（N-3）から来ています。process の中に状態を持つと、その process が死んだ瞬間に現在地が消えるからです。必須 T
FR4きっかけ便が Intake 段にあり spawn が要求されたときbase を記録し、 worktree を切り、 write-set の allowlist を書いて runner を headless で起動する便が「受け付け済み」の段にあって起動を頼まれたら、出発点（base）を記録し、作業用の worktree を切り、触ってよい file の列を書き出してから、実装役（runner）を画面なしで起動します。人の手が入らなくても安全に進む、というニーズ（N-1）から来ています。出発点と触ってよい範囲を先に記録しておけば、実装役を無人で走らせても後から検証できます。必須 T
FR5恒常常時runner と lens は claude -p（headless・stdin に契約 / diff・stdout に構造化 1 行・permission を毎回明示・口座は環境変数で切替）の 1 形で呼ぶ実装役（runner）も審査役（lens）も、同じ 1 つの形で呼びます。画面なしの claude -p に、契約や diff を入力で渡し、答えは構造化した 1 行で受け取り、許可の設定は毎回明示し、口座は環境変数で切り替えます。自律安全のニーズ（N-1）から来ています。画面のある席を建てると宛先解決や見張りの仕組みが要りますが、画面なしの 1 形なら process の起動と終了だけで完結します。必須 T
FR6きっかけrunner が終了したときrc終了を知らせる数字 0 かつ base からの commit変更の 1 区切りの記録 が 1 件以上なら Implemented、 それ以外は Failed と記帳する実装役が終わったとき、正常終了（rc 0）で、出発点から commit が 1 件以上あれば「実装済み」、そうでなければ「失敗」と記録します。記憶に頼らない、というニーズ（N-3）から来ています。「終わった」と言葉で申告させず、rc と commit の数という機械の事実で判定します。必須 T
FR7恒常常時変更した .rs ごとに、 test 差分だけを base に当てて新規・変更 test が 1 本以上 RED になり、 かつ HEAD では GREEN であることを機械で確かめ、 docs-only文書だけの変更 でない変更に test 差分が無ければ拒む変更した Rust の file ごとに、test の差分だけを出発点（base）に当てて「先に落ちる」こと、そして変更後（HEAD）では通ることを機械で確かめます。文書だけの変更（docs-only）を除き、test の差分が無い変更は受け付けません。契約は小さく、検証は base で落ちる test で表す、というニーズ（N-4）から来ています。先に落ちない test は何も守っていないので、入口で機械が確かめます。必須 T
FR8きっかけgate機械検証と審査の段 が要求されたとき契約の verify 各行を worktree で実走して行ごとの rc を記録し、 1 本でも rc が 0 でなければ FAIL とする審査（gate）を頼まれたら、契約に書いた検証コマンドを 1 行ずつ作業用 worktree で実際に走らせ、行ごとの結果を記録します。1 本でも失敗すれば FAIL です。自律安全のニーズ（N-1）から来ています。検証コマンドを実際に走らせた結果だけを信じ、実装役の自己申告を根拠にしません。必須 T
FR9禁止lens が要るのに lens が無い・diff が予算 cap を超える・stdout が parse できない・verdict が 3 値の外のときPASS を名乗らず INCONCLUSIVE判定できなかった とする審査役が要るのに居ない、diff が予算を超える、答えが読めない、答えが 3 値（PASS / FAIL / INCONCLUSIVE）の外、のどれかなら、合格（PASS）とは言わず「判定不能（INCONCLUSIVE）」にします。自律安全のニーズ（N-1）から来ています。判定できなかった便を合格と呼ぶと、壊れたものが無人で着地します。必須 T
FR10禁止verdict が PASS でない、 または main の tip が記録した base と違うときland は何もしない（main も event も変えない）審査が合格でないとき、または main の先端が記録した出発点とずれているときは、着地（land）は何もしません。main も記録も変えません。自律安全のニーズ（N-1）から来ています。合格していない便が main に載る経路を構造的に持たないためです。必須 T
FR11きっかけverdict が PASS で前提が揃ったときworktree の tree を squash 1 commit で main に載せ（tree 同一・CAS）、 main で verify を再実走し、 RED なら Failed と記帳して止まる審査が合格で前提が揃ったら、作業用 worktree の中身を 1 つの commit にまとめて main に載せ（中身が同一であることと、他の変更と競合しないことを確かめて）、main の上で検証を撃ち直します。落ちたら「失敗」と記録して止まります。自律安全のニーズ（N-1）から来ています。main に載せた直後に検証を撃ち直すことで、「作業用の木では通ったが main では落ちる」を無人で検知します。必須 T
FR12きっかけland が成立したときverdicts.jsonl に schema 版付きで 1 行 append し、 Landed と記帳する（跨版の観測面）着地が成立したら、判定の結果を版番号付きの 1 行として verdicts.jsonl に追記し、「着地済み」と記録します。次の版の器がこの記録を読めるようにするためです。自分で自分を作る、というニーズ（N-5）から来ています。着地ごとの判定を外から読める形で残しておけば、次の版がこの器を見張るときの材料になります。推奨 T
FR13恒常常時stop --all は live な runner を止め、 rc を 0（全部止まった / 対象なし）・1（残った）・2（state が読めない）の 3 値で返す冪等な 1 コマンドであるstop --all は、動いている実装役をすべて止める 1 つのコマンドです。何度撃っても同じ結果になり、結果は 0（全部止まった、または止める対象なし）・1（止められないものが残った）・2（記録が読めない）の 3 値で返します。自律安全のニーズ（N-1）から来ています。無人で動くものは、いつでも 1 コマンドで止められる必要があります。必須 T
FR14きっかけ別 process で resume が要求されたときevent log の現在地から続きの段だけを通し、 Landed まで到達できる別の process から「続きを」と頼まれたら、記録の現在地から続きの段だけを進め、着地まで到達できます。記憶に頼らない、というニーズ（N-3）から来ています。途中で死んでも記録から続きを引けるなら、長い便を小さな process の列に分けられます。必須 T
FR15きっかけ契約が不可逆操作（消す / 出す / 使う）を名乗る段に達したときapproval.requested を記帳して Blocked で止まり、 人の入力を待たずに process を終える契約が「消す・出す・使う」のどれかを名乗る段に来たら、承認を求める記録（approval.requested）を残して「保留」で止まり、人の入力を待たずに process を終えます。自律安全のニーズ（N-1）から来ています。取り消せない操作だけは人が決める、という線を守るために、機械は止まって記録し、勝手に待ち続けたり進んだりしません。必須 T
FR16きっかけ人が approve を逐語付きで与えたときapproval.received（逐語付き）を記帳し、 次の resume で続きを通す人が承認（approve）を逐語付きで与えたら、それを記録（approval.received）し、次の「続きを」で先へ進めます。自律安全のニーズ（N-1）から来ています。承認を会話の記憶ではなく逐語付きの記録として残せば、誰が何を許したかを後から確かめられます。必須 T
FR17恒常常時規則の種類は閉じた enum と網羅 match で持ち、 値は tracked な manifest 1 file から起動時に読む規則の「種類」は Rust の閉じた enum と網羅 match で持ち（足し忘れは compile が止める）、規則の「値」は repo に置いた manifest 1 file から起動時に読みます。規則の値は manifest に、というニーズ（N-3）から来ています。種類を型で閉じれば足し忘れを compile が止め、値を 1 file に置けば AI が場当たりで規則を生やせません。必須 T
FR18禁止manifest に未知 kind・id 重複・型不一致・user 由来で裁定 id の無い行が在るとき起動前に全件を行番号付きで拒否する（黙って落とさない）manifest に知らない種類・重複した id・型の合わない値・user 由来なのに裁定 id が無い行があれば、起動する前に問題を全部まとめて行番号付きで断ります。黙って読み飛ばしません。記憶に頼らない、というニーズ（N-3）から来ています。壊れた規則を黙って読み飛ばすと、規則が効いていないことに誰も気づかないからです。必須 T
FR19状態marker所属の目印 file（.vessel器の所属の目印）が自分の NAME を言っている間hook は SessionStart で名乗りを出すrepo root の目印（.vessel）が「自分の名前」を言っている間は、hook は起動時に名乗りを出します。自分で自分を作る、というニーズ（N-5）から来ています。どの器がその repo に仕えるかを目印 1 つで決め、別の器や別の版と二重に動かないようにします。必須 T
FR20禁止契約の write-set の外へ Edit / Write しようとしたとき編集の時点で deny し、 policy が読めなければ fail-closed で deny する契約で触ってよいとした file の外を編集しようとしたら、その編集の時点で止めます。許可リストが読めないときも、通すのではなく止めます。契約は小さく、というニーズ（N-4）から来ています。契約の外を触った変更は後の審査では見つけにくく、編集の時点で止めるのが最も安いからです。必須 T
FR21恒常常時hook は自分の出力 1 行を（who / what / when / bytes / tokens / wall）の schema で記録し、 v3 の計測 store を後付けできる形を保つhook は自分が出した 1 行について、誰が・何を・いつ・何 byte・何 token・何 ms、の形で記録を残します。あとで計測の仕組みを足すときに、経路を作り直さなくて済むようにするためです。消費は害、というニーズ（N-2）から来ています。起動時に注入される文章の量を後から測れるように、記録の形だけ先に決めておきます。推奨 T
FR22恒常常時到達点の計測では人由来の event を数え、 approval 以外が 0 件であることを機械で示す到達点を測るときは、人が関わった記録を数え、承認以外が 0 件であることを機械で示します。自律安全のニーズ（N-1）から来ています。「人手 0」を言葉で主張せず、記録を数えて示すためです。必須 T
FR23恒常常時退避物は session id で一意、 消費済みは同一 suffix で表し、 消費は move、 DATA が無い周は brief を出さず、 別 session の退避物は自動消費せず、 重複起動は冪等とする開発 session（この AI）の作業記憶は、退避 file を session id で一意にし、使い終えた file は決まった名前の付け方（同じ suffix）で見分け、削除でなく移動し、記録が読めない周は状況説明を出さず、別 session の退避物は勝手に片付けず、二重に起動しても同じ結果になるようにします。記憶に頼らない、というニーズ（N-3）から来ています。開発 session が context を切り替えるときに作業状態を失わず、別 session の記憶を自分のものと取り違えないためです。推奨 I
