§1. 問い (何を調べたか)

この文書が調べたのは「いまの作り方 (管理席を何席も並べて、 席が自分の手で実装する) は scribe v2 が最初に描いた形なのか」「そうでないなら、 何を既定の形と呼ぶべきか」「席ごとに口座を分けられるなら、 実装役を使い捨ての claude -p でなく席の中の teammate にしてもよいのか」の 3 点です。 答えは出しません。 材料を並べて、 決める文書 (ADR-0016) に渡します。

SRS が描いた並列の層は FR5 (runner / lens は claude -p の 1 形) と FR4 (契約 1 本に worktree 1 つと runner 1 つ) であり、 便の並列は pipeline の run の層で担保する想定だった。 記録時点 (2026-09-11) の現実は planner 1 席 + 管理席 3 席 (各 1 口座) が並び、 便の大半を席が自分の手で実装している。 問いは 3 つ: (Q-a) 席並列は v2 の本来の動きか。 (Q-b) 既定の配送構造として何を定義すべきか。 (Q-c) 口座分離が席の層で達成できるなら、 runner を teammate (Agent tool の subagent) にする方が優れるか。

§3. 3 案の比較

「席を並べる」「pipeline の便を並べる」「席が pipeline の便を流す」の 3 つを、 審査の独立性・planner の詰まり・衝突・費用・口座・聞き返しの 6 つの軸で並べます。 どれが良いかは書きません。

軸(A) 席並列 (記録時点の形)(B) pipeline 並列 (SRS が描いた形)(C) 混成 (planner 1 + 管理席 N が pipeline を流す)
gate の独立性散文 + planner の再実測 (実装・review・merge が同じ席)構造 (write-set guard・verify 行・lens・land の CAS)構造 (便は pipeline)。 席が手で実装する便だけ (A) と同じ
planner の律速全 PR の再実測と go が planner に集まる。 席を増やすほど集まるgate は機械。 planner は契約と裁定だけ(B) と同じ。 QUESTION の中継が席の仕事になる
衝突の調整dispatch の散文 (触らない worktree の列挙)・rebase は席の手write-set の交差は intake で検査できる (未実装)・land は base 固定の CAS(B) と同じ
費用席は常時 context を持つ。 cycle と tick の運用費が席数分runner は便ごとに使い捨て。 席の費用は planner 1 つ分席数分の運用費は残るが、 席の context は契約と中継だけで軽い
口座分離の層席ごと (1 席 1 口座)run ごと (--account-dir・渡さなければ親の口座)席ごと。 run は親 (席) の口座を継承する (記録時点の s2-07l.46 の形)
聞き返し席から planner へ QUESTION (注入・不達の周あり)無い (runner は対話しない)。 契約の穴は gate の FAIL か黙った推測runner が typed な record で質問を返し、 席が planner へ中継する口を足せば可 (未実装・ADR-0016 §2.2)
憲法の向きC16 (edit time で止める)・N2 (散文の規則は規則ではない) の両方と緊張C16 / N2 の向きに合う。 C3.4 (完了条件は 1 enum) は Stage で充足(B) と同じ。 席の役割を SRS に書く必要がある (記録時点の SRS は席の役割を定めていない)

§4. teammate と claude -p の差 (事実だけ)

席の中で起こす teammate (Agent tool の subagent) と、 画面なしで起こす claude -p の違いを、 いま分かっている事実だけ並べます。 「口座を分けるため」だけが claude -p の理由ではありません。

観点teammate (Agent tool の subagent)claude -p (runner / lens の記録時点の形)
口座親 session の口座に固定--account-dir で便ごとに切替可。 渡さなければ親の口座
settings の読み込み親 session の settings を継承する (器から制御できない)user / project / local の settings を 1 つも読まない形を器が強制する (ADR-0011・実測で hook 0 件)
session の要否生きている席が要る (席が cycle すると subagent の親が変わる)binary から起こせる。 席が無くても回る
判定入力親が読む text (自由文)stream-json の record と rc (typed・ADR-0012)。 lens の verdict は最終行の JSON
聞き返し途中で親へ text を返せる (multi-turn)記録時点では不可。 最終行に typed な record を返して止まる形は足せる (ADR-0016 §2.2)
権限親の permission を継承--allowedTools を凍結した写しから毎回明示 (ADR-0009・ADR-0010)
起こす手間1 tool 呼出worktree + 契約 + 写し + 起動 (pipeline が担う)
記録時点の用途席の中の review (lens-NN)pipeline の runner / lens

口座分離を席の層で達成した場合に残る差は、 settings 不読の強制・無 session での起動・typed な判定入力・毎回明示の権限の 4 つである。 teammate 化は「口座分離が要らない」だけでは正当化されない (ADR-0016 §4 (B))。

§5. 未解決の問い (ADR へ渡す)

この文書では決めません。 次の 4 つを決める文書 (ADR-0016) と、 要件を書き直す裁定 (SRS・user) に渡します。

  1. 既定の配送構造を SRS に書くか (記録時点の SRS は「planner や管理席のように session をまたいで対話を続ける」と役割に触れるだけで、 席の仕事の境界を定めていない)。
  2. QUESTION の口の形: record の置き場 (runner の最終行 JSON か run dir の file か)・段の名前・誰が答えるか・回答の記帳の actor。
  3. 管理席が自分の手で実装してよい便の境界 (pipeline が回せない便 = 器の穴・design-intent・host 作業、 で閉じるか)。
  4. teammate の用途を席の中の review に限るか。 再検討の条件 (口座・settings・無 session・typed record の 4 差が teammate 側で埋まったとき) を残すか。
